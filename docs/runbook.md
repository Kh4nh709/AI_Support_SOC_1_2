## Start and stop

`db` is PostgreSQL 16 on port `55432` (`DB_PORT`, volume `pgdata`), `app` is uvicorn on port `8000`, `worker` runs the `pull`, `pipeline`, `triage`, `health`, `digest` and `investigate` jobs (`backend/app/web/handlers/`, discovered by `iter_handlers()`; `investigate` is ②'s single-shot analysis, **② operations** below). **Every worker start re-arms three self-scheduling chains** — `pull` and `health` (`enqueue`, idempotent through the jobs table's partial unique index) and `digest` (`digest.ensure_scheduled`) — so a chain that died is repaired by `docker compose restart worker` alone, no other action (**Alarms**, below). The stack publishes both ports on every interface of the host (`docs/limitations.md` (xxxv)). `ui` is the React UI on port `8080`, loopback only (**UI (service `ui`)** below), and it is the only console, the admin console included (**Admin console** below). Port `8000` serves `/api/*`, `POST /webhook/alerts` and `GET /health`, and renders no page: the Jinja analyst pages went in P10-T13, the Jinja admin pages, the sign-in page and the session cookie in P11-T19 (DEC-205).

## Admin console

An admin signs in with the React sign-in form and has seven pages: `/admin/overview`, `/admin/users`, `/admin/llm`, `/admin/labels`, `/admin/lab` ("Gán nhãn lab": the lab runs and their TP and FP labels, DEC-213, on the trial branch only), `/admin/knowledge` (the learned-knowledge drafts and entries, DEC-210) and `/admin/audit` (the rules and digest pages were removed with DEC-214: the UI neither shows nor edits the auto-close rules, and has no daily digest to review; the backend behind them stays). Each calls `/api/admin/*` through the same-origin proxy of `ui`; none is a page of port `8000`.

## Learned knowledge and RAG (DEC-210)

Learned knowledge lets ① and ② read, beside the signed decision tables, what past human decisions were: the decision history of the alerts and cases like the one in hand, and the entries an admin approved from earlier conclusions. A Tier-1 close or a Tier-2 conclusion may propose a **draft** (`KNOWLEDGE_DRAFT_ENABLED`); an admin approves it into an **entry** whose Markdown file is published in `kb_learned/` (the database holds the content, the file is its copy); a **lookup** (`RAG_ENABLED`) finds the history and up to three similar entries for each alert and case and puts them in the prompt as a reference, never as a rule and never as a reason to close. Its jobs run in their own service, `rag-worker`. Only `knowledge_draft` calls DeepSeek: since P14 (DEC-213, the trial only) `rag_lookup` calls no model, it uses Voyage and `vectordb`, and the job `knowledge_embed` calls Voyage (**Voyage vector RAG (DEC-213)**, below). **Both switches default to `false`**: merging the code changes nothing about learned knowledge, and with `RAG_ENABLED=false` ①'s prompt and behaviour are what they were (spec §7.1).

**The release is the integration branch, `director/integration`** (INT-T01, INT-T02): DEC-210's learned knowledge together with DEC-211's SOAR/SIEM follow-up, merged and tested as one. The steps below are the same, and migration 020 is still the only new migration (`schema_migrations` goes from 19 to 20). Merging it brings what DEC-211 changes whatever the two switches say: the webhook runs its database work in a worker thread and answers `400` to an alert id that is not ①'s `alert_id` shape (**SOAR intake (DEC-207)**), ①'s prompt carries the SIEM context block while `PROMPT_INCLUDE_SIEM_CONTEXT` is `true` (its default), and the alert page shows the SOAR sections and, for a ① that gave up, why. ### Rollback

**Rollback.** Set `RAG_ENABLED=false` and `KNOWLEDGE_DRAFT_ENABLED=false` in `.env` (the lookup first, if both are on), then `docker compose up -d --force-recreate app worker rag-worker`. ① and ② are then what they were before: no lookup is enqueued, `triage` is not delayed, no block is added (spec §7.9), and no draft is proposed. **Entries stay: no data is removed**, neither the three tables, the drafts and approved entries, the `rag_results` and `llm_runs` rows, nor the files in `kb_learned/`; what was stored is only no longer read. `rag-worker`, which stays up, has only the jobs already queued left to run, and **it stays up until they have run**: the main `worker` claims none of the three types, so a `rag_lookup`, `knowledge_embed` or `knowledge_draft` job left `pending` with no `rag-worker` is a `job_backlog` alarm that never clears. **Drain the RAG queue before anything is removed:** run `psql "$DATABASE_URL" -Atc "select count(*) from jobs where job_type in ('rag_lookup','knowledge_embed','knowledge_draft') and status in ('pending','running')"` until it prints `0` (the jobs do not look at the switches, so they run out by themselves). **A draft waiting for next month's budget is a `pending` job in the future and keeps the count above 0.** Raising `RAG_MONTHLY_USD_CAP` does not release it: its time is fixed when it is queued, and with a cap of 0 it is queued again for the month after each time it runs. **Wait for the month to turn, or, rolling back, run this Owner command once the switches are off** (the only statement of this section that deletes: it removes the draft jobs that have not come due, and nothing else; the conclusions they were for get no draft): `psql "$DATABASE_URL" -c "delete from jobs where job_type='knowledge_draft' and status='pending' and scheduled_at > now()"`, **then run the drain count** above. `docker compose stop rag-worker` with jobs still counted leaves them waiting. 020 stays under the old code too (new tables, a nullable column and wider CHECKs, none of which the v1.1 code reads), so there is no down-migration. Only when that count is `0`, to take the second compose file out as well, delete the `COMPOSE_FILE` line from `.env`, run `unset COMPOSE_FILE` in any shell that sourced `.env` (it stays exported there and keeps the override in force; or work in a fresh shell), and run `docker compose up -d --remove-orphans`: `rag-worker` goes and `app` is recreated without the mount; the files stay on the host. Switching the feature on again is steps 7 to 9, and the entries are in force again at once.

### After `make db-restore`

`make db-restore` brings the rows back and not the files: a backup is `pg_dump` only, and `kb_learned/` is git-ignored. Until the files are rewritten every active entry fails its hash check at the next lookup: it is left out, `rag.integrity_failed` is written and the `knowledge_integrity` alarm fires. And `make db-restore` stops `app` and `worker` and, when the override is in use, `rag-worker` too (a failed stop of a service that is not there is ignored), because a running `rag-worker` keeps a connection to the database being replaced and its drop step fails (`FAILED at drop`); it starts `app` and `worker` again and never `rag-worker`, which comes up only after the rebuild. The explicit `docker compose stop rag-worker` first is kept: it is harmless, and the order below does not depend on the make target. **Run the rebuild in `app`**: it is the one container that mounts `kb_learned/` read-write (`rag-worker` has it `:ro`, so a rebuild there fails to write, and `worker` has none). On the trial a restore goes through step 7 of **Voyage vector RAG (DEC-213)**, with its dump check, never through this block. With the second compose file in use, the order is:

```bash
docker compose stop rag-worker
make db-restore FILE=backups/soc-<UTC stamp>.dump        # the dump that just rehearsed clean (Backup and restore)
docker compose exec app python -m app.rag.publish --rebuild
docker compose up -d rag-worker
```

→ `db-restore: … (N migrations)` and `app` and `worker` started again by the make target; then one JSON line on stdout, `{"rebuilt": N, "skipped": 0, "root": "/srv/kb_learned"}`, N being the active entries (`select count(*) from knowledge_entries where status = 'active'`); an entry it will not rewrite is a `{"rebuild": "skipped", "entry_id": …, "reason": …}` line on stderr, `reason` being `content_sha256` (its content no longer hashes to its `content_sha256`), `path` (its `file_path` is not `entries/<category>/<entry_id>.md`) or `os_error` (the file could not be written: a read-only mount, a wrong owner, a full disk), the others are still written, and the command **exits 1** if anything was skipped (`skipped` is then not `0`); then `rag-worker` `Up`. `app` also runs as the host user, so the files come out owned by it; the same command on the host (`PYTHONPATH=backend .venv/bin/python -m app.rag.publish --rebuild`) writes the checkout's `kb_learned/` (as the checkout user, so only where that user may write: on ATTT-M1, where the checkout user is 1001 and `app` runs as 1000, the `entries/` directories `app` made belong to 1000 and the host command skips what it cannot write with `os_error`, which is why the rebuild is run in `app` there), and `--rebuild --root PATH` writes another directory. A dump that predates 020 needs `make migrate` first (**Migration 020** above), and then `rebuilt` is `0`; and **before restoring one, set `RAG_ENABLED=false` and `KNOWLEDGE_DRAFT_ENABLED=false` in `.env` and recreate `app worker rag-worker`** (the lookup read of ① and ② is a savepoint that falls back to no material, but the transitions that queue a `rag_lookup` or `knowledge_draft` job fail on the 019 schema's `ck_jobs_job_type` CHECK, and with them the ingestion, the decisions and the escalations). The same command repairs one file that was edited or deleted by hand (the `knowledge_integrity` alarm). It reads the database and writes files; it changes no row. ## Archiving the old queue (DEC-212)

The Owner's fresh start (ruling 30/10/2026): every alert and case that arrived **before 2026-10-30T20:15:00+07:00** is closed out without review. They are **not analyst decisions** and are never read as one, which is why they get a status of their own, `archived`, and not `closed_benign` (`rag/history.py` counts `closed_*` over 90 days as decisions, the blind arm reveals ① for a decided head, and the evaluation and agreement views count them; none of them counts `archived`). The command is `python -m app.domain.archive`; the rules are `domain.transitions.archive_before`'s, in this order, all in one transaction:

1. the cases that are `investigating` and created before the cutoff become `archived` (`concluded_by` stays empty: nobody concluded them);
2. the `escalated_tier2` alerts of those cases become `archived`;
3. the queue heads (`duplicate_of IS NULL`) in `received`, `enriching`, `queued_tier1` or `tier1_active` that were received before the cutoff become `archived`.

An archived alert keeps its `case_id`, `acknowledged_by`, `triage_status` and every other column; it gains `closed_at`, `sealed_at` and `close_reason`. **Not touched:** `duplicate` rows (already sealed; about 202 000 of them sit under the old heads), anything a person or a rule closed (`closed_*`, `auto_closed`), concluded cases, and anything received at or after the cutoff. One `alert.archived` per alert and one `case.archived` per case go to the audit log (`actor_role='system'`, no actor; payload `{reason, before, from_status, decision: "DEC-212"}`, plus `case_id` on an alert that was in a case). No `tier1.decided`, no `tier2.concluded`, no `label.created` and no job of any kind is written. A row an analyst changes while the command runs is skipped, never forced; a second run archives 0.

**There is no reopen.** An archived alert is sealed and never an open cluster again, and nothing moves it back. The way back is the backup taken in step 2 (**Backup and restore**, `make db-restore`). Every command runs from the primary checkout, in a shell that has sourced `.env`; *(not run by the agent)*.

`--before` must carry a UTC offset (`+07:00`, `Z`): without one the command exits 2 before it reaches the database, because the time would be read in the server's time zone. **Where the commands run.** Every command below runs from the trial checkout, `/project/project/AI_Support_SOC_trial`, in a shell opened there, never from the primary checkout (that is live). - **What exists.** The Voyage RAG is built (P14, DEC-213) and runs on the trial only. Its parts: the eleven `.env` keys of the table above; migration `022_true_positive.sql` (①'s verdict `escalate` is renamed `true_positive`; it refuses while a `triage` run still says `escalate`), `023_vector_rag.sql` (the contracts: the job type `knowledge_embed`, `rag_results.failure_kind`, the stored ranking) and `024_lab.sql` (below); the job type `knowledge_embed`, which `rag-worker` claims and which puts an approved entry's vector in `vectordb` (and deletes it when the entry is retired); the lookup `rag_lookup`, which calls **no model**: it embeds the alert's or the case's fingerprint with Voyage, asks `vectordb` for the 20 nearest entries, adds the database search's candidates, re-checks every one against the main database and has Voyage rerank them, with **no fallback to an LLM ranker** (Owner, 03/11), so any failure of Voyage or of `vectordb` is a `failed` lookup, and ① and ② run without the RAG and say so (the notice "Không áp dụng RAG" beside their conclusion, and the health check `rag_lookup_failures` of **Alarms**); the command `python -m app.rag.vector_index` with `--rebuild` and `--check` (step 6); and one new container, `vectordb` (`pgvector/pgvector:0.8.0-pg16`), in `docker-compose.rag.yml`. `vectordb` has no table until the first `--rebuild`, embedding job or lookup makes it (`ensure_schema`).

**6 · The index.** The index is derived: the main database is the only source of an entry's text, status and hash, and `vectordb` has no backup of its own. Make it, then check it, in `rag-worker`, the one container that has the address:

**8 · The free-tier limits.** Read them on the Voyage dashboard before a lab run. The account is the free tier with no payment method (Owner, 03/11): the published limits of 2 000 requests per minute and 2 to 8 million tokens per minute belong to Tier 1, which needs a payment method, and the free tier's are **not published**, so the dashboard is the only place that says what the account may do. A lab run that sends many alerts at once can meet them: the lookup then fails with `rate_limit` (its first attempt is asked again once, after 10 seconds, if that can still finish before ① starts; otherwise it is a failure like any other), ① and ② run without the RAG and say so, `rag_lookup_failures` alarms at five in an hour, and the lab measurement counts the lookups that failed (**Measuring**). The remedy is to slow the run down or to wait, not to repeat a lookup by hand.

**After the first lab lookups, check what they cost against the dashboard.** Each alert costs **two** Voyage requests (the embedding of its fingerprint and the rerank of its candidates), and the rerank's tokens grow with the number of candidates, up to 40, so the lab's alert rate decides whether the free tier carries the run, and only the dashboard says what the tier allows. Only when a few lookups have run (a few alerts of the first `kb` run have arrived and their lookups are stored), in the shell of step 2 (it has sourced `.env`), in a paste of its own:

```bash
psql "$DATABASE_URL" -Atc "select count(*), max(input_tokens), avg(input_tokens) from llm_runs where pipeline = 'rag_lookup'"
```

→ `count|max|avg`: the lookups' run rows (one per attempt that sent a request), the most tokens one of them used and the mean (`input_tokens` is the embedding's and the rerank's together). Put them beside the dashboard's requests per minute and tokens per minute for the same minutes: twice the alerts per minute is the requests, and the mean times the alerts per minute is the tokens. If the free tier cannot carry the lab's alert rate (the dashboard is at its limit, or `rate_limit` rows begin to appear in step 6's query), **pace the runs**: send the alerts of a run more slowly, split a run, or wait. Adding a payment method raises the limits (spec §5.5: the free tokens still apply), and that is the Owner's decision.

#### Lab procedure

The Owner's lab (spec §6), on the trial. It needs steps 1 to 6 done. **The trial's `.env` already has `RAG_ENABLED=true` and `KNOWLEDGE_DRAFT_ENABLED=true`** (`grep -c '^RAG_ENABLED=true$' .env` and `grep -c '^KNOWLEDGE_DRAFT_ENABLED=true$' .env` print `1` and `1`), so nothing in this section switches the lookup on: step 5 did, at once, and from then on every alert and case that arrives gets a Voyage lookup, even on an empty index (it then finds only the decision history). The way back on after a rollback depends on which one. After a rollback of **Learned knowledge and RAG (DEC-210)** (both switches off) it is that section's steps 7 to 9 (drafts first, the lookup after the first approved entries). After the Voyage rollback (step 9, which stops `vectordb`) it is step 9's own order (`vectordb` first, then `RAG_ENABLED=true`).

1. **Before the first run, point n8n's webhook at the trial** (`:8001`, the trial's `app`; live is `:8000` and must not receive lab alerts). Until then a run's alerts land on live; an alert received before this is outside every run's window, so it is never lab data. **What tells the two stacks apart is the port, not the key:** `.trial/make_env.py` built the trial's `.env` from live's and copies `WEBHOOK_API_KEY` as it is, so unless one of the two was rotated since, both stacks take the same key. The credential n8n sends is the value of `WEBHOOK_API_KEY` in the trial's `.env` (the key's name only; its value is never printed, pasted into a command or written in the repository), in the `X-API-Key` header, from an address that is in the trial's `WEBHOOK_IP_ALLOWLIST`: `make_env.py` set that list to the trial network and loopback, not to live's, so check that n8n's source address is in it: the ranges are the `WEBHOOK_IP_ALLOWLIST` entry of `SET` in `.trial/make_env.py` (loopback and the trial's /16) and the subnet in `docker-compose.trial.yml`, and `grep -c '^WEBHOOK_IP_ALLOWLIST=' .env` prints `1` when the line is there (a count; never a plain grep of the `WEBHOOK` lines, which prints the key as well). A wrong key gives `401` and an address outside the list `403` (`backend/app/web/routers/webhook.py`), and in both cases the alert is not received.
2. **Create the run before each attack run**, on the admin page "Gán nhãn lab" (`/admin/lab` of the trial's `ui`, `http://127.0.0.1:8081/admin/lab`): a name (unique, at most 80 characters), the purpose, `kb` ("Xây kho": the run builds the knowledge base) or `test` ("Chấm điểm": the run is scored), and its window, start and end, **in Vietnam time (UTC+7)**: the form says so and stores the instants with their zone. An alert belongs to the run whose window holds its `received_at`. The window is half-open, `[start, end)`, and two runs may not overlap (a run may start where another ends); the page refuses an overlap. End the window a few minutes after the attack, so that the alerts that arrive late fall inside it: an alert received outside every run belongs to none and is never scored. A run recorded by mistake is removed by the Owner as the database owner (**The lab**, above).
3. **Label every alert of the run TP or FP after it ends**, when its alerts have arrived. The run page lists the run's alerts blind (the alert's own fields and nothing of ①); the buttons "TP — tấn công thật", "FP — không phải tấn công" and "Bỏ nhãn" set, change and clear the label, and a counter ("Đã gán n/total") shows the progress. **Only the queue heads are listed**: with `DEDUP_ENABLED=false` every alert is a head; with grouping on (`DEDUP_ENABLED=true`) an alert grouped under a head is not listed and cannot be labelled (`docs/limitations.md`, (li)). An unlabelled alert is not scored and is counted as such. A case is a real attack when any of its alerts is labelled TP.
4. **Approve the `kb` runs' concluded cases into the knowledge base.** Analysts work the `kb` runs' alerts and cases as in production (a Tier-1 close or a Tier-2 conclusion proposes a draft while `KNOWLEDGE_DRAFT_ENABLED=true`); an admin approves the drafts on `/admin/knowledge` ("Duyệt"). With the RAG on, each approval enqueues a `knowledge_embed` job, and the entry is in `vectordb` once `rag-worker` has run it; `--check` (step 6) shows `missing: 0` when all of them are.
5. **Do not approve drafts from `test` runs until the measurement is done.** An entry approved from a test run after the knowledge base is frozen would let the measurement see an answer it should not: the report flags it `after_cutoff` (**Measuring**). Leave those drafts pending, or reject them, until `measure` has run.
6. **A refused request is worded in Vietnamese on the page; the reasons are listed in the module docstring of `backend/app/web/routers/admin_lab.py`:** `409` `overlap` (the window meets another run's), `422` with a field and a reason (`required`, `empty`, `too_long`, `invalid`, `taken` for a name in use, `not_after_starts` for an end that is not after the start), `409` `not_a_queue_head` (the alert is a duplicate under a head: label the head), `409` `outside_every_run`, and `404` `not_found`. A run's two instants must have a UTC year from 2000 to 2099.

#### Measuring

`eval/lab_measure.py` (P14-T11) scores ① and ② against the labels, RAG off and on, over the `test` runs, and calibrates the RAG's thresholds on the `kb` runs. It writes nothing to the database (its transactions are `READ ONLY`), so it can run beside the trial. Run it in `app`, where `eval/` is mounted (`./eval:/srv/eval:ro` in `docker-compose.yml`, which the trial's override leaves alone), with the image's `WORKDIR /srv` and `PYTHONPATH=/srv/backend`: it reads the database and the keys from the container's environment (no `--env-file` is needed: `/srv/.env` does not exist there, and the environment wins over the file). The mount is `:ro`, so the default report directory `eval/results/lab/` cannot be written in the container: pass `--out /tmp/lab`. Never pass `--dsn` (a DSN on a command line). Run it in a terminal that stays open: a run lasts as long as the model takes to answer, and **Ctrl-C** ends it cleanly (the subjects that finished are written as a report marked PARTIAL, exit 8). **While a measurement runs, do not restart or recreate `app`** (`docker compose restart app`, `up -d --force-recreate app`, an `up -d` that recreates it, a `make db-restore`): the run is a process of that container, only a database error and Ctrl-C are caught, and anything else ends it with no report and the paid calls lost. Every run is first estimated, then run, in three pastes, because `--yes` spends money: the estimates only (exit 5 is expected), then the small run, then the full run. A run-name goes in quotes (the option takes several names, so a name with a space splits into two and exits 2). First, the estimates only:

```bash
# the estimates only: the whole set, and the small run
docker compose exec app python eval/lab_measure.py measure --out /tmp/lab
docker compose exec app python eval/lab_measure.py measure --test-runs "<test run name>" --out /tmp/lab
```

→ each prints its one `estimate:` line and stops with exit 5; nothing was called, nothing was spent. **The monthly cap is checked per tool run, not for the month:** the tool writes no `llm_runs` row, so the small run (the second paste), a `--tiers 1` run and every earlier lab run of the month are in no later run's `month_spend`, and the cap stops none of them on account of the others. Read the figures against the month's cap as **their sum plus this month's earlier lab runs** (the full run measures the small run's subjects again), and give them to the Owner. Then, only when the Owner has read the figure and accepts it, the small run:

```bash
docker compose exec app python eval/lab_measure.py measure --test-runs "<test run name>" --yes --out /tmp/lab
```

→ read its report (the exit code, the cost, the counts). Only when that small run's report reads right, the full run (its estimate is the first line of the first paste):

```bash
docker compose exec app python eval/lab_measure.py measure --yes --out /tmp/lab
```

1. **The estimate.** Without `--yes` it prints one line, `estimate: lab_measure measure tiers=… n1=… n2=… calls≈… usd≤… month_spend=… cap=…` (an upper bound: every prompt is priced at its token budget), calls nothing and stops with exit 5: this is the estimate only. Read it against the month's cap and tell the Owner the figure: `--yes` is the Owner's go-ahead for that figure.
2. **A small run** (the second paste). `--test-runs` with the name of one `test` run in quotes (several names are separate quoted words): its own estimate is in the first paste, and `--yes` follows only once the Owner has accepted it. It proves the plumbing, the report and the cost on a few alerts before the whole set.
3. **The full run** (the third paste). No `--test-runs`: every `test` run, with `--yes` once the Owner has its estimate and the small run's report reads right. `--tiers 1` or `--tiers 2` runs one tier only, and the default is both; each such run is estimated first as well.

The report is two files, `lab_measure_<UTC stamp>.md` and `.json`, in `/tmp/lab` of the container (a recreate removes them): copy them out at once with `docker compose cp app:/tmp/lab ./lab-reports` *(not run by the agent)*. The Markdown carries, per tier and per arm (RAG off and on): n and the unlabelled excluded; the accuracy of the **model's own conclusion**, TP recall and TP precision; how often the gate or the override held, split by whether the model was right; RAG coverage and the mean best percentage; the failed lookups by kind (a 429 or any other error: such a subject is scored "RAG on" with no RAG in it, and counted); the leak check; a paired line (the same subjects in both arms) and a second over the subjects whose RAG-on prompt carried at least one match, where the RAG could act; the cost. The exit codes:

| exit | means |
|---|---|
| `0` | done |
| `2` | usage: a bad option (`--tiers`, `--kb-cutoff`), an unknown run name, a `kb` run given to `measure` or a `test` run given to `calibrate`, an empty `LLM_MODEL_PROPOSER` (`measure` needs the model), or `--out` that cannot be written (checked before the estimate) |
| `3` | not ready: no `test` run is recorded, nothing labelled to score, `calibrate` finds no labelled alert with a stored ranking, or the Voyage key is missing or was refused (`auth`) |
| `4` | the DSN or the database is unusable |
| `5` | the estimate needs the Owner's go-ahead: run it again with `--yes` |
| `6` | stopped by the monthly cap: some evaluations were refused a call and are counted as no answer |
| `7` | nothing was answered in any arm |
| `8` | stopped part-way (a database error or Ctrl-C): a report marked PARTIAL was written for the subjects that finished |

**Read the numbers with these caveats** (the report's header prints them). **The inputs of ① and ② are bounded at the subject's first look.** ① is evaluated as of the `created_at` of its first proposer run (else `received_at` plus `RAG_TRIAGE_DELAY_S`; each row says which, and the report counts both) and ② as of its first run, and then the burst count (with `DEDUP_ENABLED=false`), the correlation section of ① and block 5 of ② hold only the alerts received before that instant, and the RAG-on arm reads only a lookup created before it, so a later stage of the attack is not in a prompt. **What is not bounded** is the neighbours' current status: the correlation section and block 5 print the status a neighbour has now, so a prompt in either arm may still show an analyst decision made after the subject's first look. That is the same in both arms, so the RAG difference is not biased by it, but the absolute accuracy may be flattered, and the report counts and lists the subjects it can have touched. That count is an estimate: it over-counts because the section's caps (20 groups, 5 samples) are not replayed, and under-counts where a decision has no date. Only the RAG-on arm also reads the stored decision history, which may hold same-run analyst decisions (listed under `history_same_run`): those subjects make the RAG difference unreliable. **To leave ① no decision to be shown, run its measurement before analysts work the test runs' alerts:** the estimate with `--tiers 1`, `docker compose exec app python eval/lab_measure.py measure --tiers 1 --out /tmp/lab`, and only when the Owner has read the figure the same line with `--yes`, while the neighbours are still undecided. ② exists only for the cases analysts escalated, so `--tiers 2` waits for them. A lookup that was rate-limited (429) and retried after ① had finished is stored nowhere, so the report's "no lookup" can hide it (it says so under its table). **The knowledge base is frozen at the start of the earliest `test` run:** an entry approved after it is flagged `after_cutoff` (`--kb-cutoff` takes another ISO 8601 instant, with `Z` or an offset), and an entry drafted from the subject's own run is flagged `same_run`; a flagged subject is listed and still counted.

**Money.** The tool's spend is **not written to `llm_runs`**: the app's monthly cap, the `monthly_cost` and `rag_budget` alarms and the admin's cost views never count it, so read the report's cost and the provider's own balance. The tool stops itself at the cap (it adds its own spend to the month's total in `llm_runs`, and exits 6), and that total is `llm_runs` plus the spend of this one process: another run of the tool is not in it (see the first paste's note). It reads the limits and the prices of the container's `.env` (`LLM_MONTHLY_USD_CAP`, `LLM_PRICE_IN_PER_M`, `LLM_PRICE_OUT_PER_M`, the prompt budgets), as the container was created with them, **not** the ones saved on the admin's Limits page: recreate the container after an `.env` edit before a run, never during one.

**`calibrate`** is where the RAG's thresholds are chosen, on the `kb` runs and never the test set (a `test` run is refused, exit 2). `docker compose exec app python eval/lab_measure.py calibrate --runs "<kb run name>" --out /tmp/lab` reads the labelled alerts of those runs and the rankings their lookups stored (`rag_results.ranked`). **It needs `kb` runs whose alerts arrived with the RAG on and with entries already indexed:** a lookup that found no candidate stored an empty ranking and adds nothing to the coverage; an alert with no lookup, a failed one or a `budget` one has no stored ranking and is counted as `no_ranking`; and when none of the labelled alerts has one the command stops with exit 3 ("no labelled alert of these runs has a stored ranking"). It prints, for each threshold from 0.30 to 0.95 in steps of 0.05, the **coverage** (the share of those alerts whose best match scores at least the threshold) and the **agreement** (of those, the share whose best entry's conclusion agrees with the label). That costs nothing: it calls neither Voyage nor a model. With `--rerank-model`, as in `docker compose exec app python eval/lab_measure.py calibrate --runs "<kb run name>" --rerank-model rerank-3 --out /tmp/lab`, it scores the same stored candidates again with that Voyage rerank model and prints the second table beside the first; that costs Voyage tokens, so it prints an estimate and stops with exit 5 until `--yes`. Choose from these tables, on the `kb` runs only: `RAG_MIN_SCORE`, the two level thresholds `RAG_LEVEL_GIONG` and `RAG_LEVEL_RAT_GIONG`, and `rerank-2.5` against `rerank-3` for `RAG_RERANK_MODEL`; they are provisional until then (`docs/limitations.md`, (li)). Choose them before the first `test` run: a lookup stores its matches with the thresholds in force when it ran, and `measure` reads the stored lookups.

**Applying the thresholds** comes after `calibrate`, before the first `test` run, and only when no `lab_measure.py` run is going on (a recreate of `app` ends a running measurement with no report): set the chosen values in `.env`, then `docker compose up -d --force-recreate app worker rag-worker`.

### Grouping switch (DEC-165)

`DEDUP_ENABLED` is a §6.3 key, a `.env.example` line and a row of the table above. `true` (the default, and what a `.env` without the line gets) groups alerts into clusters as before: a repeat of an open head's rule, source IP, destination IP and agent is a `duplicate` that only bumps the head's `occurrence_count`. `false` (**the Owner's decision of 30/09**) stops grouping: every alert is its own queue row and its own `triage` job, with its own enrichment and `risk_score`. The queue then shows a **User** and an **IP nguồn** column, so each row says whose alert it is and where it came from. The value is read as `true|false` (also `1|0`, `yes|no`, `on|off`); anything else stops the worker at startup with a message naming `DEDUP_ENABLED`, never a silent default.

To turn grouping off, from the primary checkout, in a shell that has sourced `.env` *(not run by the agent)*: put the line `DEDUP_ENABLED=false` in `.env` (edit it, do not paste the file anywhere), then

```
docker compose up -d --force-recreate app worker
docker compose exec -T worker printenv DEDUP_ENABLED
```

The second command prints `false`. A plain `docker compose restart worker` is **not** enough: the container keeps the environment it was created with. To turn grouping back on, set `DEDUP_ENABLED=true` (or delete the line) and recreate the same way.

What to expect once it is off:

- Two identical alerts a second apart are two rows, each `occurrence_count` 1, neither a `duplicate`. An alert that matches an auto-close rule is auto-closed on its own, and no cluster lock is taken. **The queue is longer and ① runs once per alert** — the spend row of **What to watch** against `LLM_MONTHLY_USD_CAP` is the number to look at in the first days.
- The same `alert_id` received twice is **still** refused (`409 duplicate` on the webhook, one `intake` row): that is receipt idempotency, upstream of grouping, and the switch does not touch it.
- **The switch is forward-only.** Clusters already open are left exactly as they are: nothing is split, closed or re-counted, their `occurrence_count` stays where it was, and they keep their place in the queue until an analyst decides them — they just stop receiving new members. Nothing that arrived before the restart is regrouped or ungrouped.
- Turning it back on is forward-only too: new alerts group again under any open head still inside `DEDUP_IDLE_GAP_MINUTES`, `MAX_CLUSTER_AGE_HOURS` and `MAX_CLUSTER_SIZE`, the rows made while it was off included. Rows that were already separate are not merged.

To check it worked, an hour after the restart *(not run by the agent)*: `psql "$DATABASE_URL" -Atc "select count(*) from alerts where received_at > now() - interval '1 hour' and (status = 'duplicate' or duplicate_of is not null)"` prints `0`.

### SOAR intake (DEC-207)

When the alerts arrive from the team's SOAR stream (n8n), which has already enriched, grouped and closed them and posts each finished alert to `POST /webhook/alerts`, this system stops doing those four things. Four switches, **all `true` by default**: merging the change alters nothing, and behaviour changes only when the Owner edits `.env`. Each is a §6.3 key, a `.env.example` line and a row of the table above, read as `true|false` (also `1|0`, `yes|no`, `on|off`); anything else stops the worker at startup with a message naming the key.

- `DEDUP_ENABLED=false`: no grouping; every alert is its own queue row and its own `triage` job (**Grouping switch (DEC-165)**, above).
- `PULL_ENABLED=false`: the worker seeds no `pull` job; one already pending ends after one run and is not re-armed. The `backfill` and `replay` commands of `app.infra.puller` do not read the flag.
- `AUTOCLOSE_ENABLED=false`: no rule is loaded or evaluated; every non-duplicate alert takes the `received` path to `queued_tier1`, with a `triage` job. The G8′ hard blocks go with the rules: SOAR owns the decision to close.
- `ENRICHMENT_ENABLED=false`: no `SELECT` on `assets`, `identities` or `iocs`; the context comes from the payload's `enrichment` (DEC-208 / DEC-211 S5: `asset.criticality`, `asset.in_inventory`, `asset.user_is_admin`, `asset.owner`, `asset.role`, the worst `ti` / `ioc` verdict), else the unknown context (`asset_present` false, `criticality` `unknown`, privilege `null`, IoC reputation and all three `lookup_status` `skipped`). The risk score still runs.

The code of all four, the `enrichment/` and auto-close modules and the tables `assets`, `identities`, `iocs` and `autoclose_rules` stay: Tier 2's dossier and the Overview's inventory block still read the first three, the backend routes of the removed rules and digest pages still read `autoclose_rules` (DEC-214), and removing any is a later, separate decision (DEC-207 item 5).

**The alert id the webhook takes (DEC-211 R6).** `POST /webhook/alerts` accepts only an `id` of a shape ① can render: the Wazuh `<epoch>.<n>`, or the SOAR `gl-<event ULID>-<message UUID>` (an upper-case Crockford ULID, a lower-case UUID), written with ASCII digits (a look-alike in bold, fullwidth or Arabic-Indic digits is refused). Any other id, or none, or one that is not a string (`not-a-soar-id`, a number, the test generator's `gl-TEST-<rule>-<epoch ms>`) is answered `400` with `{"detail": {"missing": "id"}}`, exactly as an empty id always was, and writes one `rejected_alerts` row (reason `id`, the document as received) and nothing to `intake`, `alerts` or `jobs`. The pattern is not widened: n8n gives its test scenarios real `gl-<ULID>-<uuid>` ids, as the other nine already have.

**The `timestamp` it takes (INT-T02).** Every alert needs a `timestamp` the sort key can be made from: the ISO text Wazuh and the SOAR send (`2026-09-20T00:00:00.000+0700`, with or without the colon in the offset, or `Z`). One that is absent, null, not text (an epoch number), or not an ISO date-time is answered `400` with `{"detail": {"missing": "timestamp"}}` and one `rejected_alerts` row (reason `timestamp`, the document as received), and nothing else is written; it used to be a `500` and no row. It is judged after the id and `rule.id`, so a body with several faults is told the first of `id`, `rule.id`, `timestamp`.

**The body it takes (INT-T02).** The body is read as UTF-8 and nothing else, and then parsed. A body that is not strict UTF-8 (UTF-16 or UTF-32, with or without a byte-order mark; a UTF-8 byte-order mark; bytes that are not UTF-8) or a JSON string or key holding a NUL (`"\u0000"`) or a lone surrogate (`"\ud800"`) is `not_json`: `400` with `{"detail": {"missing": "not_json"}}` and one `rejected_alerts` row holding the first 4096 characters of the body (a NUL in it shown as U+FFFD), never the document. Before, these were a `500` with no row, or a `201` for an alert the pipeline could never read. A plain UTF-8 body, Vietnamese text included, is stored exactly as received.

A SOAR sender that suddenly gets 400s *(not run by the agent)*: `psql "$DATABASE_URL" -Atc "select reason, coalesce(raw_payload->>'id', raw_payload->'_source'->>'id'), count(*) from rejected_alerts where reason in ('id', 'timestamp', 'not_json') and received_at > now() - interval '24 hours' group by 1, 2 order by 3 desc limit 5"` (the `coalesce` reads the id of an alert posted wrapped as an indexer hit, `{"_source": {...}}`, as well as a bare one; a `not_json` row has none, its text is in `raw_payload->>'body'`).

**Before switching** *(not run by the agent)*: `make backup`, and copy `.env` and `docker-compose.yml` aside. The tag `checkpoint/pre-soar-intake` marks the commit before this change.

**How to switch** *(not run by the agent)*: put the lines in `.env` (edit it, do not paste the file anywhere), e.g. `PULL_ENABLED=false`, `AUTOCLOSE_ENABLED=false`, `ENRICHMENT_ENABLED=false` and, as DEC-165, `DEDUP_ENABLED=false`; then recreate the containers. **`up -d`, not `restart`**: a restart keeps the environment the container was created with.

```
docker compose up -d app worker
docker compose exec -T worker sh -c 'printenv | grep -E "^(DEDUP|PULL|AUTOCLOSE|ENRICHMENT)_ENABLED="'
```

The second command prints `KEY=value` for each switch the container has; the four you turned off read `false`. A switch that `.env` does not name is not in the container's environment and means `true`. If a value is still the old one, repeat the first command with `--force-recreate`. Merging this change itself is code-only and goes in with the usual `docker compose restart app worker` (the **restart** row, above); the switches do nothing until `.env` names them.

What to expect with all four off:

- **Alerts** reach the queue as the webhook receives them, each its own head, `queued_tier1`, with a `triage` job. Receipt idempotency still holds: the same `alert_id` twice is a `409`.
- **The context comes from the payload's `enrichment` (DEC-208), else the unknown context.** A payload with a valid block (schema `1.x`) gives the asset's criticality and inventory flag, whether the account is an admin and the worst IoC verdict; a payload with no block, or with any field outside its vocabulary, gets the unknown context, whole, and the log names the field. Three consequences hold for an alert with the unknown context (`docs/limitations.md`, DEC-207 item 3): gate step 4 flags every ① `false_positive` (a warning beside the model's own verdict, which it no longer holds back as `needs_review`: DEC-217), because `asset_criticality = unknown` is one of its blocks; the risk score is the severity base alone (28 for `medium`), with no asset, account or IoC addend; and the auto-close digest is empty (it is for every alert in this mode, as nothing is auto-closed; the UI has neither a digest page nor a rules page since DEC-214). An alert SOAR enriched also has an unknown occurrence count (`occurrence_count: không rõ`, DEC-208 item 4), so a `false_positive` for it always carries a step 4 warning, whatever its asset says. An unknown or absent context never opens a path to a closed alert (DEC-207 item 4).
- **The heartbeat**, only when `PULL_ENABLED=false`, is stamped by every alert the webhook accepts (not by a `409`, and not by a body that is refused), so the `heartbeat` alarm stays green on a flowing stream even though the pull no longer moves it. With the pull on, the default, the webhook stamps nothing, exactly as before: a pull that died still turns the `heartbeat` alarm red beside a webhook that keeps receiving. With the pull off the `heartbeat` check no longer uses the 30-minute keepalive window: it reads the last real alert against `WEBHOOK_SOURCE_MAX_AGE_H` hours (24 by default), so a quiet night is green, a stream with no alert for longer than that alarms, and a system that has received no alert yet reads `ok`, detail `no webhook alert yet`. The `inventory_empty` alarm reads `ok`, detail `n/a — enrichment off`, whatever `assets` holds.
- **The blind arm and the admin pages** are unchanged (DEC-101, DEC-206): no ① suggestion shows on a blind, undecided alert, in the queue, on the alert page, in the audit list or in the usage list; the overview answers and renders with no auto-closed alert and no inventory (the digest page was removed from the UI, DEC-214).
- **The spend** moves the other way from DEC-165: ① still runs once per alert, so the `LLM_MONTHLY_USD_CAP` row of **What to watch** is the number to look at in the first days.

**Rollback**, three levels, each only as deep as needed *(not run by the agent)*:

1. **The flags.** Restore the lines in `.env` (`true`, or delete them) and `docker compose up -d app worker`, then the same `printenv`. Nothing else was changed, and alerts already received stay as they are. **Turning `PULL_ENABLED` back on is not just "the behaviour of before": the pull catches up, and after SOAR mode it re-ingests every alert SOAR already posted.** `source_cursor.last_sort` did not move while the pull was off, so the first pull starts at `last_sort - PULL_OVERLAP_S × 1000` (`last_sort` is in milliseconds, `PULL_OVERLAP_S` in seconds) and reads every alert the indexer indexed during the whole off-window. The pull keys an alert on the indexer's own `(manager name, Wazuh id)`; the alerts SOAR posts carry other keys (the team's samples, `docs/plan/tasks/P12/soar-payload-sample*.json`, have `id` = `gl-…` and `manager.name` = `graylog`), so **none** of what SOAR already posted is recognised as received: every one comes in again as a new alert. Each one that is not grouped as a duplicate gets a ① run, the auto-closed ones included (D8), so every alert of the off-window gets a **second ① run**, and with auto-close on again the closed ones also fill the next 08:00 digest. After days in SOAR mode that is a flood in the Tier-1 queue, in the digest and in the model spend. **Unless the Owner wants that re-ingest, the cursor must be moved to the switch-back time before the pull is turned on.** Read it first *(not run by the agent)*: `psql "$DATABASE_URL" -Atc "select last_sort, last_pull_at from source_cursor"` (`last_sort` is the indexer's sort value in milliseconds since the epoch, `last_pull_at` the last pull that ran, from before SOAR mode). Moving the cursor is the Owner's decision, recorded, and never done silently by anyone else; this runbook gives no statement for it. While the pull is off the **What to watch** row "a pull in the last 5 min, no error" reads `f|…`, first column false, because `last_pull_at` goes stale: `f|t` if the last pull before the switch succeeded, `f|f` if it ended on an error. That is expected, and no alarm of its own (the `heartbeat` alarm reads `source_heartbeat`, which the webhook keeps moving with the pull off).
2. **The code.** Revert the merge of this change, or, by the Owner only, `git reset --hard checkpoint/pre-soar-intake`; then `docker compose restart app worker`.
3. **The data.** `make db-restore FILE=backups/soc-<timestamp>.dump`, **only if data was damaged**. There is no migration in this change, so levels 1 and 2 never need level 3.

### Running an analysis

On a case page, a **tier2** or **admin** session sees the ② panel, titled `PHÂN TÍCH AI ②` (`frontend/src/strings.ts`, `case.aiHeading`). The case page is the React UI (`http://127.0.0.1:8080/`, **UI (service `ui`)** above); the Jinja case page this section was first written against retired in P10-T13, and the React panel uses the same state texts (`frontend/src/strings.ts`). The panel moves through four states:

| state | what the page says | what you can do |
|---|---|---|
| idle | `Chưa có phân tích nào cho case này.` | press **Phân tích** |
| running | `Đang phân tích…`; the panel re-fetches itself every 3 s | wait: the button is hidden while a job is live |
| done | the result: conclusion, confidence, summary, narrative, hypotheses, evidence with its marks, next steps, and the recorded snapshot beside the current alert count | read it; press **Phân tích** again for a fresh run |
| failed | `Phân tích thất bại — có thể thử lại`, and the last finished run's result underneath if there was one | press **Phân tích** |

The same through the API (a tier2 or admin bearer token) *(not run by the agent)*: `POST /api/tier2/cases/{id}/analyze` answers `202 {run_id, job_id}`, then `GET /api/tier2/runs/{run_id}` answers `running` until the job finishes and `done` with `{status, result, evidence_check, citation_warnings, stopped_by}` after. A `404` on that `GET` means no such run: the page treats a job that ended without a run row as **failed**, the API cannot tell it from an unknown id.

The refusals, in the order the API checks them:

| answer | when | on the page |
|---|---|---|
| `404` | no such case | — |
| `409` `case đã kết luận` | the case is no longer `investigating` | the button is not drawn: `Case đã kết luận — không thể phân tích thêm` |
| `429` `analyze quota exceeded for today` | the user already made `ANALYZE_QUOTA_PER_USER_DAY` (default 30) analyses in the last day | the panel says `Đã dùng hết lượt phân tích trong 24 giờ gần nhất` (the 429 carries no count, so the sentence gives none) |
| `409` `an investigation is already running for this case` | a job for this case is `pending` or `running` (one live job per case, by the jobs table's partial unique index) | `Đang có một lượt phân tích chạy cho case này` |

The quota counts `case.analyzed` rows in `audit_events` for that user, at request time. The count and the insert are two steps, not one: two requests racing at the limit can both pass, so a user can end **one over** the limit (N14, accepted, P5-T04 review).

### What ② does

One press builds the nine-block dossier from the database alone (case facts, representative alerts and logs, timeline, entities, correlation, Tier-1 decisions, playbooks, analyst notes and the previous ② result, and the scope block; with `RAG_ENABLED` a tenth block, the learned section, goes between the notes and the scope block, **Learned knowledge and RAG (DEC-210)**), inside an estimated budget of `CASE_PROMPT_BUDGET_TOKENS` (default 60,000; the estimate is characters over four); if it is over, it cuts in a fixed order — raw logs to 4 KB, representatives to 15 clusters, the timeline — and records each step. It lints the prompt (G6') before anything is sent, then makes **one** model call with no tools, plus **at most one** repair call when the answer breaks the schema. It scans each dossier block for prompt injection, checks the cited evidence against the case's alerts, and writes a single `llm_runs` row. **It changes no case or alert status (G7): the only writes are `llm_runs` and `cases.last_analyzed_at`**; the route adds the `case.analyzed` audit event. The snapshot, the cut steps (`agent_trace.truncations`) and `estimated_tokens` are stored in that row's `agent_trace`.

### What `need_more_data` means

On the P14 branch (DEC-213, the trial) `need_more_data` is **the system's hold**, never the model's answer. The model concludes `false_positive`, `policy_violation` or `confirmed_incident` and says in `next_steps` what is missing: its schema (`investigate_v3`) refuses `need_more_data` and the prompt no longer offers it. ② stores `need_more_data` instead only on an **overrule**: it replaces the model's conclusion because (a) **no cited evidence verified**, or (b) the dossier held a **high-severity injection finding** and the model had said `false_positive`. Every run with a result keeps the model's own conclusion in `evidence_check.model_conclusion`, so the case page can tell "the model concluded X" from "the model concluded X and the system held it"; an overruled one keeps `evidence_check.original_conclusion` as well (and `forced_by = high_severity_injection_finding` for (b)). On an overrule the panel shows a warning line, `Mô hình đề xuất <original> nhưng kết luận đã bị hạ xuống need_more_data: <reason>`. Read the original before acting on the label: an overruled `confirmed_incident` is a real lead the check could not back with a log line. (A stack on `main` has no P14: there the model could also answer `need_more_data` itself, and the label meant two things.)

### The evidence marks

Each cited item is marked **`Đã kiểm chứng`** (verified) or **`Chưa kiểm chứng`** with a reason. **Verified** means the quote is a verbatim substring of the `raw_log` or the description of an alert in this case, after Unicode NFKC and whitespace collapsing, in either the plain or the HTML-escaped form the model was shown; an alert that is a duplicate of a case alert counts as that alert. The rejections:

| reason | on screen | means |
|---|---|---|
| `not_in_case` | `alert này không thuộc case` | the `alert_id` is not in the case, nor a duplicate of one |
| `quote_not_found` | `trích dẫn không có trong log hay mô tả của alert` | the alert is in the case, the text is not in it |
| `quote_too_short` | `trích dẫn ngắn hơn 8 ký tự …` | under `8` characters after normalising: too short to prove anything |

### Cost and failures

**Every paid call is costed**, into whichever row that attempt writes, including a failed attempt's. A job that is retried leaves one row per non-final attempt with `stopped_by = 'transient'` under an attempt-scoped `run_id`, so the month's spend (`LLM_MONTHLY_USD_CAP`, default 30, summed over all `llm_runs`) never loses a call. The outcomes of a run:

| `stopped_by` | when |
|---|---|
| (empty) | a valid result was recorded |
| `cap` | the monthly cap was already reached when the run started: **0 model calls** were made |
| `permanent` | the API answered a 4xx, which the adapter never retries (a rejected key, a malformed request, a prompt past the model's context window): retrying changes nothing |
| `linter` | the dossier failed the safety lint before sending |
| `schema` | the answer broke the schema, and the one repair broke it again |
| `transient` | the model timed out or answered 5xx |

`LLMTimeout` is not retried inside the model adapter: the job is retried instead, up to `JOB_MAX_ATTEMPTS` (3) attempts, `JOB_BACKOFF` apart (10 s, then 60 s). A job that exhausts them ends `failed` with a `job.exhausted` event. What the page then says depends on the last attempt: after a model timeout or 5xx it wrote the `transient` row and the page says `Phân tích không có kết quả: <reason>`; if it died on anything else there is no row and the page says `Phân tích thất bại — có thể thử lại`. The same `Phân tích không có kết quả: <reason>` line is what `cap`, `permanent`, `linter` and `schema` show, because those runs finish normally with a row and no result. A case's investigate runs, read only *(not run by the agent)*:

```
psql "$DATABASE_URL" -Atc "select created_at, stopped_by, cost_usd, run_id from llm_runs where pipeline = 'investigate' and subject_id = '<case_id>' order by created_at"
```

`stopped_by` is empty for a recorded result and `transient` for a non-final attempt. `<case_id>` is the case id from the page's address, not an alert id.

### Operating notes

- The `investigate` handler runs on the `jobs` queue in the existing `worker` container (found by `iter_handlers()`, nothing to enable). Its statements carry a `5 s` statement timeout, and its first statement raises the idle-in-transaction timeout from `10 s` to `JOB_LOCK_TIMEOUT_S`, since the transaction is open across the model call.
- **`2 × LLM_TIMEOUT_S < JOB_LOCK_TIMEOUT_S`** must hold (240 s against 300 s by default): a send and its one repair must both finish before `reclaim_stale` re-queues a job it thinks is dead. Nothing enforces it in `.env`. Raise one, raise the other.
- With `LLM_MODEL_PROPOSER` empty the job completes without reading the case and writes nothing (no row, no status change). The page then says `Phân tích thất bại — có thể thử lại` while it is polling and `Chưa có phân tích nào cho case này.` after a reload.
- A merge that changes ② is a code-only change: `docker compose restart app worker` *(not run by the agent)*; the code is a live mount. A compose or mount change is `docker compose up -d`.
- **If the worker is down, a queued job stays `pending` and the page keeps saying `Đang phân tích…` and re-fetching every 3 s.** There is no stale-job state and no timeout on the page (P5-T05 open question 1). Check `docker compose ps worker` and the pending-jobs row of **What to watch**; `docker compose restart worker` starts the job. A job locked for longer than `JOB_LOCK_TIMEOUT_S` is re-queued by the worker's loop (**Worker stuck**, above).

### Limitations

- ② is **built but not measured**. The frozen gold set was run through ① only (P7); no figure exists for how often ② is right. Treat its conclusion as a starting point for the analyst, not a verdict.
- The `[truncated] N bytes dropped` marker the dossier puts in a cut block reads to the injection scan as a **medium** finding (the truncation flag is not carried to it). Only **high** overrules a `false_positive`, so this is noise, not a wrong conclusion.
- The quota can be exceeded by one per race (above).
- The polling, the four states and the overrule text were exercised against a fake model and a probe of the htmx swap; the panel was not driven in a real browser (P5-T05 open question 3).

### 3 · The rule for the advisor — say it aloud, before the first alert

- **(a) The queue opens with the 383 replayed heads** (`replay` 307 + `wazuh` 76 at 19/09). - **(e) *"ẩn — nhánh mù"*** in the queue's ① cell, and as the title of the ① panel (*"PHÂN TÍCH AI ①"*) on the alert page, is the blind branch: whatever ① said — or has not yet said — about that alert is hidden until it is decided, and so is whether ① ran at all (`triage_status` and `run_id` are stripped with the suggestion — DEC-101). ### 6 · What P8's export does with the pilot's alerts — and why

P8's export, `eval/ops_export.py`, handles these **itself**; the Owner does not keep them out by hand, does not skip them, and does not decide them differently. The pilot's figures are section 6a of its output, and the file has them only when the pilot's window is given *(not run by the agent)*:

```bash
PYTHONPATH=backend python3 eval/ops_export.py --until <UTC instant> --pilot-start <UTC instant> [--pilot-end <UTC instant>] --env-file .env --out docs/results/operations.md
```

`--pilot-start` is the start written into `STATE.md` (§2), inclusive. `--pilot-end` closes the pilot, exclusive, and needs `--pilot-start`; left out, the end is the database's own `now()`. `--until` is required (without it the export exits 2) and closes the report's own window, which is not the pilot's. Every instant is ISO 8601 and must end in `Z` or `+00:00` — a local time with any other offset is refused, exit 2; `date -u '+%Y-%m-%dT%H:%M:%SZ'` prints the current one. The export is read-only, calls no model and no network; without `--pilot-start` section 6a prints `not measured: pilot start not given`.

- **`source='lab'` rows** — the 22–24/09 lab scenarios on the same host, retagged after each run by `eval/lab_tag.py` from the seconds in `docs/lab-run-log.md` (DEC-085). They are G2's, not the pilot's. The export splits them rather than dropping them: section 6a prints the pilot's figures per arm and per source (`wazuh`, `lab` and all), so the lab alerts have a line of their own and the `wazuh` line is the live traffic. Decide them like any other alert if they reach the queue during the pilot; the tag separates them later.
- **Reopened alerts** — any alert with an `alert.reopened` audit event: the ① verdict was visible in the digest before the second decision, so it is blind no longer (P4 planning decision 7). The export excludes it: it is in no decision figure on either arm, not only the blind-branch agreement, and it is counted apart as `đã mở lại (loại khỏi pilot)` (Q35, DEC-166).
- **Alerts an escalation swept into a case** — until T2 (DEC-215, 11/11) an escalation took the other correlated heads (same agent, source IP or user within ±2 h) into its case without a decision of their own (never one that another analyst holds, DEC-166); since T2 it takes only the alert it was made on, and its own duplicates, and the correlated alerts stay in the Tier-1 queue with their status, to be decided one by one (concluding the case closes only that alert and its duplicates). The alerts swept before T2 are no decision either: counted apart, per arm and source, as `kéo theo (không phải quyết định)` (Q34, DEC-165), and in no decision count, denominator or agreement. A pilot window that opens after T2 reads 0 on this row.
- **The 383 pre-inventory heads** (§4 a) — a named limitation; P8's chapter says whether they are in or out of each table, with the sentence attached.
- **Decisions on the visible branch** are reported as *"có thể thiên lệch"* (`docs/chot-v3-14-ngay.md` §A3; architecture §6): the analyst saw ① before deciding. They are counted, per person, and labelled — never pooled with the blind branch.

### 7 · Limitations of this pilot, stated

- **The connection is plain HTTP** — the app is published on `8000` and `ui` on `127.0.0.1:8080` without TLS, so the password typed at sign-in and the Bearer token the React UI keeps in the tab's `sessionStorage` cross the network in clear wherever the Owner's tunnel does not encrypt them. Until P11-T19 the same login also set a `soc_session` cookie (used by the admin pages on `8000`): `HttpOnly`, `SameSite=Lax`, `Secure` off, and there was no CSRF token beyond `SameSite=Lax`. It sets none now: a request is signed in by its `Authorization: Bearer` header alone, which a page of another site cannot attach. Acceptable for two users on one host; stated for the record (P4 planning decision 8).
- **`REVIEW_DELTA_TOLERANCE=20`** and **`RETRIAGE_FACTOR=10` / `RETRIAGE_ABS_DELTA=200`** are unvalidated v1 constants. The pilot's evidence about them is the number of `409` conflicts on decide, **and only with `DEDUP_ENABLED=true`** (the default; see `Grouping switch (DEC-165)` above): that conflict is a head that gained occurrences after the analyst opened it (`cluster_grew`, `occurrence_count` over `seen_occurrence_count` by more than `REVIEW_DELTA_TOLERANCE`). With it `false` nothing is grouped, every alert keeps `occurrence_count` 1, and no `cluster_grew` can happen — the count measures nothing about the constants, whatever it reads; a `409` that still shows up is `already_decided` or `not_active` (two presses, or two analysts). They are **not audited** — `select count(*) from audit_events where event_type='authz.denied'` counts refused roles, not conflicts — so count them from the app's own log, which is the container's stdout (row **h**): `docker compose logs --no-log-prefix --since '<the start written in STATE.md, YYYY-MM-DDTHH:MM:SS>' app | grep -c '/decide HTTP/[0-9.]*" 409 '`. uvicorn's default access log is on (`docker-compose.yml`'s `command` does not pass `--no-access-log`) and each line ends with the status, `INFO:     <client> - "POST /api/tier1/alerts/<id>/decide HTTP/1.1" 409 Conflict` — the format was measured on a scratch uvicorn with the same defaults, the count itself was not run against the stack. Acknowledge, escalate and reopen answer `409` too: replace `/decide HTTP/[0-9.]*"` with `/api/tier1/.*` to count them all. **The count lives in the container's log**: `docker compose up -d --force-recreate app` or `make down` removes the container and the log with it, so read and write the number down first (or save `docker compose logs --no-log-prefix app > ~/pilot-app-$(date +%F).log`). Note the number in `STATE.md` at the end of the pilot. *(not run by the agent)*
- **The two analysts are the author and the advisor** (`docs/chot-v3-14-ngay.md` §A3): the blind branch controls what they see, not who they are.
- The day-1 queue (§4 a) and the `HR-computer` share of the live stream (§4 b) are limitations of the same pilot and are listed with these in P8 (`P4-tasks.md` §11 item 4).

### 8 · Stop / rollback

- **Pause or stop the pilot:** `docker compose stop app ui` stops the UI and the API and nothing else (read the `409` count first, §7: the log goes when the container is removed, a `stop` keeps it). **Leave the worker running** — it keeps ingesting and ① keeps running, and both are wanted for the lab (22–24/09) and for P8's export. To resume, `make run-app` and `docker compose up -d ui` (rows **h**, **ui**) — sessions survive a restart (they are tokens checked against `users`, not server memory).
- **Nothing in P4 needs a rollback of data.** Every decision is one `tier1.decided` audit row (append-only) plus a status the state machine owns; a wrong decision is corrected the way the design says — reopen when the state machine allows it, or a note in the DEC — never by an `UPDATE`.
- **Stop the worker only for the host, or to restart it after a merge** (row **d1**), never for the pilot: `kill -- -$(cat /home/user1/soc-logs/worker.pid)` for the detached form, `Ctrl-C` in its terminal for the foreground form; starting it again (row **d1**) resumes the puller from `source_cursor.last_sort` (row **d2**) and the pending `triage` jobs from where they were — nothing is lost, nothing is re-done.
