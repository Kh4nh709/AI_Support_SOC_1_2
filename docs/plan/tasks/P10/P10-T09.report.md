## 1. Built

All paths are under `frontend/src/`.

**`features/tier1/aiState.ts`.** The one place the ① state is decided; `AiCell.tsx` only words it, and P10-T10 reuses it.
`DECIDED` (`closed_fp, closed_benign, closed_confirmed, escalated_tier2, auto_closed`, the same as `visibility.SHOW_STATES`).
- `aiStateOfRow(row)`: **hidden** (no `suggested_action` key, `suggestion_visible === false`, status not in `DECIDED`) → **ready**
  (a string action; `forced = gate_forced === true`) → **unavailable** (`triage_status === "unavailable"`) → **pending**.
  The blind arm is never `pending`: a blind row carries `suggestion_visible: false` and no keys, and is `hidden`.
- `aiStateOfView(view)`: **decided** (status in `DECIDED`) → **hidden** (no `suggestion` key, not visible) → **ready** →
  **unavailable** → **pending**.

**`api/tier1.ts`.** `QueueRow` (the ① keys optional: the server strips them, they are absent and not null), `QueueResponse`,
`QueueFilters`, `QUEUE_PAGE_SIZE = 50`, `queuePath` (an unset filter is left out: an empty `band=` or `status=` is a 422),
`fetchQueue(filters, page, signal)`, and a minimal `AlertView` for `aiStateOfView` (P10-T10 completes it).

**Band table (rulings R8, R13).** `strings.ts` `S.band` is code → label (`critical` "Rất cao", `high` "Cao", `medium` "Vừa",
`low` "Thấp") and `bandCodeOfLabel(label)` is its inverse: the one table. Chips and the filter speak codes; a row's `risk_band`
is the server's label and its badge colour is looked up label → code. An unknown label is shown raw in a neutral badge, no
score is "—". `api/types.ts` has `BAND_CODES`, `BandCode`, `isBandCode`.

**`live/socket.ts`.** `connectLive({token, onChange, onStatus, onUnauthorized?, url?}) → disconnect`, over the global
`WebSocket`. The URL is `ws(s)://<host>/api/ws` with no query, ever. The token is read when the socket opens and sent as the
first frame `{"type":"auth","token"}`; `ready` makes the status `live`; `alerts.changed` is honoured only after `ready`
(`ids` of strings, or `many: true`). A drop is `offline` and reconnects with a doubling backoff (1 s → 30 s; reset when a socket that stayed live for 10 s drops, not on `ready` alone: fix round 1).
Close **4401** calls `onUnauthorized(sentToken)` and stops; **4403** stops (no reconnect); **1011** and anything else back off
and reconnect. A constructor that throws schedules a reconnect. No token → offline, no socket. Disconnect is idempotent.

**`live/invalidate.ts`.** `createInvalidator(client, windowMs = 500)`: a leading-and-trailing throttle. The first change flushes
at once and opens a 500 ms window; changes inside it are folded (`many` wins) and flushed once when it closes, which opens the
next window. A flush invalidates `["queue"]` plus `["alert", id]` per id (`["alert"]` for `many`). So a burst costs two flushes.

**`live/LiveProvider.tsx`.** One socket per token (opened for `useAuth().session?.token`, closed with it). `useLiveStatus()`
is `"live" | "offline"`; it is offline with no provider, so a page rendered alone polls. The status is kept together with the
token it was reported for, so the socket of an ended session never speaks for the next one. Every transition to `live`, the
first one after mount included, runs one `many` invalidation through the throttle (changes while down were not heard, and an
alert committed between the page's fetch and the server's subscription is in no message: fix round 2, §7). The query cache is cleared when the token changes or ends (what one
session fetched, under its own role, is not shown to the next; whether ① is shown on an alert is decided per alert, by a sha256
of its `alert_id`, not per person). `live/LiveIndicator.tsx` is the
header's `Trực tiếp` / `Mất kết nối` (`role="status"`, the word and not only the colour).

**`api/client.ts`.** Additive `reportUnauthorized(sentToken)`: calls the 401 hook only if that token is still the current one,
the same rule as a 401 answer. **`api/queryClient.ts`** `createQueryClient()`: no retry for a 4xx `ApiError`, at most two for
the rest.

**`features/tier1/QueuePage.tsx`** (with `queueParams.ts`, `QueueFilterBar.tsx`, `QueuePagination.tsx`, `AiCell.tsx`).
- View in the URL: `?band=&category=&agent=&status=mine&page=`; only non-defaults are written, only understood values are read

### Item 1: ruling R17, DEC-101 blind-arm leak (backend, `9734db3`)

**The leak.** ① is the only first-time writer of `triaged_count` (`tier1/triage.py`, +1 per run) and `needs_retriage` is computed
from it in the queue SQL (`RETRIAGE_FACTOR` 10, `RETRIAGE_ABS_DELTA` 200). On a blind (`suggestion_visible` false), undecided
(status not in `SHOW_STATES`) head, a counter that ticks, a ⟳ that lights up, or a row that jumps to the top of the queue
each say "① just ran", which migration 018 (R12) keeps the NOTIFY trigger silent about.

**The fix.**
- `visibility.ANALYST_HIDE` has eight keys now: the six of before plus `triaged_count` and `needs_retriage`. So the queue JSON, the
  alert detail JSON (`get_alert_view`, which returns `triaged_count`) and the Jinja queue (`row.needs_retriage` is falsy when the
  key is absent; no template change) all drop them on such a head, and once decided, or on the visible arm, they come back.
  `LABELING_DENYLIST` already denied both.
- `queue.py`: the retriage formula is one fragment, `_NEEDS_RETRIAGE_SQL`, used by the SELECT. The `ORDER BY` uses
  `_NEEDS_RETRIAGE_SORT_SQL`: the same formula AND (`COALESCE(a.suggestion_visible, false)` OR `a.status = ANY(show_states)`), so a
  blind, undecided head sorts as if it did not need a retriage. (An output alias cannot be used inside an expression in
  `ORDER BY`, hence the shared fragment; `COALESCE` because NULL sorts first under `DESC`.)
- Tests: `test_visibility.py` (the two keys in both literal sets; the visible arm and a decided head keep them),
  `test_queue.py` (a blind retriage head has neither key and does not jump the queue; a visible one keeps both and sorts first;
  the two mixed; the sort and the strip share one notion of "decided"; `get_alert_view` hides `triaged_count` and a decision
  brings it back), `test_pages_alerts.py` (the Jinja queue: no marker, no jump; the old marker test now uses the visible arm),
  `test_tier1_api.py` (the API keys).

**Deviation.** The 018 trigger's status list is a literal in SQL, pinned to `SHOW_STATES` by a regex parity test. Here the sort
takes `show_states` as a **bound parameter read from `visibility.SHOW_STATES` at call time**, so there is no second list to
drift; `test_queue_sort_and_strip_share_one_notion_of_decided` monkeypatches `SHOW_STATES` and shows the sort follows it.

### Item 2a: starvation (`124ecf4`)

`createInvalidator`'s flush used TanStack's default `cancelRefetch: true`, so each flush aborted the fetch under way; with an
answer slower than the 500 ms window a steady stream never let one land. Now every flush passes `cancelRefetch: false`.
**Plain `false` is not enough**: a flush that joins a fetch under way is dropped, and that fetch started before the change,
so after the stream stopped the list stayed on an older state. So `refresh(queryKey)` checks `client.isFetching` first and,
if a fetch was under way, invalidates once more when it has landed (guarded by `cancel()`): the trailing fetch, never
concurrent with the one it follows.
- Tests: `invalidate.test.ts` "with a fetch under way" (a real `QueryObserver` with a 700 ms fetch under fake timers: a steady
  stream of 30 changes lets a fetch land and aborts none; a change after the fetch started gets one more fetch, exactly one; a
  change before it started gets none; `cancel()` stops the follow-up) and `QueuePage.test.tsx` "shows a slow answer while
  changes keep coming, and ends on the last change" (MSW `delay(700)`, 15 changes 100 ms apart: the list updated during the
  stream, and ends on the last change).
