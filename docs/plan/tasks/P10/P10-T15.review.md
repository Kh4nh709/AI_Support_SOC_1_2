### Findings
1. **Important, at the decision level.** With the switch off, identical siblings are separate heads within ±2 h that share the agent, user or srcip. So escalating one of them sweeps them all into the case (A11b, `correlated_cluster_ids`).
   - The pilot export counts one decision.
   - The other alerts cost a ① run but get no human decision.
2. **Minor.** At `MAX_ALERTS_PER_CASE`, `correlation.py:129` orders by `occurrence_count DESC` with no tie-break, so which siblings are kept is arbitrary.
3. **Minor, one of them safety-relevant.** With every count at 1, three signals go dead:
   - **the gate's `occurrence_lt` guard.** `kb/lookup.py:42` maps it to `occurrence_count`. The false-positive rule `sbf-1` (`kb/decision_tables/ssh_brute_force.yaml`) requires `occurrence_lt: 50`, so each alert of a 500-attempt burst would qualify as FP. Four other tables use the same fact;
   - `needs_retriage`;
   - the case page's "ongoing" signal.
4. **Minor.** The runbook keys table has no `DEDUP_ENABLED` row and still says "62 keys".

## Decisions
- **Owner, 30/09: keep the sweep** ("Giữ kéo vào cùng case"). One escalation gives one case for the whole burst.
  - The pilot records swept alerts separately as "kéo theo", not as decisions.
  - This goes to P10-T16.
- **Director ruling R22.** With the switch off, the gate's occurrence facts use the burst count: the number of alerts with the same `rule_id`, `srcip`, `dstip` and `agent_name` within the dedup window, instead of `occurrence_count`. The brute-force FP guard therefore keeps working.
  - Goes to P10-T16.
  - **The Owner must not set `DEDUP_ENABLED=false` until P10-T16 is merged.**
- **Also to P10-T16:**
  - the correlation cap tie-break (finding 2);
  - the runbook keys row (finding 4).
