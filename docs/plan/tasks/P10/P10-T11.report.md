## 1. Built

All paths are under `frontend/src/`.

**`api/tier2.ts`.** Hand-written types and calls for `backend/app/web/routers/tier2.py` and `tier2_runs.py` (the routes answer
plain dicts, so there is no generated schema): `listCases(offset, limit=50)`, `getCase(id)`, `addNote(id, body)`,
`concludeCase(id, conclusion, reason)`, `getInvestigation(id, runId|null)` (`?run_id=` only when a run is named),
`postAnalyze(id)`; `statusOf(error)`; `CONCLUSIONS`, `OPEN_CASE_STATUS = "investigating"`, `isInvestigationState`. Every path
segment goes through `encodeURIComponent`. All calls go over the existing `api()`.

**`features/tier2/useLoad.ts`.** One read of the backend for a page: `{data, error, loading, reload, replace}`. `reload()` keeps
the last answer on screen while it runs (so a form being typed in is never torn down) and resolves to the answer or `null`;
`replace(data)` takes the body of a POST and drops any read still in flight; only the newest read counts.

**`features/tier2/parts.tsx`.** `asText` (any server or model value as text), `BandBadge` (`data-band` is the code; colours are
keyed by code; an unknown label is shown as it came, neutral), `ErrorNotice` (role alert, with Thử lại), and the class strings.

**`CasesPage`** (`/cases`). `<h1>`; a 7-column table (title as a link to `/cases/:id`, status, severity, clusters, alerts with
copies, created, last analysed or "chưa phân tích"); a pager of 50 rows (Trước / Sau; Sau is enabled only when a page came back
full, because the route answers a bare list with no total). Empty list: "Chưa có case nào."; a failed read: error and Thử lại.
Unknown status or severity codes are rendered raw.

**`CasePage`** (`/cases/:caseId`). Left column under `<h2>` "THÔNG TIN CASE", right column the ② column. Left:
- **Summary** (`region` "Tóm tắt case"): status label, severity label, created and last analysed in +07 (or "chưa phân tích"),
  cluster count; "Còn tiếp diễn" with the hint and the last time seen when `ongoing`.
- **Heads**: a table, one row per head: description linking to `/alerts/:id` and the rule id, the band (label from
  `risk_band`, colour by code), the head status, the last seen time, and a "Xem log"/"Ẩn log" toggle. The raw log (up to about
  1000 KB) is collapsed by default; opened, it is one `<pre tabIndex=0>` of text and nothing else (an always-present
  `<tr hidden>` holds it, so opening adds exactly one element). `raw_log_truncated` shows "[đã cắt]" beside the toggle, open or
  shut. The head's own severity is not shown (the band is the risk).
- **Timeline** (`list` "Diễn biến"), oldest first, from what the detail records: created, each note (by author name, or id),
  the last run of ②, the conclusion (who and what).
- **Notes**: each with `author_name` (or `author_id`), the time in +07 and the body as text. The form (open cases only) posts
  `{body}` (trimmed), clears the box, then reads the case again; a 422 shows `S.case.noteInvalid` and keeps the text.
- **Conclusion**: open case: a group of exactly three radios ("Dương tính giả", "Vi phạm chính sách", "Xác nhận sự cố"; values
  `concluded_fp`, `concluded_policy_violation`, `confirmed_incident`), the scope note beside "Xác nhận sự cố" only (also its
  accessible description), a required reason, and Kết luận, enabled when both are given. A 200 shows the answer as the case
  (no refetch). A 409 reads the case again first, then says who concluded it (`concluded_by_name`, else `concluded_by`, else
  the 409's own `concluded_by`, else "—") and when; the form then goes because the case is concluded. A 503 says
  `S.decision.timeout` and keeps the input; a 422 says `S.case.concludeInvalid`. A concluded case shows the conclusion label,
  the reason, who and when, the scope note under a confirmed incident, and no form of any kind.
- A 404 shows "Không tìm thấy case"; any other failure shows the error with Thử lại.

**`InvestigationColumn`** (`{caseId, caseOpen}`; a `<section class="w-[560px]">` headed `<h2>` "PHÂN TÍCH AI ②"). Reads
`GET .../investigation` on mount and keeps the answer.
- **idle**: "Phân tích" (or `S.ai2.idleClosed`, no button, on a concluded case).
- **running**: `S.ai2.running`, no button. Polls every 3 s with `?run_id=`: the `run_id` of the 202 is kept in state (a `done`
  view has top-level `run_id: null`, so the id is never read from it); a poll still unanswered is not asked again; the timer is
  cleared on done, failed, stalled, an error and unmount. A 202 does not read at once; the first poll is at 3 s.
- **stalled**: the minutes and "Kiểm tra lại" (one read with the run_id); no polling and no Phân tích.
- **failed**: `S.ai2.failed` and Phân tích (or `S.ai2.failedClosed`, no button); a previous result, if any, under "Kết quả của
  lượt phân tích trước".
- **done**: the suggested conclusion as the server's `conclusion_label` (not remapped) with its code, the confidence, the
  summary, the narrative (`whitespace-pre-wrap`), the hypotheses with the evidence for and against each (the
  `S.ai2.noCounterEvidence` warning when a hypothesis has none against), a flat evidence list, the next steps, the disclaimer, the time of the result;
  the `overruled` sentence alone in its own element; `changed` shows the stale notice and the snapshot against the current
  numbers. A run with no result shows `S.ai2.stopped(stopped_text)` and, when the case is open, " — có thể thử lại".
  "Phân tích lại" on an open case; nothing on a concluded one.
- **evidence marks**: each item carries "Đã kiểm chứng" only when the server's `verified` is true, else "Chưa kiểm chứng" with
  the server's `reason_text`; the alert id is plain `<code>` text and the quote is text between quotes.
- **refusals** (role alert beside the button, cleared by the next attempt; one post at a time): 429 `S.ai2.quotaExhausted`;
  409 "an investigation is already running…" says `S.ai2.alreadyRunning` and reads, so the column follows the live run;
  409 "case đã kết luận" says `S.ai2.concluded`; any other 409 detail is shown as the server said it; anything else
  `S.common.unknownError`. A read error shows the error and Thử lại; a 404 says the case was not found; a 422 on a bad
  `run_id` is an error state and the polling stops. A `state` the UI does not know is an error, not a guess.
- Everything the model wrote is rendered as text: no `dangerouslySetInnerHTML`, `eval(`, `new Function` or `localStorage`.

**`routes.tsx`.** `/cases` and `/cases/:caseId` render `CasesPage` and `CasePage` under the same `RequireRole roles={TIER2_UP}`.

**`strings.ts`.** `S.band` is now the four server labels keyed by code (`BANDS`: `low` "Thấp", `medium` "Vừa", `high` "Cao",
`critical` "Rất cao"), the only place label and code are paired; `bandCodeOf(label)` reads a label back to its code (or `null`);
`S.severity` (a case's and an alert's `severity`) is a separate table; the case and ② copy; `S.ai2.evidence`.

**The poll.** `refetchInterval` is a function of the query: `POLL_MS` (3 s) while the last good answer is `running` and the query is
not in error, `false` for `idle`, `stalled`, `done`, `failed`, an error, and (TanStack unsubscribes) an unmounted column. There is
no `queued` state on the server, so `running` is the only polling state. The `run_id` of the 202 is kept in component state with
its case (`{ caseId, runId }`, so another case has none) and is the third part of the key. Every read names it, else the run the
last answer for that key named, read back from the cache in `queryFn`; a `done` view carries no top-level `run_id`, which is why
the kept one is what the poll sends. There is no `enabled` option: the poll needs no gate, since the interval function is the gate.
`staleTime` is one poll interval so the view the 202 seeds (a `running` view for the new run, `setQueryData`) is not read again the
moment it is shown, and the `["investigation", caseId]` invalidation of the 202 uses `refetchType: "none"` and runs before the seed,
so no extra GET follows the 202: the first poll is 3 s later, as the round-0 test pins (`[null]` at 2.9 s, `[null, RUN]` at 3.0 s).

**The writes** are `useMutation`:

- Analyze: on success it marks `["investigation", caseId]` stale (no refetch), seeds the new run's key and keeps its `run_id`,
  then invalidates `["case", caseId]` and `["cases"]`. A 409 (already running, or the case concluded) clears the kept run and
  invalidates `["investigation", caseId, null]`, so the column reads what the server holds. The double-click guard (a ref, set in
  the same tick) is kept: `isPending` only turns true after a render.
- A note: on success it clears the box and returns the invalidation of `["case", caseId]` (so the button stays busy until the note is
  back, with its id, author and time), and invalidates `["cases"]`. A refusal shows the server's answer (422 or the generic
  error) until the next try, derived from the mutation, and keeps what was typed.
- A conclusion: on success it puts the answer into `["case", caseId]` (`setQueryData`, so it shows as it comes, as before), then
  invalidates `["case", caseId]` and `["cases"]`. A 409 awaits the invalidation of the case first, then names who concluded it
  from the fresh case (`concluded_by_name`, else the id), else from the 409's own detail: the same order as round 1. A 503, a 422 and
  anything else keep the form and what was typed.

## 9. Fix round 3

Base `ae00f19`; tip after this round is in the reply to the Director.

**The finding.** The ② job writes `last_analyzed_at` and the timeline when it completes (`investigate.py:548`). The analyze
mutation invalidates `["case", id]` at the 202, which is too early, and nothing read the case again when the poll reached the end.
So after a run finished, the left column still showed "chưa phân tích", the old timeline, and "Còn tiếp diễn" with its re-run hint
beside a fresh result, until a window focus or a reload.

**The fix** (`features/tier2/InvestigationColumn.tsx`, in the `queryFn` of the ② read). Before it asks, the read takes the answer
the cache holds for its key. When the new answer is `done`, `failed` or `stalled` and the one before it was `running`, it invalidates
`["case", caseId]` and `["cases"]` (the list shows the analysed time too). Why here and not in an effect:

- It fires once per transition: the answer before a transition is `running` exactly once; a poll that finds the job still running
  does nothing, and a run that has ended is not asked about again (the interval function stops), so the case is not read again.
- A page that opens on a run that is already terminal has no answer before it, so it does not invalidate: the case is read once,
  by the page itself.
- A recheck (Kiểm tra lại) from `stalled` is not a transition from `running`; when that job goes on to end, it is.
- The read of the 202's run starts from the `running` view the mutation seeds, so a run started on this page is covered from its first
  poll. A page opened on a run that is running is covered from its first answer.

**Tests** (`CasePage.test.tsx`, a describe "when the analysis ends", 3 new; 510 in all). A stateful server writes
`last_analyzed_at` when the poll that names the run is answered, as the job does, and counts the GETs of the case.

- "reads the case again when a running analysis is done, and shows the new time and timeline entry": Phân tích, the 202, the 3 s
  poll answers `done`; the summary shows the new `last_analyzed_at` (30/09/2026 10:30:00, +07), "chưa phân tích" and "Còn tiếp diễn"

- "reads the case once, and no more, when the page opens on a run that is already done": one GET of the case after the page and the
