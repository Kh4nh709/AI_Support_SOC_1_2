## 1. Built

**`scripts/ui_e2e_stack.sh <scratch_db>`.** Runs in the foreground while the stack is up; Playwright starts it as its `webServer`
and stops it with SIGTERM.
- The database name must be exactly `soc_ui_e2e_test`. The cluster is that of `TEST_DATABASE_URL` (the environment, else the
  `.env` of the checkout, else the primary checkout's, read with `sed`, never printed; `scripts/ui_e2e_cluster.sh`);
  `scripts/dsn_env.py` turns it into `PG*` for libpq, so a DSN never reaches an argument list. The live `DATABASE_URL` is never
  read. The database is created and migrated with `scripts/migrate.sh`, three users are seeded (`e2e-t1` tier1, `e2e-t2` and
  `e2e-t2b` tier2) with the seed CLI, which reads passwords from `SEED_PASSWORD_<USER>`.
- `JWT_SECRET`, `WEBHOOK_API_KEY` and the three passwords are given by `scripts/ui_e2e_run.sh` (which generates them, so that it
  can scan for them afterwards) or generated inside the script when it is run alone. The children get them from a mode-600 env
  file in the state directory (`env -i bash -c '. "$1"; shift; exec "$@"'`), so no secret is in any argument list.
  Playwright's fixtures get them (with the `PG*` of the scratch database) from `secrets.json`, mode 600, in a mode-700 state
  directory (`/tmp/soc-ui-e2e-<random>`, made by the script, refused if it exists) that the trap removes.
- One run at a time: an exclusive `flock` on `/tmp/ui-e2e-stack-<uid>.lock`, held (by the script and, being inherited, by every
  child) for the whole run.
- A watchdog in every wait (`tick`): the script cleans up when its stdin (a pipe or, under Node, a socket) reaches end of file, or
  when its parent is no longer the process that started it.
- Processes, all on `127.0.0.1`: the LLM stub on 18100, uvicorn `app.web.main:app` on 18000, the worker (`app.web.worker`),
  and `vite preview` of the production build on 18080 (`e2e/vite.preview.config.ts`: `/api` and the `/api/ws` upgrade proxied to
  18000). The webhook is posted to 18000 directly (the UI server proxies `/api` only). Ports are checked free first.
- Every child runs under `env -i` with an explicit list, from the state directory: no provider key, no proxy variable, no `.env`
  (`config.load` reads `.env` from the working directory only). `WEBHOOK_IP_ALLOWLIST=["127.0.0.1"]`, `EVAL_BLIND_FRACTION=0.5`,
  `REVIEW_DELTA_TOLERANCE=20`; `INDEXER_URL` is not set (its default is empty), so the worker's `pull` job has no host to name.
- `trap cleanup EXIT` (also on failure): on a non-zero exit, prints the tail of each log with every secret of the run masked;
  kills every child's process group; `DROP DATABASE ... WITH (FORCE)`; removes the state directory. `INT`/`TERM` exit 0 so the
  trap runs. `E2E_BACKEND_DIR` (optional) points the children at another backend directory; it exists for the red step below.
  The ready line names the backend directory in use, and a one-line `WARNING` says so when it is not this checkout's `backend/`.
  `make ui-e2e` unsets an inherited `E2E_BACKEND_DIR`: it is used only when given on the make command line.

**`make ui-e2e`** runs `scripts/ui_e2e_run.sh`: it makes the run's secrets, runs `npm run e2e` with its output tee'd into a private
directory (removed on exit), and, after the runner has exited, `scripts/ui_e2e_scan.py` searches `frontend/test-results`,
`frontend/playwright-report` and that output for the run's secrets, for a DSN (`postgresql://`), for a JWT and for a Bearer
header. A match fails the target; only the file name is printed, never the match. The scan has to run in the wrapper: Playwright
prints its summary after the `webServer` has been torn down.

**LLM approach: (a), a local OpenAI-compatible stub** (`scripts/e2e_llm_stub.py`, stdlib only, `127.0.0.1:18100`). The real
`DeepSeekAdapter` talks to it over HTTP, exactly as it talks to DeepSeek (`LLM_BASE_URL`), so the adapter, the proposer and
verifier calls, the gate and the investigate pipeline are the product's own. Nothing in `backend/app` imports test code
(`backend/tests/fakes/llm.py` is not used), no live model can be called (no key in any child; the stub is the only endpoint
configured), and `LLM_API_KEY` is a placeholder. Answers:
- **Triage** (proposer and verifier): verdict `needs_review`, confidence `medium`, one reason whose `claim` carries a per-alert
  token (`stub-claim-<sha1 of the alert id>`) and quotes the rule description; the verifier agrees. The token appears in the
  API only inside `suggestion.reasons[].claim`, which makes a leak of the blind arm searchable.
- **Investigate**: `false_positive`, `medium`, and two evidence items on the case's first raw log: the first log line (verified by
  the server's evidence check) and a line no log holds (rejected as `quote_not_found`). The alert id comes from the `alert_id:`
  line of the dossier that precedes the `wazuh_raw_log` block (the blocks themselves carry no id).

**`frontend/playwright.config.ts`.** One worker, file order, `retries: 0`, `forbidOnly`, `list` reporter, chromium; `webServer`
runs `bash ../scripts/ui_e2e_stack.sh soc_ui_e2e_test` (timeout 240 s, `gracefulShutdown` SIGTERM 60 s, `reuseExistingServer:
false`). One worker, because the specs share one database and one worker process, and a logout of `e2e-t1` ends every token that
user holds (`sessions_invalid_before`). `make ui-e2e` passes `PY` as an absolute path (npm runs in `frontend/`). `trace` and
`video` are `off` (a trace held the passwords, the webhook key and every token); a screenshot on failure stays.

**`frontend/e2e/fixtures.ts`.** Secrets read lazily from `secrets.json` (a generic message on failure, never the parser's).
`postAlert` / `postDuplicates` post to the real webhook with `X-API-Key` (a unique agent and description per head, rule `99001`);
alert ids are `<epoch>.<n>` and are chosen by the arm rule of `soar/pipeline._suggestion_visible` (`armOf`: `int(sha256(id)[:8],
16) % 2 == 0` is visible), so a spec that needs a blind head has one without any product change. `loginAs` / `signIn` use the
real login page; `apiLogin` / `apiLogout` use the API from a context no page holds. Every request-context call goes through
`apiPost` (inside `guarded`), and a password fill through `fillSecret`: a failure is rethrown as a new error that names the call
and the class of the failure (`ECONNREFUSED`, `timeout`, ...), never the original message or its call log, which carries the
request headers. `sql` runs one `psql` statement against the
scratch database; `waitForStatus`, `waitForTriage`, `occurrenceCount` poll it. `captureTraffic` keeps every `/api` answer
(except the login's, which carries a token) and every socket frame the page received (never the frames it sent: they carry the
token). Specs assert on names and counts; a body is never printed.

## 4. Deviations and interpretations

- **Secrets to Playwright by a file, not the environment.** The brief says they are exported only to child processes and to
  Playwright. Playwright starts the script as a `webServer` and cannot take an environment back from it, so the script writes
  `secrets.json` (mode 600, in a mode-700 directory it removes) and the fixtures read it. Nothing is printed.
- **Blind spec scope.** "Every `/api` body lacks the keys" cannot be taken literally over the whole queue: the other heads in
  it are in the visible arm and carry `triaged_count` and the rest legitimately. The key and value checks are on the head's own
  JSON (its row of a list, its view, its acknowledge answer). The token, which exists only for this head, is searched in every
  body and every frame, and the eight key names in every frame.
- **The arm is chosen by the alert id** (the suite finds an id of the arm it needs). If `_suggestion_visible` ever changes, the
  spec fails and does not pass vacuously: it checks the server's `suggestion_visible: false` and the `llm_runs` row.
- **The second concluder is a second user** (fix round 1; the first round used two sessions of `e2e-t2`, so the 409 could not
  tell "the first" from "the viewer"). Three users are seeded: `e2e-t1`, `e2e-t2`, `e2e-t2b`.
- **Realtime clock.** Started when the webhook answers, as briefed; the timing is printed (`console.log`, a number only). See
  the concern below.
- **`console.log` in `realtime.spec.ts`** for that number; no other output of a value.

## 5. Concerns

- **The 2 s of the realtime spec has a thin margin.** Measured 962, 863, 977 ms in the counted runs (869, 745, 757 ms before fix
  round 1) and 1422 and 972 ms in the two red runs. Kept at 2 s, the spec's number, with no retry and no product knob; to be
  revisited only if it flakes on the Owner's host. The path is the worker's idle poll (`run_forever`, `sleep_s = 1.0`, not configurable), the server's 500 ms
  coalescing and the client's fetch, so about 1.6 s is the worst case I can account for, plus anything else the worker is doing
  (its `health` and `pull` jobs). On a slower host the spec could fail without a product fault; I have not tuned it, because a
  knob for the worker's idle would be a product change. If it flakes, the honest fix is a knob in the worker or a budget of
  3 s, the Director's call.
- **The specs are serial and depend on order in one respect only:** a logout of `e2e-t1` ends every token that user holds, so a
  spec that logs out must have finished its logout request before the next login (both do, by `waitForResponse`).
- **Small accessibility note, not a defect of this card:** on the alert page the decision panel has a `region` and the reason
  textarea with the same name `Lý do`, so `getByLabel("Lý do")` matches both; the specs use the `textbox` role.
- The `Terminated  sleep 1` line the first round printed at the end is gone: the wait loop is a `read -t` on the stdin socket, not
  a `sleep`.
