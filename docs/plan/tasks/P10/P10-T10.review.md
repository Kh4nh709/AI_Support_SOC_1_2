### Findings
1. **Important: the count guard stopped working under live refresh.**
   - The form sent `seen_occurrence_count = view.occurrence_count`, and the view refetches on `alerts.changed`.
   - If the cluster grew from 37 to 120 while the analyst typed, the POST sent 120. The server saw no growth and never answered `cluster_grew`, so the fan-out closed 120 alerts without the review the guard exists for.
   - The Jinja form fixed the count at render time.
2. **Minor.** The blind no-poll was correct but unpinned.
3. **Minor.** `stopped_by` never shows on the real page, because `get_alert_view` does not carry it.
4. **Minor.** The case link was a dead end for tier1.
5. **Minor.** `AiColumn`'s optional `state` prop could bypass `aiStateOfView`.
6. **Minor.** Report §4.10 gave the wrong reason for clearing the draft after escalate.
7. **Nits.**
   - The acknowledger was named as the decider for `closed_confirmed`.
   - `S.ai1.decidedMine` was unused.
   - `useMe`'s query key carried the token.

**The Coder's concerns, and the Reviewer's advice on each:**
- `user_id` is a uuid string, so fix the types.

## Director ruling R19
- `seen_occurrence_count` is held from the moment the form is first drawn for this acknowledgement. Live refetches do not update it. It changes only when a 409 `cluster_grew` answer brings the refetched count.
- While the live count differs, the form shows "N → M".
- Why: the guard exists to force a review when the cluster grows.
- Cost if wrong: one extra 409 round-trip.

**Other decisions:**
- **Accepted for v1.0, for `docs/limitations.md`:** the ① unavailable state shows generic text without `stopped_by`, because the backend view does not carry it.
- **Parked until after v1.0:** `Session.userId`, which would replace `useMe`.
