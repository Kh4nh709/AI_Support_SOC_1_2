## 1. Built

**Contract.** `GET /api/tier1/queue?sort=risk|time|occurrences|agent&dir=asc|desc`. `sort` defaults to `risk`. `dir`
omitted: `time` and `occurrences` are `desc`, `agent` is `asc`. An unknown or empty `sort` or `dir`, and any `dir` with
`sort=risk`, is a 422 (a string `detail`, like the other filters of the route).

**Backend.**
- `backend/app/tier1/queue.py`. `QUEUE_ORDER_BY` is a dict from `(sort, dir)` to a literal SQL fragment; `_order_by()`
  looks the request up in it and raises `ValueError` for anything not in it, so no request value is ever formatted into
  SQL (`_QUEUE_SQL` takes only the looked-up fragment; every other value stays a bound parameter).
  - `risk` is `_NEEDS_RETRIAGE_SORT_SQL DESC, a.risk_score DESC NULLS LAST, a.first_seen_at ASC`, character for
    character what it was.
  - `time` is `a.last_seen_at <dir> NULLS LAST`, `occurrences` is `a.occurrence_count <dir>`, `agent` is
    `a.agent_name <dir> NULLS LAST`.
  - Every non-risk order ends with `a.risk_score DESC NULLS LAST, a.first_seen_at ASC, a.alert_id ASC`: a total order, so
    `OFFSET` paging is stable. `needs_retriage` plays no part in any of them.
  - `list_queue(..., sort="risk", direction=None)`: the two new parameters have defaults, so the other caller
    (`alerts_pages.py`, P10-T13's file, which calls `list_queue(conn, page=page)`) needs no change. `counts_by_band` and
    `total` do not depend on the sort.
  - `SORT_DEFAULT_DIR` holds the default direction of each key.
- `backend/app/web/routers/tier1.py`. `get_queue` takes `sort: str = "risk"` and `sort_dir` (alias `dir`) and passes them on.

**Blind arm (R17).** No sort key reads anything of ①. A test asserts the whitelist's sort keys are exactly
`{risk, time, occurrences, agent}` and that no fragment names `llm_runs`, `triage`, `suggest`, `confidence`, `gate` or
the run alias. The blind head does not move under any sort when its `triaged_count` changes.

**React** (`frontend/src/`).
- `api/tier1.ts`: `QueueSortKey`, `QueueSortDir`, `QueueSort`, `SORT_DEFAULT_DIR`, `isSortKey`, `isSortDir`;
  `queuePath(filters, page, sort?, pageSize)` and `fetchQueue(filters, page, sort?, signal?)` send `sort` and `dir`
  together, and neither for the risk order.
- `features/tier1/queueParams.ts`: `QueueView` gains `sort?` (the absence of it is the risk order). `readView` and
  `viewToParams` round-trip `sort` and `dir` beside the filters; an unknown key, `sort=risk` or a `dir` alone is no sort,
  and a missing or unknown `dir` takes the key's default. `nextSort(current, key)` is the click rule: the key's default
  direction on the first click, the opposite on a second click on the same key. `viewSearch` keeps the sort.
- `components/DataTable.tsx`: an optional `Column.ariaSort`, written to `<th aria-sort>`; a column that names none has no
  attribute. `AlertSections` is unaffected.
- `features/tier1/SortControls.tsx` (new): `SortHeader` (a `<button>` inside the `<th>`, the arrow `aria-hidden` so the
  button's name is the column's name) and `RiskOrderButton` ("Sắp theo mức rủi ro", `aria-pressed` while the queue is in the
  risk order, and then a no-op).
- `features/tier1/QueuePage.tsx`: the columns are built by `columnsFor(sort, onSort)`; agent, occurrences and last seen are
  sortable, the ① column is not. The query key is `["queue", filters, sort ?? null, page]`, so the live layer's
  invalidation of `["queue"]` (an `alerts.changed`, a socket resync, the offline poll) refetches the sorted page. A sort
  change and a filter change both go to page 1; a filter change keeps the sort, and "Xoá bộ lọc" clears filters, not the
  order. `QueuePagination` keeps the sort in every link.
- `strings.ts`: `S.queue.sort = { asc: "▲", desc: "▼", byRisk: "Sắp theo mức rủi ro" }`.
- No `dangerouslySetInnerHTML` and no `localStorage` in any touched file.

## 4. Deviations

- The new backend tests went into `test_queue.py` (the `list_queue` level) and `test_queue_filters.py` (the route, which is
  the file that tests the queue route's filters); `_all_rows` and `_order` in `test_queue.py` gained `**kwargs`.
- `agent_name` is `NOT NULL` in the schema, so `NULLS LAST` on the agent order is defensive only. It is kept so the three
  fragments read alike and nothing changes if the column is ever relaxed.
- A 422 for a bad `sort` or `dir` is the route's string-`detail` 422 (`list_queue` raises `ValueError`), the same as `band`
  and `status`, not FastAPI's own validation error list. The status code is what the contract names.
- The db tests ran through a launcher outside the repository (`p10t14_pytest.py`), not `make test-db`: it points
  `TEST_DATABASE_URL` and the `PG*` variables at `soc_p10t14_test` as plain environment for pytest, and prints no DSN.
- `queuePath` takes the sort as its third parameter, before `pageSize`, and `fetchQueue` as its third, before `signal`
  (both were positional before); the only caller is `QueuePage`, and the new `api/tier1.test.ts` pins the request path.
- "Sắp theo mức rủi ro" is always visible, with `aria-pressed`, instead of appearing only after a sort: it does not shift
  the layout, and a screen reader hears which order is on. Pressed in the risk order it does nothing.
- `Column.ariaSort` is a small addition to the shared `DataTable`; the brief named `aria-sort` on the `<th>` and the table
  had no way to set it.
