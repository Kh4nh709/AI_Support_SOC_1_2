## 1. Built

**R22, the gate's occurrence facts with the switch off.** In `evaluate_alert`, `occurrence_count` is the row's own value, unless
`cfg.DEDUP_ENABLED` is false: then it is `burst_count(conn, alert_id, cfg)`, one function over one constant query
(`BURST_COUNT_SQL`, exposed through `burst_count_query` so the plan test runs the query the job runs). The value goes into
`TriageInput.occurrence_count`, which is where the gate facts, both `llm_runs` rows, the prompt's `occurrence_count: N` line and the
verifier's prompt all read it: same fact name, nothing else changes.

*Semantics.* The burst count is the number of alerts (this one included, any status, sealed `duplicate` rows of a pre-switch cluster
included) with the same `rule_id`, `srcip`, `dstip` and `agent_name` and `first_seen_at >= this alert's first_seen_at -
MAX_CLUSTER_AGE_HOURS`, counted when ① runs (no upper bound). It mirrors the largest cluster dedup would have built. Parameters are
bound (`alert_id`, the age in hours); the alert itself is read by primary key in the same statement. The four key columns are
`ingest/dedup.py`'s cluster key, restated because `tier1/` may not import `ingest/`. With the switch on the query is never run
(a test asserts it) and the row's `occurrence_count` is used, byte-identical.

*Every table that uses the guard.* `occurrence_lt: 50` on the FP path of nine decision tables (`brute_force`, `c2_beacon`,
`data_exfiltration`, `malware`, `policy_violation`, `recon`, `ssh_brute_force`, `suspicious_login`, `web_attack`); all of them read
the one fact, so the one change fixes all of them. The tests use `sbf-1` (`ssh_brute_force`) and a synthetic `occurrence_gte` table.

*Plan (no migration).* `ix_alerts_dedup` cannot serve the query (it is partial, open non-duplicate alerts only, and ends in
`last_seen_at`). The plan is the primary key for the alert and a BitmapAnd of `ix_alerts_corr_srcip` and `ix_alerts_corr_agent` for
the burst, the rest a filter. Measured with EXPLAIN ANALYZE on a 200,000-alert seed: never a sequential scan; about 1.5 ms for a
500-alert burst; about 15 ms for the worst key measured (a `srcip` that is empty on about 30 % of the table). Once per alert. So the
brief's condition for an index (a sequential scan on a realistic seed) did not arise and no migration is needed. The in-repo plan
test (`test_burst_query_takes_bound_parameters_only_and_uses_an_index`) runs with `enable_seqscan = off` and asserts the plan is
built on `ix_alerts_*` indexes with no `Seq Scan on alerts`; the 200,000-row measurement above is what shows the planner chooses them by itself.

**Pilot "kéo theo" (Q34).** New query `Q_PILOT_SWEPT`, id `Q34`, appended to `PILOT_QUERIES`. Its CTE takes `case_alerts` rows added in
the pilot window `[pilot_start, coalesce(pilot_end, now()))` for non-synthetic alerts that are **not** the subject of a
`tier1.escalated` event (`NOT EXISTS (audit_events … subject_id = ca.alert_id)`): the heads an escalation sweeps into its case, A11b.
It groups by the swept alert's own arm (`alerts.suggestion_visible`) and source, with the same ROLLUP and `_source_order` as the
other pilot tables. Rendering:

  định), blind arm" and "..., visible arm", with the basis `SWEPT_BASIS`;
- section 6a gets `### kéo theo (không phải quyết định) (Q34)`: the per-source table and three bullets (basis; never a decision, not in
  any denominator or agreement; A12 duplicates are not counted);
- section 8 prints Q34's SQL like the others;
- with no `--pilot-start` there is no kéo theo anywhere (same as the other pilot content).
The count is zero, not missing, when nothing was swept. It is never added to a decision, a denominator or an agreement: Q29 to Q33
are byte-identical before and after a sweep (test).

**Correlation tie-break.** `cluster_ids_query` is now `ORDER BY occurrence_count DESC, alert_time DESC, alert_id ASC LIMIT`; its

## 7. Fix round 1 (the Reviewer's findings on `d5e961b`)

**Item 1, R22 leaked into the evaluation harness (Important).** `evaluate_alert` is also the B2 to B4 path of `eval/run_configs.py`, whose
Config comes from `--env-file`. With the Owner's `DEDUP_ENABLED=false` in `.env`, B2 to B4 would have taken the burst count while B1
(`b1_facts`) kept the row's `occurrence_count`: the invariant "B1 facts == `evaluate_alert` facts" breaks, the prompt text changes (so every
LLM cache key misses and the run re-spends), and the gate's step 2 sees a different `occurrence_count`. DEC-165 item 5 evaluates the thesis on
pre-switch data, with grouping.

- **Fix.** `eval/run_configs.py`: `pin_dedup(cfg)` returns the Config with `DEDUP_ENABLED=True` whatever the env file or the process environment
  says, and prints `DEDUP_PIN_NOTICE` (one line, no value of any key) when it overrode a `false`. `_load_config(env_file)` is the one place the
  harness loads a Config; `cmd_run` (before its `estimate:` line, so the notice leads the run's output) and `cmd_human` both use it.
  `b1_facts` documents that its equality with `evaluate_alert` holds because every Config has passed `pin_dedup`.
- **Other entry points.** `git grep` over `eval/*.py` and `scripts/*.py`: `eval/run_configs.py` is the only file that reaches
  `evaluate_alert` or `build_facts`. The other scripts read Config only for the DSN or unrelated keys, and `dedup_verify.fold_clusters` folds
  independently of the switch. Nothing else needs the pin.
- **Tests** (`backend/tests/test_run_configs.py`, section "P10-T16 fix round 1"): an env file saying `false` is overridden and announced;
  every spelling of false, in the env file and in the process environment, is pinned and a `true` or unset switch is silent; the override
  keeps every other Config field (compared by field name, never by repr: DEC-122); with a `false` env file `b1_facts` equals the
  `evaluate_alert` facts (`occurrence_count` 1 over a 4-alert burst, and the test shows the burst of 4 when the pin is lifted); a B4 run
  over a `false` env file and one over a `true` env file send the same user prompts, leave the same cache file names, the second run sends
  nothing new and bills 0.0, and the notice appears once, before the `estimate:` line and the run headline, and not on the `true` run.
- **Red steps** (all restored; `git diff` showed only the intended change afterwards):
  1. tests written before the fix: 6 red, among them the genuine leak (`occurrence_count` 4 against 1);
  2. pin removed (`pin_dedup` returns the Config unchanged): 6 red;
  3. pin kept, the notice print removed: 4 red.
