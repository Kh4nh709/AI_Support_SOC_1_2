## Built

`eval/run_configs.py` (was a one-line stub; now mode 100755, see Deviation 10). Two subcommands.

**`run`** evaluates one configuration on one gold set in one thinking mode.

- **Usage first (exit 2), before any file or connection.** B2–B4 need `--thinking {disabled,enabled}`, which has no default (DEC-042).
  B0/B1 refuse `--thinking` (Deviation 3). `--template` works only with B4 and must exist. G3 runs only B3/B4.
  `--max-workers` is 1..4 (`run_bounded`'s ceiling). `--approved-usd` must be finite and ≥ 0.
- **`gold_sha(gold, sha_file)` (exit 3).** The sha file exists, its hex equals the sha256 of the gold's bytes,
  both files are `git ls-files --error-unmatch`, and `git diff --quiet HEAD -- both` holds, so a staged edit
  counts as an edit. This check comes before the env file is read and before any connection, so acceptance 2
  never opens `.env`. `gold12 = sha[:12]`. The full sha is in the results header and in `eval_runs.metrics.gold_sha256`
  (amendment 2), not on each `Prediction`.
- **G2.** Rows come from `label_export.read_gold_csv`. `scenario_id`/`kind` are added from the same file (Deviation 1).
  `category_expected` is joined from `--lab-windows` by `scenario_id`; a missing window is exit 3. Labels outside
  escalate/benign, a gold set other than G2, a severity outside the DEC-053 band, a repeated cluster, and a header
  other than `GOLD_COLUMNS` are all exit 3. Every gold alert must be in `alerts` (exit 3).
  `Prediction.category` is the alert's own `alerts.category`; `severity` is the gold row's.
- **G3.** Targets come from the manifest's `alert_id`s, with `truth=None` and `cluster_id = alert_id` (amendment 3).
  Every target must exist with `is_synthetic` true; otherwise exit 3, naming `eval/adversarial/load.py`.
  The sha check still runs against `gold_v1`. `metrics.run.manifest_sha256` is recorded.
- **B0**: `metrics.B0_MAP[gold severity]`. **B1**: `b1_facts(conn, alert_id, cfg)`, then `kb.get_decision_table(category)`.
  No table, or no rule that holds, gives `needs_review`; otherwise `apply_table(...)[0]`.
  B1 runs on the run's read-only connection with a savepoint per item. Neither B0 nor B1 constructs an adapter,
  and all their measurements stay `None` (amendment 4).
  `prompt_version` is `severity_for` for B0 and `kb:` + sha256 of `kb/decision_tables/*.yaml` in name order, 12 hex, for B1;
  `model_id` is `none` for both.
- **B2/B3/B4**: `switches_for()` gives B2 `EvalSwitches(include_context=False, include_correlation=False, gate_mode="steps_1_3")`,
  B3 `EvalSwitches(gate_mode="steps_1_3")`, and B4 `DEPLOYED`, or `replace(DEPLOYED, proposer_template=…)` with `--template`.
  `cfg_run = replace(cfg, LLM_THINKING=args.thinking)`. There is **one** `DeepSeekAdapter(cfg_run, spent_usd=guard.total_usd)`
  per run, and one `CachingAdapter(inner, cache_dir, thinking=args.thinking, spend=guard)` per item.
  Items run through `run_bounded(..., max_workers)`. Each item opens its **own** connection, runs `SET TRANSACTION READ ONLY`
  first, calls `evaluate_alert`, then rolls back and closes. `evaluate_alert` returning `None` becomes `exception:AlertNotFound`.
- **Mapping to `Prediction`.** `verdict = final_verdict if outcome == "ok" else None`. `reasons_kept`/`reasons_dropped` are copied
  as given (amendment 7). `cost_usd`/`latency_ms` come from the evaluation, or `None` when no call returned (Deviation 6).
  `cached`/`billed_usd` come from the item's `CachingAdapter.results` (amendment 5; Open question 1).
  Row `outcome` is `TriageEvaluation.outcome` (`ok` for B0/B1, `exception` for an item `run_bounded` captured).
  Row `error` is `None` for `ok`, otherwise the outcome token or `exception:<ClassName>`, never `str(exc)` (amendment 10).
- **Money.** `month_spend(conn)` is `llm_runs.month_spend_usd(conn)` plus the sum of numeric `metrics.run.billed_usd`
  over this calendar month's `eval_runs`. It is computed **once** on the main read-only connection, and
  `SpendGuard(lambda: month_spend, cap, cfg_run)` gets the float (amendment 9). The estimate is
  `estimate_cost(n, calls_per_alert, usd_per_call) × 1.10` (1 call for B2/B3, 2 for B4;
  $0.00028 disabled / $0.00415 enabled, P7-tasks §4). The line printed is
  `estimate: <config> <gold_set> thinking=<m> n=<n> calls≈<c> usd≈<e> month_spend=<s> cap=<cap>`.
  `refuse_if_over` refusing is exit 6. Above $5 without `--approved-usd ≥ e` is exit 5, and the approval command is
  printed with `--approved-usd` rounded up to the cent and the DSN replaced by `<DSN>`.
  `--estimate-only` prints the line and applies the same refusals, then exits 0 (Deviation 4).
  A `SpendGuard` stop mid-run leaves the remaining items `cap`/`verifier_cap` errors; the run is still recorded
  with `metrics.run.stopped_by_cap = true`, and the exit code is 6.
- **Outputs.** `<out-dir>/<eval_run_id>.json` holds `{eval_run_id, gold_sha256, gold_set, config, llm_thinking, prompt_version,
  model_id, predictions: [asdict(Prediction) + alert_id, outcome, error]}`. It is written atomically, with no prompt,
  model output or raw log.
  - `model_id` is every call's response model, the verifier's included (amendment 6). Several models are joined with
    a sorted `+`, with a warning; `none` means no call returned (Deviation 7).
  - `prompt_version` is the evaluations' own: `prompt_version(TRIAGE_TEMPLATE)` or `file:<sha12>`.
  - Unless `--no-record`, one `eval_runs` row is inserted on a **separate** read-write connection.
    `metrics = metrics_json(preds, gold_sha256, llm_thinking=(thinking or "none"), config, gold_set, manifest_rows (G3),
    extra={eval_run_id, billed_usd, cache_hits, live_calls, stopped_by_cap, template_sha256, manifest_sha256, max_workers})`.
  - The headline is `run <id> <config> <gold_set> thinking=<m> n=<n> macro_f1=… recall_escalate=… deferral_escalate=… errors=<k> billed=$<b>`;
    G3 prints `asr=…` in place of the three gold metrics.
- **Credentials.** The DSN is `--dsn`, else `DATABASE_URL`. Once read, every DSN field of the `Config` is blanked,
  so no `Config` in the process can print one (DEC-122). Database errors print the exception class only.
- **Exit codes** (module docstring and parser epilog): 0 done; 2 usage; 3 not ready; 4 DSN or database unusable;
  5 approval needed; 6 cap.

## Open questions

1. **How `cached` and `billed_usd` were read from P7-T02's adapter.** One `CachingAdapter` per work item is built **before**
   `run_bounded`, all over the run's single inner adapter and sharing the cache dir, key locks and `SpendGuard`.
   An item's side record therefore stays readable after its evaluation raised, and money spent before a raise is still counted.
   After the pool, `item.adapter.results` (a list of `CachedResult`) gives:
   - `cached = all(r.cached)`, or `None` if the list is empty;
   - `billed_usd = round(fsum(cost_usd(r.usage, cfg_run) for r in results if not r.cached), 5)`;
   - `cache_hits`/`live_calls`, counted per call;
   - `model_id`, from `r.model` of every record (proposer and verifier).

   The run's `metrics.run.billed_usd` is `SpendGuard.live_spent_usd`, which prices every live call as it returns.
   That includes one whose cache write then failed, which never reaches `results`. So in that one edge case the run's bill
   can exceed Σ per-item `billed_usd`. The run's bill is the number the next run's month spend adds.
2. **Did `b1_facts` need a private helper from `tier1.triage`?** Yes: `_load` and `_Subject`. `correlation`, `TriageInput` and
   `build_facts` are reached through the `tier1.triage` namespace, so B1 follows whatever ① calls.
   `evaluate_alert` builds its `TriageInput` inline, so there is no helper to reuse. `b1_facts` copies the fields by the dataclass's
   field names plus `evaluate_alert`'s one conversion (`origin_host or ""`); the equality test pins the result.
   A public `tier1.triage.facts_for(conn, alert_id)`, used by both, would remove the duplication; `backend/app` is frozen here.
3. **B4's verifier calls are keyed by content that carries no alert id** (facts, table, verdict, reasons). Two alerts with equal
   facts and reasons send one identical verifier call, and the second is a cache hit within the same run. This showed up as
   3 calls instead of 4 in a test; the tests now seed distinct facts.
   For P7-T08: a first B4 run can show `cache_hits > 0`, `live_calls < 2n`, and items with `cached=False` but `billed_usd < cost_usd`.
   That is the cache working, not a stale cache.
4. **`human`'s a/b order and `kappa_v1.json`'s may differ.** Both use `resolve_labelers`, but over different id sets (gold vs
   candidates). `report.py` pairs `vs_truth` with the human file by the keys `a`/`b`, not by `labeler_id`. P7-T08 could check
   `human.a.labeler_id == kappa.labeler_a` before rendering, or `report.py` could match on `labeler_id`.
5. The worker connections hold a read-only transaction open across the model calls (up to 2 × `LLM_TIMEOUT_S`).
   `evaluate_alert` makes no database call after them. So a server-side `idle_in_transaction_session_timeout` would only cost
   a suppressed rollback error. A new session on the test cluster shows `0` (disabled); the live role's setting was not
   measured (DEC-128).
