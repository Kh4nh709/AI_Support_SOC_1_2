## Built

All in `backend/app/tier1/triage.py`. Nothing in `security/`, `llm/`, the templates or the schema.

- **`EvalSwitches`** (`:369`), a frozen dataclass: `include_context=True`, `include_correlation=True`,
  `gate_mode="full"`, `proposer_template: Path | None = None`. `__post_init__` raises `ValueError`
  for any `gate_mode` outside `GATE_MODES = {"full", "steps_1_3"}`, so an invalid instance cannot be
  built, `dataclasses.replace` included. **`DEPLOYED = EvalSwitches()`** (`:391`) is B4. B2 is
  `EvalSwitches(include_context=False, include_correlation=False)`, B3 is
  `EvalSwitches(gate_mode="steps_1_3")`.
- **`TriageEvaluation`** (`:395`), a frozen dataclass. It carries `alert_id`, `switches`, `outcome`
  (checked against `OUTCOMES`: `ok | builder_violation | schema | cap | transient |
  verifier_transient | verifier_cap`), `proposed_verdict`, `final_verdict`, `gate_result`,
  `reasons_kept`, `reasons_dropped`, `forced_by`, `verifier_verdict`, `model_id`, `prompt_version`,
  `usage`, `cost_usd`, `latency_ms`, `calls` and `facts`. It also carries the intermediates the job
  writes from: `built`, `findings`, `violations`, `proposal`, `state`, `verdict_for_verifier`,
  `vbuilt`, `verification`, `result` and `exception`. The field rules:
  - `final_verdict` (the gated `suggested_action`) and `gate_result` (`gate.gate_result(...)`) are
    set only for `ok`.
  - `proposed_verdict`, `reasons_kept = len(state.reasons)`,
    `reasons_dropped = len(state.dropped_reasons)`, `forced_by` and `verifier_verdict` come from the
    gate state whenever the gate started. Steps 4–7 never change either reason list, so the two
    counts are step 3's (design note 4).
  - `calls`, `usage` (through `llm.triage._sum_usage`), `latency_ms` and `cost_usd` are summed over
    the adapter results that came back (design note 3). A call that raised brought back nothing to
    count or price.
- **`evaluate_alert(conn, alert_id, *, adapter, cfg, switches=DEPLOYED) -> TriageEvaluation | None`**
  (`:522`) returns `None` for a missing alert. It loads the row and builds the correlation, playbook,
  decision table, `TriageInput` and facts exactly as the job did. It then calls
  `build_proposer_prompt(..., include_context=, include_correlation=)`, the detector and the linter,
  and builds the adapter at the same point (`adapter or DeepSeekAdapter(cfg, spent_usd=...)`) before
  calling `propose`. The two gate modes then differ:
  - `"full"` runs `run_steps_1_to_5`, the verifier prompt and its linter, `verify`,
    `step6_verifier` and `step7_output_guard`, in today's order.
  - `"steps_1_3"` runs `gate.start`, `step2_basis`, `step3_quotes` and `step7_output_guard`. No step
    4, no step 5, no verifier build or call.

  It runs only `SELECT`s and catches `LLMBudgetExceeded` / `TransientError` into `outcome`. Every
  other exception propagates as before. The verifier-prompt linter's `PermanentError` is
  byte-identical and still ends the job.
- **Override template** (`_with_proposer_template`, `:447`): the system prompt comes from the same
  `llm.triage._system_prompt(template, "triage_v2")` the deployed one uses (template, then the
  rendered schema). It is swapped into the built prompt, `estimated_tokens` is recomputed, and
  `prompt_version = "file:" + sha256(template bytes)[:12]`. The deployed template keeps
  `prompt_version(TRIAGE_TEMPLATE)`.
- **`run_triage_job`** (`:700`) keeps its idle timeout, missing-row, closed-status and
  `llm_enabled` checks. It then calls `evaluate_alert(conn, alert_id, adapter=adapter, cfg=cfg,
  switches=DEPLOYED)` and, per `outcome`, performs the old branch's writes, events, status changes
  and raises. The transient path still goes through `_last_attempt_or_raise`, and the
  verifier-transient path still re-raises below `JOB_MAX_ATTEMPTS`.

**Behaviour preservation, checked mechanically as well as by the 20 tests.** An AST walk lists
every `write_run` / `write_event` / `_set_triage_status` / `_last_attempt_or_raise` /
`_verify_failed_last_attempt` / `raise` in the old and new `run_triage_job`, in source order. The
new side's `ev.` references are mapped back to the old local names (`ev.findings→findings`,
`ev.violations→violations`, `ev.exception→exc`, `ev.vbuilt→vbuilt`,
`ev.verdict_for_verifier→verdict_for_verifier`, `ev.prompt_version→pv`). Result: 20 calls on each
side. **All 17 write calls are identical**, and the only differences are the three expected ones:

```
+raise PermanentError(f'alert not found: {alert_id}')          # new: row gone between the two reads
-raise PermanentError(f'verifier prompt failed the linter: …')  # moved, unchanged, into evaluate_alert
-raise
+raise exc                                                       # verifier transient: the same object
```

## Deviations

1. **`git merge main` was not run.** The session's permission classifier refused it ("Modify
   Shared Resources"). It then also refused a read-only `git diff --stat HEAD main`. I did not
   retry or work around either. Before those refusals, `git log main` / `git merge-base` showed
   `main` one commit ahead of the dispatch base: `5c312f2`, the Director's DEC-121 docs commit. So
   acceptance 1's and 5's `git diff main` were run against `e2295c1` (the merge-base), which shows
   exactly this branch's own changes. **For the merger:** run the literal `git merge main` and the
   two `git diff main --stat` commands. `5c312f2` probably also edits the P7-T01 row of `STATE.md`
   (its message says T01 was dispatched), in which case merging gives a one-line conflict on that
   row. Keep `main`'s dispatch text plus this row's `review` status and CODE DONE note.
2. **Test seeding.** The card says "insert alerts through `domain.transitions.open_alert` as
   `test_triage_job.py` does", but `test_triage_job.py` seeds with a direct `INSERT INTO alerts`.
   I followed the explicit instruction, as `test_queue.py` does: `open_alert` → `start_enrichment` →
   `finish_enrichment`. That also gives every alert its real pending `triage` job for the
   writes-nothing check. The file uses its own `agent_name`/`alert_user`/`srcip`, so the ±2h
   correlation window holds only what each test seeds.
3. **`run_triage_job` reads the alert row twice**: its own `_load` for the status check (kept, as
   the card says) and `evaluate_alert`'s own `_load`. This is reads only, one extra primary-key
   `SELECT` per job. The one observable difference: if a context column were `NULL` (it never is for
   a queued alert), the `defensive_default_context` log line would print twice. A new
   `PermanentError("alert not found: …")` covers the row vanishing between the two reads; it is
   today's missing-row error.
4. **Two private helpers are imported from `llm/triage.py`** (`_system_prompt`, `_sum_usage`)
   instead of copied: an override template is then composed exactly like the deployed one, and the
   evaluation's usage has `Proposal.usage`'s semantics. `llm/triage.py` is out of this card's scope,
   so I could not make them public.
5. **Verifier-transient re-raise.** The old bare `raise` inside the `except` is now
   `raise ev.exception`, the same exception object. The worker reads only `classify(exc)` and
   `str(exc)`; the traceback gains one frame.
6. **Incident, fixed during development.** One failing assertion in the new test file, on its
   first run, printed the `Config` repr through pytest's assertion introspection. That repr includes
   `TEST_DATABASE_URL`, so a truncated prefix of the test DSN (the user and the first characters of
   its password) appeared in this session's tool output. It is in no file and no commit, and this
   report does not repeat it. Fixed at the root: the file's `cfg` fixture now blanks
   `DATABASE_URL*`/`TEST_DATABASE_URL` on the `Config` it returns, no assertion contains `cfg`, and
   every later test run went through a credential mask. The Owner may want to rotate that role's
   password.

## Open questions

1. **Budget cuts with an override template (P7-T07).** `build_proposer_prompt` takes no template,
   so with `proposer_template` the system prompt is swapped after the build. Phase-5's budget cuts
   (`PROMPT_TOTAL_BUDGET_TOKENS`, 40 000) are therefore decided against the *deployed* system
   prompt's size. This matters only if a v1.1 few-shot template pushes some alert over the budget.
   `built.estimated_tokens` is recomputed for the prompt actually sent, so T04/T07 can detect that
   case. The clean fix is a `template=` parameter on `build_proposer_prompt` (`llm/triage.py`, out
   of scope here). Should T07 carry it?
2. **`model_id`** is the proposer response's model; the verifier's is `verification.model`. If B4
   ever runs different proposer and verifier models, T04 decides how `eval_runs.model_id` records
   both.
3. **Verifier-failure outcomes** (`verifier_cap` / `verifier_transient`) have `final_verdict` and
   `gate_result` set to `None`, but their steps 1–5 state is exposed. `proposed_verdict`,
   `reasons_kept`/`reasons_dropped` and `forced_by` are filled, and `state` is on the evaluation.
   Whether those count toward the evidence-verified rate is for T03 to decide.
4. **`evaluate_alert` does not check `cfg.llm_enabled`.** That stays the job's check, as the card
   says. The harness must pass a `cfg` whose proposer model is set.
