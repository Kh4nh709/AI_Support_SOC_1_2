## 3 · Deviations

**(a) `find_open_cluster` takes the `Alert`, not a key tuple, and has a third optional argument.**
The card's signature is `find_open_cluster(conn, alert) -> ClusterHead | None`, which is what is
implemented; architecture v3 §3.2's older `find_open_cluster(conn, key) -> Alert | None` is
superseded by the card, as the card says it is. The added `cfg: Config | None = None` defaults to
`config.load()`, so callers written to the card's two-argument signature are unaffected; it exists
so a test can pass ceilings without touching the environment.

**(b) One public function the card does not list: `find_open_cluster_query(alert, cfg=None)`.**
It returns the SQL and the parameter tuple that `find_open_cluster` then executes. Without it the
D7 `EXPLAIN` test has to retype the query, and a retyped copy would keep reporting
`Index Scan using ix_alerts_dedup` after the module's own predicate had drifted away from the
index — which is the one failure mode D7 exists to catch. Verified: it is the seam that makes the
acceptance-5 red actually red.

**(c) `cluster_lock` refuses a `None` in any of the four key values (`PermanentError`).**
Not asked for. Found while writing the test: `hashtext(NULL)` is `NULL`,
`pg_advisory_xact_lock(NULL)` takes **no lock and raises nothing**, so a `None` arriving from a
future caller would run the whole dedup region unserialised while looking exactly like success.
All four are `NOT NULL` columns (B1/D10), so this can only be an upstream bug — hence permanent,
not transient. Covered by `test_cluster_lock_tu_choi_gia_tri_null`.

**(d) `bump_parent` raises `PermanentError` when no row matches.** The card fixes the return type
as `int`, so the missing-row case needed a decision. The head was read `FOR UPDATE` in the same
transaction moments earlier and cannot have gone anywhere; retrying the job three times would not
conjure it back, so `errors.classify` must see it as permanent (a bare `LookupError` would be
classified *transient* by `infra/errors.py`, which would be wrong).

**(e) Two of my own tests could not fail, and were rewritten.** Both were found by running the
DEC-025/027 break for the thing each claimed to test, and both are now proven red. This is the
substantive finding of the task:

- `test_status_khac_duplicate_la_lop_chan_doc_lap` asserted against SQL it wrote itself, so it
  could not see the module change at all. Measured: **deleting `AND status <> 'duplicate'` from
  `dedup.py` left the entire file green.** The predicate is unreachable while
  `ck_alerts_ban_sao_phai_seal_va_tro_goc` stands, because that CHECK forces `closed_at` *and*
  `sealed_at` onto every `duplicate` row, so a duplicate always fails "still absorbing" first —
  which is precisely why phase-2 calls `status <> 'duplicate'` the *second* layer. The replacement,
  `test_status_khac_duplicate_la_lop_chan_thu_hai`, drops that CHECK inside its own transaction
  (PostgreSQL DDL is transactional and the `db` fixture rolls back), inserts the unsealed duplicate
  the constraint would have refused, asserts it passes the first layer, and asserts the query still
  refuses to make it a head. Removing the predicate now reddens it.
- `test_last_seen_at_luon_bang_now_cua_db` asserted `now() - last_seen_at < 1 second`, which a
  timestamp in the **future** also satisfies. It stayed green against the acceptance-7 break
  writing an agent clock running fast — one of the exactly two cases B2 exists for. The bound is
  now two-sided (`timedelta(0) <= age < 1s`).

**(f) No `statement_timeout` is set in this module.** Phase-2 step 1 shows
`SET LOCAL statement_timeout = '3s'` next to the lock, but `infra.db.transaction()` (P2-T02)
already issues it, and the transaction belongs to P2-T10. Setting it here would be a second,
silently-diverging source for the same value.

Nothing else. No new dependencies. No frozen contract touched (no schema, no migration, no config
key, no route, no import-rule change). Files changed: exactly the two the card lists, plus this
report and my own `STATE.md` row.
