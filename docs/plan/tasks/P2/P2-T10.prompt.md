  **1 · `soar/risk.py` — phase-4 (b), on the DEC-004 vocabulary.** `compute_risk_score(severity: str,
  ctx: AlertContext, occurrence_count: int) -> tuple[int, dict]`:
  ```
  RISK_BASE   = {"critical": 70, "high": 50, "medium": 28, "low": 10}
  CONTEXT_CAP = 25
  ASSET       = {"high": 30, "medium": 10, "low": 0, "unknown": 0}     # INBOX 2026-09-06 · P2-T10 — recommended default
  IOC         = {"malicious": 25, "suspicious": 10, "clean": 0, "not_found": 0, "skipped": 0}
  context  = ASSET[ctx.asset_criticality] + (15 if ctx.identity_privileged is True else 0)
           + IOC[ctx.ioc_reputation] + (10 if occurrence_count >= 100 else 5 if occurrence_count >= 10 else 0)
  score    = min(100, RISK_BASE[severity] + min(CONTEXT_CAP, context))
  ```
  Phase-4's formula weighted two asset tiers DEC-004 abolished; the recommended re-weighting above
  keeps **every row of phase-4's worked table unchanged** because the cap binds (`critical` bare → 70;
  `critical` + `high` asset + `malicious` → 95; `high` + full context → 75; `medium` + full → 53;
  `low` + full → 35; `low` bare → 10) — your test table is that table. The four constraints hold:
  additive only (`skipped` and `not_found` add 0 — E3), deterministic, capped at 100, no threshold
  anywhere reads it. Return the components dict for `risk_score_components` (B4b). The display bands
  are P4's. If the INBOX DEC changes the four asset numbers, it is a four-number edit; note in your
  report which version you shipped.

  **2 · `soar/pipeline.py` — `run_pipeline_job(conn, job)`.** The worker (P2-T02) opens the 3-second
  transaction and calls you with `job.subject_id` = the `intake_id`. In order:
  1. `SELECT raw_text, via, manager_id, source_alert_id, processed_at FROM intake WHERE intake_id = %s`;
     already `processed_at IS NOT NULL` → return (idempotent re-run after a crash between COMMIT and
     `finish_job`).
  2. `doc = json.loads(raw_text)`; `result = parse_wazuh_alert(doc)`. Rejected → `INSERT INTO
     rejected_alerts (raw_payload, reason, source_ip)` (`source_ip = ''` for a pulled row) and the
     receipt `outcome='rejected', error=<reason>`; done. (A heartbeat never reaches you — P2-T11
     settles it at intake time.)
  3. Derive the two values the parser does not decide: `source = 'replay' if via == 'pull' and
     result.envelope == 'bare' else 'wazuh'` (planning decision 3 — the INBOX default; a webhook row
     is `wazuh` whatever its shape); `suggestion_visible` from a **stable** hash (D13, `prompts/P2.md`):
     when `EVAL_BLIND_FRACTION == 0.5`, `int(sha256(alert_id).hexdigest()[:8], 16) % 2 == 0`; for
     any other fraction `(… % 100) >= int(EVAL_BLIND_FRACTION * 100)`. Never Python's `hash()` — it
     is salted per process.
  4. `rules = autoclose.load_rules(conn)` — **before** the lock (phase-3 §Cache rule: no rule query
     inside the serialised region).
  5. `dedup.cluster_lock(conn, …)`; `head = dedup.find_open_cluster(conn, alert)`. If a head:
     `dedup.bump_parent`, `transitions.open_alert(kind="duplicate", duplicate_of=head.alert_id, …)`,
     receipt `outcome='duplicate'`; done — no enrichment, no job (D1).
  6. Internal enrichment — the three lookups, **always, for every non-duplicate alert** (E1, M1):
     `lookups.lookup_asset(conn, alert.agent_name, alert.origin_host)`, `lookup_identity(conn,
     alert.alert_user)`, `lookup_ioc(conn, alert.srcip, alert.dstip, srcip_is_private=…,
     dstip_is_private=…)` → build the `AlertContext` (you may import both `enrichment` and `domain`;
     planning decision 4) with `lookup_status = {"asset": …, "identity": …, "ioc": …}`.
  7. `risk_score, components = compute_risk_score(alert.severity, ctx, 1)`.
  8. `decision = autoclose.evaluate(conn, alert, ctx, rules=rules)`. Matched → `open_alert(kind=
     "auto_closed", rule=decision.match, context=ctx, risk_score=…, risk_components=…, source=…,
     suggestion_visible=…)` (which enqueues `triage` — D8), receipt `outcome='auto_closed'`; done.
  9. Else `open_alert(kind="received", …)` → `start_enrichment` → `finish_enrichment(context=ctx,
     risk_score=…, risk_components=…)` (A1, A4, A5 — the last one enqueues `triage`: **E6 holds
     because those two writes are one function in `domain`**), receipt `outcome='alert'`; done.
  The receipt is one `UPDATE intake SET processed_at = now(), outcome = %s WHERE intake_id = %s` at
  the end of each branch — **once**, in the same transaction as everything else, so the row is either
  fully processed or untouched (G12's "processed_at or error"). On a **permanent** exception the
  worker has already rolled back; your handler catches it, and in a **fresh** short transaction writes
  `UPDATE intake SET processed_at = now(), outcome = 'rejected', error = %s` (017 lets `app_rw`
  write exactly those three columns, and pins `error` once set — a second failure is recorded in
  `jobs.last_error`, never by rewriting it), then re-raises so `finish_job` marks the job. On a
  **transient** exception write nothing to `intake` — the job retries.
