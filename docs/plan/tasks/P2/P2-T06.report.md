## 3. Deviations from the card, and why

- **`_apply()` covers four edges, not all eighteen.** The card's design note 1 describes a single `_apply()` used by every transition. I built `_apply()` for the four single-row alerts transitions whose guard reduces to `status = ANY(from)` plus, for `acknowledge`, one extra column check (A4, A5/A6, A7, A17). `open_alert` (A1-A3) is an INSERT with no prior row, so its guard ("no row with this id yet") is a `UniqueViolation` catch, not an `UPDATE ... WHERE`. `decide` (A8-A10) needs a `SELECT ... FOR UPDATE` optimistic-lock read before its guard can even be evaluated (the delta check needs the current `occurrence_count`), plus a second fan-out `UPDATE`. `escalate` (A11-A12) is a five-statement transaction (cases INSERT, case_alerts INSERT loop, two alerts UPDATEs) with a rowcount check that has no single "the guard" to express as `_apply`'s WHERE clause. `conclude_case` (A13-A16) is the cases-table analogue of `decide`. Folding these into one generic `_apply()` would have required it to accept an optimistic-lock read, an arbitrary number of statements, and a rowcount comparison as parameters — making that helper as large as the sum of the direct SQL it would replace, for no behavioural gain. Every edge still funnels through this one module, every guard still lives in a `WHERE` clause (never a prior bare `SELECT` used as the guard itself — `decide`'s `SELECT ... FOR UPDATE` is safe because the row stays locked for the rest of the transaction), and every write is still followed by its audit event in the same transaction. Acceptance 3's grep (the thing G2 actually polices) passes either way.
- **`escalate`'s correlation call is coded against P2-T07's card signature, not a merged implementation, and two tests are skipped as the card anticipates.** `P2-T07` (`domain/correlation.py`) is still `todo` on `main` (verified: `grep -n "P2-T07" docs/plan/STATE.md` shows `todo`; `correlation.py` is still the one-line docstring skeleton). `transitions.py` imports the *module* (`from app.domain import correlation`), not the function name, so the module still imports cleanly with no `correlated_cluster_ids` defined yet; `escalate()` calls `correlation.correlated_cluster_ids(conn, subject)` per the exact signature P2-T07's card gives (`correlated_cluster_ids(conn, alert) -> list[str]`). Every test that exercises `escalate()`'s own guard/rowcount/fan-out logic (`test_A11_*`, `test_A11b_*`, `test_A12_*`, `test_escalate_truncates_at_max_alerts_per_case`) monkeypatches `correlation.correlated_cluster_ids` to a fixed return value with `monkeypatch.setattr(..., raising=False)`, so none of them depend on P2-T07 landing. Two tests are `skip`ped, named `P2-T07 not merged`, because they are the ones that would prove the *real* predicate integrates correctly rather than a stub: `test_escalate_pulls_in_real_correlated_alerts` and `test_escalate_truncates_real_correlated_alerts_at_cap`. **The Reviewer should re-run these two once P2-T07 merges** (drop the `@pytest.mark.skip`).
  - `escalate()` only has `alert_id`, not a full `Alert`, so I defined a small local dataclass `_CorrelationSubject(alert_id, agent_name, alert_user, srcip, alert_time)` — exactly the fields P2-T07's predicate needs — built from one `SELECT` on the trigger row, and pass that where P2-T07's card says `alert`. This is my best reading of an interface that has not shipped yet; the two skipped tests above are also the check that this reading was right.
  - `escalate()`'s given signature (`escalate(conn, alert_id, user_id, *, title, severity) -> str`) carries no `llm_suggestion` parameter, even though phase-6's doc shows the `tier1.escalated` payload carrying one. I followed the card's literal signature and write `"llm_suggestion": None` in that payload every time — a spec inconsistency between the card and the phase-6 doc, not something for me to resolve by widening the signature.
- **`AlertContext`'s three enrichment-context jsonb columns.** `finish_enrichment`/`open_alert("auto_closed")` split `AlertContext`'s seven fields into `asset_context={"present","criticality","owner","role"}`, `identity_context={"privileged"}`, `ioc_context={"reputation"}`, and pass `lookup_status` through unchanged. The card names the four column targets but not the JSON shape inside each; no acceptance test pins it, and P3's prompt builder (which reads these back) is a later task, so this is a documented choice rather than a frozen contract.
