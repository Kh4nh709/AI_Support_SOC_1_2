## 1. Built

- `backend/app/ingest/autoclose.py`
  - `evaluate(conn, alert: Alert, ctx: AlertContext, *, rules: Sequence[Rule] | None = None) -> AutocloseDecision` — the pipeline's entry point: the six G8′ hard blocks in the fixed order, then first-match-wins over `rules` (defaults to the 60 s cache).
  - `load_rules(conn) -> list[Rule]` — `SELECT ... ORDER BY created_at ASC, autoclose_rule_id ASC`, parsing and whitelisting `match` per rule; a rule outside the whitelist is dropped with a warning, never widened.
  - `reload_rules(conn) -> list[Rule]` / the module-level 60 s TTL cache (`RULE_CACHE_TTL_S`) read through the private `_cached_rules`.
  - `simulate(conn, match: list[dict]) -> SimulateStats` — the identical hard-block + whitelist decision over the last 30 days of clusters, rebuilding `AlertContext` fields from the stored `asset_context`/`identity_context`/`ioc_context` jsonb columns.
  - `rule_width_report(conn, days: int = 7) -> list[dict]` — layer 2, sums `occurrence_count` (never counts rows) against `Config.AUTOCLOSE_RULE_WIDTH_PCT`.
  - `Rule`, `AutocloseDecision`, `SimulateStats` — frozen dataclasses; `AutocloseMatch` is imported, not defined, here (see the dependency note above).
  - Private: `_parse_match`/`_value_ok`/`_scalar_ok` (whitelist validation, load-time), `_condition_matches`/`_rule_matches`/`_first_match` (matching, shared by `evaluate` and `simulate`), `_first_hard_block` (the six checks, pure), `_alert_field_values`, `_asset_ctx`/`_identity_ctx`/`_ioc_ctx` (jsonb → field values for `simulate`).
- `backend/tests/test_autoclose.py` — 39 test functions (41 test items; `test_ioc_reputation_non_bad_values_are_not_blocked` is parametrized ×3), 15 of them `@pytest.mark.db`.

## 3. Deviations from the card and why

- **Item 1's literal `-v` does not produce `PASSED` lines under this repo's `pyproject.toml`, so items 2–4's greps against it would read `0`/`0`/`0` regardless of correctness — measured, not assumed.** `backend/pyproject.toml`'s `addopts = "-q --strict-markers"` has carried `-q` since `d3c467a` (P0-T02). pytest's verbosity is `count(-v) - count(-q)`; one `-q` (from `addopts`) plus one `-v` (from the card's command) nets to verbosity 0 — dots, not per-test lines (reproduced against `test_config.py`: `-v` alone → `backend/tests/test_config.py ...` dots; `-vv` or `-v -v` → one `PASSED` line per test). This is the first card in this project to grep `/tmp/*.txt` for per-test `PASSED` lines, so the conflict had not surfaced before. I ran item 1 with `-vv` in place of the card's `-v` — same test file, same markers, same `-rs`, only enough extra verbosity to get the per-test lines every other acceptance item on this card assumes exist. Recommend the card (and any future one using this pattern) say `-vv` explicitly.
- **Item 10's grep also matches `SimulateStats.samples`, which design note 5 requires by that exact name — a conflict inside the card itself, not something I introduced.** Design note 5 is explicit: `simulate(...)` returns `{"clusters": n, "alerts": ..., "by_severity": {...}, "by_asset_criticality": {...}, "samples": [≤ 20 alert_ids]}`. `grep -cE "sample|SAMPLE"` is case-sensitive but substring-based, so it can never distinguish that required field name from the withdrawn v1 mechanism (`AUTOCLOSE_SAMPLE_RATE`/`is_control_sample`/`sampled_for_control`) planning decision 7 actually targets. I renamed every incidental use I control (the internal cap constant, the local accumulator variable, one line of prose) away from the word, leaving the floor of 2 occurrences that cannot go lower without renaming the public field itself — which would break the contract design note 5 states, and likely the REST route P4/P5 builds on it. I did not rename the field. Evidence the intended check (no control-sample mechanism) is satisfied: `grep -nE "AUTOCLOSE_SAMPLE_RATE|is_control_sample|sampled_for_control|SAMPLE_MAX_PER_RULE" backend/app/ingest/autoclose.py` → no output, exit 1.
- **`asset_context`/`identity_context`/`ioc_context`'s jsonb key shape is this module's own invention, not yet pinned by any card.** `simulate()` reads these three columns back into `AlertContext`-equivalent field values; no merged or in-progress card (P2-T06, P2-T08, P2-T10 are all still `todo`) states their internal JSON shape. I used the shape that mirrors `AlertContext`'s own field grouping — `asset_context={"present": bool, "criticality": str, ...}`, `identity_context={"privileged": bool|None}`, `ioc_context={"reputation": str}` — consistent with `lookup_status={"asset":...,"identity":...,"ioc":...}` (phase-4:307, already three top-level groups). Flagged in §4 for the Reviewer/Director to confirm once P2-T06/T08 actually write these columns.
- Everything else matches the card as written. No frozen contract (schema, `output_schemas.json`, config keys, API routes, import rules, job/event types) was touched.
