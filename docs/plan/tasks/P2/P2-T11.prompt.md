- **Design notes:**

  **1 · The query — the probe's shape plus one key, measured today.**
  ```
  POST {INDEXER_URL}/{INDEXER_INDEX}/_search
  {"size": PULL_PAGE, "sort": [{"timestamp": "asc"}], "fields": ["timestamp"],
   "query": {"range": {"timestamp": {"gte": <cursor_ms - PULL_OVERLAP_S*1000>}}},
   "search_after": [<last sort value>]   # only from the second page of one pull
  }
  ```
  A plain `_search` returns hits with `_id, _index, _score, _source, sort` and **no `fields`**; with
  `"fields": ["timestamp"]` the indexer adds `fields.timestamp[0]` in UTC, and on every hit checked
  `sort[0]` equals the epoch-millis of `_source.timestamp` (planning decision 6). Request it, so
  the parser's primary path (F4) applies to live pulls. `gte` takes epoch-millis (the cursor's unit);
  the very first pull, with no cursor row, uses `PULL_START` (`2026-08-01`) converted to epoch-millis —
  it finds nothing before 02/09 and that is expected (DEC-017), not an error. Auth is basic
  (`INDEXER_USER`/`INDEXER_PASSWORD`); the client is `httpx.Client(verify=INDEXER_CA, auth=…,
  timeout=…)`; a missing or unreadable `INDEXER_CA`, or empty credentials, is a `ConfigError` naming
  the key at client construction — **there is no insecure mode** (§6.3; acceptance 9 greps for it).

  **2 · `pull_once(conn, client, cfg) -> PullResult`** `(hits, new, duplicates, heartbeats,
  last_sort)`. One transaction the caller owns (the `pull` handler runs inside the worker's):
  - read `source_cursor` for the manager (see note 4 for the key); page through `_search` with
    `search_after` until a page returns fewer than `PULL_PAGE` hits;
  - for each hit: `manager_id = _source.manager.name` (default `'default'`), `source_alert_id =
    _source.id`; heartbeat (note 3) or `INSERT INTO intake (manager_id, source_alert_id, raw_text,
    sort_key, via) VALUES (…, 'pull') ON CONFLICT (manager_id, source_alert_id) DO NOTHING RETURNING
    intake_id` — a returned id means new → `enqueue(conn, "pipeline", str(intake_id))`; `None` means
    the overlap re-read it → count it, do nothing. **`raw_payload` is never in the INSERT** — it is a
    generated column (014; measured: naming it is rejected);
  - `sort_key = hit["sort"][0]`;
  - `source_heartbeat.last_seen_at = now()` for the manager whenever the request succeeded, and
    `last_alert_at = now()` when at least one non-heartbeat hit arrived (`INSERT … ON CONFLICT
    (manager_id) DO UPDATE`);
  - **last**: `INSERT INTO source_cursor (manager_id, last_sort, last_pull_at, last_error) VALUES (…,
    <last hit's sort[0]>, now(), NULL) ON CONFLICT (manager_id) DO UPDATE …` — the cursor moves in the
    same transaction as the intake rows, so it advances only when they commit (§3.1). No hits → the
    cursor is not moved back and `last_pull_at` still updates.
  A transport/TLS/5xx failure → write `source_cursor.last_error` in a **separate** short transaction
  (the caller's has rolled back) and raise `TransientError` — the job retries with backoff and health
  (P5) reads `last_error`.

  **3 · G9 — the bytes, not a re-serialisation.** `raw_text` is the hit object's **exact text sliced
  from the response body**. `json.loads` then `json.dumps` reorders nothing in Python 3.12 but
  normalises whitespace and escapes — it is not the received document (DEC-023 item 5). Do it
  position-wise: locate the `"hits": {"hits": [` array in the body, then walk it with
  `json.JSONDecoder().raw_decode(body, idx)` — each call returns `(obj, end)`, and `body[start:end]`
  is the hit's text; skip whitespace and commas between elements. Your fixtures therefore **must not
  be canonical JSON**: write `indexer_search_page_2.json` with irregular spacing and a non-sorted key
  order inside one hit, so the byte-compare test can assert `raw_text == the slice` **and** the
  control `raw_payload::text != raw_text` (a canonical fixture would pass against a re-serialisation
  too — that is the vacuous-green shape DEC-025 names).

  each `intake` row, where the UNIQUE lives. Say this in the module docstring: the cursor is per
  index pattern; if a second manager ever ships into the same index, the cursor still works and the
  intake rows still disambiguate.
