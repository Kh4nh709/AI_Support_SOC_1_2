## 3. Deviations from the card and why

- **Two of the card's literal "break this" instructions do not reproduce on this host's Python (3.12.3), and I substituted an equivalent break that does, rather than claim the acceptance untested (rule 7's own escape hatch: "the command is not testing what the card says it tests, and that is a card defect to report, not a pass to claim").**
  - **Acceptance 4's suggested break ("break the +0700 normalisation")**: `datetime.fromisoformat` on Python ≥3.11 already parses `+0700` (no colon) and a trailing `Z` natively — verified directly (`datetime.fromisoformat('2026-08-17T00:56:56.130+0700')` succeeds unaided) and by `ruff`'s `FURB162` flagging my own `.replace("Z","+00:00")` calls in the test file as dead code for this target version. My `_OFFSET_NO_COLON_RE` regex in `wazuh_parser.py` is therefore not load-bearing on this interpreter — it is kept as explicit, cheap, version-independent documentation of phase-1's Khối 3 trap (in case the code ever runs under an older Python), but disabling it did not turn the acceptance red. I instead broke the fallback branch's field lookup itself, which does reproduce a red result for the same acceptance line (see item 4 above).
  - **Acceptance 8's implied break ("R8: same instant, two zones, same hash" depends on UTC-converting first")**: `datetime.timestamp()` on an *aware* datetime is already timezone-correct regardless of which offset the object carries (Python computes the true POSIX time), so removing the explicit `.astimezone(UTC)` call before `.timestamp()` does not change the result. I kept the explicit conversion (it documents R8's intent for a future reader and is the literal phase-1 wording — "bucket tính trên `alert_time` đã quy về UTC") but demonstrated the red case with a genuinely timezone-naive alternative formula instead (see item 8 above).
  - Neither finding required a code change — both are cases where the standard library already does more than the 2026 spec assumed of it. Flagging them here per rule 7 rather than silently claiming the card's literal break worked.
- **Post-review fix (review round 1, bucket (a)) — the docstring at `backend/tests/test_wazuh_parser.py:157` asserted the opposite of what §3 above had already measured, and the Reviewer was right to block on it.** It read *"`datetime.fromisoformat` rejects it unnormalised; the parser must not"*. On the only interpreter this project supports it does not reject it — `backend/pyproject.toml:11`/`:15` pin `target-version = "py312"`, and `python3 -c "from datetime import datetime; print(datetime.fromisoformat('2026-09-02T16:15:36.255+0700'))"` prints `2026-09-02 16:15:36.255000+07:00`. That is the same measurement the bullet directly above this one reports in my own words, so the commit shipped a test file contradicting its own report, with the false half in the tree where a future reader meets it and the true half in a document they may never open. It documented `_OFFSET_NO_COLON_RE` (`wazuh_parser.py:38`) as load-bearing when it is not.
  The docstring now reads: *"`+0700` (no colon) is exactly the sample archive line's own shape. `datetime.fromisoformat` parses it natively on py312; `_parse_iso` normalises it anyway so the parser does not depend on the interpreter version (report §3)."*
