## 3. Deviations

1. **Test isolation against the shared session database required real fixes, not just my own tests passing (found via `make test-db` on the whole suite, not just this card's three files).** `backend/tests/conftest.py`'s `db` fixture only rolls back what a test never commits; anything committed persists for the rest of the pytest session because `_test_database` is session-scoped. Several of my `test_jobs_worker.py` tests committed rows unnecessarily (sequential `claim_job`/`finish_job` calls on one connection don't need intermediate commits to see their own writes) or unavoidably (`run_forever` commits internally as part of its own correct behaviour — `reclaim_stale`'s commit, `claim_job`'s commit, and the success/exception-path commits all happen regardless of what the calling test does). Fixed by (a) removing commits that weren't load-bearing, relying on the fixture's teardown rollback, and (b) adding an explicit `DELETE … WHERE subject_id = '…'; commit()` at the end of every test that has to commit (the four `SKIP LOCKED`/cross-connection and `reclaim_stale` tests, and all seven `run_forever` tests). Verified by running the *entire* suite's `db`-marked tests together, four times, not just this task's own files — `test_schema_v3_016.py::test_ck_jobs_job_type_admits_the_six_v3_types` (`count(*) FROM jobs` expecting exactly 6) and three `test_schema_v3_017.py` append-only-count assertions were the ones that caught the leaks.
2. **`run_forever`'s per-job-type statement timeout uses design note 4's "option B."** `handlers` stays exactly the plain `Mapping[str, Handler]` design note 1 fixes (matching what `web/worker.py`, P2-T10, is described as building: `{"pull": …, "pipeline": …}` with plain callables — not `(handler, timeout)` tuples). A second, optional keyword, `timeouts: Mapping[str, str] | None = None`, carries the per-job-type override (job types absent from it get `DEFAULT_STATEMENT_TIMEOUT = "3s"`). P2-T10 will need to pass `timeouts={"investigate": "5s"}` for P5's `conclude` — flagged again in Open questions.
3. **Acceptance 6a's named failing case doesn't reproduce as written; the real failure mode is worse.** The card says moving `enqueue` before `finish_job` raises `duplicate key value violates unique constraint "ux_jobs_mot_job_song_moi_subject"`. It doesn't, because `enqueue` (correctly, per acceptance 2) always inserts with `ON CONFLICT … DO NOTHING` — there is no code path through the public `enqueue()` that can raise that error; the only way to see the literal raised exception is to bypass `enqueue` entirely with a bare `INSERT` (which is what acceptance 2's own failing case does, on a *different* call site). Reordering `worker.py`'s two calls instead demonstrates a silent lost reschedule: the `pull`/`triage`/etc. job ends up with only its original `succeeded` row and no re-armed `pending` row, no exception, no log line indicating anything went wrong. I've recorded this because it's the actual thing a reviewer changing `worker.py`'s ordering later needs to watch for, and it's strictly worse than what the card describes (silent data loss vs. a loud error).
4. **`db.py`'s docstring can't name the pooling package literally.** Acceptance 8's `grep` for `psycopg_pool` is a plain string match over the whole file, including comments — my first draft explained planning decision 2 ("no `psycopg_pool`") in prose and tripped the guard on itself. Reworded to "no pooling library." No code changed.
5. **Design note 5's `ck_audit_actor_role` text is incomplete, not wrong for what this card needs.** It states `actor_role IN ('system','llm','analyst')` (3 values). Measured against `docs/Schema/009_audit_actor.sql` (and the live constraint): it is `IN ('system','llm','analyst','admin')` — 009 added `'admin'` after the presumed source of that note was written. Doesn't affect `write_event`, which never duplicates this closed set in Python (by design — the DB CHECK is the sole authority per design note 5's own framing); noted for the record only.
6. **`finish_job`'s `job.exhausted` audit write is a direct `INSERT`, not a call to `audit.events.write_event`.** G1 / the package map (§4: `infra` "May import" — `—`) forbids `infra/*` importing `audit`, `write_event` included; `test_import_rules.py` would reject it. The card's Goal line ("the audit-event writer everything above it calls") is accurate for every other module in the tree but doesn't quite name this one exception — `infra/jobs.py` sits *below* `audit` in the layering and has to write its one audit row itself. Stated here per the card's own rule ("say so in your report rather than reconciling them yourself" — DEC-007 item 7) rather than treated as something to paper over.

7. **Post-review fix — `test_connect_with_no_dsn_and_no_database_url_raises_config_error` was green by
   accident, not by construction.** The test deleted `DATABASE_URL` from the environment and asserted
   `connect()` raises `ConfigError`. But `config.load()` reads **two** tiers (`infra/config.py`
   docstring: "a real environment variable, then `.env`"), and the `.env` tier is a path resolved
   relative to the **process CWD**. Deleting the variable silences only the first tier. The test
   therefore passed for one reason and one reason only: working rule 1 puts this task in a fresh
   worktree, `.env` is git-ignored, and a worktree has none — the exact accident `db.py`'s own
   `connect()` docstring describes. Run from any checkout that *does* have a `.env` with
   `DATABASE_URL` — `main`, and every developer machine — `connect()` picks that DSN up and opens a
   **real connection** instead of raising. Reproduced: with a one-line `.env` in the working
   directory the test fails `psycopg.OperationalError: connection failed: … FATAL: database
   "soc_dev_placeholder" does not exist` — a unit test the card describes as needing no server was
   one merge away from dialling the developer's live database. This is precisely DEC-025's "green
   while proving nothing" class, and it is a Coder defect, not a card defect: `test_config.py`
   (P2-T01) already neutralises the file tier on every one of its ~40 `load()` calls with
   `env_file="/dev/null"`, so the pattern existed in the repo and I did not follow it. Fixed by
   `monkeypatch.chdir(tmp_path)` plus an `assert not (tmp_path / ".env").exists()`, which makes the
   absence deliberate: the test now passes identically with and without an ambient `.env`.
   `connect()` itself is unchanged — the defect was entirely in the test's hermeticity. Both
   directions demonstrated red per rule 7: (a) the pre-fix test with a `.env` present, above; (b) the
   post-fix test with `connect()`'s `if not dsn: raise ConfigError(...)` guard disabled →
   `2 failed` (this test and `test_connect_with_empty_explicit_dsn_raises_config_error`), proving the
   assertion is not vacuous. Both experiments restored; `git diff` over `backend/app/` is empty.
   Scanned for the same class elsewhere in this card's files: `jobs.py:146,174` also call
   `config.load()`, for `JOB_MAX_ATTEMPTS`/`JOB_BACKOFF`/`JOB_LOCK_TIMEOUT_S`. None of those three
   keys is present in the repository's `.env` today, so those tests are not currently affected — but
   they are latent instances of the same shape (see Open questions).

Everything else matches the card as written.

## 4. Open questions / follow-ups

- P2-T10, when it builds `web/worker.py`'s real handler table, should pass `run_forever(..., timeouts={"investigate": "5s"})` for P5's `conclude` (see Deviations item 2) — otherwise `investigate` jobs silently run under the 3s default instead of the 5s the card's design note 4 calls for.
- The silent-reschedule-loss failure mode (Deviations item 3) is worth one line in whatever checklist a future reviewer of `worker.py` uses, since nothing in the acceptance suite as written would catch a regression that reintroduces it via the literal wording of the card's failing case.
- **Ambient-`.env` leakage into unit tests is a repository-wide hazard, not just this card's (Deviations item 7).** Any test that exercises a code path calling `config.load()` without pinning the file tier is only as hermetic as the directory pytest happens to run from. Within this card, `test_jobs_worker.py`'s backoff, exhaustion and reclaim tests read `JOB_BACKOFF`, `JOB_MAX_ATTEMPTS` and `JOB_LOCK_TIMEOUT_S` through `config.load()`; none of those keys is in the repository's `.env` today, so they pass honestly, but nothing stops someone adding one. The structural fix is an autouse fixture in `backend/tests/conftest.py` that neutralises the `.env` tier for the whole suite (chdir to `tmp_path`, or have `load()` take its default env file from a test-controlled setting). `conftest.py` is outside this card's file list (working rule: "Do not touch any other file"), so I have not made that change — flagging it for the Director to place with whoever owns `conftest.py` next.
