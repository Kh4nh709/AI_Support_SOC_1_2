Deviation, explained in full: `run_pipeline_job`'s own step-1 idempotency guard (`processed_at IS NOT NULL → return`, required by the card and by acceptance 7/E6) makes it *structurally impossible* to reach `_write_rejection_receipt` a second time on the same row through a literal "reset the job, re-run the worker" cycle — the second run returns cleanly at step 1 before ever touching `intake` again, and the job is marked `succeeded`. ## 3. Deviations from the card and why

1. **Three tests (E6, G7, and the "receipt never rewritten" test) run against their own scratch databases, not the shared `soc_p2t10_test`.** Discovered while validating acceptance 14: `run_pipeline_job`/`pull_job` called through the real worker loop commit for real (`infra.worker.run_forever` and `db.transaction()` both call `conn.commit()`), and `intake` is append-only even against the table owner (017's `trg_intake_immutable` blocks `DELETE` for everyone) — so a row these three tests commit to the *shared* session database can never be cleaned up, and it broke `test_puller.py` (stray `source_cursor`/`source_heartbeat`) and `test_schema_v3_016/017.py` (row-count assertions) when `make test-db` ran the *whole* suite against one `TEST_DATABASE_URL`, exactly as acceptance 14 does. Isolating these three onto their own throwaway databases (created, migrated and dropped by a small fixture each) fixed it with zero change to any other file; `make test-db`'s full-suite run is green as a result (see item 14).
2. **Acceptance 1's literal `-v` and acceptance 10's literal "re-run after resetting the job"** — both explained in place, in section 2, rather than repeated here.
3. **`make test`'s 2 unrelated failures, and the blocked `git merge main`** — filed as an INBOX BLOCKER; also explained in section 2, item 14.
4. Everything else follows the card as written; the four planning decisions (1, 3, 4, 8) are implemented as their recommended defaults, and DEC-067's seven-field `AlertContext` (positional: `asset_present, asset_criticality, asset_owner, asset_role, identity_privileged, ioc_reputation, lookup_status`) was verified against `domain/alert.py` before use — the shipped dataclass, not the index.
