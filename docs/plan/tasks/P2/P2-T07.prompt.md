- **Design notes:**

  **1 · `summarize_for_prompt(conn, alert) -> CorrelationSummary`.** The phase-4 P4-2 query, grouped:
  `WHERE (agent_name = %s OR alert_user = %s OR srcip = ANY(%s)) AND alert_time BETWEEN %s - interval '2 hours'
  AND %s + interval '2 hours' AND duplicate_of IS NULL AND status <> 'duplicate' AND alert_id <> %s
  GROUP BY rule_id, category, status ORDER BY sum(occurrence_count) DESC LIMIT 20`. Each row is a frozen
  dataclass `CorrelationRow(rule_id, category, status, cluster_count, alert_count, first_seen, last_seen,
  src_ip_count)` — the six fields `prompts/P2.md` names plus the two phase-4 adds; all of them closed-set
  or numeric/datetime, which is what lets P3 place them **outside** an untrusted block (G6′). Then up to
  **5 samples** — the newest heads with the highest `occurrence_count` inside the same window — as dicts
  with an **explicit column list**: `alert_id, rule_id, category, severity, status, occurrence_count,
  alert_time, description, raw_log` (the last two are free text and P3 wraps them; you just carry them).
  `srcip = ANY(%s)` takes `[alert.srcip]` when it is non-empty, `[]` when it is `''` — an empty `srcip`
  must not correlate every other empty-`srcip` alert in the window (measured: FIM/rootcheck rules all
  carry `''`).

  **2 · `correlated_cluster_ids(conn, alert) -> list[str]`.** Phase-6's predicate **verbatim**:
  same three-way OR and ±2 h window, `duplicate_of IS NULL`, `alert_id <> %s`, **`status IN
  ('queued_tier1', 'tier1_active')`**, `ORDER BY occurrence_count DESC LIMIT %s` with
  `Config.MAX_ALERTS_PER_CASE`. The four exclusions the status filter buys (phase-6's table:
  `auto_closed`, `closed_*`, `received`/`enriching`, `escalated_tier2`) are four tests. Do **not** quote
  200 as a limit that routinely binds — phase-6 says why; it is a guard rail and your test proves it
  cuts at exactly `MAX_ALERTS_PER_CASE` when set to a small value via the environment.

  **3 · Windows use `alert_time`, not `received_at`** (P4-3: "when did these events happen"). And the
  `+2 h` half is nearly empty when ① runs — that is honest, not a bug (phase-4 P4-3); do not "fix" it.

  **4 · The `EXPLAIN` proof, without flakiness.** Phase-4 measured a `BitmapOr` over the three
  indexes on 3,000 rows. On a nearly empty test table the planner will sequential-scan whatever you
  do. Run the `EXPLAIN` under `SET LOCAL enable_seqscan = off` and assert the plan names all three of
  `ix_alerts_corr_agent`, `ix_alerts_corr_srcip`, `ix_alerts_corr_user` — that answers "are the three
  predicates index-able" (the property phase-4 cares about), not "what did the planner feel like
  today". **Failing case:** change `alert_time BETWEEN …` to `received_at BETWEEN …` → the three
  index names disappear from the plan; show it red once.

  **5 · Read-only, enforced.** Both functions run inside a transaction the caller owns, execute only
  `SELECT`s, and the test proves it: run each under `SET TRANSACTION READ ONLY` — a write would raise
  `cannot execute … in a read-only transaction`. That is E4 as a test rather than a review note.

  **6 · Rows you insert in tests** need the twelve `NOT NULL`-without-default columns — measured:
  `alert_id, rule_id, rule_level, severity, description, agent_name, alert_time, category, resolved_by,
  mapping_version, event_bucket_hash, raw_payload`. One `_insert_alert(conn, **overrides)` helper; give
  the busy-agent test ≥ 30 heads across ≥ 3 rules so `LIMIT 20` and the ordering are exercised, and
  give it `duplicate` rows too so `duplicate_of IS NULL` is seen to exclude them.

  **7 · Your own database, DSN inline.** `TEST_DATABASE_URL=postgresql:///soc_p2t07_test` on every
  pytest line (DEC-023 item 8).
