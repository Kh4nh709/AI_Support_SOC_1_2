**Note on flakiness (why the test isn't a literal 1-row table).** An early version seeded a single row and got a *passing* `BitmapOr` plan purely because the table had never been `ANALYZE`d (Postgres's default-guess statistics for an unanalyzed relation happen to favor `BitmapOr`). Later in a full-suite run, autovacuum caught up and analyzed the table for real (measured: PostgreSQL's `ANALYZE` writes `pg_class.reltuples`/`relpages` via an in-place update that survives a `ROLLBACK` of the transaction that issued it — confirmed directly), and the *same* 1-row test flipped to a plain `Index Scan`. Design note 4 anticipated exactly this ("on a nearly empty table the planner will sequential-scan whatever you do"); the fix actually needed is a real, `ANALYZE`d, 200-row table with independent (not correlated) column values — under that condition the result is reproducible (verified across 5 repeated seed/cleanup cycles).

## 3. Deviations

1. **Two functions gained small public `_query` helpers** (`rows_query`, `samples_query`, `cluster_ids_query`) beyond the two names the card lists. This mirrors an existing pattern in this codebase — `ingest.dedup.find_open_cluster_query` — used for exactly the same reason: the EXPLAIN test must prove the predicate the module *actually executes*, not a hand-retyped copy that could silently drift from the real query. Not scope creep against the card's "the module, its DB tests, and the EXPLAIN proof" — the EXPLAIN proof is explicitly in scope, and this is how the existing codebase makes that proof possible.
2. **One comment wording changed mid-development.** A first draft's comment said `never received_at` literally, which the acceptance's own grep (item 3) would have caught (grep is textual, not semantic — it doesn't know the difference between code and a comment naming the forbidden column). Reworded to describe the semantic difference (event-time vs. receipt-time) without spelling the column name.
3. **The duplicate-exclusion test needed a second, more isolated case.** `test_correlation_loai_ban_sao`'s fixture used a row with `status='duplicate'` — which is *also* excluded by the independent `status <> 'duplicate'` / `status IN (...)` filters, so removing `duplicate_of IS NULL` entirely from the predicate left that test green (a DEC-027 "guard that cannot fail," caught while doing the mandated mutation-testing pass). Added `test_correlation_loai_duplicate_of_rieng_biet_voi_status`, which sets `duplicate_of` on a row whose `status` is *not* `'duplicate'` (a shape the real pipeline never produces, but one the DB CHECKs don't forbid either) — this isolates the clause and does turn red under the mutation. Not a card requirement by name, but required by rule 7/DEC-027's own standard, applied to my own test suite.
4. Everything else matches the card's design notes and phase-4/phase-6 SQL verbatim (three-way OR, ±2h window on `alert_time`, `duplicate_of IS NULL`, the exact `status IN ('queued_tier1', 'tier1_active')` phase-6 predicate, `LIMIT Config.MAX_ALERTS_PER_CASE`, the five-sample/20-row caps, the explicit sample column list).
