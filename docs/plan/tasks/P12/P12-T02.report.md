**The occurrence design, and why it reads the document and not a switch.** The card says "when the context comes from SOAR". The first reading is
`not cfg.ENRICHMENT_ENABLED`. I did not use it, for a reason in `eval/run_configs.py` that I may not edit: its `pin_dedup` forces `DEDUP_ENABLED=true` because
`evaluate_alert` would otherwise feed ① a burst count while `b1_facts` (which reads the same `tier1._load` and no `cfg`) reads the row's count, and B1 would
diverge from B2–B4 and every cache key would move (DEC-165 / R22; pinned by `test_b1_facts_equal_evaluate_alert_facts`). A switch-driven `None` would reopen exactly
that, for the Owner's own `.env` (`ENRICHMENT_ENABLED=false`) and every pre-switch gold alert. Reading the alert's own document in `_load` puts the `None` where
both callers see it, leaves every document without a block (all gold data, all existing tests) byte-for-byte as before, and also holds when a payload has a block
but the schema is wrong, or when someone runs with `ENRICHMENT_ENABLED=true` against a SOAR payload: SOAR sent one representative either way.

**The unknown on the page.** `fact()` still accepts only an Enum, an int, a datetime or an `Id` (a free string and `None` are still `TypeError`s, tested). The
phrase is one `TEMPLATE_CONSTANTS` entry used as a `PromptBuilder.line()` part, which is the builder's other legitimate channel (as `SENTENCE_ABSENT` is for
`sentence()`); the line reads `severity: medium · category: malware · occurrence_count: không rõ · risk_band: medium`, the same position the count had.
The linter strips it as a constant; a look-alike (`khoảng 3`) is `free_text`. **Frozen-contract notice, as the card asks:** this is a new template constant
(`len(HEADINGS) == 9` and `len(SENTENCES) == 7`, which `test_builder.py` pins, are untouched; no enum value, no output schema, no template file; `prompt_version`
is the template's hash and does not move; the prompt of a known count is byte-identical to before, tested for 0, 3 and 50).

**Mapping details the card left open, and what I chose** (each is a test):

- `asset_present` = `asset.in_inventory` (absent → false); `lookup_status.asset` = `found` / `not_found` / `skipped` for `true` / `false` / absent.
- `identity_privileged` is `user_is_admin` **only when the alert names an account** (`asset.user` a non-empty string); otherwise `None` and identity `skipped`,
  even when SOAR wrote `false`. The SC03 sample has `user: null, user_is_admin: false` and the card expects "identity `skipped`" for it; `false` for an alert
  with no account would claim a look-up that did not happen. `lookup_status.identity` is `found` for a bool, `skipped` otherwise.
- IoC: `found` when any verdict was read (`clean` included, as the team proposes), `skipped` with no block. `ti: null`, `ti: []`, `ioc: null` are "no block"; `ioc: {}`
  is a block without a verdict, a fault.
- Absent vs wrong: an absent or `null` *block* (`asset`, `ti`, `ioc`) is "no block"; a present *scalar* that is not valid (`criticality: null`, `in_inventory: null`,
  `criticality: "critical"`) makes the whole context unknown; `user_is_admin` / `user` may be `null`.
- `asset.critical` is ignored whatever it holds (`true`, `"yes"`, `5`), and with no `criticality` it never makes an asset `high`.
