### Named-risk checks
1. **SQL injection and LIKE escaping: ✅.**
   - Every value is bound as a parameter. The f-strings put only module constants into the SQL: `ENTRY_COLUMNS`, `DEDUP_KEY_EXPRESSION`, `_TUPLE_COLUMNS`, and the tags `k{level}`, `src`, `usr`.
   - The escape (history.py, `_LIKE_SPECIAL`) covers `\`, `%` and `_`, and PostgreSQL's default LIKE escape is the backslash. The exact `regexp_replace(...) = ANY(base)` test decides the match, so a LIKE slip can only lose rows, never add them; tests H4 and H5 cover it.
   - Level 4's `OR` sits inside the `AND (`…`))` of `_PREFIX` and `_SUMMARY`, so it cannot escape the window or the exclusion.
   - `limit` and each full-text phrase are bound; the phrases go in as an `unnest` text array through `plainto_tsquery`.
2. **Self-exclusion for a case subject: ✅ complete.**
   - It covers the case id and the alerts whose `case_id` is the case (history.py:112-125). It also covers the `case_alerts` heads and their duplicates, including late duplicates that carry no `case_id`.
   - The alert-subject path reads only `alerts.case_id`, which is sound: `ux_case_alerts_mot_alert_mot_case` (006_chot_hop_dong.sql:81) allows one case per alert, and `escalate` sets `alerts.case_id` on the heads in the same transaction, with a rowcount check (transitions.py).
   - One A5 hole lies outside T02's wording (M3).
3. **Deviation 3: it serves "the same rule across hosts", but only partly the spec's intent.**
   - The deviation is reasoned. `plainto_tsquery` ANDs every word, so querying the whole fingerprint (month, counters, the words `category` and `log`) would match almost nothing. The entry side is still searched on its full `fingerprint_tsv`.
   - **Same rule, fixed description: it works.** The rule id or the description phrase finds the same rule on any host.
   - **Description built from the event: it fails.** The phrase then carries the event's own IP, account or host, so it finds only entries about that same IP or user, the opposite of "across hosts" (I1).
   - **Same kind of event under another rule or decoder: no path.** The log template, the part most likely to capture "the same kind of event", is never queried. Such events are found only through the category, MITRE or scenario overlap.
   - An OR of the template's distinct lexemes, ranked by `ts_rank_cd`, would restore that recall (M8). Acceptable if the controller rules on it, and once I1 is fixed.
4. **Regex backtracking: ✅ none found.**
   - Each pattern can start only at the start of a run of its characters (lookbehind), its quantifiers are bounded, or its separators are unambiguous. `_HALF_PLACEHOLDER` is linear because a `<` cannot be inside a `[A-Z_]` run.
   - I timed what the timing tests leave out, a large inventory: 10,000 hostnames over a 50,000-character line took at most 0.25 s, on text that shares the hostnames' prefixes, and 0.16 s on a first call including the regex compile.
5. **`file_matches`: ✅ for traversal and symlinks.**
   - `resolve()` plus `is_relative_to` refuses `..`, absolute paths and symlinks that lead out of the root. A NUL byte gives `ValueError`, which is caught. A FIFO and a directory fail `is_file()`. Files over 1 MiB are refused.
   - The leftovers are Minor (M6).

### Issues
#### Critical (Must Fix)
None.

#### Important (Should Fix)
- **I1 (plan-mandated): the rule descriptions enter the fingerprint unplaceholderised.**
  - **Where.** fingerprint.py:132-138 builds the descriptions with only `_one_line`, and :165 writes them as `rule:` lines. Only `raw_log` goes through `placeholderise` (:148).
  - **Why it happens.** Wazuh fills `$(field)` into descriptions when an alert fires; this repo's own conf/local_rules.xml:84 and :121 do it.
  - **Probe.** I gave `_build` a row whose description was `Successful Remote Logon Detected - User: \FPT\hr02 - from ip:79.79.78.202 host WS-07`, with `agent_name=WS-07`. The output still had `rule: … \FPT\hr02 - from ip:79.79.78.202 host WS-07`: the IP, the account and the alert's own host all survived.
  - **What it causes.**
    - The values reach the ranking model.
    - They are stored in `knowledge_entries.fingerprint` (the T03/T04/T05 contract); V3 checks only a draft's free-text fields, so nothing catches them there.
    - Through `search_phrases` (fingerprint.py:212-223) they make the full-text search match only entries about the same user or IP.
  - **Fix.** Pass each description through `placeholderise(description, sorted(hosts), users=users)` before one-lining and cutting it (build `hosts` and `users` first). A fixed description is unchanged, so both sides stay comparable. Add a test with a description built from the event. The brief names "the rule descriptions" without generalising them, so this needs the controller's ruling.

#### Minor (Nice to Have)
- **M1: a JSON-escaped account passes both checks.** The `DOMAIN\user` pattern (generalise.py:57-59) requires exactly one backslash. When `win.system.message` is empty, `raw_log` is the JSON dump of `data.win` (wazuh_parser.py:249), where the account reads `FPT\\admin02`. The probe gave `placeholderise` → `"FPT\\admin<N>"` and `literal_findings` → `[]`; a name without digits would leak whole. Allow `\\{1,2}` between the domain and the user.
- **M2: `by_conclusion` and the ruling.** If "exactly" means all six keys always, use `{name: counts.get(name, 0) for name in CONCLUSIONS}` at history.py:316 and flip the test at test_rag_history.py:521. That also gives `rag_results.history` a stable JSON shape.
- **M3: an A5 hole across tasks.**
  - Candidates exclude by `source_alert_ids` and `source_case_ids` only (candidates.py:40-43).
  - The plan's T04 merge appends the merged source only to `evidence` (plan line 368). An entry that absorbed a draft from the subject's cluster or case would then stay a candidate.
  - Needs a ruling: either T04 also appends to the `source_*_ids` columns, or candidates also read `evidence`.
- **M4: `decision_history` does not check a case id.** `_heads` (history.py:186) sends a case Subject's id to a `uuid` column unchecked. A hand-built `Subject("case", "x")` aborts the transaction. `case_fingerprint`, `self_exclusion` and `entry_by_id` all guard against this; `parse_subject` covers the normal path. Use `as_uuids` and return an empty history.
- **M5: the empty `History` shares one mutable dict.** `_EMPTY` (history.py:95), returned at :291, :294 and :320, shares a single `by_conclusion` dict. A caller that mutates it corrupts every later empty history. Build a fresh empty `History` each time.
- **M6: `file_matches` leftovers.**
  - It checks `st_size` and then calls `read_bytes()`, which is unbounded if the file grows in between (entries.py:177-179).
  - `hmac.compare_digest` raises `TypeError` on a non-ASCII `content_sha256` (:182; confirmed), against the docstring's "False, never an error". The hash is not secret, so `==` is enough.
  - Fix: open, `fstat`, then read at most `MAX_FILE_BYTES + 1`.
- **M7: the inventory read is not deterministic.** `SELECT hostname FROM assets LIMIT 10000` has no `ORDER BY` (fingerprint.py:180). Above 10,000 assets an arbitrary subset is scrubbed, and the fingerprint can differ from one run to the next.
- **M8: full-text recall.** Consider adding the template's lexemes ORed together (named risk 3).
- **M9: test hygiene.**
  - `test_an_alert_that_is_not_there_is_a_permanent_error_that_does_not_echo_much` (test_rag_fingerprint.py:258) asserts nothing about the message, and the message does echo the id (fingerprint.py:190).
  - test_rag_fingerprint.py:98-99 has a duplicate `@pytest.mark.db`.
  - `_case` (test_rag_fingerprint.py:277) gives heads after the tenth a negative `days_ago`, which puts their first sighting in the future.
  - No candidate test uses a real `alert_fingerprint(...).text` from one host as the entry and the same rule from another host as the subject.

Those values also undercut deviation 3's claim of matching across hosts. The fix is one line plus a test, but it needs the controller to rule against the brief's wording.
