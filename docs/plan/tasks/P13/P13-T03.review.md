### Named-risk checks
1. **Model text into `matches` or `PromptMaterial`: none.**
   - `Match` is built from `cand.entry_id`, a validated `KbLearnedLevel` and `cand.content_sha256` (`match.py:_validated`).
   - `_matches_json` serialises only those fields.
   - `prompt_material` takes the content from the database after the hash re-check (`lookup.py:428-447`).
   - Reasons go only to `match_notes` (cleaned) and to `llm_runs.result`.
2. **Injection through the content or the fingerprint: blocked.**
   - Both always go through `wrap.untrusted_block` (NFKC → nonce strip → escape), so a forged `<untrusted_data` or the real nonce is neutralised.
   - The linter runs before both sends (`agent.py:_lint_or_raise`, before each call).
   - Gap: the repair builder is not value-free for keys containing `": "` (I1). The linter backstop holds: no free text reaches the model.
3. **Transient path: correct.**
   - On a non-final attempt the only write before `conn.commit()` is the run row: no `rag_results` row and no event. `SET LOCAL` dies with the commit.
   - The worker's `rollback` and `finish_job(transient)` then follow.
   - The final attempt writes exactly one `failed` row plus one event, and returns.
   - `is_transient` agrees with `infra.errors.classify` on every exception the adapter raises.
4. **The jsonb cleaning: the audit trail holds.**
   - On `system_prompt` and `user_message` it is a no-op in practice: they come from the template and database text, which cannot hold a NUL or a lone surrogate, so the stored prompt equals the sent one.
   - On `result` it replaces NUL and lone surrogates with U+FFFD, visibly. Without that, the insert fails.
   - Edge: `_clean` can merge two dict keys that differ only by NUL vs U+FFFD. Negligible.
   - Separate gap: only the first prompt is stored (M5).
5. **Budget: no RAG call can be sent with either cap reached, as far as the database knows.**
   - `rag_limits` is read first; unreadable settings raise `LLMBudgetExceeded`.
   - Then `rag_spent_or_exhausted` returns `inf` when the global cap is reached, so `inf >= cap_usd`.
   - Both run on every attempt, in-adapter retries and the repair included.
   - The remaining overshoot comes from cost not yet written to the database: concurrent writers, and this lookup's own first call (M1).

### Issues

#### Critical (Must Fix)
None.

#### Important (Should Fix)
**I1. A model-written key containing `": "` defeats the value-free repair, and turns a schema refusal into a `failed` lookup. This contradicts ruling 2.**
- **Cause:** `rag/agent.py:154`, `error.partition(": ")`, splits at the first `": "`, which can sit inside the model's own key. `message` is then not `"unexpected key"`, so `_object_prefix` is skipped.
- **The probe confirms both effects:**
  - **The key reaches the repair outside a block.** With `{"matches": [], "matches: missing": 1}`, the repair carries the bullet `- matches: missing: unexpected key`. It passes the linter because every word is a constant. The model can echo any vocabulary words, `TEMPLATE_CONSTANTS` sentences included, which falsifies the claim at `agent.py:8-11`.
  - **Any other word fails the repair linter.** With `{"matches": [], "a: b": 1}` (or `"x\ny: z"`), the result is `PermanentError: rag prompt failed the linter: free_text at line 15`, and the repair is not sent.
- **What follows in the job:**
  - `lookup.py:355-357` writes a `failed` row, `rag.lookup_failed` and `stopped_by="linter"`, so a model outcome is recorded as our template defect.
  - `prompt_material` then returns `None`, so ① and ② lose the AI-free history too.
  - Attacker-controlled log text in the `context` block can steer the model into writing such a key. That suppresses history for chosen alerts and creates alarm noise.
- **Fix:**
  - In `_repair_line`, use `error.rpartition(": ")`, or handle the `": unexpected key"` suffix first. No validator message contains `": "`; only an unexpected-key path carries model text.
  - Add tests:
    - in `test_rag_match.py`: the keys `"a: b"`, `"matches: missing"` and `"matches[0].x: y"` each give `<root>` or `matches[]: unexpected key`;
    - in the job tests: `{"matches": [], "a: b": 1}` twice degrades to `ok`/`empty` with no event.
  - The same line exists in `llm/investigate.py:158`. That is outside this task; it is for the Director.

#### Minor (Nice to Have)
- **M1. `rag/budget.py:60-63` overclaims**, as do the docstrings at `tests/test_rag_budget.py:272-273` and `tests/test_rag_lookup_job.py:536-537].
  - They say a cap crossed "by this very call" stops the repair. It cannot: the first call's cost lives only in `Tape` until `_record_run` writes it after `rank` returns (`lookup.py:259` and the lines after `:344`).
  - The test simulates the crossing with a `triage` row.
  - Either fix the wording, or add the tape's spend to what the adapter reads. ① and ② have the same one-call overshoot.
- **M2. The ranking prompt has no size bound** (`match.py:49-50`).
  - 20 × 6,000 B + 4,000 B is about 124 KB, roughly 50k estimated tokens. That is above the project's own `PROMPT_TOTAL_BUDGET_TOKENS=40_000`, which ① enforces (`llm/triage.py:479`). The repair resends all of it.
  - That costs money against the $3 sub-cap, and a provider 4xx on length becomes `failed`.
- **M3. The candidates' content is sent and matched without checking `sha256_text(content) == content_sha256`** (`lookup.py:324-329`, `386-387`).
  - A tampered database row can take one of the 3 slots. It is dropped only at prompt time, with no `rag.integrity_failed`.
  - This is spec-conformant (V-R1 names the file); it is a cheap hardening.
- **M4. Every non-LLM `PermanentError` from `rank` is recorded as `stopped_by="linter"`** (`lookup.py:355-357`), an unknown schema (`agent.py:99-104`) for example.
- **M5. The run row stores only `tape.sent[0]`** (`lookup.py:259`).
  - For a repaired lookup, the repair message actually sent is absent, and so are the first answer's schema errors: `gate_result` holds only the faults.
  - What the model received cannot be rebuilt from the row. This matches ② (`tier2/investigate.py:450`).
- **M6. The `bad_level` branch (`match.py:162-165`) is unreachable from the job**, because `call_json` has already enforced the level enum. One bad item that survives the repair drops all the valid ones too. This is within ruling 2 ("no matches"); recorded only.
- **M7. A 429, or any 4xx, from the shared adapter becomes `LLMPermanent`** (`adapter.py:108-117`), so the lookup is `failed` on its first attempt with no queue retry (`lookup.py:349-353`). §7.9 says a failing DeepSeek "retries by the queue's backoff". This is inherited from the adapter.
- **Nits:**
  - `lookup.py:24` is a 183-character docstring line, not rewrapped after the ruling-2 edit.
  - Repair bullets are not de-duplicated after the `[]` normalisation (`agent.py:220-221`); this is inherited.

### Assessment
**Task quality: Needs fixes**

**Reasoning:** The anti-poisoning core is sound:
- model text cannot reach `matches` or `PromptMaterial`;
- every untrusted text is wrapped, and the linter runs before both sends;
- the transient and final-attempt transactions are correct;
- both caps stop every attempt.

I1 is a one-line, model-triggerable (and log-steerable) defect in the repair builder. It falsifies the module's value-free claim and sends an explicit ruling-2 case down the `failed` / `rag.lookup_failed` / `stopped_by="linter"` path, losing the history. It should be fixed, with tests, before merge. The Minors can go to the parked list.

## Director's ruling (25/10)
- **I1: fix,** with the tests the reviewer lists. The same line in `llm/investigate.py:158` (②, pre-existing) goes to **T08**.
- **M3: upgraded to Important.** The ranking prompt is a prompt, and spec anti-goal A4 says "An entry changed after approval reaches a prompt". Before a candidate is sent, its `sha256_text(content) == content_sha256` and its file match are checked. A candidate that fails is dropped and writes `rag.integrity_failed {"entry_id"}`.
- **M2: upgraded to Important** (cost against the $3 sub-cap; a length 4xx becomes `failed`).
  - Each candidate block holds only the entry's closed fields, its title and its summary, never its whole content.
  - The whole ranking prompt is bounded by an estimated-token budget of 12,000 (`llm.adapter.estimate_tokens`), counted on the first message. The lowest-ordered candidates are dropped until it fits.
  - The repair resends the same bounded message.
- **M1:** wording only. The docstrings say the cap is read from the database before each attempt, and that this attempt's own spend is counted only after its run row is written.
- **M4–M7 and the nits:** deferred to the whole-branch triage.

# P13-T03 fix round 1 — scoped re-review (`728e429..1e15d41`)

**How it checked:**

**I1: ADDRESSED.**
- `agent.py:162-164` strips the `": unexpected key"` suffix first and reports the error against `_object_prefix`. That returns only a schema path or `<root>`.
- Only an unexpected-key error carries model text (`llm/schemas.py:142-144`).
- Probes gave `<root>` or `matches[]` for: `"a: b"`, `"matches: missing"`, `"x\ny: z"`, `"q: unexpected key"`, `"<root>: expected a JSON object"`, `"a.b: c.d"`.
- Tests cover both the repair and the job degrading with no event.

**M3: ADDRESSED.**
- `lookup.py:331-345` checks the content hash and `file_matches` before the send. Only `intact` candidates reach `select_candidates` (:346) and `rank` (:375); `rank` validates against what it sent (`match.py:285`).
- `rag.integrity_failed` is written once per entry per attempt.
- **The file-edit race is acceptable.** What is sent is the database content whose hash matched at check time, and `prompt_material` re-checks at prompt time.

**M2: ADDRESSED.**
- `entry_digest` (`match.py:112-134`) holds conclusion, category, mitre, scenario, rules, tags, the title (200 chars) and the summary. It is wrapped and limited to 4,000 bytes.
- **Crafted content in `render_entry_markdown`'s shape** cannot bring other sections into the block, as the probes show. Other shapes stay wrapped and bounded.
- `select_candidates` (`match.py:158-167`) keeps the longest prefix that fits, measured on the rendered message.
- The repair resends the same message (`agent.py:231`).
- `candidates_dropped_for_budget` is on every run row.

**M1: ADDRESSED** (`budget.py:57-66`; the two tests' docstrings; `lookup.py:24` rewrapped).

**New breakage: none Critical or Important.** Four Minors:
- **N1. The stand-in nonce makes the budget under-count.**
  - `match.py:163` sizes the message with `"0"*16`, and `strip_nonce` replaces any 16-zero run in the text. Text with long zero runs is therefore measured short.
  - A probe sent 10 candidates at 12,728 estimated tokens, about 6% over budget.
  - **Fix:** size with the real nonce (`rank` creates it first and passes it in), and add a zero-run test.
- **N2. The dropped count is lost when every candidate is cut.**
  - If the context plus the first candidate exceeds the budget, `select_candidates` returns `[]`. The job then writes `ok`/`empty` with no run row and no count.
  - **Fix:** log the count, or skip an oversized single candidate instead of cutting at it.
- **N3. Integrity events are duplicated on transient retries.** They are written before the call, and a non-final attempt commits them, so there can be up to 3 per entry per lookup job.
  - **Fix:** write them on the terminal branches only.
- **N4 (latent). `_TITLE` (`match.py:95`) is quadratic on a long run of spaces.**
  - It is unreachable through `render_entry_markdown`, and the integrity check keeps tampered content out.
  - **Fix:** `^# +(.*)$`.

**Out of scope:**
- The repair suffix is unbounded and not de-duplicated (a deferred nit).
- The `scenario:` line is closed only if T04/T05 validate `soar_scenario`.
- The digest relies on content in `render_entry_markdown`'s shape; T05 should guarantee it.
- `wrap` cuts before it escapes (pre-existing; the budget still measures the rendered text).
- `llm/investigate.py:158` is already ruled to T08.

**Verdict:** all findings addressed.
