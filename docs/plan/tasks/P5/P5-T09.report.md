## 3 · The red steps

### 3.1 · Design note 5 (a)–(c)

- **(a) a hardcoded/shared alert id in a row's button.** First attempt (hardcoding only the "Đúng"
  button's `hx-post`) showed a real gap: a bare `in resp.text` check still passed, because the
  other two buttons in the same row still carried the right id. Strengthened
  `test_get_page_buttons_target_their_own_alert_id` to `resp.text.count(...) == 3` (one per
  button); broke it, watched it go red (`assert 2 == 3`), restored it, watched it go green again.
- **(b) rendering the reviewed row without re-reading the database.** The obvious version of this
  test (`test_second_review_is_409_and_shows_the_first_reviewers_verdict`, two real HTTP requests
  against a scratch DB) turned out not to discriminate either: by the time the *second* request's
  handler even runs, the first reviewer's verdict is already committed and visible to *any* fresh
  read, including the very first (`before`) one — so a broken implementation that just reused
  `before` would still pass it by coincidence. Added
  `test_conflict_fragment_uses_the_post_rollback_reread_not_the_pre_call_snapshot`, which
  monkeypatches `digest.build` so specifically its *first* call inside the request reports no
  verdict (standing in for genuine interleaving) while a real, already-committed competing review
  is only visible on a second call. Broke the handler (`after = before` instead of a fresh
  `digest.build(...)` call), watched it go red (`calls["n"] == 1`, and separately the missing
  "Đúng"), restored it, watched it go green again.
- **(c) dropping the disagreement marker.** Removed the `<strong data-field="disagreement-marker">`
  span from `_digest_row.html`; `test_disagreement_sorts_first_and_carries_a_marker` went red
  (`'data-field="disagreement-marker"' in disagree_row` failed); restored it, green again.

### 3.2 · The three known pitfalls

1. **Commit-before-return on a 409.** Removed the `conn.rollback()` call in `review_submit`'s
   `except StaleState` branch; `test_409_rolls_back_before_a_later_commit_would_run` (a real-shape
   `get_conn` — commit on success, rollback on exception, both call-recorders, mirroring
   `test_tier1_api.py`'s proof for P4-T03's `_conflict_response`) went red
   (`assert ['commit'] == ['rollback']`). Restored, green again.
2. **The 403 test's own commit must never reach the shared test database.**
   `test_non_admin_is_refused_and_authz_denied_row_present` runs on its own scratch database
   (`sdb`/`scratch_dsn`, built/migrated/dropped the same way `test_pages_rules.py`'s and
   `test_auth.py`'s do), never the `db`/`client` fixture. Direct evidence in acceptance item 10:
   after the full run, `soc_p5t09_test` carries zero `authz.denied` rows for any `/admin/digest*`
   path. The ordering proof (item 9) is the second, end-to-end form of the same evidence.
3. **htmx 2.0.4 not swapping 4xx/5xx.** Emptied `digest.html`'s `{% block scripts %}`;
   `test_htmx_before_swap_listener_is_present` went red (`'htmx:beforeSwap' in resp.text` failed).
   Restored, green again.

### 3.3 · The Director's heads-up: the out-of-band flash had no swap target

Mid-task, Director 1 flagged a real bug, found by the P4-T05 review and verified in jsdom against
htmx 2.0.4: `_flash.html`'s `<div id="flash" hx-swap-oob="true">` only renders when `flash` is
truthy, and `_page()`'s `GET /admin/digest` never passes one — so on every normal page load there
is **no `id="flash"` element in the DOM at all**, and htmx silently drops an out-of-band swap with
no matching target. The 409 conflict flash (and every other row-response flash) would never have
appeared in a real browser, even though every response-body assertion in this file's tests still
passed (`TestClient` reads the raw HTTP response text; it never merges an OOB swap into a DOM the
way a browser does, so this class of bug is invisible to a response-text-only test suite).

**Fix (a), as directed:** `digest.html` now carries its own empty `<div id="flash"></div>`,
outside `<table id="digest-rows">` (never touched by any row's `outerHTML` swap) and outside the
`{% if %}` branches (present in every state — both empty states and the row table). Since
`_page()` never sets `flash` on `GET`, `base.html`'s own `{% include "_flash.html" %}` renders
nothing on this page, so this placeholder is always the *only* `id="flash"` element — confirmed by
three tests: `test_page_carries_exactly_one_flash_placeholder_with_rows`,
`..._empty_state`, and `test_a_review_response_targets_the_pages_flash_placeholder_out_of_band`
(the row fragment's own `id="flash" hx-swap-oob="true"` matches the page's placeholder id).

**Red step:** removed the placeholder `<div>`; both "exactly one `id="flash"`" tests went red
(`assert 0 == 1`); restored it, green again.

**The `HX-Redirect` note does not apply here.** `review_submit` never redirects — every path
(200 success, 409 conflict) returns the re-rendered row fragment directly as an `HTMLResponse`, no
`RedirectResponse` and no `HX-Redirect` header anywhere in this router, so there is no flash that
could be lost to a pre-swap navigation.

## 4 · Deviations from the card

The prompt (`docs/plan/tasks/P5/P5-T09.prompt.md`) was written 23/09, against an older
`tier1/digest.py`. Per the Director's dispatch, current code and `DECISIONS.md` win; every place
they disagreed with the card is listed here.

1. **`day` is a `str`, not a `date`.** The card's design notes describe it loosely as "a date
   object". P5-T08's actual, merged `build`/`unreviewed_count`/`review` all take `day: str` (an
   ISO `YYYY-MM-DD` string). The router follows the real signatures.
2. **A fourth file, `backend/app/web/templates/_digest_row.html`.** The card's file list names
   only `admin_digest.py`, `digest.html`, `test_pages_digest.py`. Design note 2 requires the HTMX
   response to be "the same row re-rendered" — to avoid two copies of that markup (one in the
   page's loop, one hand-built for the fragment), the row is its own partial, included by
   `digest.html` and rendered standalone by the router, exactly the way `_flash.html` is already a
   shared partial in this codebase. No other card owns this path (P5-tasks.md §9 lists only
   `digest.html` under T09 in `templates/`).
3. **Tests authenticate via `dependency_overrides`, not "a real admin cookie."** The card's design
   note 5 says the tests use "a real admin cookie". The actual, already-merged convention every
   sibling page-test file uses (`test_pages_rules.py`'s `client` fixture, P5-T10) overrides
   `deps.current_user` and `pages.page_user` with a fixed `Claims` instead. `test_pages_digest.py`
   follows that convention.
4. **The empty state "chưa có rule tự đóng nào" is keyed on *enabled* rules**
   (`app.ingest.autoclose.load_rules`, which already filters `WHERE enabled`), not on "does any
   row exist in `autoclose_rules` at all." A rule that exists but is switched off cannot have
   auto-closed anything today either way, so the message is still the correct one to show; a raw
   existence count would need either new SQL (forbidden by acceptance item 6) or importing
   `admin_rules.py`'s module-private `_list_rules` (another card's file). Tested directly
   (`test_a_disabled_only_rule_still_reads_as_no_rule`).
5. **"Now, in `DISPLAY_TZ`" is read from the process clock, not the database.** `tier1/digest.py`'s
   own CLI computes "today" with a `SELECT (now() AT TIME ZONE %(tz)s)::date::text` query, but this
   page may issue no SQL of its own (acceptance item 6). `_now_local(tz)`
   (`datetime.now(ZoneInfo(tz))`) is used instead, only to choose the *default* value of a display
   parameter — never a control timestamp, never persisted — and is the one seam
   (`monkeypatch.setattr(admin_digest, "_now_local", ...)`) the day-default tests replace.
6. **`htmx:beforeSwap` was written directly from the card's own three-line spec, not copied from
   P4-T05/P5-T07.** Neither is merged into `90ec4d1` yet — `backend/app/web/routers/alerts_pages.py`,
   `templates/queue.html`, `cases_pages.py` and `templates/case.html` do not exist in this tree.
   There was no prior art in the merged tree to follow.
7. **The card's acceptance preamble (the `TDB`/`dsn_env.py` shell lines, the `main` 22/09 baseline
   of "1042 passed, 1 skipped, 549 deselected, 2 xfailed") is superseded by the Director's
   dispatch**, which supplies `run_merge_tests.sh`/`order_proof.sh` directly and the `90ec4d1`
   baseline (lint 0; test 1567 passed, 0 failed; test-db 806 passed). The Director's scripts and
   baseline were used throughout; see §2.
8. **`STATE.md` is untouched**, per the Director's explicit hard rule ("Change nothing in it"),
   which supersedes the card's own report step ("then set your `STATE.md` row to `review`").
