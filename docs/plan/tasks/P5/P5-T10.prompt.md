- **Design notes:**

  **1 · The preview is the point of the screen, so it runs before the write and its numbers are the real ones.**
  The create form posts the `match` to a preview route that calls `simulate(conn, match)` and renders
  `SimulateStats` in full: **clusters**, **alerts** (the duplicate-inclusive total, which is the number that
  matters — 99,920 of 100,526 alerts on this host are duplicates), the severity breakdown, the
  `asset_criticality` breakdown, and the ≤ 20 sample `alert_id`s **as links to the alert page**. Only then
  does a second, explicit action write the rule. `simulate` applies the **same predicates** `evaluate()` does,
  hard blocks included — so the preview is a promise the system keeps, and the screen should say so in one
  sentence: *"xem trước dùng đúng vị từ của bộ máy, đã tính cả sáu chặn cứng"*.
  A `match` outside the whitelist raises `PermanentError` from `_parse_match`; render it as a **422 flash
  naming the offending field**, never a 500.

  **2 · The hard blocks are shown, not assumed.** G8′ blocks six conditions before any rule is consulted, and
  on this host the fourth one — **asset not in inventory — hard-blocks 523 of 606 heads (86 %)**. A preview
  that returns `clusters: 0` will usually mean *the inventory, not the rule*, so the screen states the six
  blocks next to the preview and, when the preview is empty, says which block accounted for the most
  candidates. An admin who cannot tell "my rule matches nothing" from "everything it matches is hard-blocked"
  will write a worse rule.

  **3 · Toggle, audit and cache, in one transaction.** `PATCH`/`POST` toggle → `UPDATE autoclose_rules SET
  enabled = …` → `write_event(conn, "admin.autoclose_rule_toggled", rule_id, "admin", actor_id=…,
  payload={"name": …, "before": <bool>, "after": <bool>})` — **before and after, both, explicitly**
  (`prompts/P5.md:33`) — then `reload_rules(conn)` **after the commit**, so the 60 s cache cannot serve a
  state that no longer exists. Creating a rule does the same. `created_by` is the acting admin's `user_id`;
  `rule_id` is a `uuid4` the application assigns (the column has no default).

  **4 · The width warning belongs here and nowhere else.** `rule_width_report(conn, 7)` marks rules above
  `AUTOCLOSE_RULE_WIDTH_PCT`; show the percentage beside the rule. **Do not confuse it with
  `rule.suspected_wrong`** (P5-T08): width says *this rule closes a lot*, the digest signal says *humans keep
  saying this rule is wrong*. They are different measurements, they can disagree, and a screen that merges
  them destroys the distinction the architecture drew.

  **5 · Role and refusal.** `require_role("admin")` on every route; a `tier1` or `tier2` session gets a 403
  with an `authz.denied` row that **commits before the raise** (P4 planning decision 3).

  **6 · Tests (`backend/tests/test_pages_rules.py`, `db`).** The preview renders every `SimulateStats` field
  and **writes nothing** (assert `autoclose_rules` count is unchanged after a preview); a whitelist violation
  renders a 422 flash naming the field; creating a rule writes the row, the audit event and makes
  `load_rules` return it **without waiting for the cache TTL** (assert through `autoclose.evaluate` or
  `load_rules` immediately after); toggling writes `before`/`after` in the payload and flips the rule's
  effect; the width warning appears for a rule above the threshold and not for one below; a non-admin is
  refused and the `authz.denied` row is present after the 403. **Red steps (DEC-025):** (a) drop the
  `reload_rules()` call → the immediately-live test goes red while the row-was-written test stays green,
  which is exactly why both exist; (b) write the audit payload with only `after` → the before/after test goes
  red; (c) make the preview write the rule → the writes-nothing test goes red.
