### 2b · The idle-timeout math (Director item 1), measured

`LLMTimeout` (the `LLM_TIMEOUT_S` wall-clock deadline, DEC-033) is **never retried**
inside `DeepSeekAdapter.complete()` — that module's own design note 3. So a genuine
timeout bounds **one** logical send at `LLM_TIMEOUT_S` (120 s default), not
`LLM_TIMEOUT_S × (1 + LLM_RETRY)`; the adapter's internal retry loop is for *other*
(non-timeout) errors, which fail fast in practice. `run_investigate_job` makes at most
two logical sends (`llm.investigate.investigate()`'s "one repair and no more"), so the
worst case attributable to LLM calls is **2 × 120 s = 240 s** — a **60 s / 20 % margin**
under `JOB_LOCK_TIMEOUT_S = 300 s` (default). A job cannot be reclaimed while its call is
still running, at these defaults. (The adapter's own retry loop for non-timeout errors
could in theory push one send past 120 s across up to `1 + LLM_RETRY` attempts; that
ceiling is identical to ①'s existing, already-accepted `run_triage_job` — this card adds
no new exposure there.) Measured practical numbers (P5-T02, `docs/investigate-size-
class.md`): p95 14.65 s at the 60 k-token synthetic class, 14.68 s at the 12.8 k
real-corpus ceiling — well under 30 s even with a repair, far inside both the 240 s
theoretical bound and the 300 s job lock.

## 3 · Deviations

1. **`STATEMENT_TIMEOUT` validation lives in `web/handlers/__init__.py`, not a new
   file** (Director item 2, explicit no-edit exception for this one purpose). The
   card's own acceptance 4 wording ("`git diff main --stat -- … handlers/__init__.py`
   → empty") is superseded by the dispatch; recorded here as the dispatch instructs.
2. **The isolation level is `REPEATABLE READ`, not `REPEATABLE READ READ ONLY`**
   (design note 4's literal words). Measured, not guessed: `READ ONLY` succeeds as a
   statement in this position, but it applies to the *rest* of the same
   worker-provided transaction — and this handler still has to write the `llm_runs`
   row and update `cases.last_analyzed_at` later in that same transaction. Both then
   fail with `psycopg.errors.ReadOnlySqlTransaction`. `SET TRANSACTION READ WRITE`
   cannot lift it partway through either (same "before any query" rule, and by then
   the dossier's own queries have already run). Ending the transaction early to start
   a fresh read-write one would put this handler's writes outside the worker's own
   commit boundary — exactly the "do not restructure the worker" the card rules out.
   `REPEATABLE READ` alone gives the consistent-snapshot property design note 4 is
   actually after, without that conflict. A second, unrelated finding from the same
   investigation: wrapping the attempt in a `SAVEPOINT` (as a seemingly safer fallback)
   **always** fails with `psycopg.errors.ActiveSqlTransaction: SET TRANSACTION
   ISOLATION LEVEL must not be called in a subtransaction`, regardless of what ran
   before the savepoint — so the fallback for "something already queried this
   transaction" (never the real worker; see below) is a full `ROLLBACK`, not a
   savepoint. Every claim here is reproduced directly in `test_investigate.py`
   (`test_isolation_level_helper_sets_repeatable_read_read_only`,
   `test_isolation_level_read_only_would_break_this_handlers_later_write`,
   `test_isolation_level_inside_a_savepoint_is_refused_by_postgres`), not just
   asserted in a docstring.
3. **The evidence check's injection scan runs over `dossier.text` as one synthetic
   block, not per-block.** `security/detector.py`'s own docstring says `scan()` is
   meant to run over block *contents*, never the assembled prompt (which would also
   match the template's own instructions). `Dossier`'s public API (P5-T03's file, not
   touched by this card) exposes `.text` and nothing at the block level, so there is no
   way to reach individual blocks from `tier2/investigate.py` without importing
   `tier2.dossier` internals this card has no license to add. Risk is bounded: the
   detector's patterns target injection shapes (base64 runs, imperative-command
   density, hidden characters, delimiter look-alikes) the dossier's own short,
   structural Vietnamese headings do not resemble, and the direction of any false
   positive is the conservative one (forcing `need_more_data` on a clean case, never
   the reverse). Demonstrated working end-to-end in
   `test_high_severity_injection_finding_forbids_false_positive`.
4. **The P7-2 snapshot, `Dossier.truncations` and `Dossier.estimated_tokens` live in
   `agent_trace`, not inside `result`'s envelope** (design note 3(c)'s "your choice").
   `result` stays the pure `investigate_v2`-validated object (or `NULL`) so a reader
   (P8, or a later P5-T05) never has to know this module's storage convention to read
   a `result` that validates against the frozen schema — see §4.
5. **`quota is counted from `audit_events`, and the route writes `case.analyzed` with
   `actor_role='analyst'` at 202 time** — the card's own named departure from

## 4 · Where the snapshot, truncations and `estimated_tokens` live in `llm_runs`

In the `agent_trace` column (jsonb), on every row this job writes (success, `schema`
failure, and every LLM-exception path alike — dossier-building already succeeded by
the time any of those can happen):

```json
{"alert_count": <int>, "total_occurrences": <int>, "last_seen_at": "<iso8601>|null",
 "truncations": [<Dossier.truncations, verbatim>], "estimated_tokens": <int>}
```

`result` is always either `NULL` or the pure `investigate_v2`-validated object (no
envelope). `evidence_check` carries `{verified, rejected, original_conclusion?,
forced_by?}`. `citation_warnings` is a flat list of strings, one per rejected evidence
item. `gate_result`/`verifier_result` are always `NULL` on `investigate` rows (①'s
columns).
