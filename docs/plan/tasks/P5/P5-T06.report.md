## 3 · Deviations from the card and why

- **The card's read-first list cites `backend/app/tier1/decide.py` and
  `backend/app/web/routers/tier1.py` as "the shape this card copies"** (P4-T03's files).
  On this worktree, cut from the director tip `dc5cedd`, both are still 1-line skeletons —
  P4-T03 is a sibling wave-1 card, dispatched in parallel, not yet merged. There was nothing
  to copy. `submit()`'s guard/call/translate shape and the router's `require_role` /
  `Depends` / typed-exception-to-`HTTPException` pattern were instead built directly from
  `web/deps.py` (merged, P4-T01) and `web/routers/labels.py` (merged, P6-T02), which already
  establish the same conventions (`Admin`/`Tier2` one-`Depends`-object pattern, a
  `LabelError`-style exception hierarchy translated in the router, a `db`-fixture `TestClient`
  with overridden `deps.current_user`). No functional gap results — P4-T03's own card
  independently specifies the same 409/500 shape for `tier1/decide.py`, and this card's own
  design note 1 spells out `submit()`'s behaviour without needing the sibling file.
- **The module docstring for `tier2/conclude.py` originally spelled the literal string
  `case.note_added`** to explain why no such event type exists (design note 2's own
  instruction: "say this in the report so it reads as a decision, not an omission"). Acceptance
  item 4's own grep (`grep -c "case.note_added" backend/app` → `0`) catches this — the guard
  is written to make sure the name never enters the source tree, including as a negative
  example. Reworded to "a note added name is not one of the 27 `ck_audit_event_type` fixes"
  before the final run; verified `0` after.
- **`P5-tasks.md` §9's file-disjointness table and this card's own "Files — create" list agree**
  on `backend/app/web/routers/tier2.py`, `backend/tests/test_conclude.py`,
  `backend/tests/test_tier2_api.py`; no divergence found there.
- **Exact HTTP response shapes are the card's own design notes, filled in where they are silent**
  (the card gives the four routes' status codes and field lists in prose, not a JSON schema):
  `GET /api/tier2/cases` returns a bare JSON array (no pagination-metadata wrapper — the card
  says "OFFSET-paged" and nothing about a total-count field); `offset`/`limit` query
  parameters (`offset >= 0`, `1 <= limit <= 200`, default `50`) are this card's own choice, not
  named anywhere in `P5-tasks.md` or the card. `case_detail`'s head columns
  (`alert_id, rule_id, severity, description, agent_name, alert_time, srcip, category,
  occurrence_count, status`) are a practical set for a case-overview grid, chosen because the
  card names only the *rule* (G10, explicit list) and not the columns themselves. `list_cases`
  and `case_detail` are exposed at module level (not `_`-prefixed) specifically so P5-T07 can
  import them directly — the card says P5-T07 "builds on your REST layer next," and this is
  the seam that makes that literal rather than requiring P5-T07 to re-derive the SQL.
- **`list_cases`'s occurrence-count query counts alert *rows* (`COUNT(*)` over heads ∪
  duplicates), not `SUM(occurrence_count)` over the heads.** Measured read-only against
  `soc_dev` (`SET SESSION CHARACTERISTICS AS TRANSACTION READ ONLY`, DSN from
  `app.infra.config.load(env_file=".../.env")`, never printed): a head's own `occurrence_count`
  already counts its merged duplicates one-for-one (`ingest/dedup.py`'s `bump_parent` bumps
  only the head; a duplicate keeps its own column at the schema default of 1) — for one
  measured cluster, head `occurrence_count = 622` and `count(*)` of its 621 duplicate rows
  plus the head itself was also `622`. The two formulas agree numerically, but `SUM` over
  heads-and-duplicates-both would double-count (622 + 621 = 1243, wrong), so the row-count
  form is the only one of the two that is actually correct across the `OR` — and it is also
  the one design note 3 / DEC-036 name and the one red step (a) exercises. Not a functional
  deviation from the card, but the reasoning is recorded here since it is not otherwise
  written down and a future reader (P5-T07, or whoever edits this query next) would otherwise
  have to re-derive it or get it wrong the double-counting way.
- **`add_note`'s unknown-case behaviour (404) is not named anywhere in the card** — design
  note 2 says nothing about a missing `case_id`, and design note 3's "404 when absent" is
  stated only for `GET /cases/{case_id}`. Left as a raw `IntegrityError` this would have been
  an unhandled 500. Added a translation (`UnknownCase`, keyed on the FK constraint name
  `fk_case_notes_case` specifically, not on `author_id`'s FK, so an author-side FK violation —
  which should not happen in practice, `author_id` is always the session's own claims — is not
  misreported as "case not found") for interface cleanliness, matching `GET
  /cases/{case_id}`'s 404 and giving P5-T07 one consistent 404 shape across the REST layer
  rather than two different failure modes for the same underlying condition.
- **`POST …/conclude` on a `case_id` that never existed answers 409, not 404.**
  `domain.transitions.conclude_case` raises the same `StaleState` for "case is concluded" and
  "case does not exist" (§domain code, unmodified, out of scope to change); design note 1 maps
  `StaleState` → 409 without carving out the missing-row case. Inherited as-is and recorded
  explicitly in a test (`test_conclude_route_404_style_conflict_for_unknown_case`) and in this
  report per the card's own "record every deviation" instruction — it reads as a surprising
  status code without this note.
- **Owner actions after merge: none.** `case_notes` already exists (migration 015, already
  applied — checked first, per the dispatch instructions' migration rule) so this card needs
  no migration. No `.env` key, no `conf/*` file, no manual step. (Contrast T09/T10/T11/T12,
  which do carry Owner actions per `P5-tasks.md` §10 — this card is not one of them.)

  a decision. `ck_audit_event_type` fixes 27 names and none of them is a "note added" event —
  adding one would be a frozen-contract change (context pack §6, and P5-tasks.md planning

  either). The note row itself, in an append-only-by-convention table
  (`case_notes`, no `UPDATE`/`DELETE` path anywhere in this card), *is* the record. Nothing
  further to decide here; recorded as the card asked.
- **P5-T07 depends on the exact shape of `list_cases`/`case_detail`'s return dicts and on
  `conclude.Note`/`conclude.ConcludeConflict`/`conclude.UnknownCase`.** Since P4-T03 (the
  sibling this card's design notes point to for precedent) was not mergeable into this
  worktree at dispatch time, the response/exception shapes above are this card's own
  invention rather than a continuation of an established one. If P4-T03 lands with a
  materially different `DecisionConflict`-style shape for `tier1/decide.py`, a Reviewer or
  P5-T07's Coder may want to reconcile the two for consistency — nothing here blocks P5-T07,
  but the two need not look alike by accident.
