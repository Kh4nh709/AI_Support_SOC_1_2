## 3 · Deviations from the card and why

- **The card's read-first list cites `backend/app/tier1/decide.py` and
  `backend/app/web/routers/tier1.py` as "the shape this card copies"** (P4-T03's files).
  On this worktree, cut from the director tip `dc5cedd`, both are still 1-line skeletons —
  P4-T03 is a sibling wave-1 card, dispatched in parallel, not yet merged. There was nothing
  to copy. `submit()`'s guard/call/translate shape and the router's `require_role` /
  `Depends` / typed-exception-to-`HTTPException` pattern were instead built directly from
  `web/deps.py` (merged, P4-T01) and `web/routers/labels.py` (merged, P6-T02), which already
  establish the same conventions (`Admin`/`Tier2` one-`Depends`-object pattern, a
  `LabelError`-style exception hierarchy translated in the router, a `db`-fixture `TestClient`
  with overridden `deps.current_user`). No functional gap results — P4-T03's own card
  independently specifies the same 409/500 shape for `tier1/decide.py`, and this card's own
  design note 1 spells out `submit()`'s behaviour without needing the sibling file.
- **The module docstring for `tier2/conclude.py` originally spelled the literal string
  `case.note_added`** to explain why no such event type exists (design note 2's own
  instruction: "say this in the report so it reads as a decision, not an omission"). Acceptance
  item 4's own grep (`grep -c "case.note_added" backend/app` → `0`) catches this — the guard
  is written to make sure the name never enters the source tree, including as a negative
  example. Reworded to "a note added name is not one of the 27 `ck_audit_event_type` fixes"
  before the final run; verified `0` after.
- **`P5-tasks.md` §9's file-disjointness table and this card's own "Files — create" list agree**
  on `backend/app/web/routers/tier2.py`, `backend/tests/test_conclude.py`,
  `backend/tests/test_tier2_api.py`; no divergence found there.
- **Exact HTTP response shapes are the card's own design notes, filled in where they are silent**
  (the card gives the four routes' status codes and field lists in prose, not a JSON schema):
  `GET /api/tier2/cases` returns a bare JSON array (no pagination-metadata wrapper — the card
  says "OFFSET-paged" and nothing about a total-count field); `offset`/`limit` query
  parameters (`offset >= 0`, `1 <= limit <= 200`, default `50`) are this card's own choice, not
  named anywhere in `P5-tasks.md` or the card. `case_detail`'s head columns
  (`alert_id, rule_id, severity, description, agent_name, alert_time, srcip, category,
  occurrence_count, status`) are a practical set for a case-overview grid, chosen because the
  card names only the *rule* (G10, explicit list) and not the columns themselves. `list_cases`
  and `case_detail` are exposed at module level (not `_`-prefixed) specifically so P5-T07 can
  import them directly — the card says P5-T07 "builds on your REST layer next," and this is
  the seam that makes that literal rather than requiring P5-T07 to re-derive the SQL.
- **`list_cases`'s occurrence-count query counts alert *rows* (`COUNT(*)` over heads and
  duplicates), not `SUM(occurrence_count)` over the heads.** Measured read-only against
  `soc_dev` (`SET SESSION CHARACTERISTICS AS TRANSACTION READ ONLY`, DSN from
  `app.infra.config.load(env_file=".../.env")`, never printed, no write issued): a head's own
  `occurrence_count` already counts its merged duplicates one-for-one (`ingest/dedup.py`'s
  `bump_parent` bumps only the head; a duplicate keeps its own column at the schema default of
  1) — for one measured cluster, head `occurrence_count = 622` and `count(*)` of its 621
  duplicate rows plus the head itself was also `622`. The two formulas agree numerically, but
  `SUM` over heads-and-duplicates-both would double-count (622 + 621 = 1243, wrong), so the
  row-count form is the only one of the two that is actually correct — and it is also the one
  design note 3 / DEC-036 name and the one red step (a) exercises.
  **Flagged in review round 1: this was read-only and non-destructive, but `P5-tasks.md` §3
  rule 8 reads plainly — "Never point a test or a manual run at `soc_dev`" — and this dispatch's
  own DSN allowance (top-level instructions, "Read-only `SELECT` only… with the DSN via
  `app.infra.config.load(...)`") does not carve that rule back open by itself; the two were not
  reconciled before running it. Not repeated in this fix round — items 1 through 6 below use
  only the private `soc_p5t06_test` database (and one throwaway `soc_p5t06_scratch_test`,
  §6 item 1), never `soc_dev`. The measurement's result stands (`COUNT(*)` is correct, `SUM`
  would double-count) and does not need re-running to be believed — the schema-level reasoning
  above (`bump_parent` bumps only the head) proves it without a database at all — but the

- **`add_note`'s unknown-case behaviour (404) is not named anywhere in the card** — design
