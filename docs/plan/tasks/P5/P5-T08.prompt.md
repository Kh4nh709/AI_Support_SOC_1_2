- **Design notes:**

  **1 · `build(conn, day)` — what a row is, and what orders them.** Every alert with `status = 'auto_closed'`
  whose `closed_at` falls in `day`'s 24 h, with an **explicit column list** (G10): `alert_id`, `rule_id`,
  `description`, `severity`, `category`, `agent_name`, `occurrence_count`, `first_seen_at`, `last_seen_at`,
  `autoclose_rule_id` and the rule's name, plus ①'s verdict through **`tier1.queue.latest_suggestion`** —
  never a second hand-written join (P4 planning decision 5: one function reads ①, one place to change).
  **Disagreements first:** rows where ①'s `suggested_action` is **not** `false_positive` sort to the top —
  the rule closed it and the model would not have, which is the most interesting thing on the page — then by
  `occurrence_count DESC`, then `alert_id` so the order is total and the CSV is diffable. Already-reviewed
  alerts carry their verdict so the page can grey them; they are not excluded (re-reading yesterday's
  decisions is part of the loop).

  **2 · `review(conn, alert_id, verdict, reviewer_id)` — three effects, in one transaction.**
  (a) `INSERT INTO autoclose_reviews (alert_id, reviewer_id, verdict)` — the PK is `alert_id` alone, so a
  second review of the same alert is an `ON CONFLICT … DO UPDATE` (one review per alert, last reviewer wins)
  **or** a 409; pick one, state it in the report, and test it.
  (b) **The label, and the one mapping that needs a decision.** `correct` → `triage_labels(label =
  'false_positive', source = 'digest', labeler_id = reviewer)` — the reviewer is confirming the auto-close
  read the cluster right. **`wrong` writes no label**, and `unsure` writes none either. *Reason, and it is the
  card's most consequential judgement:* `wrong` says only that auto-closing was wrong; it does not say what
  the alert **is**, and `triage_labels` feeds P7's evaluation. Inventing `escalate` from a reviewer who only
  said "not this" would put a fabricated label in the gold-set table, and the cross-phase rule is that
  evaluation validity is never relaxed for convenience. The reopen (c) puts the alert back in the Tier-1
  queue where a **real** decision, and therefore a real label, is produced. **If the Director prefers
  `wrong → escalate`, that is a one-line change and their call — raise it in your report, do not decide it
  differently on your own.**
  (c) `wrong` → `domain.transitions.reopen(conn, alert_id, reviewer_id, reason='digest')` — A17,
  `auto_closed → queued_tier1` only. **`autoclose_rule_id` must survive the reopen** (the architecture's own
  test: *"review 'wrong' đưa alert về queued_tier1 và **giữ autoclose_rule_id**"*) — `reopen` clears
  `closed_at` and sets `close_reason`; assert the rule id is still there afterwards. A `StaleState` (the
  alert is no longer `auto_closed`) surfaces as a conflict the caller can render, not as a 500.

  **3 · `rule.suspected_wrong`.** After a `wrong` review, count that rule's `wrong` verdicts in the last
  **7 days** (join `autoclose_reviews` to `alerts.autoclose_rule_id`); at **≥ 2**, write the `rule.suspected_wrong`
  audit event once per rule per 7-day window — **check for an existing event in the window before writing**,
  or every subsequent `wrong` re-fires it. The event type exists in `ck_audit_event_type`; no new name.
  Notification is **not** this card's: `infra/notify.py` is P5-T11's and importing it here would make the
  digest depend on the ops lane. The event is the record; whoever watches events sends the message.

  **4 · The job, and why it re-arms itself.** `web/handlers/digest.py`: `JOB_TYPE = "digest"`,
  `handle = run_digest_job`. `job.subject_id` is the **ISO date** (`YYYY-MM-DD`), which is what makes the job
  idempotent per day: the partial unique index on `(job_type, subject_id)` refuses a second live row for the
  same day, so a re-run cannot duplicate anything (`prompts/P5.md:55`). At the end of a successful run the
  handler calls `ensure_scheduled(conn)`, which `enqueue`s **tomorrow's** date with
  `scheduled_at = now()::date + 1 + time '08:00'` built as a `psycopg.sql` expression — **evaluated by the
  database**, never a Python timestamp (§9: control timestamps come from the database's own clock), the same
  mechanism `infra/puller.py` uses for `pull`. `ensure_scheduled` is also exposed on the CLI
  (`python3 -m app.tier1.digest --ensure`) so a chain that was ever broken can be re-armed by hand, and
  **P5-T11's health check notices when it is broken** — a job that silently never runs is exactly the failure
  DEC-018/DEC-021 refused to accept from a compose cron, and the same standard applies here.

  **5 · The CSV is the cut path, so it is not an afterthought.** `to_csv(rows) -> str` and
  `python3 -m app.tier1.digest --csv <path> [--day YYYY-MM-DD]`: one header row, one row per cluster, columns
  in §1's order, `\n` line endings, UTF-8, deterministic. If the digest UI is cut this file **is** the digest,
  so it carries everything the page would show, including ①'s verdict and the disagreement flag.

  **6 · What today's database means for your tests, and why you build your own rows.** Measured 23/09:
  `alerts.status` is `duplicate` 99,920 + `queued_tier1` 606 — **zero `auto_closed`** — and `autoclose_rules`
  has **0 rows**. 523 of 606 heads are `asset_context.present = false`, so G8′'s `asset_not_in_inventory`
  hard-blocks them, and at most **77** heads in the whole database could ever auto-close. **Every test in
  this card therefore creates its own auto-closed cluster**; none of them may assume live content, and a test
  that passes only because `soc_dev` happens to have rows would be meaningless here.

  **7 · Tests (`backend/tests/test_digest.py`, mostly `db`).** `build` picks up only the 24 h window and only
  `auto_closed`; disagreements sort first (build one agreeing and one disagreeing cluster and assert the
  order, not just membership); ①'s verdict comes from `latest_suggestion` (insert an `llm_runs` row in
  P3-T10's shape). `review`: `correct` writes the review **and** the `false_positive` label; `wrong` writes
  the review, **no** label, reopens to `queued_tier1` and **keeps `autoclose_rule_id`**; `unsure` writes only
  the review; a second review of the same alert behaves as design note 2(a) says. `rule.suspected_wrong` fires
  at the second `wrong` in 7 days and **does not re-fire** on the third. The job is idempotent: enqueue the
  same day twice → one `jobs` row; a successful run leaves exactly one pending job for tomorrow at 08:00.
  `to_csv` is byte-stable across two builds. **Red steps (DEC-025):** (a) remove the disagreement sort key →
  the ordering test goes red while a membership assertion stays green, which is why the test asserts the
  order; (b) drop the existing-event check in `rule.suspected_wrong` → the does-not-re-fire test goes red;
  (c) write a `triage_labels` row for `wrong` → the no-label test goes red (and that is the test that guards
  P7's gold set from a fabricated label).
