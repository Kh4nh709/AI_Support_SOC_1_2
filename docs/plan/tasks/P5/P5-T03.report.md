## 1 · Built

`backend/app/tier2/dossier.py` (891 lines, replacing the 1-line skeleton):

- `build(conn, case_id, *, nonce, cfg=None) -> Dossier` — the public entry point. Reads
  the nine blocks from the database only, renders deterministic text, applies §7.6's
  truncation cascade inside `cfg.CASE_PROMPT_BUDGET_TOKENS`, returns a `Dossier`.
- `Dossier` (frozen dataclass) — `text`, `nonce`, `snapshot`, `truncations` (a tuple of
  `{step, before, after}` dicts), `estimated_tokens`.
- `Snapshot` (frozen dataclass) — `alert_count`, `total_occurrences`, `last_seen_at`
  (P7-2's requirement, design note 5).
- `Entity` (frozen dataclass) — `kind`, `value`, `count_7d`, `history`, `lookup`.
- `UnknownCase(Exception)` — `case_id` names no row in `cases`.
- Entity regex/extraction: `_extract_ipv4`, `_extract_ipv6`, `_extract_hashes`,
  `_extract_domains`, `_extract_raw_values`, `_build_entities` (the deterministic
  type/count/value ranking and the 50-entity cap).
- Bulk lookups/history (one SQL per entity type, `= ANY(%s)`, never per entity):
  `_bulk_asset_lookup`, `_bulk_identity_lookup`, `_bulk_ioc_lookup`,
  `_bulk_host_history`, `_bulk_username_history`, `_bulk_ip_history`.
- Query fetchers (one query each, explicit column lists, explicit `ORDER BY`):
  `_fetch_case`, `_fetch_heads`, `_fetch_duplicate_spans`, `_fetch_timeline`,
  `_fetch_tier1_events`, `_fetch_trigger_alert_id`, `_fetch_notes`,
  `_fetch_previous_run`.
- Block renderers: `_block1_case` … `_block9_scope` (one per §7.6 block).
- Public constants: `RAW_LOG_INITIAL_BYTES`/`RAW_LOG_CUT_BYTES`/
  `MAX_REPRESENTATIVE_CLUSTERS`/`TIMELINE_MAX_LINES`/`MAX_ENTITIES`/
  `ENTITY_HISTORY_DAYS` (the budget knobs); `STEP_RAW_LOG_CUT`/
  `STEP_REPRESENTATIVES_CUT`/`STEP_TIMELINE_DROPPED`/`STEP_STILL_OVER_BUDGET`/
  `STEP_ENTITIES_CAPPED` (the `truncations[].step` vocabulary); `SENTENCE_OUT_OF_SCOPE`
  (block 9, verbatim); `DOSSIER_TEMPLATE_CONSTANTS` (this module's own headings + the
  block-9 sentence, for a caller/test that lints a rendered dossier alongside
  `llm.builder.TEMPLATE_CONSTANTS`); `TLD_ALLOWLIST`; `ENTITY_TYPE_ORDER`.

`backend/tests/test_dossier.py` (577 lines, new) — 25 tests (10 non-`db`, 15 `db`), plus
this file's own fixture helpers (`_make_user`, `_make_case`, `_insert_alert`, `_make_head`,

### 2.1 · Red steps, each shown red once and restored (DEC-025)

**(a) "remove `ORDER BY` from the entity query."** This module's entity ranking
(`_build_entities`) sorts by `(type, -count_7d, value)` — `value` is unique within a type,
so this key is always a strict total order regardless of what row order any entity query
returns; none of the per-type bulk lookup/history queries can change the rendered output by
construction. I performed the demonstration instead against `_fetch_heads`'s
`ORDER BY alert_time, alert_id` — the query entities are extracted *from*
("From the case's raw_logs and descriptions"), and the one query whose row order *does*
reach the rendered text directly (block 2's and block 5's display order, with no
downstream Python re-sort). Stripped, then ran `test_two_builds_are_byte_identical_except_
the_nonce` and `test_entity_cap_50_is_deterministic` five times each (3–20 heads): **green
every time.** Scaled to 200 heads (`MAX_ALERTS_PER_CASE`) and compared five independent
builds' SHA-256 digests directly: still identical every time. **Honest finding, not a gap
papered over:** the card's own caveat anticipates exactly this ("if it does not, the query
is returning one row and the test is too small — enlarge it, that is the finding") — here
enlarging to the realistic ceiling still didn't trigger it, because Postgres chose a stable
index/seq scan for this `alert_id IN (subquery)` shape at every scale tried within one
session, never a hash plan whose bucket order would vary. The `ORDER BY` is restored (it is
still required by design note 3's blanket rule — every query explicit to a total order —
independent of whether this particular demonstration could observe its absence), and
`git diff` on the file shows no trace of the experiment.

**(b) "swap the truncation order to cut the timeline first."** Reordered the three cut
blocks in `build()` so `timeline_dropped` runs before `raw_log_8kb_to_4kb` and
`representatives_to_15_clusters`. `test_truncation_steps_fire_in_section_7_6_order` went
red: `AssertionError: assert ['timeline_dropped', 'representatives_to_15_clusters'] ==
['raw_log_8kb_to_4kb', 'representatives_to_15_clusters', 'timeline_dropped']` — and,
exactly as the card predicts, the *within-budget* half of the same assertion would have
stayed green (dropping the timeline first happened to bring this fixture under budget in
only two steps). Reverted; suite green again.

**(c) "move the previous-② block outside its wrapper."** Changed
`_block8_notes_and_previous` to append the previous-run body directly instead of through
`wrap.untrusted_block`. `test_every_free_text_block_is_wrapped_including_notes_and_
previous_run` went red: `Violation(kind='free_text', token='{"suggested_conclusion"',
line=92, count=11)`. Reverted; suite green again.

## 3 · Deviations from the card and why

1. **`STATE.md` is untouched**, though the card's own acceptance item 7 lists a STATE.md
   row in `git status --short` and its Report section says to set the row to `review`.
   Director 1's dispatch for this wave explicitly overrides this: *"STATE.md. Change
   nothing in it."* — the Director manages STATE.md centrally across the five parallel
   wave-2 worktrees, which is also why one Coder editing a shared file would conflict with
   the others. Followed the dispatch.

2. **Block 1's title and "who escalated" are wrapped, not `fact()`-ed**, though design
   note 1 lists them under "case header as facts." `cases.title` is analyst-supplied free
   text (`domain.transitions.escalate(..., title: str, ...)`), which `llm.builder.fact()`
   explicitly rejects (`TypeError: free strings are not allowed outside a block`);
   `cases.created_by` is a UUID, which matches none of `llm.builder.ID_PATTERNS`. Current
   code (the `fact()` type contract) wins over the card's literal wording per the
   dispatch's own precedence rule. Rendered instead as a small `context`-sourced wrapped
   block alongside the case's severity/cluster-count/occurrence-count/time-span facts,
   which *are* `fact()`-able and are rendered that way.

3. **Block 4 (entities) and block 6 (Tier-1 decisions) are wrapped wholesale**, although
   design note 1's summary sentence names only blocks 2, 3, 5, 7 and 8 as needing
   `security.wrap.untrusted_block`. Both are required by G6' regardless, and this is what
   design note 7's own acceptance test (`security.linter.lint` returns no violation)
   actually enforces: entity values (IPv4/IPv6 addresses, hashes, domains, usernames,
   hosts) match none of `llm.builder.ID_PATTERNS`, so `fact()` cannot render them, and
   `audit_events.event_type`/`actor_role` have no `FACT_NAMES` entry either. Context pack
   §7.1's own "always inside blocks" list independently names `agent.name` and
   `data.dstuser`/`srcuser` — two of the four entity-adjacent fields — confirming this
   reading rather than contradicting it.

4. **7-day entity history is computed only for the three entity families that map to a
   structured `alerts` column** — host → `agent_name`, username → `alert_user`, ipv4/ipv6
   → `srcip`/`dstip` (one combined SQL, since an IP can appear in either). md5/sha1/sha256
   and domain entities have no such column; their `count_7d` and `history` are `0`/`{}`
   rather than a free-text `LIKE`/regex scan of every alert's `raw_log`/`description` in
   the last 7 days, which design note 2 does not specify a query shape for and which would
   be unindexed and unbounded in cost. They still get their inventory lookup against
   `iocs` and, when absent, `llm.builder.SENTENCE_ABSENT` — never a blank field.

5. **`enrichment.lookups`'s three functions are not called directly** for entity
   inventory lookups; `dossier.py` writes its own bulk `= ANY(%s)` queries against
   `assets`/`identities`/`iocs` instead, matching their `status`/vocabulary conventions.
   Design note 2 requires "one SQL per entity type … never one query per entity," and
   `lookup_asset`/`lookup_identity`/`lookup_ioc` are single-row functions by design (P2-T08,
   `backend/tests/test_lookups.py`) — calling them in a loop would be exactly the
   per-entity query pattern the card forbids.

6. **Correlation's "clusters not already in the case" filter (design note 1, block 5) is
   applied at the samples level only**, dropping any correlation sample whose `alert_id`
   is already a head of this case. `domain.correlation.CorrelationSummary.rows` is
   pre-aggregated by `(rule_id, category, status)` and carries no `alert_id` to filter a
   grouped row on, and `domain/correlation.py` is out of this card's scope to edit (Files
   — modify names only `tier2/dossier.py`). Samples are the only place a concrete alert
   identity is ever named in that summary, so that is where the exclusion is applied.

None of these touch a frozen contract (§6) and none required a `DECISION_REQUEST`.

## 4 · Open questions / follow-ups

- **Red step (a)'s inconclusive result (§2.1)** is worth a second look once P5-T04 is
  built and a real 60k-token case exists: if a future dossier ever gets large enough that
  Postgres's planner switches to a hash-based plan for the heads query, the "every query
  explicitly ordered" discipline (already in place) is what protects against it — nothing
  to fix now, but worth knowing the demonstration itself never got to exercise that path.
- **`MAX_ALERTS_PER_CASE` is trusted, not re-enforced.** `dossier.build` does not cap the
  number of heads it reads; it relies on `domain.transitions.escalate` having already
  capped `case_alerts` at 200 rows per case when the case was created. This matches the
  card's own framing of the 200 cap as a guard rail enforced at escalate time
  (`domain/correlation.py`'s docstring), not something every later reader re-derives.
- **No Owner action is required for this card** — P5-tasks.md §4.1 lists none for T03,
  and nothing here touches `.env`, `conf/`, or any human-only step.
