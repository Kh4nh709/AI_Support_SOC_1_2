### 2.1 · Red steps, each shown red once and restored (DEC-025)

**(a) "remove `ORDER BY` from the entity query" — corrected in Review round 1.** The
first submission's §2.1 said this didn't go red because "Postgres chose a stable
index/seq scan… never a hash plan." **That explanation was wrong, and the Reviewer's
finding said why: every fixture in the first submission inserted heads in already-
ascending `alert_time` order, so physical heap order already matched the desired sort —
removing `ORDER BY` had nothing to disagree with.** The real test is a fixture whose
*insertion* order disagrees with the sort key. Two such tests now exist:
`test_heads_reverse_insertion_order_still_renders_chronologically` (4 heads inserted
latest-first) and `test_heap_move_between_builds_does_not_change_the_text` (a no-op
`UPDATE` moves one head's tuple between two builds of the same data). Stripping
`_HEADS_SQL`'s `ORDER BY alert_time, alert_id` turns **both** red:
```
test_heads_reverse_insertion_order_still_renders_chronologically:
  AssertionError: assert ['2000001.100001', ...] == ['2000004.100004', ...]
test_heap_move_between_builds_does_not_change_the_text:
  AssertionError: assert '## Case\n...' == '## Case\n...'  (texts differ)
```
Restored; both green again. The same technique also confirmed `_TIMELINE_SQL` and
`_TIER1_EVENTS_SQL`'s `ORDER BY` clauses matter:
`test_timeline_inserted_latest_first_still_renders_chronologically` and
`test_tier1_events_inserted_newest_first_still_render_oldest_first` both go red when
their respective `ORDER BY` is stripped (`assert 1445 < 1374`, `assert times ==
sorted(times)` failing) and pass restored. The module docstring's determinism paragraph
is corrected too (it no longer claims every query "ends in a primary key" — the
duplicate-spans query orders by its group key, `duplicate_of`, which identifies *its*
rows, not `alerts`' own PK).

**(b) "swap the truncation order to cut the timeline first."** Re-verified after the
`build()` rewrite (representatives selection and the timeline capping changed its shape
substantially). Reordering the three cut blocks so `timeline_dropped` runs first still
turns `test_truncation_steps_fire_in_section_7_6_order` red:
`AssertionError: assert ['timeline_dropped', 'representatives_to_15_clusters'] ==
['raw_log_8kb_to_4kb', 'representatives_to_15_clusters', 'timeline_dropped']`. Reverted;
suite green again.

**(c) "move the previous-② block outside its wrapper."** Re-verified. Still turns
`test_every_free_text_block_is_wrapped_including_notes_and_previous_run` red:
`Violation(kind='free_text', token='{"suggested_conclusion"', ...)`. Reverted; suite
green again.

## 3 · Deviations from the card and why

1. **`STATE.md` is untouched**, though the card's own acceptance item 7 lists a STATE.md
   row in `git status --short` and its Report section says to set the row to `review`.
   Director 1's dispatch for this wave explicitly overrides this: *"STATE.md. Change
   nothing in it."* — the Director manages STATE.md centrally across the five parallel
   wave-2 worktrees, which is also why one Coder editing a shared file would conflict with
   the others. Followed the dispatch. **Kept.**

2. **Block 1's title and "who escalated" are wrapped, not `fact()`-ed**, though design
   note 1 lists them under "case header as facts." `cases.title` is analyst-supplied free
   text (`domain.transitions.escalate(..., title: str, ...)`), which `llm.builder.fact()`
   explicitly rejects (`TypeError: free strings are not allowed outside a block`);
   `cases.created_by` is a UUID, which matches none of `llm.builder.ID_PATTERNS`. Current
   code (the `fact()` type contract) wins over the card's literal wording per the
   dispatch's own precedence rule. Rendered instead as a small `context`-sourced wrapped
   block alongside the case's severity/cluster-count/occurrence-count/time-span facts,
   which *are* `fact()`-able and are rendered that way. **Kept.**

3. **Block 4 (entities) and block 6 (Tier-1 decisions) are wrapped wholesale**, although
   design note 1's summary sentence names only blocks 2, 3, 5, 7 and 8 as needing
   `security.wrap.untrusted_block`. Both are required by G6' regardless. **Kept, refined
   in Review round 1 (should 9):** block 4's *lookup results* (found/not_found/skipped,
   and the criticality/privilege/reputation when found) are no longer inside that wrap —
   they are trusted, closed-set data from our own `assets`/`identities`/`iocs`, rendered
   through `fact()` (`lookup_asset`, `lookup_identity`, `lookup_ioc`,
   `asset_criticality`, `identity_privileged`, `ioc_reputation`) immediately after the
   wrap closes. Only the entity *value* itself (and its 7-day history breakdown) stays
   inside the wrap now — before this fix, a forged username inside `raw_log` could fake a
   "found, privileged" sibling line no reader could tell from a real one;
   `test_entity_lookup_fact_cannot_be_forged_from_inside_the_wrap` covers it.

4. **7-day entity history is computed only for the three entity families that map to a
   structured `alerts` column** — host → `agent_name`, username → `alert_user`, ipv4/ipv6
   → `srcip`/`dstip` (one combined SQL, since an IP can appear in either). md5/sha1/sha256
   and domain entities have no such column; their `history` is `None`, rendered as **"not
   computed"** (Review round 1 should 10 — the first submission rendered nothing
   distinguishable from a computed-and-empty result; `"none"` is now reserved for that
   case only). They still get their inventory lookup against `iocs` and, when absent,
   `llm.builder.SENTENCE_ABSENT` — never a blank field. **Kept, window changed:** the
   ruling in Review round 1 anchors the window *before* the case
   (`[earliest head alert_time − 7 days, earliest head alert_time)`) rather than
   `now() − 7 days` — deterministic regardless of when `build()` runs, and excludes the
   case's own alerts by construction. `test_history_window_is_anchored_before_the_
   earliest_head_not_now` and `test_history_window_excludes_the_case_own_alerts` cover
   both properties.

5. **`enrichment.lookups`'s three functions are not called directly** for entity
   inventory lookups; `dossier.py` writes its own bulk `= ANY(%s)` queries against
   `assets`/`identities`/`iocs` instead, matching their `status`/vocabulary conventions.
   Design note 2 requires "one SQL per entity type … never one query per entity," and
   `lookup_asset`/`lookup_identity`/`lookup_ioc` are single-row functions by design (P2-T08,
   `backend/tests/test_lookups.py`) — calling them in a loop would be exactly the
   per-entity query pattern the card forbids. **Kept, and now worst-wins (blocker 3):**
   `iocs`' PK is `(value, source)`, so `_bulk_ioc_lookup` now ranks
   `malicious > suspicious > clean` with `source` as the tie-break (a total order over
   physical row order, unlike `lookup_ioc`'s own bare `max()`), and skips a private
   address before it ever reaches the query (mirroring `lookup_ioc`'s C4 rule, replicated
   rather than imported — `tier2` may not import `enrichment`'s sibling `ingest` package,
   where the canonical `_is_private` lives).

6. **Correlation's "clusters not already in the case" filter — flipped in Review round
   1, per the Reviewer's ruling.** The first submission reused
   `domain.correlation.summarize_for_prompt` and applied the exclusion only at the
   samples level (rows, being pre-aggregated by `domain.correlation.rows_query`, carried
   no `alert_id` to filter on, and that query doesn't exclude the case's own alerts at
   all — so a case's own cluster could appear as its own "correlation"). **Blocker 4
   replaced this wholesale:** `dossier.py` now runs its own `_CORRELATION_ROWS_SQL` /
   `_CORRELATION_SAMPLES_SQL`, both carrying `AND alert_id NOT IN (SELECT alert_id FROM
   case_alerts WHERE case_id = %(case_id)s)` directly in SQL, both reusing
   `domain.correlation._WINDOW_PREDICATE` and `_params` by import (sanctioned by the
   Reviewer: *"Reuse domain.correlation's predicate constant by import if you can do so
   cleanly"*) so the ±2h/agent/user/srcip window can never drift from `escalate`'s own.
   `test_correlation_excludes_the_cases_own_clusters` /
   `test_correlation_finds_a_real_external_cluster` are the negative/positive pair.

None of these touch a frozen contract (§6) and none required a `DECISION_REQUEST`.
