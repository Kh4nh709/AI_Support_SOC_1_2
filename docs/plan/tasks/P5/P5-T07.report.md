## 3 · Deviations from the card and why

- **`case_detail()`'s heads carry only a "case-overview grid" column set — no `raw_log`, no
  `risk_score`, no `last_seen_at` — but design note 3 and this card's own acceptance tests need
  all three.** Measured against the merged `web/routers/tier2.py` (P5-T06, `55b760e`):
  `_HEAD_COLUMNS = ("alert_id", "rule_id", "severity", "description", "agent_name", "alert_time",
  "srcip", "category", "occurrence_count", "status")`. P5-T06's own report (§3) names this choice
  explicitly: "a practical set for a case-overview grid." Design note 3 of *this* card asks for
  "the heads with severity, the risk band (never the raw score...), occurrence_count and
  last_seen_at" and "raw_log escaped inside `<pre>`" — none of which `_HEAD_COLUMNS` carries.
  Read-first item 3's "call them, do not re-query" and the card's file scope (`tier2.py` is not in
  my "Files — modify" list, and P5-T06's file is explicitly scope-out) rule out fixing this by
  editing `tier2.py`. **Resolution:** `cases_pages.py`'s `_supplement`/`_enrich_heads` run one
  additional, read-only, G10-explicit-column query (`SELECT alert_id, raw_log, risk_score,
  last_seen_at FROM alerts WHERE alert_id = ANY(...)`) over the case's own head ids, merging the
  three fields into each head dict. This does **not** re-derive `list_cases`/`case_detail`'s own
  case/head listing SQL — that SQL is called unchanged — it supplements data that query does not
  carry. `list_cases()` itself (the case list page) needed no such addition: every field design
  note 2 asks for (`cluster_count`, `occurrence_count`, `last_analyzed_at`, ...) is already in its
  return shape.
- **The ongoing-cluster trigger is `head.status == "escalated_tier2"`, not `last_seen_at >
  last_analyzed_at` (`docs/phase-7-tier2.md` §P7-2, "Việc còn lại" item 3).** The doc's own
  wording is listed under "remaining work," not a settled contract, and it depends on
  `last_analyzed_at`, which only P5-T04 (② , wave 4, not merged into this tree and may be cut)
  ever populates — a page that "must work without" ② should not gate a Tier-1-visible signal on
  a field ② alone writes. `ck_alerts_h3_escalate_khong_seal` (schema.sql) guarantees `sealed_at
  IS NULL` for the whole span a head is `escalated_tier2` ("Cụm đang điều tra vẫn phải hút bản sao
  — D-C5"), so `status == "escalated_tier2"` is a reliable, ②-independent proxy for "this cluster
  is still absorbing duplicates," and it is what design note 3's own words ("still absorbing
  duplicates") describe more directly than the doc's `last_analyzed_at` comparison. `last_seen_at`
  is still shown in the label's own text (via the same supplementary query) for the analyst's
  benefit; it is not the trigger.
- **A one-row `users` lookup (`_username`) for the conclude form's 409 flash.** Design note 3
  requires the 409 flash to name "who concluded it and when"; `ConcludeConflict.concluded_by` is a
  bare UUID (`tier2/conclude.py`, unchanged). `_username` is a single `SELECT username FROM users
  WHERE user_id = %s`, not a second case/head query, and falls back to the UUID string if the
  lookup somehow misses (never raises).
- **P4-T05 (`alerts_pages.py`, `templates/{queue,alert}.html`) is not merged into this tree.**
  `STATE.md`'s own P4-T05 row reads `todo`, wave 2 (dispatched in parallel with this card, per
  DEC-151); `backend/app/web/routers/` and `backend/app/web/templates/` on `55b760e` do not
  contain it. The card's read-first list cites it for "the list/detail vocabulary, the OFFSET
  pager, the risk band rendered as a band" — since it does not exist to read, this card instead
  followed the closest merged precedent for the same conventions: `web/templating.py`'s own
  `band_class` filter and its docstring ("P4-T05's row class for a risk band") for the band
  rendering; `web/routers/tier2.py`'s own `offset`/`limit` bounds (`ge=0,le=2**31-1` /
  `ge=1,le=200` default `50`) for the pager, mirrored exactly on both page routes; and
  `web/routers/labels.py` / `templates/labels.html` (P6-T02, merged) for the page-router shape
  (`page_user` before the role gate, a `_page`-style render helper with `flash`/`status_code`,
  `<details>`/`<pre>` for raw text blocks).
- **Vietnamese status/conclusion labels are not defined in code anywhere on this tree.**
  `STATUS_LABELS`' three concluded values and the conclude form's three radio labels are
  `docs/phase-7-tier2.md`'s own "Ba kết luận" table (lines 335-337) verbatim: *"Không phải sự
  cố"*, *"Có vi phạm nội quy, không phải tấn công"*, *"Là sự cố thật"*. `"investigating": "Đang
  điều tra"` is this card's own choice (no doc gives an exact UI string for it), consistent with
  that same document's vocabulary (*"Trợ lý điều tra"*). `HEAD_STATUS_LABELS` (a head's own
  `alerts.status` while it belongs to a case) is likewise this card's own choice — no source names
  it.
- **No `STATE.md` row in this commit.** The Setup section's dispatch instructions state plainly
  "STATE.md. Change nothing in it," which supersedes the card's literal acceptance item 7 (written
  before this dispatch convention) — the same tension `P5-T06.report.md` §3 recorded and resolved
  the same way.
- **Owner actions after merge: none.** No migration, no `.env` key, no `conf/*` file, no manual
  step. `case_notes` already exists (migration 015); this card adds no schema.

## 4 · Open questions / follow-ups

- **The supplementary `_supplement` query duplicates one piece of information `tier2.case_detail`
  already half-computes** (P5-T06's report names `raw_log`/`risk_score`/`last_seen_at` as
  deliberately left out of a "case-overview grid"). If a later card gives `case_detail()` a
  richer, detail-specific column list (as opposed to the shared one `list_cases`/`case_detail`
  currently use), `cases_pages.py`'s `_supplement`/`_enrich_heads` become redundant and should be
  deleted in favour of reading the richer dict directly — flagged here so a future Reviewer or
  Coder does not have to re-derive this reasoning from the diff alone.
- **P4-T05 is not merged.** If its eventual `queue.html`/`alert.html` pager or risk-band markup
  differs in shape (e.g. a different `data-field` naming convention) from what this card used,
  the two page families will not look alike by accident — worth a pass for visual/markup
  consistency once P4-T05 lands, not a functional gap.
- Everything else: none.
