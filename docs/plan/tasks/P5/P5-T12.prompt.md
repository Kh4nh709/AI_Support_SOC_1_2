- **Design notes:**

  **1 · Not a compose cron, and the reason is on the record.** The schedule is a **user crontab** entry
  (a systemd timer is the sanctioned alternative — pick one, state which, and say why in the report).
  `conf/soc-backup.cron` is a committed, commented file the Owner installs with `crontab conf/soc-backup.cron`
  or pastes into `crontab -e`: one line at `BACKUP_HOUR` (02:00), running `backup.sh` from the repository root
  with the DSN sourced from `.env`, appending stdout **and** stderr to a log under the Owner's home, and
  `MAILTO=""` so a silent failure is not mailed into a void. DEC-018/DEC-021's reasoning is the whole point:
  a schedule that depends on a daemon this account may not be able to drive is a schedule that silently never
  runs, and a backup that silently never runs is worse than no backup because it is believed.

  **2 · Retention is 14 dumps, and the current script prunes by the wrong key.** `prompts/P5.md:36` says
  *"keep 14"*. `backup.sh` on `main` prunes with `find … -mtime +$RETENTION_DAYS` — and `RETENTION_DAYS` is
  **365**, the §6.3 key for **data** retention, not for backup files. As written, nothing is ever pruned and
  the two meanings are conflated. Replace it with **keep the 14 newest `soc-*.dump` files**, controlled by a
  shell-level `BACKUP_KEEP` defaulting to 14. **`BACKUP_KEEP` is not a §6.3 key**: §6.3 governs
  `infra/config.py`, `.env.example` is generated from it (`make lint` runs `gen_env_example.py --check`), and
  a variable only a shell script reads never enters that file — so this adds no frozen-contract surface.
  Say all of this in your report: it is a small change with a reason someone will otherwise re-litigate.
  `backups/latest.dump` stays tracked in git and is refreshed on every run (the Owner's 20/09 decision, in
  the script's own comment) — **it is not counted against the 14 and is never pruned.**

  **3 · `restore.sh` is the drill's tool, and it is deliberately not `make db-restore`.** `make db-restore`
  stops `app` and `worker` and replaces the **live** database — the right tool for a real recovery and the
  wrong one for a rehearsal, because a failed drill would then be an outage. `scripts/restore.sh <dump>
  [--into <dbname>]` instead: refuse to run unless the target database name is given and is **not** the one in
  `DATABASE_URL` (a rehearsal that can overwrite production is not a rehearsal — print both names and exit 2);

  P8's ten-line record is made of, so print it in a form that can be pasted.
