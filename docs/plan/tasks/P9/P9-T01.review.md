- **The snapshot really is the base parser's output.** All 56 corpus cases rebuilt with `ba7b070`'s parser are identical to `linux_parse_snapshot.json`. The snapshot has not changed since `4623a75`.
- **Security.**

  - `raw_log` is wrapped as untrusted text and capped for the prompt. `_truncate_raw_log` applies.
  - None of 2,973 real Windows documents uses the JSON fallback. The largest message is 2,279 B, and the largest `data.win` is 3,661 B.
- **Real data under HEAD's parser.** `raw_log` is non-empty for 2,969 of 2,969 Windows documents; the base parser gave 0. 511 get a `srcip`, all IPv6 link-local.
- **Tests.** T01's commit modifies no existing test. The filters for `-`, loopback and `$` accounts are tested.
- **Real fixtures:** waived by the Owner (DEC-152). The synthetic fixtures are marked `"_fixture": "synthetic"`.

## Findings and what was done
1. `enrichment/lookups.py:61` matches identities exactly and case-sensitively, but Windows names are case-insensitive. Today that errs strict. **No code change.** For P9-O1, the Owner writes Windows accounts exactly as Windows logs them.
2. `_win_json`'s docstring claimed totality, but a lone surrogate raises in `_truncate_raw_log`, just as it does for a `full_log`. It cannot reach production, because the `intake` jsonb cast rejects such a document. **Applied at merge:** the docstring now says so. A fix to `_truncate_raw_log` would be its own card, because it is shared with Linux.
