## Design notes — what is settled

  **1 · The trigger function and the six triggers. Settled; write them exactly like this.**

  ```sql
  CREATE FUNCTION raise_immutable() RETURNS trigger LANGUAGE plpgsql AS $fn$
  BEGIN
    RAISE EXCEPTION 'append-only table: % is immutable', TG_TABLE_NAME;
  END
  $fn$;

  CREATE TRIGGER trg_audit_events_immutable BEFORE UPDATE OR DELETE ON audit_events
    FOR EACH ROW EXECUTE FUNCTION raise_immutable();
  CREATE TRIGGER trg_llm_runs_immutable     BEFORE UPDATE OR DELETE ON llm_runs
    FOR EACH ROW EXECUTE FUNCTION raise_immutable();

  -- DEC-016, retained by DEC-020: a row trigger does NOT fire on TRUNCATE
  CREATE TRIGGER trg_audit_events_no_truncate BEFORE TRUNCATE ON audit_events
    FOR EACH STATEMENT EXECUTE FUNCTION raise_immutable();
  CREATE TRIGGER trg_llm_runs_no_truncate     BEFORE TRUNCATE ON llm_runs
    FOR EACH STATEMENT EXECUTE FUNCTION raise_immutable();
  CREATE TRIGGER trg_intake_no_truncate       BEFORE TRUNCATE ON intake
    FOR EACH STATEMENT EXECUTE FUNCTION raise_immutable();
  ```

  `intake`'s **row-level** trigger is `⟨OWNER QUESTION 1⟩` — under DEC-020's fix it becomes a
  column-pinning trigger that permits an UPDATE touching only `processed_at`, `outcome` and
  `error`, not a blanket refusal. Do not write it until the DEC says which.

  **2 · The TRUNCATE trigger is not optional, and it is a different trigger.** DEC-016 found this by
  testing rather than reasoning, and DEC-020's adversarial verification reproduced it independently
  — it is the one part of DEC-016 that survived. Re-measured on a throwaway database today: with
  only the row-level trigger, `TRUNCATE audit_events` as the owner wipes the table with no error;
  with the statement-level trigger it raises `append-only table: audit_events is immutable` and the
  rows survive. Without it, one statement defeats G2 and G11.

  **3 · Conditional role creation. Settled in form, qualified in effect.**

  ```sql
  DO $$
  BEGIN
    IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'app_rw') THEN
      CREATE ROLE app_rw NOLOGIN;
    END IF;
  END
  $$;
  ```

  Measured today: `app_rw` exists here (`rolcanlogin=f`, `rolcreatedb=f`, `rolcreaterole=f`,
  `rolsuper=f`), `user1` is a member, `SET ROLE app_rw` succeeds. `user1` has `rolcreaterole = f`,
  so a **bare** `CREATE ROLE app_rw` fails outright — hence the `DO` block. But per DEC-020 the
  block is not a portability fix: on a cluster where `app_rw` is genuinely absent it fails with
  `permission denied to create role`. Say so in your report; do not present the migration as
  self-contained.

  **4 · The privilege list is explicit, never `GRANT ALL PRIVILEGES`.** Measured: with
  `GRANT SELECT, INSERT, UPDATE, DELETE`, `TRUNCATE` is never granted to `app_rw` and is denied
  even before any `REVOKE`. `GRANT ALL PRIVILEGES` **would** grant `TRUNCATE`, and a `REVOKE` naming
  only `UPDATE, DELETE` would not take it back. Acceptance proves the distinction on a table that
  is *not* append-only.

  **5 · The sequence grant, and why it is there.** v1 uses `GENERATED BY DEFAULT AS IDENTITY` for
  `rejected_alerts`, `jobs` and `audit_events`, and an IDENTITY sequence needs no separate grant —
  measured: `INSERT` as `app_rw` into an IDENTITY table succeeds with no sequence grant, while the
  same insert into a `bigserial` table fails with `permission denied for sequence …_id_seq`.
  `GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO app_rw` costs nothing and closes the
  gap if anyone ever adds a `serial`.

  **6 · Testing needs care with transactions.** Every failure below aborts the current transaction,
  so wrap each attempt in a `SAVEPOINT` (or use a fresh connection per case) and
  `ROLLBACK TO SAVEPOINT` after each expected error. `RESET ROLE` before setup and teardown.

  **7 · The residual weakening, for `docs/limitations.md` in P8 — and DEC-020 widened it.** Not "a
  session can `RESET ROLE`": measured, **all** of `RESET ROLE`, `SET ROLE NONE`, `SET ROLE user1`,
  `SET SESSION AUTHORIZATION user1` and `DISCARD ALL` (pgbouncer's default reset query, outside a
  transaction block) return a pooled connection to the owner, which can then `DROP TRIGGER`. Repeat
  this in your report as a one-line note for P8.

  **8 · Columns you must supply in test inserts** (measured — `NOT NULL` with no default):
  `audit_events`: `event_type`, `subject_id`, `actor_role`, and `ck_audit_actor_id_theo_role`
  requires `actor_id IS NULL` when `actor_role='system'`. `llm_runs`: `run_id`, `pipeline`,
  `subject_type`, `subject_id`, `system_prompt`, `user_message` — and
  `ck_llm_runs_pipeline_khop_subject` forces `('triage','alert')` or `('investigate','case')`.
  `intake`: `manager_id`, `source_alert_id`, `raw_payload`, `via`.

  **9 · Test as the owner against your own scratch database.** Not `soc_dev` (shared) and not
  `soc_test` (the conftest fixture drops and recreates it every session). Create `soc_p1t06`,
  migrate it, assert, drop it. `CREATEDB` is granted (DEC-008, re-measured today).
