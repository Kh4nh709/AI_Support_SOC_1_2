## Migration conventions — every migration in `docs/Schema/` follows these
- The file opens with a comment block, then a standalone `BEGIN;` line, and ends with a standalone `COMMIT;` line — exactly like `001`–`012`. Verified: every one of the twelve has exactly one of each. `docs/Schema/build_schema.py` strips the **first** standalone `BEGIN;` and the trailing `COMMIT;` when it concatenates, so do not put a second standalone `BEGIN;` line anywhere in the file.
- The last statement before `COMMIT;` is `INSERT INTO schema_migrations (version) VALUES ('<file stem without .sql>');`. Migrations `001`–`007` do this; `008`–`012` forgot to and `scripts/migrate.sh` compensates for them only (DEC-008). Yours must record itself or it re-applies on every run.
- Name every constraint explicitly (`CONSTRAINT ck_… CHECK (…)`, `CONSTRAINT uq_… UNIQUE (…)`). An unnamed constraint gets a generated name that a later migration cannot drop by name.
- New surrogate keys use `bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`, matching v1 — **never `serial`/`bigserial`**. Measured on this cluster: with the grants migration 017 issues, `INSERT` as `app_rw` into an `IDENTITY` table succeeds and into a `bigserial` table fails with `permission denied for sequence …_id_seq`. Every P1 test runs as the owner, so a `bigserial` would pass here and break the application in P2.
- **You are P1-T07, so the "never run `build_schema.py`" rule that the five migration cards carry is inverted for you**: running it exactly once, and committing the result, is your deliverable. You still never hand-edit `docs/Schema/schema.sql`, and you still never edit a `[0-9][0-9][0-9]_*.sql` file.
