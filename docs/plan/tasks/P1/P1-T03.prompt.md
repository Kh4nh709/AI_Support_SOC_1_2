- **Design notes:**

  **1 · The DDL, transcribed from §6.1.**

  ```sql
  CREATE TABLE intake (
    intake_id        bigint      GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    manager_id       text        NOT NULL,
    source_alert_id  text        NOT NULL,
    raw_payload      jsonb       NOT NULL,   -- G9: byte-identical to what was read
    sort_key         bigint,                 -- indexer `sort`; computed for replay rows (DEC-019)
    via              text        NOT NULL,
    received_at      timestamptz NOT NULL DEFAULT now(),
    processed_at     timestamptz,            -- G12: this or `error`, within 60 s
    outcome          text,
    error            text,

    CONSTRAINT uq_intake_manager_source UNIQUE (manager_id, source_alert_id),
    CONSTRAINT ck_intake_via     CHECK (via IN ('pull','webhook')),
    CONSTRAINT ck_intake_outcome CHECK (outcome IS NULL
      OR outcome IN ('alert','duplicate','auto_closed','heartbeat','rejected'))
  );

  CREATE TABLE source_cursor (
    manager_id   text PRIMARY KEY,
    last_sort    bigint,
    last_pull_at timestamptz,
    last_error   text
  );

  CREATE TABLE source_heartbeat (
    manager_id    text PRIMARY KEY,
    last_seen_at  timestamptz,
    last_alert_at timestamptz
  );
  ```

  **2 · `intake_id` is `IDENTITY`, not `bigserial`.** Measured on this cluster: with the grants
  migration 017 issues, `INSERT` as `app_rw` into an `IDENTITY` table succeeds and into a
  `bigserial` table fails with `permission denied for sequence …_id_seq`. Every test in P1 runs as
  the owner, so a `bigserial` here would pass every acceptance line in this card and break the
  application in P2. v1 uses `IDENTITY` for `rejected_alerts`, `jobs` and `audit_events`; match it.

  **3 · `outcome` and `processed_at` are nullable, deliberately.** A row is inserted the moment it
  is read and is only later resolved; G12 is what forces a value within 60 s, and G12 is a health
  check in P5, not a DB constraint. The CHECK therefore has to admit NULL — `outcome IN (…)` alone
  would reject every freshly inserted row.

  **4 · `sort_key` is nullable and is not the key.** Live rows take the indexer's `sort` value;
  replay rows have no `sort` and P2 computes epoch-millis of the alert's own timestamp (DEC-019).
  Neither is unique and neither identifies a row — `uq_intake_manager_source` does that.

  **5 · Do not add a foreign key from `intake` to `alerts` or back.** §5's diagram reads
  `intake ||--o| alerts`, but §6.1 gives `alerts` no `intake_id` column and gives `intake` no
  `alert_id`. The link is carried by `jobs('pipeline', intake_id)`. Adding an FK would be a §6.1
  extension; if you think one is needed, that is a `DECISION_REQUEST`, not a judgement call.

  **6 · Do not add any GRANT, REVOKE or trigger to `intake`.** Migration 017 owns the append-only
  enforcement, and it is currently **blocked**: DEC-020 found that §6.1's
  `REVOKE UPDATE, DELETE ON … intake FROM app_rw` contradicts **G12**, because `processed_at`,
  `outcome` and `error` are written by an UPDATE after the pipeline job runs. That is an Owner
  question about §6.1's wording, not something 014 works around. Create the table with its
  constraints and nothing else; whatever the Owner rules, 017 applies it on top without touching
  your file.

  **7 · Test as the owner against your own scratch database.** Do not use `soc_dev` (shared) or
