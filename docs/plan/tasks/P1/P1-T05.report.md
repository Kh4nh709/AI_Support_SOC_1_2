## 3. Deviations

**From the card's DDL: none.** The five ALTER blocks are the card's text, in its order, including the order
of the 27 event names. Four judgement calls the card pre-decided and this migration follows without
extending: `role` nullable with a NULL-admitting CHECK; `stopped_by` with no CHECK; `manager_id` and
`origin_host` nullable; `suggestion_visible NOT NULL DEFAULT true`.

Three things the card asked to be **recorded**:

1. **`DROP COLUMN IF EXISTS sampled_for_control` dropped nothing.** psql printed
   `NOTICE: column "sampled_for_control" of relation "alerts" does not exist, skipping` and the migration
   exited 0. This is DEC-022 option A: the migration states the contract, and here it is a verified no-op.
   The INBOX `DECISION_REQUEST` of 2026-09-05 on this clause is **already resolved** (DEC-022) — I opened
   nothing new.
2. **`cost_usd` stores per-call cost ROUNDED.** `numeric(10,5)` is $0.00001 granularity. One trivial
   `deepseek-v4-flash` call at about $0.0000287 is stored as `0.00003` — asserted by
   `test_cost_usd_stores_a_real_per_call_cost_rounded_to_five_places`, which is where P3 will find it
   written down. **Any total that needs precision must be summed from `input_tokens`/`output_tokens`,
   not from `cost_usd`.**
3. **No database anywhere held a `job_type='enrich'` row**, so the `ADD CONSTRAINT` never had to refuse to
   validate and no `NOT VALID` was considered. If some future database does hold one, `ADD CONSTRAINT`
   will fail there and that is the correct behaviour.

**Prompt vs `P1-tasks.md`: no disagreement to report** (DEC-007 item 7). The Planner's §P1-T05 section, its
task-table row, its "Planning decisions" line on `ck_jobs_job_type`, and the INBOX/DEC-022 entry all say
what this prompt says. Nothing had to be reconciled.

**One deliberate wording change inside the migration's own comments.** The card's conventions describe a
header saying which migration this runs after. Writing "Runs after 015" would assert a dependency that does
not exist — 015 is P1-T04's file, dispatched in parallel and off the P1 exit gate (DEC-029). The header says
instead that 016 runs after 014 and does not depend on 015, because the two files touch no common table, so
either merge order works. Behaviour is unaffected: `migrate.sh` applies files in glob order and skips what
`schema_migrations` already records.

**Files touched: exactly the two the card lists, plus the two the Report section mandates**
(`docs/plan/tasks/P1/P1-T05.report.md`, and the `P1-T05` row of `docs/plan/STATE.md` set to `review`).
`docs/Schema/schema.sql` was not regenerated and is untouched — `build_schema.py` was never run without
`--check`.

## 4. Open questions / follow-ups

1. **For P1-T07.** `docs/Schema/schema.sql` is now behind by one migration on this branch, so
   `python3 docs/Schema/build_schema.py --check` exits 1 on `main` from the first P1 merge until T07
   regenerates it. Expected, per the card's conventions; not a defect of this task. Nothing else in
   `make lint` or `make test` reads it.
2. **For P1-T06 (017).** 016 adds columns to `llm_runs` and `audit_events`, two of the three tables 017
   makes append-only. The pinning triggers 017 installs are row-level and column-agnostic, so merge order
   between 016 and 017 does not matter — but 017's tests, if they enumerate `llm_runs` columns, will see
   eight more of them after 016 merges.
3. **For P3.** Two contract facts this migration fixes in the database, both worth knowing before writing
   ①/②: `cost_usd` is rounded (deviation 2 above), and `llm_runs.role` admits NULL — a run that omits
   `role` is legal, so P3 must not rely on the column being populated for v1-era rows.
4. **No `enrich` job type exists any more.** Any P2+ code or document still naming an `enrich` job is now
   wrong against the database, which will refuse the insert. Nothing in `backend/` is affected today:
   `grep -rn job_type backend/` matches only `test_schema_v3_016.py`, and every `enrich` hit under
   `backend/app/` is the enrichment *stage* (`soar/pipeline.py`, `soar/risk.py`, `enrichment/`), not a job
   type. The string survives only in v1 design documents, in 016's explanatory comment, and in the negative
   test that proves the database now refuses it.
