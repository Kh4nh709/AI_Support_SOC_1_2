## DEC-025 — the demonstrated failing case for each load-bearing item

A green command that cannot go red is not evidence. Four counterfactuals were run rather than
reasoned about:

1. **The whole test module goes red without the migration.** Moved
   `docs/Schema/014_intake_cursor_heartbeat.sql` out of the tree, re-ran acceptance 10 → **32
   failed**, every one on `psycopg.errors.UndefinedTable: relation "…" does not exist` (the last
   being `source_heartbeat`). Restored; `git status --porcelain` empty. This confirms the Coder's
   claimed RED and, more importantly, that the `db` fixture really migrates from this worktree's
   `docs/Schema/` — the tests are not asserting against a stale database.

2. **The byte-compare control is real: a plain `jsonb` column could not pass the claim.** Built
   `CREATE TABLE counterfactual (id int primary key, raw_text jsonb NOT NULL)` on the migrated
   scratch database and round-tripped both fixtures through it:
   ```
   indexer_sample_rule5503.json: byte-identical? False   in=3035  out=2462
   archive_line_5503.json:       byte-identical? False   in=2889  out=2336
   ```
   Reproduces the report's extra-evidence numbers exactly. Also checked that the control
   (`payload_text != raw_text`) is not passing for the trivial reason of a trailing newline:
   with the newline stripped, `jsonb` still does not reproduce either fixture's key order. So the
   claim assertion discriminates, and this is the acceptance item that would have gone green
   against an unimplemented G9.

3. **The IDENTITY assertion discriminates `bigserial`.** Two throwaway tables on the same cluster:
   ```
   cf_ident |YES|BY DEFAULT|<null>
   cf_serial|NO |<null>     |nextval('cf_serial_intake_id_seq'::regclass)
   ```
   Acceptance 6's `is_identity` and the test's three-way `(is_identity, identity_generation,
   column_default)` both go red on a `bigserial`. Design note 2's failure mode is genuinely caught
   by an owner-run test, which was the open question.

4. **The self-recording `INSERT INTO schema_migrations` is load-bearing.** Deleted the
   `014_intake_cursor_heartbeat` row from the scratch database and re-ran `scripts/migrate.sh` →
   `migrate: applying 014_intake_cursor_heartbeat` then
   `ERROR: relation "intake" already exists`, **exit 3**. Restored the row → `migrate: 0 applied,
   13 already present`, exit 0. Acceptance 1's `0 applied` and acceptance 11's third grep therefore
   both have a real failing case; without the statement the migration re-applies and breaks every
   subsequent run.

Acceptances 3, 4, 5 and 9's `not json` line carry their failing case inside themselves — each is a
paired reject/accept, and I observed both halves with their exit codes. Acceptances 2, 7 and 8 are
direct catalogue reads whose expected values are exact (`11`, a 4-name list, `0`), so any added
column, relaxed `NOT NULL` or added foreign key moves them; item 1's counterfactual already showed
these queries returning nothing when the tables are absent. Acceptance 13's empty output is
corroborated by a second, independent signal (`--name-status`) rather than trusted alone, which is
the `diff a b && echo IDENTICAL` trap.
