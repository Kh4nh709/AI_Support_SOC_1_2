**Public functions — SQL.** `raise_immutable() RETURNS trigger` — raises `append-only table: <table> is immutable`; used by six of the seven triggers (UPDATE/DELETE on `audit_events` and `llm_runs`, DELETE on `intake`, TRUNCATE on all three). `intake_pin_receipt() RETURNS trigger` — rejects any change to an `intake` payload column (`payload columns are immutable`) and any change to `processed_at`/`outcome`/`error` once that column is non-null (`receipt columns are pinned once set`).

**Public functions — Python.** None; the file is tests. Four module-level helpers: `_run(db, sql, params, role)` runs a statement inside a SAVEPOINT, optionally under `SET ROLE`, and returns the psycopg error or `None`; `rejects()` / `accepts()` wrap it with the expectation; `seed()` inserts as the owner and `seed_as_app_rw()` inserts through `app_rw` (see acceptance 12 — that distinction is what stops eleven of the tests from being silently green).

### The seven triggers and what each one closes

`trg_audit_events_immutable`, `trg_llm_runs_immutable` (BEFORE UPDATE OR DELETE, FOR EACH ROW) · `trg_intake_pin_receipt` (BEFORE UPDATE, FOR EACH ROW) · `trg_intake_immutable` (BEFORE DELETE, FOR EACH ROW) · `trg_audit_events_no_truncate`, `trg_llm_runs_no_truncate`, `trg_intake_no_truncate` (BEFORE TRUNCATE, FOR EACH STATEMENT — a row trigger does not fire on TRUNCATE, DEC-016).

raises `migration 017: role app_rw does not exist on this cluster`. That block is the

design note 3 ("017 therefore **creates `app_rw` when it is absent**, inside a `DO … IF NOT
EXISTS` block", explicitly marked *SUPERSEDED BY DEC-024(a)*), acceptance 1 (`grep -c 'CREATE
ROLE'` → **`1`**, "It was `0` until 05/09"), and context pack §6.1 ("Migration 017 **creates
`app_rw` as `NOLOGIN`** when `pg_roles` shows it absent"). I implemented design note 3: create
NOLOGIN when absent, and on `insufficient_privilege` stop with `migration 017: role app_rw does
not exist and this migrator cannot create it`, HINT naming HUONG-DAN §0. Everything else in the
block is transcribed unchanged. This is DEC-025's propagation gap surviving in one more place —
the card's own design note 3 records it being fixed, but the SQL listing above it was not
updated to match. **The listing should be corrected before the next card copies it.**

**2 · The header comment block is rewritten, not transcribed.** The card's two-line header says
the migration "Needs role app_rw to exist on the cluster (cluster-global; created once by a

## 4. Open questions / follow-ups

**The two `docs/limitations.md` lines (design note 10), to carry into P8:**

> (a) `app_rw` also holds legacy grants on the v1 `soc` database; making it LOGIN exposes `soc`
> to the same password, `DATABASE_URL` points only at `soc_dev`, and revoking `CONNECT` on `soc`
> needs `postgres`.
>
> (b) The owner's socket session is passwordless and can `DROP TRIGGER`: append-only is enforced
> against the application, not against whoever holds the `user1` OS account.

**Re-measured on this build, and DEC-024(b) says P8 must carry the three-way result verbatim
rather than a summary — so here it is, reproduced against 017 as merged** (one table carrying
both layers, three deletes):

1. as `app_rw` → `ERROR:  permission denied for table audit_events`
2. as `user1`, superuser, no trick → `ERROR:  append-only table: audit_events is immutable` — **the trigger fires**
3. as `user1` with an explicit `SET session_replication_role = 'replica'` → `DELETE 2`, 0 rows left

`DROP TRIGGER trg_audit_events_immutable ON audit_events` as the owner also succeeds. So the
precise claim is the one DEC-024(b) corrected me toward in advance: the privilege layer does not
bind the owner, **the trigger still does**, and defeating it takes one deliberately named
statement that has no other reason to appear in this codebase. The owner cannot breach
append-only by accident.

**Follow-up 1 — the card's design-note-1 SQL listing is stale.** See deviation 1. Not a blocker
for this task; it is a live trap for anyone who copies that block.

**Follow-up 2 — `IS DISTINCT FROM` pins the value, not the write.** Found while writing the
tests, not stated in the card. Re-writing a receipt column with the value it already holds is
**not** rejected — the trigger compares values. Two consequences: (i) a P2 job retried after an
ambiguous failure may safely re-assert the receipt it already wrote, which is the behaviour you
want; (ii) `UPDATE intake SET processed_at = now()` twice *inside one transaction* is accepted,
because `now()` is the transaction timestamp and the second write is a no-op. The card's
acceptance 7 shows it rejected only because each `psql -c` is its own transaction. Pinned down
by `test_rewriting_a_receipt_column_with_the_value_it_already_holds_is_not_a_change`. No change
requested — this is the correct semantics, it was simply undocumented.

**Follow-up 3 — design note 6's open question stands, untouched.** If P2 needs `error`
re-writable while `processed_at IS NULL`, that is one condition in `intake_pin_receipt()` and a
DECISION_REQUEST. `test_a_still_null_receipt_column_may_be_filled_after_an_error_was_recorded`
records today's behaviour: after an `error` is written, `processed_at`/`outcome` can still be
set, but `error` itself cannot be overwritten.

**Follow-up 4 — the `insufficient_privilege` path is untestable on this host.** `user1` is a
superuser, so the loud-failure branch cannot be exercised. It is transcribed, not measured.

**Nothing blocks P1-T07.** `docs/Schema/schema.sql` is untouched by design; T07 regenerates it.
