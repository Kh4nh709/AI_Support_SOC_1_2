The Jinja routes, `_parse_day`, `_render_*` and every template are untouched. `DigestRow`, `build`, `review` and `to_csv` are

**`GET /api/admin/digest?day=YYYY-MM-DD`** answers `{day, today, rules_enabled, rows: [DigestRowOut]}`.
- `day` absent is today in `cfg.DISPLAY_TZ`; `?day=` present but empty is a bad day. `today` is that zone's date from the process
  clock (the page's own `_today_local`).
- `_strict_day`: `[0-9]{4}-[0-9]{2}-[0-9]{2}` by `fullmatch`, then `date.fromisoformat`. A bad day is
  `422 {"detail": {"reason": "bad_day"}}` before any SQL.
- `DigestRowOut` (Pydantic) is every `DigestRow` field plus `reviewed_by_name` and `reviewed_at`; both `null` while unreviewed. The
  name is `users.display_name`, or the username when the display name is blank, from one query for all reviewed rows
  (`digest.review_details`, `LEFT JOIN users`).
- `rules_enabled` is `EXISTS (SELECT 1 FROM autoclose_rules WHERE enabled)` (a rule disabled after it closed clusters does not hide
  them; the rows are listed whatever the flag says).

**`POST /api/admin/digest/{alert_id}/review`**, body `{day, verdict}` (`ReviewIn`, a Pydantic model).
1. `day` not a strict day → `422 {"reason":"bad_day"}`; `verdict` not one of the three → `422 {"field":"verdict","reason":"invalid"}`
   (the day is judged first). Both fields are `Any` in the model and judged by the route, so a missing or mistyped value gets the same
   reason as a wrong one.
2. `build(day)` has no row for the alert → `404 {"reason":"not_in_digest"}` (see Deviation 2 for the one case that is a 409).
3. `digest.review(conn, alert_id, verdict, reviewer_id=claims.user_id)`. `AlreadyReviewed` → `409 {"reason":"already_reviewed","row":
   DigestRowOut}`, the row read again after the conflict (carries the verdict, reviewer and time on file); any other `StaleState` →
   `409 {"reason":"not_auto_closed"}`.
4. `200 {"row": DigestRowOut, "reopened": verdict == "wrong"}`, the row read after the review. After `wrong` the alert has left
   `build`, so the row is the pre-review snapshot with the verdict, reviewer and time read from `autoclose_reviews`.

Both routes take `claims: Admin` (`require_admin`, a module name so a test can assert the dependency on each route).
`alert_id: deps.AlertId`. Errors are `HTTPException(detail={"reason": ...})`: fixed codes, no driver text, SQL or DSN.

**Commit before raise, checked.** `digest.review`'s whole body is one `with conn.transaction():`, so `AlreadyReviewed` or `StaleState`
rolls its savepoint back and nothing it wrote survives; the route then raises (it does not return), so `deps.get_conn` rolls the
request back too. The page `rollback()`s by hand only because it returns a response, which `get_conn` would commit. A test sends a
`wrong` verdict as the refused second review and asserts no event, no label, no reopen; the concurrency test runs the real
commit/rollback shape on its own connections.

## 4. Deviations

1. **Default day.** The Jinja page defaults to **yesterday** (`_yesterday_local`, the day the 08:00 job reviews). The JSON route
   defaults to **today** in `DISPLAY_TZ`, as spec §5.6 says; `today` is returned so the UI can offer both.
2. **(Superseded by fix round 1, F1: the 409 is now the exact variant below.) A review of an alert that is no longer `auto_closed` is `409 not_auto_closed`, not `404`, even though `build(day)` has no row
   for it.** Taken literally, step 2 (404 when `build(day)` lacks the alert) would make `not_auto_closed` reachable only in the
   microseconds between `build` and `review`: `build` lists only `auto_closed` alerts, and a row reopened by Tier 1 or by a `wrong`
   review leaves it at once, which is exactly what a stale page sends. Spec §4.5 maps `409 not_auto_closed` to "the buttons are replaced
   by the sentence". So the route asks `digest.alert_status` when `build` has no row: an existing alert in another status is
   `not_auto_closed`; unknown, synthetic, or `auto_closed` on another day is `404 not_in_digest`. The race window is still handled
   by `StaleState` (the lock test). If the Director wants the literal order, delete the `alert_status` branch and the two tests of
   a reopened alert become 404.
3. **`tier1/digest.py` gains three reads, not one.** The plan allows a reviewer-name join there. `rules_enabled` and `alert_status`
   went there too because `test_pages_digest.py::test_router_has_no_raw_sql` greps the router file for raw SQL.
4. **`test_path_id_guard.py` is edited.** `_id_paths_of(admin_digest) == {("post", ADMIN_REVIEW)}` would fail with the new route in the
   same module; it now lists both and checks `AlertId` on both endpoints, and four JSON tests are added.
5. **The API's day is stricter than the page's.** `_parse_day` (page, unchanged) accepts `20260930` and `2026-W40-3` through
   `date.fromisoformat`; `_strict_day` (API) accepts `YYYY-MM-DD` only.
6. **Two failure shapes stay FastAPI's own.** A JSON body that is not an object, malformed JSON, and a body with no JSON content type
   are `422 {"detail": [...]}` (the list FastAPI builds, which echoes the offending input). A missing or mistyped `day` or `verdict`
   inside a JSON object gets the route's `reason`.
7. **After `wrong` a second review of the alert is `not_auto_closed`, not `already_reviewed`** (the alert left `auto_closed`, and
   `digest.review` checks the status before the unique key). `already_reviewed` is for `correct` and `unsure`, whose alert stays
   auto-closed. The simultaneous test therefore uses `correct` and `unsure`.

Notes for the cards that use this API: `today` comes from the process clock, like the page; a pre-existing limit (P5-T08) remains: a
`wrong` review is keyed on the alert id alone, so an alert reopened and auto-closed again shows its old verdict and answers
`already_reviewed`. Running `python -m pytest` directly (not through `make test-db`) lacks the `PG*` variables, so
`test_pages_digest.py`'s four scratch-database tests error on `dropdb`; use the make target.
