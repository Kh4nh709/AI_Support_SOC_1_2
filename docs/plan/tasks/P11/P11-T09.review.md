### Findings

**F1 · Minor · `backend/app/web/routers/admin_audit.py:200-203`.** A payload number of more than 4,300 digits makes the whole page a 500.
- Cause: jsonb stores it, and `json.loads` raises `ValueError` (Python's integer-string limit), which `_payload` does not catch. This is the same failure class as deviation 3.
- Evidence (probe): `{"n": <5000 nines>}` plus one ordinary row gives `PROBE bigint-5000-digits status 500 Internal Server Error`.
- Reachability: no app writer can produce it, because Python's `str(int)` has the same limit. Only direct SQL can.
- Related, no action: numbers go through Python floats, so `0.1000000000000000055511151231257827` comes back as `0.1`.
- Fix: `except (ValueError, RecursionError):`. `PayloadTooDeep` and `JSONDecodeError` are both `ValueError`s. Add a test with a 5,000-digit number next to an ordinary row.

**F2 · Minor · `admin_audit.py:212-222`.** The size guard converts each payload to text two or three times: the CASE test, the ELSE branch and the size column. Under a Sort plan (a `subject` filter, or `group` through `ix_audit_event_type`) this happens for every matching row in the window, not for the 100 page rows.
- Evidence: `EXPLAIN (ANALYZE, VERBOSE)`, rows of 1.36 MB text and 11.7 KB stored, page limit 100:

  | Case | Time |
  |---|---|
  | 300 rows under `subject=BIG`, through the Sort | 2,293 ms |
  | 600 such rows | 6,199 ms, i.e. a 503 under the 3 s timeout |
  | newest 100 rows big, PK plan | 744–865 ms |
  | page first, then the text once per page row (`LATERAL (SELECT p.payload::text AS t OFFSET 0)`), `subject=BIG` | 530 ms |
  | the same, default page | 424 ms |
  | one conversion over 300 rows | 1.34–1.61 s |

- Reachability today: `ConcludeIn.reason` has no length cap (`web/routers/tier2.py:153-155`). A malicious tier2 insider could write large `tier2.concluded` payloads. The route then degrades to its specified 503 ("thu hẹp bộ lọc"); it does not crash.
- Fix: select the page first, with the inner `ORDER BY audit_id DESC LIMIT n`, then compute `payload::text` once per page row in a fenced LATERAL and derive both columns from it. Separately, a length cap on tier2 `reason` (500 characters, like tier1) is worth a card.

**F3 · Minor · `admin_audit.py:218` (join) and `:242-245` (actor filter).** `actor_username` is joined for any role. An `llm` row that carries an `actor_id` returns a username, and `actor=<username>` returns that `llm` row. Spec §5.8 says `null` for system and llm.
- Evidence (probe): `PROBE llm row actor_username: ana` and `PROBE actor=ana returns roles: ['llm']`.
- Reachability: no writer does this today (`tier1/triage.py:950` writes `llm` without an `actor_id`), though `ck_audit_actor_id_theo_role` allows it.
- Fix: `LEFT JOIN users u ON u.user_id = a.actor_id AND a.actor_role IN ('analyst','admin')`, and the same role condition in the username filter, plus a test. Alternatively, record that "null for llm" holds only for today's data.

**F4 · Minor · `backend/tests/test_admin_audit.py` (no test).** Deviation 9 (a database error other than a timeout stays a 500, with a generic body) is not pinned.
- Evidence: mutation m2, `except psycopg.errors.QueryCanceled` changed to `except psycopg.Error` so that every database error becomes a 503 timeout, gives `145 passed`.
- Fix: monkeypatch `_PAGE` to `SELECT 1/0 FROM audit_events a WHERE {where}`. With `TestClient(..., raise_server_exceptions=False)`, assert 500 and that the body carries no SQL. My probe got `500 Internal Server Error`.

**Inputs the spec implies that no test covers:** F1's big number, F3's `llm` row with an `actor_id`, F4's non-timeout page error, a page of many large payloads (F2), and control characters other than NUL and `\n` in a filter value. My probes show those control characters give 200.

**Break it one way: credential-like keys that still show:**

- access keys: `aws_secret_access_key`, `secret_access_key`, `access_key`, `AWS_ACCESS_KEY_ID`, `signing_key`, `encryption_key`, `hmac_key`, `master_key`, `client_key`, `license_key`;
- session and auth headers: `jwt`, `bearer`, `authorization`, `cookie`, `set-cookie`, `session_id`, `credentials`;
- key material: `private_key_pem`, `privkey`, `totp_seed`;
- connection strings: `connection_string`, `conn_str`, `database_url`;
- separators the rule does not drop: `api key`, `api.key`;
- Unicode and whitespace look-alikes: full-width `ＰＡＳＳＷＯＲＤ`, `ſecret` (long s), `pass​word` (zero-width space), `"password "`, `"token\t"`.

Caught as intended: `client.secret`, `db password`, `db.password`, `x-auth-token`, `smtp_password`, `bot_token`, `webhook_secret`, `jwt_secret`, `mfa_secret`, `user:password`, plus all 40 keys in the module's `CAUGHT_KEYS`.

**Break it the other way: innocent keys that get hidden:**
- flags: `is_secret`, `has_password`, `reset_password`, `must_change_password`, `requires_password`, `min_password`, `use_api_key`, `has_api_key`;

- pagination and protocol tokens: `page_token`, `next_page_token`, `csrf_token`;
- others: `top_secret`, `rotate_secret`, `edsn`.
