### Deviations judged

1. **`clock_timestamp()` instead of `now()`: accepted.**
   - The reasoning is right. `Conn`'s transaction begins at `auth.verify`'s `SELECT` inside `current_user`, so `now()` would be the moment before the admin-lock wait.
   - A login that completes during the wait gets `iat = time.time()` later than that moment and would pass `verify`'s `iat <= epoch` check.
   - `clock_timestamp()` is read when the `UPDATE` executes, after every lock is held.
   - No bad interaction with `verify`:
     - the stamp only moves later, so it can only kill tokens that predate the change;
     - a login after the change blocks on the target row (`SELECT … FOR UPDATE` against the change's lock) until the commit, so its `iat` is later than the stamp and it reads the new row.
   - Pinned: M13 below goes red.
   - CLI `deactivate` and `logout` keep `now()`. That is out of scope, and harmless there because `deactivate` also sets `is_active=false`.
2. **`404 {reason:"not_found"}`: accepted.** It matches the 409 shape and the other P11 routes.
3. **Added 422 shapes: shapes accepted, the content-type rule rejected in part.**
   - `body/invalid` for bad JSON, a non-object, an unknown key or a non-JSON type is fine, and nothing is echoed.
   - The claim "refused as FastAPI's own parsing would" is false for a body with **no** Content-Type. FastAPI 0.141.1's `strict_content_type=True` refuses it; this module parses it. See Finding 2.
4. **Cc and Cs refused in a display name, lone surrogate refused in a password: accepted.** Minor m2 proposes widening this.
5. **`ORDER BY username COLLATE "C"`: accepted.**
6. **No Pydantic request model and no `response_model`: accepted.**
   - FastAPI's own 422 echoes the rejected `input`, which may be a password, so hand validation is justified. The 36 validation cases cover it.
   - The cost is that the content-type handling FastAPI did for free is now hand-written, and weaker (Finding 2).
7. **Extra file `test_admin_users_routes.py`: accepted.** It puts the gate test in `make test`.

Items 8–10 of the report (draft-test changes, the CLI, baseline numbers) are notes. All accepted; the baselines match the brief.

### The actor re-check

**Ruling: a real hole for this spec, Important (Finding 1).**

- §5.1 gives the lock its purpose: "so two concurrent demotions cannot both pass". With three admins they do.
- The window is not a microsecond TOCTOU. The lock wait makes it deterministic in exactly the race the lock exists for:
  - the second request blocks on the first one's locks;
  - the first commits a demotion of the second request's actor;
  - the second then proceeds on its stale `require_role` result.
- The Coder's own ring test admits this outcome. After `A→B` commits, if `B→C` takes the locks before `C→A`, then B, already tier1, demotes C, and the test passes.
- The module docstring's premise (lines 6–7, "An actor is always an active admin") is exactly what fails.
- The last-admin invariant itself still holds.

**Smallest correct fix**
- `update_user` already holds the locked set. After the `last_active_admin` check, for a role or active-flag change, refuse an actor who is not in it.
- Placing it after `last_active_admin` keeps Review Focus 1's two-admin race answering `409 last_active_admin`.
- The route answers 403 `{"detail":"forbidden"}`, the contract `require_role` already has and P11-T12 already handles. It rolls back, writes `authz.denied` as `require_role` does and commits it, then raises.

The other write routes (create, reset, unlock, display-name-only PATCH) share the read-then-act shape of every admin route. That is m4, for P11-T20.

### Findings

**1. Important: a demoted or deactivated admin finishes a role or active-flag change.**

`backend/app/web/routers/admin_users.py:144-146` (`update_user`, after the guards), and the ring test at `backend/tests/test_admin_users.py:800-803`.

Evidence: scratch `test_review_p11t02.py`, direct `update_user` calls on committed data, as the Coder's race tests do.
- A demotes B and holds the transaction open.
- B's call (B demotes C) blocks for 1 s.
- A commits, and B's call goes through.
- Mutual case: A demotes B and B demotes A, with C present.

```
STALE-ACTOR b->c after a->b committed: False {'aabf…': ('admin', True), '3cc0…': ('tier1', True), '438e…': ('tier1', True)} 1
MUTUAL A<->B with C: None {'6ee6…': ('admin', True), '4aa3…': ('tier1', True), '5107…': ('tier1', True)} active admins: 1
```

Fix:

```python
class ActorNotAdmin(Exception):
    """The actor stopped being an active admin while this request waited on the locks."""

    if was_active_admin and not stays_active_admin and not others:
        raise UserConflict("last_active_admin")
    if ("role" in changed or "is_active" in changed) and actor_id not in active_admins:
        raise ActorNotAdmin(actor_id)
```

In the route: `except ActorNotAdmin: conn.rollback()`, then write `authz.denied` as `require_role` does, `conn.commit()`, and raise `HTTPException(403, "forbidden")`.

Tests:
- the sequential three-admin case, refused, with C unchanged and no event;
- the blocked-then-refused race;
- the ring test loosened to "exactly one refused (`last_active_admin` or not admin), one admin left".

Red step: remove the check and the new tests fail. Also update the module docstring.
