## 4. Deviations

None from the card's interfaces. Choices worth knowing:

1. **The key is added in the route, not in `_list_rules`.** `_list_rules` also feeds the Jinja page; leaving it alone is the surest way to keep the page's output as it was. The page still reads its own `width_pct_threshold` from `cfg`.
2. **`width_pct` and `width_threshold_pct` read the setting separately.** `rule_width_report` calls `config.load()` itself; the new field reads the request's `Cfg`. In production `Cfg` is `config.load()`, so they are the same number. They would differ only if a caller overrode `get_config`, as the override test does (that test checks the field alone; the second test uses the environment to check both together).
3. **Four additions beyond the card**: the `SimulateStats`-fields-unchanged test, the `width_pct`/threshold consistency test, the five-case bad-rule parametrisation (the card named one rule), and red step (d). The bad-rule cases also show the first red-run result "6 passed": they are negatives that hold before the change, and (d) is what proves they bite.
4. **A list-order assumption was wrong once.** Two rules inserted in one test transaction share `created_at`, so the list orders them by id; the test compares the set of ids. The route's order is unchanged.
5. **Tests live in `test_pages_rules.py`** (the card allows it). P11-T19 retires the page-only tests of that file; these API tests carry `/api/` paths and use only the fixtures the file keeps (`client`, `_insert_alert`, `_insert_rule`), but the fixtures' `pages.page_user` override line will need to go with the HTML routes.
6. Commit trailer: the card names `Co-Authored-By`; the session's attribution reminder also asks for `Claude-Session`. Both are on `404e40b`.

Observations, not changed: `simulate` and the tally read the 30-day window in two separate queries, so a row inserted between them could make `matched` and `clusters` disagree by one; the Jinja preview does the same. `matched` counts alert rows (clusters), not the sum of `occurrence_count`.

## 5. `_WHITELIST` described for P11-T14

`ingest/autoclose.py:55-70`. `_WHITELIST: Mapping[str, frozenset[str]]` maps **field → set of allowed operators**. It says nothing about value
types: those live in `_value_ok` and `_scalar_ok` (`autoclose.py:131-157`), so the TypeScript table has to carry both. The sets are `frozenset`s, so
their order is undefined: the table must fix its own operator order. Field order below is the dict's insertion order.

A rule's `match` is a JSON array of conditions; each is an object with **exactly** the keys `field`, `op`, `value` (any other key set is
rejected). `[]` is valid and matches everything.

| field | allowed operators | scalar value type |
|---|---|---|
| `rule_id` | `eq`, `in` | string |
| `category` | `eq`, `in` | string |
| `srcip` | `eq`, `in`, `cidr` | string |
| `dstip` | `eq`, `in`, `cidr` | string |
| `agent_name` | `eq`, `in`, `prefix` | string |
| `agent_id` | `eq`, `in`, `prefix` | string |
| `alert_user` | `eq`, `in` | string |
| `decoder` | `eq`, `in` | string |
| `dst_port` | `eq`, `in` | integer |
| `src_port` | `eq`, `in` | integer |
| `rule_level` | `eq`, `lte` | integer |
| `asset_criticality` | `eq`, `in` | string |
| `identity_privileged` | `eq` | boolean |
| `ioc_reputation` | `eq`, `in` | string |

**Value shape by operator** (`_value_ok`):

- `eq`: one scalar of the field's type (the third column).
- `in`: a **non-empty array** whose every element is a scalar of the field's type.
- `cidr`: a string that `ipaddress.ip_network(value, strict=False)` accepts. A bare address and a CIDR with host bits both pass, and so does IPv6.
- `prefix`: any string, the empty string included (an empty prefix matches every non-null value).
- `lte`: an integer, and only for `rule_level`.

**Traps for the form**:

- The integer fields (`dst_port`, `src_port`, `rule_level`) must be sent as JSON numbers; `"443"` is a `422`. A boolean is never an integer here.
- `identity_privileged` takes `eq` only, with `true` or `false`; it has no `in`.
- `asset_criticality` and `ioc_reputation` are free strings to the server. The values the pipeline produces are `high | medium | low | unknown` and `malicious | suspicious | clean | not_found | skipped` (`domain/alert.py:79,83`), so a select with those options is a convenience, not a constraint.
- A rule on `asset_criticality = high`, or on `ioc_reputation` `malicious` or `suspicious`, can never close a row: those are hard blocks, evaluated first. The preview's tally is what tells the admin so.
- The field and operator choices are validated again by the server (`422`, with `detail` the English `PermanentError` text of `simulate`, "simulate: match is outside the whitelist or malformed: ..."); the table only has to stop a bad pick, not guard.
