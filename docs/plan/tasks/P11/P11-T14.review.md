### New findings

**N1. Important — `useSubmitLatch`'s release on idle reopens too early and can fail to reopen at all.** `frontend/src/features/admin/useSubmitLatch.ts:33-35` (the `isIdle` effect); test `useSubmitLatch.test.tsx:115-135`.

- **Early reopen.** After `reset()` while a call is out, the effect releases the latch as soon as React renders idle, while the request is still out.
  - Reviewer's probe: `run("a")`, wait for pending, `reset()`, wait for idle, then `run("b")` returns `true` and the calls are `["a","b"]` with "a" still unresolved. Two writes are out at once.
  - The Coder's test at `:115-135` pins this behaviour.
  - Not reachable in RulesPage: cancel and Esc are disabled once `busy` renders, and the table is behind the modal. It is a hazard for any page that resets a mutation while its call is out.
- **Stuck shut.** If `reset()` lands in the same tick as `run()`, React never renders `isPending`, so `isIdle` never changes and the effect never fires. TanStack drops the per-call `onSettled` after a reset, so the latch stays shut after the call settles.
  - Hook probe: `run("a")` + `reset()` in one `act`, resolve, then `run("b")` returns `false`, with calls `["a"]` and `isIdle: true`.
  - Page probe: Confirm and Cancel of the toggle dialog clicked in one `act`. The dialog closes and the PATCH goes once. Then another rule's toggle is opened and confirmed: still 1 PATCH, and the dialog stays open. Every later toggle is dead until the page remounts.
- **Class.** Important. It is the same same-tick window as round-1 finding 1. The latch is the shared primitive the Director ruled every console write will adopt, so both of its guarantees have to hold: no second write while one is out, and never a dead control.
- **Fix.** Release on the request's own promise, with a per-call token, and drop the `isIdle` effect:

  ```ts
  const out = useRef<object | null>(null);
  const { mutateAsync } = mutation;
  return useCallback((variables, options) => {
    if (out.current !== null) return false;
    const token = {};
    out.current = token;
    const release = () => { if (out.current === token) out.current = null; };
    mutateAsync(variables, { ...options, onSettled: (...s) => { release(); options?.onSettled?.(...s); } })
      .catch(() => undefined)
      .finally(release);
    return true;
  }, [mutateAsync]);
  ```

  - The `mutateAsync` promise settles even after a `reset()`, so the latch reopens exactly when the abandoned call ends.
  - The token keeps a late `finally` from releasing a newer call.
  - The release in `onSettled` keeps "the caller may send again from its own onSettled".
  - Verified in a scratch copy: it passes 8 of the 9 existing hook tests, and both probes above come out right (stuck case: `run("b")` returns `true` after the settle; early case: `run("b")` returns `false` while "a" is out).
  - Replace the test at `:115-135` with: (a) after a reset, `run` returns false until the abandoned call settles, then true; (b) `run` + `reset` in one tick, then settle: `run` returns true.
  - A page test for Confirm + Cancel in one tick, followed by a working toggle, would pin the page side.

**Note (no finding): the same-tick tests catch regressions.** Two clicks inside one `act` reproduce the gap (MA and MB below). The single `act` matters for the preview: with bare clicks its own state update re-renders the button as disabled and hides a missing latch, as the fix-round report says.

Other paths checked:
- **Unmount while a call is out.** The late `release` only writes the dead component's ref (no setState). Probe: 0 `console.error` after unmount and settle. A remount gets a fresh, open ref. No early or stuck path.
- **A new `mutation` object between renders.** `mutateAsync` is the observer's bound `mutate` and stays the same across renders, so `run` stays the same too.

  - The latch is per component, not per mutation. That is conservative, never early, and never stuck.
  - Same behaviour when `setOptions` resets the observer on a `mutationKey` change: the latch waits for the real settle.
- **StrictMode.** The hook has no effects left. The ref is the same object across StrictMode's double render.
  - Probe under `<StrictMode>`: two runs in one tick give `[true,false]`; after the settle, `run("c")` is `true`; calls `["a","c"]`.
