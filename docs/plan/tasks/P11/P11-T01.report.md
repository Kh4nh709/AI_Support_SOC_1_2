## 4. Deviations

1. **`test_019_records_itself` keeps its name.** The ruling said to correct its message; the review file cites the name. Its docstring and
   message now claim only what it can see.
2. **Finding 6 also covers the `build_schema.py` check** of the 018 copy in the same test (same `assert returncode == 0` form; no DSN is
   involved, it is for consistency).
3. **Extra assertion in the upgrade test:** `schema_migrations` equals the set of file stems after the third run. Not asked; it checks the
   same thing as the third run from the table's side.
4. **Finding 5's test needs a superuser, not only the right to create roles.** It applies 019 as the session role over tables owned by the
   scratch role, which a role that is not a superuser cannot do. The skip says so. It also creates `app_rw` (NOLOGIN) when the cluster has
   none, because 017 creates it only when absent and the scratch owner cannot; `app_rw` is left in place (cluster-global, and any `migrate.sh`
   run on a fresh cluster creates it).
5. **Two helpers extracted, behaviour unchanged:** `_schema_without_019` and `_migrate`, plus the constants `SCHEMA_DIR` and
   `MIGRATION_FILES`. The upgrade test and the new test share them; they are in the finding 5 commit.
6. **`docs/db-docker.md:91` is annotated, not rewritten.** It sits in the dated cutover record of 20/09, where `0 applied, 17 already present`
   was true. The line now keeps that and adds "(17 was every migration on 20/09; on today's code `make migrate` ends at 19, see 'Restore on a
   fresh machine')". Line 52 holds the instruction and was rewritten.
7. **The finding 1 mask was applied to `scripts/restore.sh` in the worktree** (allowed by the ruling: "or restored after"), not to a copy
   outside the repo. `git checkout -- scripts/restore.sh` followed, and the file is clean in every commit but finding 7's comment edit.

Observations, not changed:

- **DELETE is still granted on a Compose-style applier.** The GRANT is a floor, not a ceiling. When the applier is the role 017's default
  privileges name (`soc` on Compose), those defaults also give `app_rw` DELETE on `settings`. The test pins "no DELETE" only for the other-role
  case, and 019's header says so. A hard "no DELETE" on the live database would need a `REVOKE DELETE` in 019; the ruling did not ask for one.
- **The sibling `test_018_records_itself` (and the 015 and 017 equivalents) have the blindness finding 2 describes:** they read the shared
  database built from `schema.sql`. 018 and the earlier files are applied on the live database already, so nothing is at risk; not touched.
