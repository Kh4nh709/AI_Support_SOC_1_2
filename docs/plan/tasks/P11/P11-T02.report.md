**Behaviour, by route** (all behind `Admin = Annotated[Claims, Depends(require_role("admin"))]`):

- `GET /api/admin/users` → `{"users": [UserRow]}`, `ORDER BY username COLLATE "C"`. One column list (`_COLUMNS`) feeds every read and every
  `RETURNING`; no `response_model`, so a column added to it would show in the response (red step c).
- `POST /api/admin/users` → `201 {"user_id"}`; `409 {"reason":"username_taken"}` from the `users_username_key` violation; the admin signs the
  `admin.user_created` row through `auth.create_user(actor_id=...)` (`actor_role='admin'`; the CLI keeps `system`/NULL).
- `PATCH /api/admin/users/{user_id}` → `200 UserRow`, through `update_user`:
  1. a change of `role` or `is_active` locks `SELECT user_id FROM users WHERE role='admin' AND is_active ORDER BY user_id FOR UPDATE`, then the
     target `FOR UPDATE`; a display-name-only change locks the target alone;
  2. values equal to the current ones are dropped; nothing left → return the row, write nothing, keep the sessions;
  3. an admin changing their own `role`/`is_active` → `self_change`; removing the only other active admin → `last_active_admin`
     (the target was an active admin, will not be, and no other id is in the locked list);
  4. `UPDATE ... RETURNING`, `sessions_invalid_before = clock_timestamp()` on a role change or `is_active → false`; `admin.user_updated`
     `{username, before, after}` over the changed fields only.
- `POST .../password` → `204`; `auth.admin_set_password` writes the hash and `sessions_invalid_before = clock_timestamp()` (own account allowed);
  event `{username, action:"password_reset"}`.
- `POST .../unlock` → `204`; `auth.unlock` clears `failed_logins` and `locked_until`; event `{username, action:"unlock"}`.
- Bodies are read by hand (`_json_object` dependency + small validators), not by a Pydantic model: FastAPI's own 422 echoes the rejected value in
  `input`, and its `detail` is a list. Reasons: `empty` (missing or null), `invalid`, `too_short` (`min: 12`), `too_long` (`max`). Only a malformed
  uuid in the path is FastAPI's own 422.

## 4. Deviations

1. **`sessions_invalid_before = clock_timestamp()`, not `now()`** (spec §5.1 says "= now()"). `now()` is the start of the request's transaction, which
   may have waited on the admin locks (or on the target row); a login completing after that start and before the change would hold a token
   newer than the stamp and survive a demotion, a deactivation or a reset. Pinned by a test and a red step. `infra/auth.logout` and `deactivate`
   (CLI) still use `now()`; they take no lock wait, and I left them alone (out of scope).
2. **`404` has an object `detail`**, `{"reason": "not_found"}`, like the other P11 routes' 404s in the plan (the task text says only "404").
3. **Added 422 shapes**: `{field:"body", reason:"invalid"}` for a body that is not a JSON object, bad JSON, a content type other than JSON (as
   FastAPI's own parsing would refuse it) and any key the route does not take; `max` on `too_long`; a missing or null field is `empty`. The reason
   set stays `too_short|too_long|invalid|empty`.
4. **Control characters and lone surrogates** in a display name, and a lone surrogate in a password, are `invalid` (they were a driver or argon2 500).
   Whitespace is stripped from the display name only; a password is never stripped.
5. **`ORDER BY username COLLATE "C"`**: "ordered by username" made independent of the database's locale.
6. **No Pydantic request model and no `response_model`** (see §1). The OpenAPI request bodies are written by hand with `openapi_extra`.
7. **An extra test file**, `test_admin_users_routes.py` (2 non-DB tests), so `make test` carries the admin gate test.
8. **The draft tests, what I changed**: the list test scanned the whole response text for `hash`/`password` (values of every user in the database
   too): replaced by a key check at any depth plus `$argon2`; the draft's `psycopg.connect` had no lock timeout (a broken guard would hang the
   suite): the race connections now carry `lock_timeout=20s`; the draft's "deactivated by the same race" test is sequential (it still proves the
   count) and is renamed for what it does; 403 is now shown for tier1 and tier2 and 401 for no token; the list ordering, the self no-op, the
   sole-admin count, the ring, the timing, the body/echo, the logs and the actor tests are new.
9. **`create_user` and the CLI**: unchanged in behaviour; `actor_id` is the only new parameter. The CLI's `set-password` still keeps the sessions
   (the break-glass path; the spec does not change it).
10. **Baseline numbers differ from the brief**: at `a530b6d`, without this card's files, `make test` here is `2172 passed` (brief: 2168). The
    DB-suite baseline matches the brief (1462 passed now = 1371 + 91).

## Observations for the Reviewer and the Director (not changed)

- **A stale actor.** `update_user` does not re-check that the actor is still an active admin: an admin demoted by a concurrent request, whose own
  request had passed `require_role` before that commit, can finish one more change (the last-admin count still holds). Every other admin route
  has the same read-then-act shape; closing it here would need the actor in the locked list and a reason the spec does not list.
- **Display names** are text but may hold bidi or zero-width format characters (`Cf`); only `Cc` and `Cs` are refused.
- `locked_until` is returned as stored, so it may be in the past; the users page decides what "locked" means.
- The list returns every user, with no pagination (spec §4.2: "the list is small").
