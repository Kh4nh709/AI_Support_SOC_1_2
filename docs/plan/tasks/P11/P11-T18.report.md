## 2. Scenario 8: how the unfrozen set is made, and `eval/`

`tier1/labels.py` takes its two paths from the repository its own code sits in (`REPO_ROOT = parents[3]`, read at request time).
So the answer is a copy of the code in another tree, with no change to the product:

- `scripts/ui_e2e_stack.sh` now makes `<state>/repo/` (mode 700, removed with the state directory on exit): `backend/app` (a copy of the
  backend's `app/`, or of `E2E_BACKEND_DIR`'s for a red step), `kb/` (a copy), and an **empty** `eval/`. The API and the worker run
  that copy (`PYTHONPATH=<state>/repo/backend`), so their `FREEZE_MARKER` and `CANDIDATES_PATH` are `<state>/repo/eval/...`.
- `frontend/e2e/adminFixtures.ts` is the only place that touches those files (`writeCandidates`, `writeFreezeMarker`). Every path is
  taken from `E2E_STATE_DIR`, resolved with `realpath`, and refused unless it is inside the state directory and the copy's
  `labels.py` is there.
- The scenario's first act, before any write, is to open `/admin/labels` and require the "no candidates" card (and not the frozen one).
  The repository's own set is frozen and has candidates, so a stack that read the real `eval/` would stop the test there with nothing
  written.
- The candidates file has the real file's columns, with marker values in `source`, `stratum`, `scenario_id`, `kind`, `truth_label`;
  the page and every answer are checked never to hold them (nor ①'s claim token), and `labels/next` is checked to answer with
  exactly the six keys and, for a cluster, exactly the nineteen of `VIEW_KEYS`.

Nothing under `eval/` was created, changed or deleted: `git status --short` shows only the files of this task, and
`git diff 311eaab --stat` (the whole tree) lists seven files, none under `eval/`. (The Bash tool of this session refuses any

## 5. Deviations, and what was not done

1. **The stack changed (test infrastructure, no product code).**
   - `scripts/ui_e2e_stack.sh`: seeds `e2e-admin` and `e2e-admin2` (role admin) beside the three users; three more run secrets
     (`E2E_ADMIN_PASSWORD`, `E2E_ADMIN2_PASSWORD`, `E2E_NEWUSER_PASSWORD`, the password the suite types for the account it creates),
     in `secrets.json`, in the log redactor and in the seed environment; and the scratch repository of section 2.
   - `scripts/ui_e2e_run.sh` generates and exports the three; `scripts/ui_e2e_scan.py` has them as needles (the scan now searches
     for 8 secrets of the run, it was 5).
   - `E2E_BACKEND_DIR` keeps its meaning (the backend whose `app/` runs); what runs is now always a copy of that `app/`.
   - `backend/tests/test_ui_e2e_scan.py`: three needle tests and a test that every needle of the scan is generated and exported by
     the run script and read by the stack script (R8 above). This is the only change under `backend/`, and it is a test.
2. **Scenario 4 is not reachable through the page with no help.** `update_user` answers `last_active_admin` only when the actor has
   stopped being an active admin between the role check and the locks (two admins acting at once), because a lone admin acting is
   always one of the admins and `self_change` answers first. Through a browser that is a race. The test makes the race
   deterministic: a `psql` transaction locks the active admin rows exactly as `update_user` does and demotes the page's own user in
   it without touching that user's sessions; the page's PATCH is held on the lock (`pg_stat_activity` says so); the transaction
   commits. The refused request, the 409 body, the dialog and its text are all real; the only thing the test does is the other
   admin's committed change. The page's list read after the refusal then gets a `403` (its user is Tier 2 for a moment), which the
   page survives, as the dialog stays. Scenario 4b is the same rule with two real requests and no help but the lock holder. The
   backend tests have the same race at the function level (`test_two_admins_demoting_each_other_at_once_leave_one_admin`).
3. **Scenario 3 takes a minute.** The server re-checks a socket's token every 60 s (`REVERIFY_INTERVAL_S`); the test waits for the
   server to close it rather than closing it from the page. The suite is about 1 min longer for it. (Everything the user did
   not do is the point: the page never acted, and the close code is `4401`.)
4. **The unlock answers `204`**, not `200`; the test says `204`.
5. **DEC-204 as the page shows it.** The brief says the audit page "shows no label or confidence of the label.created event". The
   page shows the two keys, valued `"[đã ẩn]"`: that is what the server sends (`redact` with `hide`). The test asserts the mark and
   the absence of the verdict, not the absence of the keys. If the Owner meant the keys to be gone, that is a backend change, not a
   change of this task.
6. **`fixtures.ts`** gained `Account` (a seeded user or `{username}` for the suite's own account), `apiGet`/`apiPatch`/`apiPut`,
   `psqlEnv`, `stateDir`, the exported `fillSecret`, and the two admins; `postAlert` takes `rule` and `inventory` (an asset row for
   the agent, so that the hard block "asset not in inventory" lets a rule close it). The v1.0 specs were not edited, and
   `src/e2eLoginFailure.test.ts` (which pins that `loginAs` and `signIn` clear the password field on a failed login) still passes
   with them: the new logins go through those two functions rather than through new ones.
7. **Not done: nothing of the ten.** `frontend/src/` was not touched. No real product bug turned up in `src/` or in the backend;
   the one surprise (the audit mark) is item 5. One thing to know for the merge: the spec imports its texts from `src/strings.ts`
   (as the v1.0 specs do), so a reworded string in the T20 frontend batches is followed by the spec, but a changed accessible
   name, region or `data-` attribute of a page (`data-cost`, `data-state`, `data-alert-id`, `data-audit-id`, the region names of the
   rules, labels and LLM pages) would need the spec's locator changed with it: run `make ui-e2e` after merging those batches.
