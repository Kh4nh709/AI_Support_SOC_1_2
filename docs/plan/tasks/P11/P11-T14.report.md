### 1 and 2 — a double click sent two writes (Important, and Minor)

**Cause.** TanStack Query 5 tells React that a mutation went pending through a `setTimeout(0)`. `disabled={mutation.isPending}` and the `!create.isPending` of `canCreate` are therefore one render late, and two clicks in the same
tick both pass. `mutate` was called straight from the click handler of "Tạo rule", of "Xem trước" and of the toggle dialog's confirm button.

**Fix.** `frontend/src/features/admin/useSubmitLatch.ts`, the shared hook the Director ruled: `const run = useSubmitLatch(mutation)`, `run(variables, options?)` returns a boolean.
- The latch is a ref, set before `mutate` and cleared in the call's `onSettled`. `run` returns `false` at once while a call is out, and the options of a call it turned away are never used.
- The caller's own `onSettled` is chained: the latch is released first, then it runs, so it may send again.
- One thing beyond the ruling: TanStack's per-call callbacks do not run when the mutation is `reset()` while the call is out (the observer is taken off it), which would leave the latch shut for good. The hook also releases the
  latch whenever the mutation goes back to idle, and a test pins it. **(Wrong: replaced in Fix round 2, N1, by a release on the request's own promise.)**
- `RuleCreate.tsx` uses it for the create and for "Xem trước", `RulesPage.tsx` for the toggle's confirm. `ConfirmDialog` is not changed.

### N1 — the `isIdle` release was wrong both ways (Important)

**Early.** `run("a")`, wait for pending, `reset()`, wait for idle, `run("b")` returned `true` while "a" was still on its way: two writes in flight. My own round-1 test pinned exactly that as the wanted behaviour.
**Stuck.** When `reset()` lands in the same tick as `run()`, React never renders the pending state, so `isIdle` never changes and the effect never fires; TanStack drops the per-call `onSettled` of a reset call, so nothing releases the latch.
On the page: Confirm and Cancel of the toggle dialog clicked in one `act` close the dialog and send one PATCH, and after that every toggle confirm did nothing until a remount.

**Fix.** The `isIdle` effect is gone. The latch is released on the request's own promise, with a per-call token (the shape the Reviewer verified):
`mutateAsync(variables, {...options, onSettled})` with `.catch(() => undefined).finally(release)`, where `release` frees the latch only if it still holds this call's token. The release in `onSettled` stays, so the caller may send again from its own
`onSettled`, and the token stops the first call's late `finally` from freeing the call the caller sent from that `onSettled`. The types and the comments are kept; the header comment now says why the latch does not watch the mutation's status.

**Tests.** The round-1 test "is released when the mutation is reset while a call is still out" is replaced by:

2. `is released when a call settles after a reset that came in the same tick as it`: `run` and `reset` in one `act`; `run` is `false` while the call is out and `true` once it settles.
3. (beyond the two asked) `is released when a call that was reset away fails`.
