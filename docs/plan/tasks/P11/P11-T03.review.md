### Findings

**I1 · Important.** The web accepts a model deadline that outlives the jobs' idle-in-transaction timeout. A late answer is then paid but never recorded, and the worker dies.

- **Where.**
  - The bound: `backend/app/infra/settings.py:44` (`"LLM_TIMEOUT_S": (10, 600)`), enforced at `backend/app/web/routers/admin_llm.py:81-82`.
  - The jobs' timeout: `backend/app/tier1/triage.py:165-166` and `backend/app/tier2/investigate.py:108-111` set `SET LOCAL idle_in_transaction_session_timeout = JOB_LOCK_TIMEOUT_S`, which is 300 s by default (`infra/config.py:147`).
  - The worker uses one connection for its whole life (`web/worker.py:38,51`).
  - `finish_job` runs in `except` (`infra/worker.py:96`).
  - `reclaim_stale` (`infra/jobs.py:171`) and `claim_job` (`jobs.py:106-110`) have no attempt ceiling.
- **How it happens.** A saved `timeout_s` of 301 to 600 lets one model call keep the job's transaction idle for longer than 300 s.
- **Evidence.** A scaled run of the real `worker.run_forever(..., once=True)` over a committed triage job:
  - `JOB_LOCK_TIMEOUT_S=2` stands for 300;
  - a saved `LLM_TIMEOUT_S` of 10 (inside the web bounds) stands for 600;
  - a stub client answering after 3 s stands for a model answering at 450 s.

  ```
  REVIEW-PROBE calls=[10] escaped=OperationalError: the connection is closed job=[(1, 'running', 1)] llm_runs_rows=0
  ```
  Control, with `JOB_LOCK_TIMEOUT_S=5`:
  ```
  REVIEW-PROBE calls=[10, 10] escaped=NoneType: None job=[(1, 'succeeded', 1)] llm_runs_rows=1
  ```
  Postgres's own reason, on the same server:
  ```
  IdleInTransactionSessionTimeout | terminating connection due to idle-in-transaction timeout
  ```
- **Consequences.**
  - The answered call is never written to `llm_runs`, so `month_spend_usd` undercounts and the cap can be exceeded.
  - The exception escapes `run_forever`, so the worker process dies.
  - The job stays `running`. After a restart, `reclaim_stale` re-queues it and `claim_job` raises `attempts` without a limit, so a model that keeps answering late is paid again on every cycle and never recorded. This last point is derived from the code; I did not run it.
- **Fix.** It needs a Director ruling, because the bound is the Owner's decision 2.
  - (a) **Preferred.** `_validate` takes `cfg` and refuses `timeout_s > min(600, cfg.JOB_LOCK_TIMEOUT_S - 60)`. The 422 reports that `max`, and spec §10 item 2 is amended to match.
  - (b) Alternatively, keep 600. Both `_raise_idle_timeout`s then set `max(cfg.JOB_LOCK_TIMEOUT_S, settings.BOUNDS["LLM_TIMEOUT_S"][1] + 60)` seconds, and the worst-case arithmetic in `tier2/investigate.py:19-33` is updated.
  - Either way, add the scaled probe as a test. It must show the answered call recorded and `run_forever` not raising.

### New findings

**N1 · Minor.** "Two sends" is wrong for ①.

- **Where.** DEC-202 item 1; the `infra/settings.py` module docstring (around lines 23–27); the `timeout_max` docstring.
- **Evidence.** `llm/triage.py:714-750`: `propose` and `verify` each make "one call ... at most one repair", so ① makes up to four sends. At the default ceiling that is 4 × 120 = 480 s of model time, above `JOB_LOCK_TIMEOUT_S` = 300.
- **Why it does not reopen I1.**
  - The adapter runs SQL before every attempt, which resets the idle-in-transaction timer, so each send stays well under 300 s.
  - `reclaim_stale` is called only by the worker's own loop (`infra/worker.py:60`), so with one worker it cannot reclaim a job that is still running.
  - ①'s four sends already existed with the `.env` value of 120.
- **Fix.** Correct the text: the bound protects each send; the total-time margin holds for ② and, for ①, only while there is one worker.

**N2 · Minor.** Below a job lock of 80 s, the floor cannot keep the invariant.

- **Where.** `infra/settings.py:101` (`timeout_max`).
- **Evidence.** With the real margin of 60 and the real floor of 10, a job lock of 8 s gives `timeout_max = 10`. With a stored 10 and a model answering at 9 s:
  ```
  RV2 stored=10 delay=9.0 lock=8: timeouts=[10] escaped=OperationalError job=('running', 1) llm_runs=0 took=9.0s
  ```
- **What it means.**
  - A single send outlives the session only when `JOB_LOCK_TIMEOUT_S` is about 10 s or less.
  - Between that and 80 s, one send fits but two sends plus the margin do not.
  - In every such configuration the unclamped `.env` timeout (120 by default) is the larger risk, so the floor never adds one. The floor is right.
- **Fix.** No code in this task. Record in DEC-202 that the invariant needs `JOB_LOCK_TIMEOUT_S >= 80`. If the Director wants the Owner's `.env` guarded, a config-load check `JOB_LOCK_TIMEOUT_S >= 2 × LLM_TIMEOUT_S + 60` would be a separate DEC.

**N3 · Minor, optional.** A clamped stored value is not traceable in the audit trail.

- **Where.** `web/routers/admin_llm.py`, where the change entry is built.
- **Evidence.** The probe's audit row `{'old': 120, 'new': 100}`, written over a stored 600. The previous event's `new: 600` is followed by `old: 120`, and no event explains the drop: the drop came from a `.env` change, which is not audited.
