### Deviations judged

1. **Savepoint, not `infra/db.transaction()`.** Accepted. This is the corrected rule (`17e7135`). `SET LOCAL` sits inside the savepoint, so a failed section's rollback also undoes its timeout.
2. **`{"detail": {"reason": ...}}` for the 404 and 409s.** Accepted. It is the brief's shape, and `client.ts` takes `detail`.
3. **`inventory.loaded_at` over active rows only.** Accepted. The two readings differ only when the newest load kept no row in any table. It is tested.
4. **`NOT is_synthetic` on every alert section.** Accepted. The queue, the digest and the health checks do the same, and synthetic rows are replay or eval data, not intake. `top_agents` uses the same base as `alerts_by_day.total`.
5. **Days and statuses that do not occur are absent; `triage` always has four keys; `failed_jobs` is ordered by `created_at DESC`.** Accepted. The ordering choice is defensible, but see Finding 2. P11-T11 must zero-fill days and statuses.
6. **`job_id` bounded to 1..2^63-1.** The bound is accepted; the reason given is rejected.
   - The report says an unbounded int "would reach the driver as a DataError 500". That is wrong: psycopg sends an int above int8 as `numeric`, and `bigint = numeric` compares fine.
   - Measured on the scratch database: `plain int 1e20 -> None (no error: psycopg sends numeric)`, which would give a 404.
   - The 422 is still the better answer: it names an impossible id and keeps the PK index usable.
7. **`timeout` and `query_failed` as the error codes.** Accepted. They are generic and map cleanly in `strings.ts`.
8. **A module scratch database, and three tests beyond the card.** Accepted. The 403 tests really commit, and `scratch_db.py` is the established helper. The suffix `overview` is unique in the repo.
9. **Suite counts.** Accepted. My runs give `make test` 2173 = 2172 + 1, and DB 1428 = 1371 + 57.
10. **Based on `a530b6d`.** Accepted. The branch merges cleanly with `17e7135` and with `director/admin-v1-1` (`eaec07c`).

### Findings

No Blocking and no Important finding. Four Minor ones:

1. **Minor — the lock test does not pin the lock's strength.**
   - **Where:** `backend/tests/test_admin_overview.py:944-975` (`test_two_retries_of_one_job_cannot_both_pass_the_for_update_lock`).
   - **Why it matters:** the holder there is a plain `UPDATE`, so the request waits whether the route takes `FOR UPDATE` or `FOR SHARE`.
   - **Evidence:**
     - Mutation m7 (`FOR UPDATE` → `FOR SHARE`): `57 passed`.
     - Under m7, my two-admin test gave `REVIEW results=[('500', 'DeadlockDetected'), {'job_id': 1, 'status': 'pending'}]`. Two shared locks each wait for the other's UPDATE.
     - With the shipped `FOR UPDATE`, the same test passes: one 200, one 409 `not_failed`, and one event.
   - **Fix:** add a test where two retries of the same failed job run concurrently through the route, each on its own committed connection, started by a barrier. Assert exactly one 200, one 409 `not_failed`, one `admin.job_retried`, and no exception.

2. **Minor — a job that was retried and failed again drops out of `failed_jobs`.**
   - **Where:** `backend/app/web/routers/admin_overview.py:195`, `ORDER BY created_at DESC, job_id DESC`.
   - **Why it matters:** a retried job keeps its creation time. When it fails again it sorts by that old time, and 50 newer-created failures push it off the list. The admin then cannot see that the retry failed.
   - **Evidence:** a temporary test with 50 failed jobs created in the last hour, plus one created 10 days ago whose `locked_at` (last claim) is a minute ago, gave `REVIEW listed=50 refailed_listed=False first=recent-0`.
   - **Fix:** `ORDER BY COALESCE(locked_at, created_at) DESC, job_id DESC`. `claim_job` stamps `locked_at`, and `finish_job` leaves it, so this is the last attempt. Add a test for the re-failed job. Alternatively the Director keeps the current order and P11-T11's brief says the time shown is creation.

3. **Minor — the "3 s per section" is 3 s per statement.**
   - **Where:** `backend/app/web/routers/admin_overview.py:106-125` (`_by_source`, two statements) and `:143-168` (`_funnel`, two statements), against spec §5.4 "computed in its own statement with its own timeout".
   - **Why it matters:** `statement_timeout` applies to each statement, so these two sections are bounded at 6 s, and the page at 10 statements × 3 s.
   - **Evidence:**
     - A temporary `_funnel` that runs two `pg_sleep(2.5)` statements gave `REVIEW elapsed=5.03s errors=[]`.
     - Two separate sections of 2 s each gave `REVIEW elapsed=4.02s errors=[]`.
   - **Fix:** say "per statement" in the module docstring (lines 5-7) and at `SECTION_TIMEOUT` (line 57). Optionally fold `_funnel` into one statement.

4. **Minor, a spec gap for the Director, not the Coder — the KPI "clusters waiting for Tier 1, with the oldest" has no field.**
   - **Where:** spec §4.1, `docs/superpowers/specs/2026-10-18-admin-console-v1-1-design.md:106`.
   - **Why it matters:** `funnel.by_status.queued_tier1` is limited to the range and carries no oldest. The brief's shapes, which the Coder matched exactly, leave this out.
   - **Fix:** P11-T11 takes this tile from `GET /api/tier1/queue`, which admins may read (`web/routers/tier1.py:94`). Or the Director orders a follow-up adding `waiting: {count, oldest_received_at}` to this route.
   - **Also for P11-T11's brief:**
     - `alerts_by_day` lists only days with alerts.

     - A status missing from `by_status` means 0.
