How fail-closed works:

- `effective_limits` reads `SELECT key, value, updated_at, updated_by FROM settings` inside `with conn.transaction():`. That is a savepoint when the caller is already in a transaction, so a failed read leaves the caller's transaction usable.
- Any `psycopg.Error` is `SettingsUnavailable`. It is never answered with the `.env` value. A missing row keeps that key's `.env` value. There is no cache.
- The adapter calls `limits()` once per attempt, before any socket. `SettingsUnavailable` raises `LLMBudgetExceeded("limits unreadable — fail closed")`, so ① and ② record `stopped_by='cap'`. The cap is `limits().cap_usd`. The deadline is `timeout_s or limits().timeout_s`.
- The ② route answers `503` with detail `{"reason": "limits_unavailable"}`. The 429 and its text are unchanged.
- `monthly_cost` fails with a detail that contains "không đọc được hạn mức".
- `PUT` answers `503` with the same detail.

## 4. Deviations

1. **Error bodies are `{"detail": {...}}`.** The 422 and 503 objects are the `detail` of an `HTTPException`: `{"detail": {"field": "cap_usd", "reason": "out_of_range", "min": 1, "max": 1000}}`, `{"detail": {"reason": "limits_unavailable"}}`. The plan wrote `422 {field, reason}` and `503 {reason}`. The frontend `ApiError.detail` carries the object either way, and the Director's brief says "detail" for the ② route, so all of them use one shape. If the Director wants flat bodies for the PUT, it is a one-line change in `_unprocessable` and `_read_limits`.
2. **One bad field is reported, not all.** A body with several bad fields answers the first one in the order the body gave them. A bad field makes the whole request write nothing. A JSON body that is not an object (a list, a string, `true`) gets FastAPI's own 422 (a list `detail`), not `{field, reason}`. `null` or no body is treated as `{}`.
3. **`llm/investigate.py` does not read limits; it stops passing `timeout_s`.** The brief said its `timeout_s` "comes from the same limits". The adapter already resolves `timeout_s or limits().timeout_s` per attempt and fail-closed, so passing nothing is the single reader. `cfg` stays in the signature (`del cfg`). The test with the real adapter shows both sends under the limits' deadline.
4. **An already-aborted transaction is refused up front in `effective_limits`.** Entering `conn.transaction()` on a connection in INERROR fails on its SAVEPOINT after psycopg has counted the block as open, which leaves `conn.rollback()` and `conn.commit()` raising `ProgrammingError` for good. My test of that case found it. No current caller hits it, but a fail-closed accessor must not corrupt the caller's connection. The check is `conn.info.transaction_status == INERROR`, and it raises `SettingsUnavailable`.
5. **An advisory lock in the PUT (not in the card).** `pg_advisory_xact_lock(hashtext('admin.llm.limits'))` serializes two admins saving at once, so the second's `old` values are the first's `new` ones and the audit trail is a chain. It is released with the request's transaction and has its own test.
6. **The OpenAI client's constructor `timeout=`** is `settings.from_config(cfg).timeout_s`, not `cfg.LLM_TIMEOUT_S`. The card allowed it to stay at the config value, but the guard forbids the attribute in `adapter.py`. The value is the same and `_call_once` passes the per-call deadline anyway.
7. **The subject of the audit row** is the literal `"llm_limits"`; the card did not name one.
8. **`health.py`'s check detail** is `"$X spent this month; không đọc được hạn mức (settings unreadable, fail closed)"`. It keeps the plan's Vietnamese phrase and adds English. `value` is `None`.
9. **`eval/` and `scripts/` are untouched.** `eval/run_configs.py`, `eval/investigate_measure.py` and `eval/smoke_test.py` still read `cfg.LLM_MONTHLY_USD_CAP` and `cfg.LLM_TIMEOUT_S` straight from `.env`. They are offline harnesses outside `backend/app`, which is the card's and the guard's scope, and they build the adapter with no `limits=`, so its default (`from_config(cfg)`) is the old behaviour.
10. **A ② job sees the limits as of its transaction snapshot.** It runs under REPEATABLE READ, so a save made while a ② job is already running is seen by the next job, not by the running one (the same holds for the spend it reads on that connection).
11. **Test-file coupling.** `test_adapter.py` imports `_fake_dossier` and `_investigate_v2` from `tests.test_investigate` (the `test_ops_export_pilot.py` precedent). The pure test lives in `test_adapter.py` because `test_investigate.py`'s autouse fixture skips every test in that file when no database is reachable. The two ② job tests in `test_investigate.py` commit for real (the REPEATABLE READ rule of that file) and undo it in `finally`: the table rename in one, the `settings` row in the other.
12. **Not done, out of this card's files:** the runbook and context pack §6.3 text about `.env` precedence, and the frontend. `docs/plan/STATE.md` and `DECISIONS.md` untouched, as ordered.

## 5. Deployment note

**With this code and no migration 019, every model call stops.** That is the fail-closed design working as intended. It looks like this:

- ① writes `stopped_by='cap'` and `triage_status='unavailable'` for every alert;
- ② `POST /api/tier2/cases/{id}/analyze` answers 503;
- the `monthly_cost` health check fails (a Telegram alarm on the next tick);
- `PUT /api/admin/llm/limits` answers 503.

So the Owner must run **`make migrate`** (019: the `settings` table and `admin.settings_changed`) **before restarting `app` and `worker`** with this code. This is a code-only change to the mounted source, so `restart` reloads it. With 019 applied and no rows in `settings`, nothing changes in behaviour: every limit is the `.env` value until an admin saves one.
