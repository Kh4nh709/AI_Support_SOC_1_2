**`POST /api/admin/labels/undo`** (admin only, `claims: Admin` before the body, so a tier1 caller gets the 403 before any body error):
- The labeller is the caller (`claims.user_id`). The body is a required JSON object and a Pydantic model (`UndoIn`, `extra="forbid"`, one optional field `labeler: str | None`). `{}` and `{"labeler": "<caller>"}` are accepted; a `labeler` that is not the caller is 403 `labeler must be the current user` (`_bind`, as `api_next` and `api_post` do); any other key is a 422.
- Content type is FastAPI's own strict default (`strict_content_type=True`, 0.141): only `application/json` or `application/*+json` is parsed. No body, no content type, `text/plain`, a urlencoded or multipart form, and a JSON content type with an empty body are all 422, and nothing is deleted. That is the only reason the cookie (which lives until P11-T19) cannot be used from a cross-site form or a no-cors `fetch` to undo anyone's label. I checked it rather than assumed it: seven request shapes in a test, and the red step (d) below removes the body parameter.
- It calls `labels.undo_last(conn, claims.user_id, freeze_marker=labels.FREEZE_MARKER)`, with the marker read per request (the module attribute, so a test monkeypatches it).
- `409 {"detail": {"reason": "frozen"}}` on `labels.Frozen`; `404 {"detail": {"reason": "nothing_to_undo"}}` when `undo_last` returns `None`; else `200 {undone_cluster_id, done, total}`.
- **The body shape of 409 and 404 is `{"detail": {"reason": ...}}`**, the house style of `admin_overview.py` (spec §3: "a `detail` that is an object carries a machine-readable `reason`"). The card writes `{reason: "frozen"}`; that is the content of `detail`.
- **How `undone_cluster_id` is found.** `undo_last` returns the deleted row's `alert_id`. `triage_labels.alert_id` holds `candidate.alert_id` (what `submit_label` inserts), so the route reads `gold_candidates.csv` and takes the `cluster_id` of the first candidate whose `alert_id` equals it. When the file has no such row (the file is missing or was replaced after the label was written) the answer is the alert id itself, which is the cluster id in both gold sets (`cluster_id = alert_id = members[0]` in `eval/build_gold.py`, the fact `next_unlabelled` already relies on). A test renames a cluster so the two differ, and another removes the file.
- `done` and `total` are `next_unlabelled`'s over the caller's `labeler_order`, computed after the delete in the same transaction. With no readable candidates file they are 0 and 0.
- **One transaction.** `undo_last` runs the DELETE and `write_event` on the connection it is given and commits nothing; `write_event` commits nothing; `db.connect` is `autocommit=False`; the route adds no commit and no `infra/db.transaction()`. `Conn` (`get_conn`, `scope="function"`) commits on a 2xx and rolls back on any raise, so a failure after the DELETE gives the label back with no event. The frozen check runs before the DELETE and the 404 is returned only when nothing was deleted, so neither 4xx leaves a write behind. Proved on committed data (section 2).

**`GET /api/admin/labels/next`** now returns `cluster_id, done, total, cluster, frozen, candidates_present`, in that order:
- `frozen` is `labels.FREEZE_MARKER.exists()`.
- `candidates_present` is `CANDIDATES_PATH.is_file() and os.access(path, os.R_OK)`.
- **Behaviour when the file is missing (unchanged):** `200`, `cluster_id: null`, `done: 0`, `total: 0`, `cluster: null`, now with `candidates_present: false`. `load_candidates` returns `[]` for a missing file and `labeler_order([])` is empty, which is where that came from.
- **A file that exists but cannot be read** used to be a 500 (`PermissionError` in `load_candidates`). Now it is answered exactly like a missing file, so the flag means what the card says ("exists and is readable"). See Deviations 2.
- Nothing else is added. `cluster` is still exactly `labels.cluster_view`'s dict, which asserts its own keys equal `VIEW_KEYS` and passes `visibility.strip(mode="labeling")`. `_next_payload`, which the Jinja page also uses, is unchanged.

## 4. Deviations

1. **Three existing assertions are extended.** The card says the existing allowlist test must still pass unchanged. It pins the top-level key set to `{cluster_id, done, total, cluster}`, and so do two other tests that compare the whole body. Adding the two flags the card asks for makes all three fail by construction. I extended exactly those three assertions by `frozen` and `candidates_present`; every `cluster`-level assertion, `ALLOWED_VIEW_KEYS`, `CORRELATION_ROW_KEYS` and `SAMPLE_KEYS` are untouched and pass.
2. **An unreadable candidates file answers like a missing one** (200, empty payload, `candidates_present: false`), not a 500. The card defines `candidates_present` as "exists and is readable" and says to keep the missing-file behaviour; with the old code an unreadable file raised before the route could report the flag, so the "readable" half would have been unreachable. The undo does the same: with no readable file the progress is 0 of 0. A file that is readable but malformed is still a 500, as before.
3. **409 and 404 bodies are `{"detail": {"reason": ...}}`**, not a bare `{"reason": ...}` (see section 1); that is the shape every other P11 route has and what spec §3 says `strings.ts` reads.
4. **`undone_cluster_id` falls back to the alert id** when no candidate row matches it. The card says "map it back to the candidate's `cluster_id`" and does not say what happens with no match. The fallback is correct for both gold sets and never fails an undo that has already deleted a row.
5. **The body model forbids extra keys** and accepts `labeler: null`. The card allowed `{}` or `{labeler: <caller>}`; anything else is a 422.
6. **Red steps (b) to (e) ran on a scratch copy**, (a) in place (harness refusal, see section 3), and (d) and (e) are extra.
7. **Tests live in two files.** The behaviour tests are in `test_labels.py` (they reuse its fixtures and file builders). The tier1 403s and the one-transaction proof are in a new `test_admin_labels_api.py` on a scratch database, because they need a connection that really commits and `require_role` commits for real; the shared `db` fixture's `commit` would persist the seeded users and alerts in the database every later file shares.

Observations for the Director, not changes:

- Two undo requests of the same labeller at once: the second DELETE waits for the first's commit, re-evaluates, finds the row gone and answers 404. One double click undoes one label, not two. That is the safer outcome and needs no change.
- `undo_last` orders by `created_at DESC LIMIT 1`; two labels with the same `created_at` (not possible from the page: one per request, one transaction each) would be undone in an unspecified order. The tests set distinct `created_at` for that reason.
- The 422 for a bad body is FastAPI's own, whose `detail` is a list that repeats the rejected input. Here the input is the caller's own `labeler` string or a stray key, never a secret. The frontend (P11-T16) has no field to map it to; it is the "unexpected" path.
- `/admin/labels/undo` (Jinja) and `/api/admin/labels/undo` now both exist; P11-T19 retires the first.
