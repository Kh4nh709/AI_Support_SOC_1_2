#### Important (Should Fix)
1. **A Voyage or `vectordb` outage now also trips `llm_null_ratio` ("Model API down") while DeepSeek is healthy.**
   - **Why it alarms:**
     - `_check_llm_null_ratio` counts every `llm_runs` row of the last hour, with no pipeline filter, and alarms above 30 % (`infra/health.py:196-208`, `:73`).
     - Every `failed` lookup now writes a `rag_lookup` run row with `result` NULL (`rag/lookup.py:355`, with `ranked=None` on `lookup.py:534-546`). `assert_failed` pins this (a1e53fd diff:4460).
     - That includes the empty-key case, where nothing was sent (a1e53fd diff:4472-4479). P13's matching "no model" case wrote no row.
     - A paid, rate-limited first attempt adds a second NULL row (`lookup.py:519-532`).
     - With one NULL lookup row per alert beside at most two ① rows, an hour of alert traffic is about one third or more NULL. A dead key, a spent quota or a down `vectordb` therefore raises two alarms, and the second sends the admin to the DeepSeek runbook.
   - **Why the tests miss it:** `test_a_burst_of_failed_lookups_alarms_the_report_and_writes_health_alarm` (96158f8 diff:327-345) inserts `rag_results` rows without their run rows.
   - **Fix:**
     - Leave `pipeline = 'rag_lookup'` out of `llm_null_ratio`; `rag_lookup_failures` now owns that signal.
     - Write no run row when nothing was sent.
     - Add a test that drives real failed lookups, run rows included, through `health.check`.
