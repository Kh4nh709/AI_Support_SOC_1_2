## 3. Deviations from the card and why

- **`ID_PATTERNS` is duplicated in `linter.py`, not imported from `app.llm.builder`.** The card's design note 3 says a token is checked against "an id matching any of `builder.ID_PATTERNS`", but the Goal signature and design note 5 both give `lint()` exactly three keyword arguments (`nonce`, `constants`, `enums`) — no `id_patterns` parameter — and design note 5 states plainly "`security` may not import `llm`, so this module never imports `builder`". The only way to satisfy both the exact signature and the import rule is a private copy of the same five regexes inside `linter.py`, one-for-one identical to `builder.ID_PATTERNS` (alert_id, rule_id, mitre, agent_id, rule_ref). This is flagged here rather than silently reconciled, per the card's own instruction ("say so in your report rather than reconciling them yourself") — it is a genuine ambiguity in the card, not a judgement call I made unilaterally. The two copies can drift; nothing currently tests that they stay identical (see §4).
- **Constant-stripping skips the two single-character constants (`"-"`, `"·"`).** Design note 1.2 says "remove every occurrence of each string in constants". Applied literally as a blind whole-text substring replace, this breaks: `TEMPLATE_CONSTANTS` contains the bare bullet `"-"` and the bare separator `"·"` (from `BULLET.strip()` / `SEPARATOR.strip()`), and a global `text.replace("-", "")` would also delete every hyphen embedded inside a legitimate token elsewhere in the residual — the dashes in an ISO datetime (`2026-08-16T...`), a `rule_ref` id (`sbf-1`), or a negative integer. That would make `test_every_shipped_template_lints_clean` and `test_tokens_enum_int_datetime_id_are_allowed` impossible to satisfy for any fact line carrying a datetime. Instead, `_strip_constants` only blind-replaces constants of length > 1 (headings, sentences, `name:` labels — all safe, since none is a substring that could occur inside a legitimate closed-set value); the two single-character glyphs are left for the tokenizer's per-token **edge**-trim (§7.2's separator list), which correctly reduces an isolated `"-"` or `"·"` to nothing while leaving one embedded mid-token (as part of a datetime, id, or rule_ref) untouched. Verified this doesn't under-strip: every fixture and every shipped-template build still lints clean or dirty exactly as designed (see the token-level trace in the commit's file history if needed — the four legacy fixtures each still name their correct first offending token).
- **`Violation` carries a `count` field** not shown in the algorithm's inline `Violation(kind=..., token=..., line=...)` sketch, because design note 2 separately requires "the count of offending tokens on that line" to reach the caller. Both are present; nothing in the card is contradicted by the addition.
- **One `Violation` per line, not per token.** Design note 2 says "Report the first offending token per line and the count of offending tokens on that line" (singular deliverable per line), which is what `_line_violation` produces — one aggregated `Violation` per line that has ≥ 1 offending token, not one `Violation` per token.

## 4. Open questions / follow-ups

- The duplicated `ID_PATTERNS` (§3, first bullet) has no automated drift guard. If the Director wants one, a follow-up task (or a small addition to this one, if asked to extend it) could add a test that imports both `app.llm.builder.ID_PATTERNS` and `app.security.linter._ID_PATTERNS` and asserts their pattern strings match pairwise — deliberately not added unasked, since `security` importing `llm` even from a test file works today (tests are not scanned by `test_import_rules.py`) but the card's design note 5 phrase "this module never imports builder" reads as being about the *module*, and I did not want to quietly grow the test file into the thing that couples the two copies without being asked to make that call.
- Design note 1.3's separator list is also used as the tokenizer's edge-trim set; one consequence (not tested, not required by any named acceptance test) is that a raw dotted-quad IP address placed outside a block, with no leading/trailing punctuation, is not specifically detected as such by the `id`/`int`/`datetime`/`enum` checks — it simply fails all four and is correctly reported as `free_text` (there is no lookalike-acceptance risk; flagged here only because it is the closest thing to a design gap I found while building the token classifier, and it resolves in the safe direction — reject, not accept).
