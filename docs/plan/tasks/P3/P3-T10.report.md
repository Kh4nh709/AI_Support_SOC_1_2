  - `write_run(conn, *, run_id, role, subject_id, system_prompt, user_message, result, gate_result, verifier_result, injection_findings, citation_warnings, input_tokens, output_tokens, latency_ms, model_id, prompt_version, cost_usd, stopped_by) -> uuid.UUID` — inserts one `llm_runs` row for pipeline ①; `role` validated in Python before any SQL; `pipeline`/`subject_type` hard-coded to `'triage'`/`'alert'`; `agent_trace`/`evidence_check` always `NULL`.

  - `_raise_idle_timeout(conn, cfg)` — the handler's first statement, `SET LOCAL idle_in_transaction_session_timeout` to `JOB_LOCK_TIMEOUT_S`.
  - `_load(conn, alert_id) -> _AlertRow | None` — the explicit 26-column select (G10), with the defensive `NULL`-context fallback design note 6 asks for.
  - `_set_triage_status(conn, alert_id, status)` — the module's only write to `alerts` (G2); never touches `status`.
  - `_make_rule_check(table, facts)` — the six-reason callable gate step 4 gets.
  - `_last_attempt_or_raise(conn, job, cfg, exc, built, facts)` — planning decision 3 for a `propose()` failure.
  - `_verify_failed_last_attempt(conn, built, vbuilt, facts, proposal, alert_id, cfg, exc, *, stopped_by)` — the same shape for a `verify()` failure (`cap` or an exhausted `transient`), writing both rows "with what exists".
  - `_Subject`, `_AlertRow` — small frozen dataclasses (the correlation-window subject, the loaded row).
- `backend/app/web/worker.py` — `HANDLERS["triage"] = run_triage_job` (one import line, one dict entry; `git diff main` is 3 changed lines).

## 3. Deviations

- **The `verify()`-phase failure branches (`LLMBudgetExceeded` / `TransientError` after the proposer call already succeeded) are not named in the card's acceptance list** — only the `propose()`-phase branches are (`test_transient_before_last_attempt_propagates_and_writes_nothing`, `test_transient_on_last_attempt_is_unavailable_with_job_exhausted`). Design note 2 still requires the behaviour ("same two branches as above … on the last attempt both rows are written with what exists"), so I implemented `_verify_failed_last_attempt` and added three of my own tests for it (not counted toward the card's ≥ 18 floor, which is met by the 19 named tests alone). Interpretation I made, since the card doesn't spell out the written rows' exact shape here: both rows get `result=None` and the matching `stopped_by` (`cap` or `transient`) — i.e. the run is recorded as incomplete rather than synthesizing a "final verdict without step 6" that nothing in the spec describes.
- **`_load`'s defensive `NULL`-context fallback (design note 6) logs via `_log()` rather than adding a `gate_result`/`citation_warnings` entry.** The note says "with a warning" but doesn't specify where; since the note itself says this path "cannot happen" for a real `triage` job (a `received` alert has no such job), I kept it to a diagnostic log line rather than plumbing a new warning channel through `build_facts`/`build_proposer_prompt` for an unreachable case. Not covered by a dedicated test for the same reason.
- Everything else follows the card's design notes 1–8 and the `run_triage_job` pseudocode literally, including the SQL-formatting detail in §2 item 6.
