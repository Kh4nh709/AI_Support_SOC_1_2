## Blocking findings

1. **`backend/app/security/detector.py:284-312` (`scan`) raises on a block whose `.plain` is not a
   `str` — violates design note 4's explicit "does not raise on any input (empty block, `None`
   text, binary garbage)".** Line 288 builds a type-guarded local, `text = block.plain if
   isinstance(block.plain, str) else ""`, but that guard is used *only* for the `PATTERNS` regex
   loop two lines below. The raw `block` is passed unguarded into every one of the 8 `HEURISTICS`
   (line 301-302: `for heuristic in HEURISTICS: for ... in heuristic(block):`), and each heuristic
   reads `block.plain` directly with no guard of its own — e.g. `_heuristic_base64_run` (line 112):
   `_BASE64_RUN.finditer(block.plain)`. Demonstrated:
   ```
   class FakeBlock:
       def __init__(self, plain, source="context", truncated=False):
           self.plain, self.source, self.truncated = plain, source, truncated
   detector.scan([FakeBlock(None)])
   # TypeError: expected string or bytes-like object, got 'NoneType'
   ```
   This is exactly the shape of object the card's own "Depends on" note authorises as valid input
   ("define the input as any object with `.source` and `.plain`"). The existence of the `isinstance`
   guard shows the Coder anticipated a non-`str` `.plain` and defended the regex path; the same
   defence was never extended to the heuristics path, so the module's central promise — *never
   raises, on anything* — is false for 8 of its own functions. None of acceptance item 4's three
   scenarios (`[]`, `plain=""`, 1 MB garbage decoded to a `str` with `errors="replace"`) exercise an
   actual `None`, which is why the Coder's own test suite (42 green) never caught it. Bucket (a),
   the Coder's — nothing in the card required the incomplete guard. Fix: apply the same
   `isinstance` coercion inside each heuristic (or pass the already-guarded `text`, not the raw
   `block`, into every heuristic call).

No other blocking findings — every acceptance item, `make lint`, `make test`, import rules and
scope are clean (evidence below).

## Non-blocking notes

- **Bucket (b), card defect, free to the Coder — `obfuscation_hidden_chars` findings are
  double-counted.** Design note 2 requires porting `_PATTERNS` verbatim from
  `prompt_guard.py:60-80`, which already carries the hidden-chars regex as its 19th (last-ported)
  pair (verified byte-for-byte against the read-only reference, see Evidence). Design note 3
  *separately* and explicitly requires a standalone heuristic, "(3) `hidden_chars` — ...
  *ported*, `must`", for the identical U+200B/U+200C/U+200D/U+FEFF signal. Both were implemented
  exactly as the card specifies, so every hidden-character occurrence produces **two** `Finding`s
  (one via `PATTERNS`, `pattern=<the regex source>`; one via `HEURISTICS`,
  `pattern="heuristic:hidden_chars"`), both `category="obfuscation_hidden_chars"`,
  `level="medium"`. Demonstrated: `detector.scan([Block(plain="hello​world", ...)])` → 2
  findings, not 1. This inflates whatever `injection_findings`-derived count or rate P3-T10/eval
  computes for this category — the module's own docstring and context pack §7.3 both state the
  findings exist "for measurement and display." The Coder's docstring (lines 21-23) shows they
  noticed the heuristic duplicates a signal already in `_PATTERNS` ("the hidden-character check
  that in the reference lived inside `_PATTERNS` itself") but the report does not flag the
  resulting duplicate-`Finding` consequence. Not chargeable to the Coder — both design notes
  command the duplication unambiguously — but worth a Director decision (dedupe inside `scan`,
  or drop the regex pattern or the heuristic) before P3-T10 starts recording real
  `injection_findings` for evaluation metrics.
- **Minor — heuristic 8 (`imperative_density`) has no word-boundary check on its 20-word list**
  (line 265: `s.lower().startswith(_IMPERATIVE_WORDS_LOWER)`), so ordinary analyst prose can trip
  it: three routine, non-adversarial sentences — "Marking the alert reviewed. Setting the ticket
  status now. Disabled logging was restored after the maintenance window." — score `medium` via
  `imperative_density` (verified directly), purely from `startswith("mark")` / `startswith("set")`
  / `startswith("disable")` prefix matches with no following word boundary. Design note 3(8) does
  not specify boundary precision, so this is a reasonable reading of an underspecified `should`
  heuristic, not a clear defect against the card — flagged as a false-positive-rate risk for
  whoever tunes this heuristic later, not blocking.
