  - `check_live(conn, *, want: int = 50) -> LiveSummary` — one `SELECT` (a single statement, so every figure is from one snapshot) and the verdict. `ok` holds iff: proposer rows with `gate_result IS NOT NULL AND cost_usd > 0` ≥ `want`; triage rows (any role) with `gate_result IS NULL` = 0; triage rows with `cost_usd IS NULL` = 0; proposer rows that are still `false_positive` with a non-empty `gate_result->'missing'` = 0; failed triage jobs = 0.

Stdout: the summary as one JSON line, the table, then one `FAIL <condition>: …` line per failed condition. Exit 0 = all hold, 1 = at least one fails, 2 = no database to read (no `DATABASE_URL`, the connection fails, the read fails, or a usage error — unknown arguments are not echoed, they may hold a DSN).

## 3. Deviations

1. **The card's design (§ design notes 1–5, acceptance 1, 3, 4, 9) is replaced by DEC-156**, as the dispatch said: no `run_live`, no `--dry-run`, no `FakeLLM`, no `max_claims`, no `--want-replay`; `test_run_live_loop_offline` and its siblings do not exist. `want` counts proposer rows of **all** sources (the card counted `replay` only) because DEC-156 §3 states the condition that way.
2. **Acceptance 6's literal grep (`from llm\|import llm\b\|llm\.prompt_builder`) exits 0, not 1, and did before this change**: it matches `from llm_runs` inside a runbook `psql` string (`backend/tests/test_runbook_alarms.py:349`) and the historical comment `eval/smoke_test.py:422` ("Transcribed from llm/templates/triage_system.txt"). Neither imports anything; the dispatch says historical comments stay. The anchored grep in §2 item 5 is the one that means what the card meant.
3. **Test isolation by private tables.** `check_live` counts whole tables, and other `db` files commit rows into an append-only `llm_runs` that nothing can remove, so the in-process tests read private `alerts` / `llm_runs` / `jobs` (`CREATE TABLE … (LIKE public.… INCLUDING ALL)`, shadowing the real ones through `search_path`, created inside the `db` transaction and rolled back with it). Only the two tests that need the real tables (`…_runs_inside_a_read_only_transaction`, `test_cli_session_is_read_only`) touch `public`, and neither asserts a count. `test_cli_exit_codes_0_and_1` needs rows a subprocess can see: it commits them into its own schema `p3t11_live_cli` (reached with `PGOPTIONS`), and the fixture drops that schema in its teardown and again at its start, so a killed run leaves nothing that the next one trips on. Nothing lands in `public`. Needs `CREATE` on the test database (the scratch owner has it).
4. **The exit code 2 also covers a failed read and a usage error**, not only "no `DATABASE_URL` / no connection" — one code for "there was no database to read", so exit 1 always means a real finding.
5. **A statement timeout of 30 s** (`SET statement_timeout` in `connect_read_only`) — not in the card; a stuck query must not hold the live database. The live test's own connection sets only `read_only`.
6. **`stopped_by` and `suggested_action` are counted over proposer rows** (a verifier row has neither meaning), each with a `(none)` bucket for NULL.
