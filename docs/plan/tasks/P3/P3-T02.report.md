    verbatim), `LABEL_ABSENT`, `FACT_NAMES` (the 30 names from design note 6), `SEPARATOR`,
    `BULLET`, `HEADINGS`, `SENTENCES`, `TEMPLATE_CONSTANTS`.
  - `Fact = Enum | int | datetime | Id`; **`fact(name, value) -> str`** — `name` must be in
    `FACT_NAMES`; `bool` and `str` values are `TypeError`; `datetime` must be timezone-aware and

    `str(value)`. Returns a `_FactRendering` (private `str` subclass — see §3).

    over `security.wrap.untrusted_block`; every `attrs` value must be `Id | Enum | int` (`bool`
    and `str` both rejected) and is rendered the same way `fact()` would render it before being
    forwarded as a string.
  - `BuiltPrompt` (frozen dataclass: `system`, `user`, `nonce`, `block_index`) and
    **`PromptBuilder`** — `heading(constant)`, `line(*parts)`, `sentence(*parts)`,
    `block(text, source, *, limit_bytes=None, **attrs)`, `build()`, `.nonce` property.
    `line()` accepts a part iff it is a genuine `fact()` output or a `TEMPLATE_CONSTANTS`
    member; `heading()`/`sentence()` accept only `TEMPLATE_CONSTANTS` members; `block()` refuses

## 3. Deviations from the card and why

1. **`PromptBuilder`'s API shape follows this prompt, not `P3-tasks.md`'s row.** `P3-tasks.md`
   §9's one-line summary for P3-T02 says `PromptBuilder(system, nonce).section(...)`, but this
   prompt's design note 5 spells out five distinct methods — `heading`, `line`, `sentence`,
   `block`, `build` — with different vocabularies per method (`heading`/`sentence` require
   `TEMPLATE_CONSTANTS` membership only; `line` also accepts a genuine `fact()` rendering). Per
   this prompt's own instruction ("Where the two disagree… this prompt wins"), I implemented the
   five-method surface and did not add a generic `section()`. Flagging per the card's instruction
   to report rather than reconcile.
2. **The "private registry of fact renderings" (design note 5) is implemented as a private `str`
   subclass marker (`_FactRendering`), not a mutable set.** `fact()` is a stateless free function
   with no handle to any `PromptBuilder` instance, so it cannot populate a registry that is
   scoped *per builder instance* as the note's wording suggests. A single **global** mutable set
   populated by every `fact()` call was the other candidate and is actively wrong: I verified
   directly that it breaks the intended guarantee — once any test calls
   `fact("severity", Severity.HIGH)` (producing the string `"severity: high"`), a *hand-typed*
   `"severity: high"` passed to a different builder's `line()` would incorrectly succeed, because
   it would already be in the global registry. Returning a private `str` subclass from `fact()`
   instead gives `line()` a way to check *provenance by type* (`isinstance(part, _FactRendering)`)
   rather than *by previously-seen content*, which has no cross-instance or cross-test leakage
   and needs no shared mutable state — and it is exactly as hard to forge as a set-membership
   check, since `_FactRendering` is private to the module and only ever constructed inside
   `fact()`. Behaviourally this is indistinguishable from the note's description (a hand-typed
   lookalike is rejected, a genuine `fact()` output is accepted) — the deviation is in mechanism,
   not in the observable API or test surface, but flagging it since a Reviewer comparing this
   file against the note's literal wording would reasonably ask about it.
3. **`untrusted()`'s `**attrs` also rejects `bool`**, though design note 4 only states the
   restriction as "`Id | Enum | int`" without repeating note 3's explicit bool carve-out. Applied
   the same reasoning defensively (`bool` silently rendering `"True"`/`"False"` is almost always a
   mistake, not a deliberate int); no acceptance test depends on this either way.
4. Ten extra tests beyond the 16 named + 2 `-k` ones, covering edge cases surfaced while writing
   the implementation (listed in §1). None of the ten changes the counted acceptance total below
   16 or duplicates a named test's assertion.

## 4. Open questions / follow-ups

- **For P3-T09 (out of this card's scope):** `fact()` does not — and per design note 3 is not
  asked to — constrain which `Enum` subtype is valid for a given `name` (e.g. nothing stops
  `fact("severity", B.Confidence.HIGH)`). This is a deliberate scope boundary ("Scope out: knowing
  what an alert is"), but worth naming explicitly so whoever writes `build_proposer_prompt` in
  P3-T09 does not assume the builder enforces a name→enum-type mapping — it only enforces the
  broader `Enum | int | datetime | Id` shape and `name ∈ FACT_NAMES`.
