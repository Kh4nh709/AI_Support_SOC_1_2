## 3 · Deviations from the card, and why

1. **The card's fixture/route context is 19–25/09; the merged code has moved (as flagged in the dispatch).** Nothing in P4-T03's own design notes conflicted with current code — `domain.transitions.decide`'s pre-card signature, `tier1/queue.py`'s `get_alert_view`/`list_queue`/`latest_suggestion`, and `tier1/visibility.py`'s `strip` all matched the card's §5 description exactly (verified by reading the merged files directly, not the card's quoted snippets). No P7-T01 (`evaluate_alert`) or P7-T09 (`schemas.normalise`) surface touches this card's files at all — `tier1/decide.py` never imports `llm.triage` or `llm.schemas`; it only reads `llm_runs` rows through `tier1.queue.latest_suggestion`, which P4-T02 already wrote and this card does not modify.
2. **`escalate`'s initial guard kind mapping is my own construction**, since the card names the three kinds (`not_active`, `already_decided`, `already_in_case`) but not the exact `status → kind` table. I mapped `escalated_tier2 → already_in_case`; `closed_fp/closed_benign/closed_confirmed/auto_closed → already_decided`; everything else (`received`, `enriching`, `duplicate`) → `not_active`. Exercised by the acceptance tests and by DEC-025 case (a).
3. **`decide()`'s initial `suggestion_visible` read tolerates a missing alert (`row is None → suggestion_visible = None`) rather than raising `NotFound`**, matching the card's silence on that case: the card gives acknowledge and escalate an explicit `NotFound`/`FOR UPDATE` guard but decide's design note has no such step before `transitions.decide`, which itself turns a nonexistent `alert_id` into `StaleState` → `DecisionConflict(kind="not_active")`, exactly per the note's re-read logic. `escalate()` does raise `NotFound` on a missing row at its own `FOR UPDATE` guard — the card is explicit there.
4. **`make test-db` showed one failure at submission, in `backend/tests/test_triage_job.py::test_idle_timeout_survives_an_eleven_second_call`.** I misdiagnosed this as a pre-existing timing flake. It was not: the real cause was a leaked commit from this card's own `test_tier1_api.py`, fixed in §Review round 1, item/BLOCKER 1 — see that section for the mechanism and the proof. The "timing" paragraph that stood here is retracted.

Verdict: REQUEST CHANGES. New commits on top of `163b678`; no earlier commit rewritten.

**BLOCKER 1 — the leaked commit (not timing).** `test_api_tier2_post_decide_is_403_and_audited`
drives `require_role`'s 403 path, which calls `conn.commit()` directly on the shared `db`
fixture connection (planning decision 3: the `authz.denied` row must survive the 4xx). That
commit was real — it made everything the test had set up on that connection permanent: the
seeded users, the alert, and critically the pending `triage` job `finish_enrichment` enqueues.
`db`'s own `rollback()` at teardown only undoes what comes *after* a commit, which was nothing.
`test_triage_job.py::test_idle_timeout_survives_an_eleven_second_call` then claimed that leaked
job — the oldest pending one — instead of the one it seeded itself, and failed. This is exactly
what my original report called a timing flake; it was not, and §2 item 7, §3 item 4 and §4 are
corrected above.

Fix: `db.commit` is monkeypatched to a spy in that one test. The spy records the `authz.denied`
row for `TIER2_ID` at the moment of the real commit (read-your-own-writes on the same connection
sees it whether or not it is ever really committed) and does not call through, so nothing survives
past the test's own rollback. Proof, both embedded in the test itself:
- `assert len(commits) == 1` and the recorded row's `required == ["tier1"]` — the commit happened
  and wrote what planning decision 3 promises;
- a **second, independent connection** (`psycopg.connect(_test_database)`, opened fresh inside the
  test) reads `count(*)` from `jobs`, `alerts` and `users` filtered on this test's own ids and gets
  `(0, 0, 0)` — nothing is visible outside the test's own transaction.

`make test-db` went from `691 passed, 1 failed` to **`702 passed, 0 failed`** with this one fix
(the other ten items below add tests but do not themselves change that count from broken to
green). Re-run three times against the full suite (`run_merge_tests.sh soc_p4t03_test`) — green
every time.

**Item 3 — `escalate`'s `StaleState` handling.** `transitions.escalate`'s two `StaleState`
flavors left the connection in different states: a `UniqueViolation` (a correlated candidate
already sits in another case's `case_alerts`) aborts the connection's current transaction outright
— `_conflict()`'s re-read would itself raise `InFailedSqlTransaction`, surfacing as a 500 instead
of the intended 409; a rowcount mismatch (a candidate's `case_id` was set directly, no
`case_alerts` row, so no `UniqueViolation`, but the final `UPDATE ... AND case_id IS NULL` touches
fewer rows than expected) leaves a real `cases` row and a partially updated trigger sitting in the
transaction. Fix: `transitions.escalate` is now called inside `with conn.transaction():` — a
`SAVEPOINT` that rolls back to itself, not the whole request's transaction, on any exception, so
both flavors leave `_conflict()` reading a working transaction and nothing half-written survives
either flavor. Two new tests in `test_decide.py`,
`test_escalate_candidate_claimed_concurrently_is_conflict_and_nothing_half_written` and
`test_escalate_rowcount_mismatch_is_conflict_and_nothing_half_written`, each build one flavor
directly (a `case_alerts` row for the other flavor's target, or a direct `case_id` UPDATE), assert
`kind == "already_in_case"`, and assert the `cases` count and the trigger's `(status, case_id)` are
unchanged afterward.

**Item 4 — a 409 was committing under the real `get_conn`.** `post_acknowledge`/`post_decide`/
`post_escalate`/`post_reopen` returned `JSONResponse(409, ...)` directly on `DecisionConflict` — a
normal function *return*, not a raised exception, so the real `get_conn` dependency (commit on
success, rollback on exception) would take its `else: conn.commit()` branch and persist whatever
the guard's own reads or an earlier call in the same request had written. This directly
contradicted planning decision 3's other half: a *successful* 4xx write commits before raising, but
a *refused* one (409) must persist nothing. Fix: a `_conflict_response(conn, exc)` helper calls
`conn.rollback()` first, then returns the `JSONResponse` — all four POST handlers now go through
it. New test `test_api_409_rolls_back_before_the_wrappers_commit` in `test_tier1_api.py` uses a new
`real_shape_client` fixture — `get_conn` with the *real* shape (`commit`/`rollback` both present,
both spied so nothing really persists) — and asserts `calls[:1] == ["rollback"]`: rollback happens
before anything else, so the wrapper's own `else: commit()` (which still runs afterward, since
`_conflict_response` returns normally) has nothing left to commit.

**Item 5 — unknown ids fell through to a 409, not a 404, on `decide` and `reopen`.** Both
functions only distinguish `DecisionConflict` kinds from the re-read row inside their
`except transitions.StaleState:` handler; a nonexistent `alert_id` makes that re-read return
`None`, which previously still built a `DecisionConflict(kind="not_active")` body full of `None`s
instead of a 404. Fix: both now raise `NotFound` when the re-read row is `None`, and
`post_decide`/`post_reopen` gained the `except decide.NotFound` branch `post_acknowledge`/
`post_escalate` already had. New parametrized test
`test_api_unknown_alert_post_is_404_for_every_verb` in `test_tier1_api.py` posts to all four verbs
on `alerts/does-not-exist` and asserts 404 on each.

**Item 6 — nit, left as-is, documented.** `_ESCALATE_GUARD_KIND` stays keyed on `status` alone
rather than derived from `_conflict_row`'s `case_id` column: `escalated_tier2` already implies a
case, no test exercises the two disagreeing, and deriving it would cost an extra read for no
observed behavior change. A comment on the dict now says so.

**Item 7 — nit, documented, not changed.** `_conflict_body`'s `decided_by` is the row's
`acknowledged_by` display name, not a separate "who closed it" column (there is none —
`domain/transitions.py` never records a closer). A comment now states the v1 assumption plainly:
the acknowledger is who later decided, true under P6-2's "first acknowledger wins" and this
module's own flow, false only for a path that bypasses `tier1/decide.py` entirely (none exists
today).

**Item 8 — nit.** `_SUGGESTION_KEYS` in `test_tier1_api.py` gained `"run_id"` (`ANALYST_HIDE`
drops the queue row's top-level `run_id` too, per DEC-101 — the original tuple missed it).
`test_api_blind_queue_row_has_no_suggestion_keys` now also asserts `"false_positive" not in
resp.text`, matching the alert-detail test's stronger check.

**Item 9 — nit.** `test_tier1_api.py`'s `client` fixture's `get_conn` now has the real
dependency's shape minus the success commit: `try: yield db / except BaseException: db.rollback();
raise` — a route's own exception rolls back mid-request like production; a normal return still
never commits, so every other test in the file stays inside `db`'s one transaction, rolled back at
teardown.

**Item 10 — nit.** A NUL byte (0x00) can never reach a `text` column — psycopg raises a
driver-level error before any clean 422 would happen. `DecideIn.reason`, `EscalateIn.title` and
`ReopenIn.reason` each gained a `field_validator` rejecting one, so it is caught by Pydantic before
the request reaches `tier1/decide.py` at all. New parametrized test
`test_api_nul_byte_in_reason_or_title_is_422` covers `decide`/`escalate`/`reopen`. Separately,
`reopen()` in `tier1/decide.py` now strips and bounds `reason` to 1-500 characters (the same bound
`decide` already had) instead of relying on `transitions.reopen`'s bare "non-empty" check, which
let whitespace-only or arbitrarily long reasons through.

**Item 11 — report only, out of scope, `domain/` follow-up.** `transitions.escalate`'s A11b race:
if a correlated candidate head is decided (not case-claimed) concurrently, between this module's
`FOR UPDATE` guard reading the trigger and `transitions.escalate`'s own `UPDATE ... AND case_id IS
NULL`, the candidate's `sealed_at` is now set (by the concurrent `decide`) but its `case_id` is
still `NULL`, so the `UPDATE` still targets it and collides with `ck_alerts_h3_escalate_khong_seal`
(`status <> 'escalated_tier2' OR sealed_at IS NULL`) — a `CheckViolation`, not a `UniqueViolation`,
so `transitions.escalate` does not catch it as `StaleState`, and it is not a `DecisionConflict`
either: it surfaces as an uncaught 500 (the savepoint still rolls the partial work back correctly,
regardless — "500 with rollback" is accurate, not "500 with corruption"). Fixing this belongs in
`domain/transitions.py` (re-check status in the final `UPDATE`'s `WHERE`, or catch `CheckViolation`
too) — out of scope for this card per the Director's instruction; recorded here and in §4 for a
follow-up card.
