## 3 · Deviations from the card, and why

1. **The card's fixture/route context is 19–25/09; the merged code has moved (as flagged in the dispatch).** Nothing in P4-T03's own design notes conflicted with current code — `domain.transitions.decide`'s pre-card signature, `tier1/queue.py`'s `get_alert_view`/`list_queue`/`latest_suggestion`, and `tier1/visibility.py`'s `strip` all matched the card's §5 description exactly (verified by reading the merged files directly, not the card's quoted snippets). No P7-T01 (`evaluate_alert`) or P7-T09 (`schemas.normalise`) surface touches this card's files at all — `tier1/decide.py` never imports `llm.triage` or `llm.schemas`; it only reads `llm_runs` rows through `tier1.queue.latest_suggestion`, which P4-T02 already wrote and this card does not modify.
2. **`escalate`'s initial guard kind mapping is my own construction**, since the card names the three kinds (`not_active`, `already_decided`, `already_in_case`) but not the exact `status → kind` table. I mapped `escalated_tier2 → already_in_case`; `closed_fp/closed_benign/closed_confirmed/auto_closed → already_decided`; everything else (`received`, `enriching`, `duplicate`) → `not_active`. Exercised by the acceptance tests and by DEC-025 case (a).
3. **`decide()`'s initial `suggestion_visible` read tolerates a missing alert (`row is None → suggestion_visible = None`) rather than raising `NotFound`**, matching the card's silence on that case: the card gives acknowledge and escalate an explicit `NotFound`/`FOR UPDATE` guard but decide's design note has no such step before `transitions.decide`, which itself turns a nonexistent `alert_id` into `StaleState` → `DecisionConflict(kind="not_active")`, exactly per the note's re-read logic. `escalate()` does raise `NotFound` on a missing row at its own `FOR UPDATE` guard — the card is explicit there.
4. **`make test-db` shows one failure unrelated to any file this card touches: `backend/tests/test_triage_job.py::test_idle_timeout_survives_an_eleven_second_call`.** This test simulates an 11-second slow LLM call to prove a triage job survives past `idle_in_transaction_session_timeout` (10s, set by `db.transaction()`) — a pre-existing test with essentially no timing margin (11s attempted against a 10s real Postgres timeout). It:
   - passes standalone (`pytest backend/tests/test_triage_job.py::test_idle_timeout_survives_an_eleven_second_call`, isolated);
   - passes when the whole `-m db` suite runs **without** `test_tier1_api.py` (confirmed twice, including with `test_decide.py` present and with an 11-test scratch probe using `TestClient` against an unrelated, pre-existing route — both green);
   - fails consistently (2/2 runs) when `test_tier1_api.py` is present in the same session, whether or not `test_decide.py` is also present.
   `test_triage_job.py` imports from `app.tier1.triage`/`app.infra.worker` only — it never imports `app.tier1.decide`, `app.domain.transitions.decide`, or `app.web.routers.tier1`, so this is not a logic defect in anything this card wrote; it is the pre-existing test's thin timing margin being tipped by the additional wall-clock/connection load `test_tier1_api.py`'s eleven `TestClient` round-trips add in this sandbox. I did not modify `test_triage_job.py` (rule 10/"edit no existing test"). I tried one non-hacky mitigation inside my own file (closing each `TestClient` deterministically in the `client` fixture's teardown instead of relying on GC) — it did not change the outcome, so I reverted it rather than leave unproven code. `make lint` and `make test` (the non-`db` suite, which is what `-m "not db and not live"` runs and what most of the working-rules gate on) are unaffected and green.
