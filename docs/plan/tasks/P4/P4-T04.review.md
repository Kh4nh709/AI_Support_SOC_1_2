## Non-blocking notes

- **The `_RenderedPage` exception + import-time `main.app.add_exception_handler(...)` mechanism
  in `pages.py` (lines ~47–83) is the one piece of this diff that isn't a direct instruction from
  the card**, and the Coder flagged it themselves as an open question for the Director before
  P4-T05/P6-T02 build on top of `pages.py`. I gave it the adversarial check its unusualness
  earns: registering an app-level exception handler as an import-time side effect of a *router*
  module, rather than centrally in `main.py`, is fragile-looking specifically because `pages.py`
  circularly imports `main` mid-execution. I hypothesized this could leave `app` holding a
  reference to an empty `pages.router` if `pages` were ever imported before `main` in a fresh
  process (a plausible risk for however P4-T05/P6-T02 end up importing `page_user`), and tested
  it directly: `.venv/bin/python` scripts importing `pages` standalone before `main`, vs. `main`
  first, in fresh subprocesses — both produce the identical, complete `app.openapi()['paths']`
  list. This holds because `fastapi==0.141.1`'s `include_router` resolves included routers lazily
  (the same fact DEC-101 already established for the `app.routes` vs. `app.openapi()['paths']`
  split), not by eagerly snapshotting routes at `include_router`-call time as older FastAPI/most
  frameworks do — so the ordering hazard I suspected does not reproduce on this pinned version.
  No defect found. The Director's open question stands on its own merits (centralizing exception
  handlers in `main.py` would be more conventional regardless of whether this specific failure
  mode is real) — I'm not the scope-negotiating role, so I'm not resolving it here, only reporting
  that it isn't hiding a route-mounting bug today.

  self-correction, DEC-047), the reused `set_session_cookie`/`clear_session_cookie`/`current_user`
