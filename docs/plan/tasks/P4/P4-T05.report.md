## 3. Deviations from the card

1. **`403` is a JSON `{"detail": "forbidden"}`, not an HTML flash fragment.** The
   card's design note 1 says "else `403` with a flash fragment" and then, in the same
   sentence, "prefer the dependency" (`require_role("tier1")`, frozen in `web/deps.py`).
   `require_role` already returns `HTTPException(403)` with a JSON body — reproducing
   its audit-write-then-commit-then-raise behaviour by hand, just to wrap the same
   refusal in HTML, would mean either duplicating frozen logic (against the hard
   rules) or adding a new exception handler at app scope (touching shared
   composition-root behaviour beyond this card's file list). I followed "prefer the
   dependency" literally. Only a `tier2`/other role hand-crafting a POST ever sees
   this; the pilot's one `tier1` account never does.
2. **`_decision_form.html`'s `closed_*`/`escalated_tier2` line shows the raw status
   enum** (`Đã quyết: closed_benign — …`), not a translated label. The header's
   "status in words" requirement is explicit and I built a `STATUS_LABELS` mapping for
   it inside `alert.html`; `_decision_form.html` is also rendered **standalone** as an
   HTMX partial response (not always included from `alert.html`), so it cannot safely
   depend on a variable another template defines — putting the label map there too
   would duplicate it in two places with no shared source. Left as the plain enum,
   which is still informative to a Vietnamese-speaking analyst who has been looking at
   `status` values all session.
3. **The case link 404s today.** Per pitfall 3, `_decision_form.html` links an
   `escalated_tier2`/decided-with-a-case alert to `/cases/{case_id}` (P5-T07's route),
   not `/api/tier2/cases/{id}`. Confirmed empirically: `/cases/{id}` is absent from
   `app.openapi()['paths']` on this tree (P5-T07 is `todo` in `STATE.md` as of this
   report) — the link is correct for when P5-T07 merges, 404 until then.
4. **A light severity/NUL-byte guard was added beyond the card's text.** `decide.
   escalate` itself does not validate `severity` (that lived in `tier1.py`'s Pydantic
   `EscalateIn` for the JSON API only); my routes take HTML forms, which have no
   Pydantic model to hang the same check on, so an invalid `severity` would otherwise
   reach a raw DB CHECK violation (an ugly 500 in the live pilot). I added a 4-value
   allowlist check and a NUL-byte guard (mirroring `web/routers/tier1.py`'s `_no_nul`)
   on `reason`/`title`, both mapped to the existing `422` path. Neither is a named
   acceptance test; both are cheap, defensive, and match an existing frozen pattern
   rather than inventing a new one.
5. **`docs/plan/tasks/P4/P4-T05.prompt.md`'s worktree-setup paragraph (§"Working
   rules" 1) is stale** — it describes a worktree the Director creates at
   `../AI_Support_SOC_1_2-P4-T05` on `task/P4-T05`; my actual dispatch (Director 1's
   message) put me in a pre-existing worktree on a different branch name and told me
   explicitly not to use `task/P4-T05` or call `EnterWorktree`/`git switch`. I followed
   the dispatch, per the card's own "where the card and the current code disagree, the
   current code wins" rule extended to the dispatch instructions that supersede it.
6. **Acceptance §35's DSN-construction recipe (`../AI_Support_SOC_1_2/.env`,
   `scripts/dsn_env.py`) assumes a worktree layout that does not match mine** (my
   worktree is not a sibling of the primary checkout under that relative path). I used
   the equivalent, already-vetted `run_merge_tests.sh`/`order_proof.sh` scripts named
   in my actual dispatch instructions, which read the same `.env` from the primary
