## 3. Deviations from the card, and why

- **`TEST_DATABASE_URL=postgresql:///soc_test make test-db` — three attempts, three different, mutually inconsistent failures, none reproducing `test_pages_login.py`'s own scope.** First attempt: `audit_events`/`users` off by exactly the rows my own tests would have committed *if* they ran against the shared `db` fixture instead of a scratch database — my first draft of the test file made that mistake (see next bullet) and I fixed it. Second and third attempts, **after** that fix: `relation "llm_runs" does not exist` inside `test_schema_v3_017.py` (a file this card never touches), then `psycopg.OperationalError: … database "soc_test" does not exist … it seems to have just been dropped or renamed`, then a `soc_test_auth_test` scratch-database race inside `test_auth.py` (P4-T01's file, also untouched by this card). I reproduced the second/third class of failure **with `test_pages_login.py` removed from the tree entirely** — same symptom, so it is not this card's code. `STATE.md`'s own dispatch note records **3/3 Coder slots running concurrently** (P6-T03, P4-T07, P4-T04) — the only database that fits "dropped mid-run" and "extra committed rows from nowhere" is another session's own `make test-db` (each with its own `_test_database` session fixture, which drops and recreates `soc_test`) racing mine on the same PostgreSQL instance. `make test-db` on my own dedicated `soc_p4t04_test` is green (`512 passed`) every time I ran it, including right after the shared-DB failures. I did not keep retrying against `soc_test` in a loop once the pattern was clear (three attempts, three unrelated symptoms, and an isolated rerun works) — flagging it here per working rule 9 rather than declaring an unverifiable green. **Recommend:** the Reviewer re-run the literal command in a quiet window, or the Director gives `make test-db` the same per-agent-DSN treatment `test_auth.py`'s own tests already use (this exact hazard is why P4-T01's committing tests use a scratch database rather than the shared one).
- **My own test file first made the mistake it now avoids.** Design note 6 reads "`get_conn` → `db`"; I first overrode `deps.get_conn` with the shared `db` fixture wrapped in the real dependency's commit/rollback shape (mirroring `test_auth.py`'s `client` fixture, `db` in place of `sdb`). That is wrong for a *committing* test suite sharing `soc_test` with `test_schema_v3_017.py`'s "count from zero" assumption — exactly `test_auth.py`'s own module docstring's reason for using a scratch database instead. Fixed: `test_pages_login.py` now builds and migrates its own `soc_test_pages_test` (or `<TEST_DATABASE_URL's dbname>_pages_test`) scratch database, dropped and recreated per test session, identical in shape to `test_auth.py`'s `scratch_dsn`/`sdb`/`_require_db_marker_for_scratch` fixtures. `TEST_DATABASE_URL=postgresql:///soc_test`'s own `audit_events`/`users` tables measured empty (`select count(*)` → `0` on both) after the fixed suite runs.
- **The login page's 401/423/503 responses raise a small `_RenderedPage` exception rather than returning the rendered page directly, and this module registers that exception's handler on `main.app` at import time.** The card's design note 4 just says "commit, then re-render the page… status 401" — it doesn't specify raise-vs-return. I measured (three throwaway scripts, kept in the scratchpad, not in the repo) that `deps.Conn`'s `scope="function"` dependency only rolls back an uncommitted write for an exception that reaches an **app-level** exception handler; a route that instead catches its own `auth.LoginFailed`/etc. and just *returns* a response commits regardless of whether `conn.commit()` was ever called — which would make DEC-025's red case (d) ("drop the `conn.commit()` → red") **undemonstrable**, since nothing would actually change when I removed the commit. Raising, with a handler that reproduces the same body, restores the real property (verified above, case (d)). The handler is installed via `from app.web import main; main.app.add_exception_handler(...)` inside `pages.py`, called once at import time — not lazily on first request (measured: Starlette freezes `exception_handlers` into `ExceptionMiddleware` on the app's first ASGI call and never rebuilds it, so a handler registered after that first call is silently never seen). This works because `web/main.py` assigns `app = FastAPI()` before its `iter_routers()` loop imports this module, so `main.app` already exists whichever module triggers the import chain first — verified both ways (`main` imported first, and `pages` imported standalone first). `web/main.py`'s own source is untouched (`git diff main --stat -- backend/app/web/main.py` is empty); this is a runtime call from a file this card owns, not an edit to a file it doesn't. Flagging this for the Reviewer specifically because it's the one piece of this card that isn't a direct instruction from the prompt — if a router-scoped or otherwise less unusual mechanism is preferred, I'd want that decided before P4-T05/P6-T02 build on top of `pages.py`.
- **HTMX SRI hash: filled in, not left `None`.** The card assumed no network ("when you cannot… leave `None`"); network was in fact reachable here. Verified two ways: cdnjs's own `api.cdnjs.com/libraries/htmx/2.0.4` lists `"htmx.min.js": "sha512-2kIcAizYXhIn8TzUvqzEDZNuDZ+aW7yE/+f1HJHXFjQcGNfv1kqzJSTBRBSlOgp6B/KZsz1K0a3ZTqP9dnxioQ=="`, and downloading the exact pinned URL and running `openssl dgst -sha512 -binary | openssl base64` on the bytes reproduces the same value. `crossorigin="anonymous"` is only emitted when `htmx_integrity` is set, per the card's own template line.
