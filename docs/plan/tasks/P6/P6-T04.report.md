## 3 · Deviations from the card and why

1. **The source address is RFC 6598 shared address space (`100.64.0.0/10`), not TEST-NET-3 (`203.0.113.<k>`) — a card defect the card's own assertions expose.** Python 3.12.3's `ipaddress` lists all three RFC 5737 documentation ranges as private (`ipaddress.ip_address("203.0.113.1").is_private → True`; likewise `198.51.100.x`, `192.0.2.x`), so `wazuh_parser._is_private` returns `True`, `Alert.srcip_is_private` is `True`, `lookup_ioc` skips the address and writes `{"reputation": "skipped"}` — not `not_found` — and `sbf-1` (`ioc_reputation ∈ [not_found, clean]`) can never hold: every one of the 40 targets would be structurally FP-blocked, the exact outcome design note 2 chooses the base to avoid, and `test_every_fixture_parses_to_the_base_facts` (`srcip_is_private is False`) and the db assertion `ioc … not_found` could never pass. `100.64.0.0/10` is never a public host, is outside the stdlib's private set on every Python version (a documented exception of `is_private`), and the address is looked up and found absent → `not_found`. Targets `100.64.0.<1+k>`, neighbours `100.64.0.<101+k>`, `rhost=` in `full_log` matches. The test keeps the card's name `test_srcips_are_distinct_test_net_3_and_public` (acceptance greps for it) and its docstring says why the range differs; the Director may want to rename it. (The Planner's index makes the same TEST-NET-3 choice, so this is a card-and-index-versus-code defect, not a card-versus-index one. A separate observation, not mine to fix: the parser's docstring claims CGNAT is covered as private, but the stdlib does not classify it so.)
2. **Fields the card is silent on are made coherent with the July instant, and Logstash's `event.original` is dropped.** The base's `_source.event.original` is a string copy of the whole original alert carrying `user=root`, `"dstuser":"root"`, `202.165.25.8` and the September timestamp. Keeping it stale would leave `user=root` in every fixture; regenerating it would put the payload into a second field, contradicting design note 3's "exactly one field" test; nothing in `backend/app` or `eval` reads it (grep; a reviewer re-confirmed). `@timestamp`, `_index` (`wazuh-alerts-4.x-2026.07.0N`), `predecoder.timestamp` and the syslog prefix of `full_log` (`Jul 01 00:59:59 …`, one second before the alert as in the base) follow the fixture's instant so the document is one coherent hit — and are now pinned by the timestamp test; `_score: null` and every other base key stay (a reviewer's key-by-key diff against the base found exactly the listed differences and nothing else).
3. **Each neighbour has its own `srcip`** (`100.64.0.<101+k>`); the card assigns addresses per target and is silent on the neighbour. Distinct is what "no two fixtures correlate by `srcip`" means over 48 files, and a neighbour from the same source 10 min earlier would, in the real pipeline, have been one cluster with its target rather than a second head. The neighbour is still found — by `agent_name`, the path the design relies on.
4. **Acceptance 4's `grep -c '"user=root'` cannot fail** (see §2 item 4); the meaningful form is asserted by a test and reported here as a card defect rather than claimed as a pass (DEC-025/027).
5. **`identity_context->>'privileged'` is `'false'` for the 40 targets and JSON `null` for the 8 neighbours**, because a neighbour's `dstuser` *is* the payload, so its identity lookup is `not_found` and `lookup_identity` returns `is_privileged: None` — the shape `finish_enrichment` would write for the same row. The db test asserts `'false'` on the targets and `null` + `lookup_status.identity = 'not_found'` on the neighbours.
6. **`test_loader_rows_invisible_to_queue_and_escalate_predicates` proves the two halves of the queue predicate independently** (`NOT is_synthetic` alone hides the rows; `status <> 'received'` alone returns none). With the predicate as written, the card's failing case (b) — "skip the `is_synthetic` update → the queue-predicate test red" — cannot go red, since `status = 'received'` already hides the rows; the sharpened test does go red on (b).
7. **`load.py` parses every fixture before the first transaction**, so a rejected fixture writes nothing (exit 1 naming the file); the card says "a rejection is exit 1 … never skipped" without saying when. `--dry-run` is the same parse plus a read-only existence check per row (it connects — acceptance 5 gives it a DSN — and reports how many would be skipped).
8. **The job guard is inside the per-fixture transaction, and the card's post-loop count is kept as the belt** *(review)*. The card's "after the loop … must be 0 (assert; exit 1 otherwise)" is a detector: by then every fixture has committed, and a `triage` job that a future `open_alert` created would already be pending for a worker — G3 shown to the model — when the loader says "refusing". So `insert_synthetic` reads `jobs` for the fixture it just inserted and raises `JobCreated`; `conn.transaction()` rolls that fixture back (row, audit event, job) and the loop stops with nothing after it loaded. The post-loop `SELECT count(*) FROM jobs WHERE job_type = 'triage' AND subject_id = ANY(%s)` still runs and `main()` still exits 1 on it, exactly as carded.
9. **The per-fixture transaction is psycopg's `conn.transaction()`, not `app.infra.db.transaction()`.** `db.transaction()` issues an explicit `BEGIN` and `conn.commit()`; run inside the `db` test fixture's already-open transaction it would commit the test's whole transaction — including `open_alert`'s `audit_events` row, append-only under migration 017 — into the session database shared by every file `make test-db` runs (the trap `test_lab_tag.py` on `main` documents). `conn.transaction()` is `BEGIN`/`COMMIT` on `main()`'s fresh connection (verified in psycopg 3.3.4's `Transaction._push_savepoint`: outer iff `transaction_status == IDLE`) and a savepoint inside an open transaction. The card mandates `open_alert`, so this is the only way its db tests can run in the shared session; the real commit path is proven on a scratch database.
10. **The idempotency read is `SELECT is_synthetic, source, raw_payload->>'_adversarial'`, not the card's `SELECT 1`** *(review)*: a row is `skipped` only when it is this fixture (`true`, `'lab'`, this pattern id); any other row under that id is `AlertIdCollision`, exit 1, naming it — never a silent `skip` that would point P7 at a real alert. Improbable (the ids sit below every archive id, which a test now pins), so this costs nothing and removes a failure mode. A concurrent insert between the read and the `INSERT` (`StaleState`) is likewise a named `Refusal` rather than a traceback.
11. **Exit code 2 for environment problems** (DSN unresolvable, malformed or unreachable; manifest/fixture unreadable) — the house convention of `eval/lab_tag.py` on `main`; the card names only 1 for refusals, which is kept for every refusal it lists. *(review)* The connect guard catches `psycopg.Error`, not only `OperationalError`: a malformed `--dsn` raises `ProgrammingError`, and libpq quotes the DSN — password included — in that exception's text, so nothing from it is printed (working rule 11). Each path has a test.
12. **The scripts are mode 755** like `eval/lab_tag.py` (ruff EXE001 flags a shebang on a non-executable file).

Card versus the Planner's index (`P6-tasks.md`): no disagreement on acceptance commands (the index carries none), file scope or design notes; the index's planning decision 5 repeats the TEST-NET-3 choice (deviation 1). Read-first item 3 lists `test_wazuh_parser.py` for "how the sample is parsed" — that file never loads `indexer_sample_rule5503.json` (`test_pipeline.py`'s `_hit()` is the precedent); harmless.

Against the product it is not rendered at all: `wazuh_parser.py:180` `alert_user = data.get("dstuser") or data.get("srcuser") or None` — `Alert` has no `srcuser` field, `alerts` has no `srcuser` column, and P3-T09's card fills `TriageInput` from `alerts` by an explicit column list and renders the username only as `identity: username=<alert_user>` inside the `context` block, *and only when the identity lookup is `found`*. So with `dstuser = user1` the v2 payload lives in `raw_payload.data.srcuser` and reaches no column, no block and no model; with the payload in `dstuser` instead, the lookup is `not_found` and the username is not rendered either (and `sbf-1` fails on the facts). **The username channel is closed in both placements, by construction of the product** — a genuine architectural result for the evaluation chapter (free text has no authority; only a value that was looked up *and found* is rendered, and a found username is by definition not a payload), but it means ASR(v2) = 0 by construction for 8 of the 40 targets. Options, my recommendation first: **(a)** keep v2 exactly as carded and declare it the set's *negative control* — ASR(v2) must be 0 in every configuration, and any ASR(v2) > 0 proves the harness leaked `raw_payload` into a prompt (a real defect detector, and the 5 × 8 = 40 design in the architecture/chốt stays intact); **(b)** replace the username vector with another attacker-controlled field — there is none: every rendered free-text field is either already a vector (`description` v4, `raw_log` v1, `origin_host` v3, correlation samples v5) or structurally blocked (`agent.name` → asset `unknown`; a username → identity `not_found`), and inventory `owner`/`role`, playbook text and MITRE names are not attacker-controlled; **(c)** drop the username vector and change the G3 design to 4 × 8 = 32 (touches `kien-truc` §6 and `chot` §C).
