  **3 · The allocator (planning decision 2 — every parameter on the CLI; the defaults are the Director's until INBOX `2026-09-16 · P6 / G1 sampling design` is answered).** Input: the pool rows, `target` (300 for G1), `unknown_cap_pct` (40.0), `take_all_crit_high` (True), `category_floor` (25), `seed`. Output: exactly `min(target, len(pool))` rows, deterministic for a given input and seed. **Amended 19/09 (Director, DEC-096 — a card ambiguity the Coder disclosed, bucket (b)):** "exactly" holds when the strata can supply it; when the `unknown` cap binds *and* the classified strata are exhausted, the allocator returns **fewer** rows than `min(target, len(pool))` and `gold_coverage.md` states the shortfall and which constraint bound — never fills from a capped stratum to hit the number. The size-contract test asserts `≤` with the shortfall reason, not `==`. Steps, in this order:
  1. **Strata** are `(category, severity)`; `unknown` is a category like any other (DEC-052/057) — it is capped, never dropped.
  2. **Take-all rule.** If `take_all_crit_high`, every pool row with `severity ∈ {critical, high}` enters the sample first (137 today: 94 `unknown`, 43 classified). If that alone exceeds `target`, fall through to proportional allocation over all strata with the cap (step 4) and say so in the coverage table — do not silently keep them all.
  3. **The cap.** `unknown_budget = floor(target × unknown_cap_pct / 100)` (120 for 300 @ 40 %). `unknown` rows already taken in step 2 count against it; the remainder (`max(0, unknown_budget − taken_unknown)` = 26 today) is drawn from `unknown` medium/low strata proportionally to their pool sizes (838 : 869 → 13 : 13 by largest remainder). If step 2 already exceeded the budget (94 > 120 would not, but a 20 % cap → 60 would), the cap binds on medium/low `unknown` only (0 drawn) and the coverage table prints `unknown cap exceeded by the take-all rule: <n> of <budget>` — the Owner asked for a cap, and the table tells them where the two rules collided rather than the code deciding which one wins.
  4. **Classified medium/low.** `remaining = target − len(sample so far)` (137 today) is allocated across the classified `(category, severity)` strata with `severity ∈ {medium, low}` **proportionally to pool size** with **largest-remainder rounding** so the allocations sum to `remaining` exactly; then the **floor**: for every playbook category present in the pool whose total in the sample (crit+high taken + this allocation) is below `category_floor`, raise it to `min(category_floor, category pool size)` and take the difference from the category with the largest allocation (repeat until no category is below its floor or nothing can be moved); within a category the medium/low split is proportional to the category's medium/low pool sizes, largest remainder. Today: proportional gives `ssh_brute_force` 107, `suspicious_login` 21, `privilege_escalation` 9 → the floor lifts `suspicious_login` to 25 and `ssh_brute_force` gives 4 → 103 (95 medium + 8 low); `privilege_escalation` 9 (1 + 8) is already ≥ 25 with its 31 high.
  5. **Draws.** Within a stratum, `random.Random(seed).sample(sorted(ids), k)` — the ids sorted first so the draw depends on the seed and the set, not on file order; a fresh `Random(seed)` per stratum keyed by `seed` only would repeat the same offsets, so seed each stratum's generator with `Random(f"{seed}:{category}|{severity}")` — a string seed is deterministic in CPython 3.12 (`random.seed(str)` uses the sha512 path, version 2) and a test asserts a re-run reproduces the draw byte for byte.
  6. **Floors are reported, not enforced here:** `allocate` returns what it can; `main` compares `len(G1 sample)` to `--g1-floor` (200) and `len(G2 sample)` to `--g2-floor` (60) and sets exit 1 with a `FLOOR MISS` line (note 7). The expected default composition for today's pool is in `P6-tasks.md` §6 decision 2 (`unknown` 120 · `ssh_brute_force` 115 · `suspicious_login` 25 · `privilege_escalation` 40); your acceptance 4 prints yours and the report pastes both.
