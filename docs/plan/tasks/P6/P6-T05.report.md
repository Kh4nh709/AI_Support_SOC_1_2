## 3 · Deviations from the card and why

- **Card design note 4 says fixture alerts go through `open_alert`; the tests use a direct
  `INSERT` instead** (the `test_transitions.py::_insert_alert` pattern). Found in-session:
  `open_alert` writes an `audit_events` row on every call, `audit_events` is append-only at the
  database level (migration 017's trigger — no test can delete from it), and `TEST_DATABASE_URL` is
  one session-scoped database shared by every file a `make test-db` run touches. Going through
  `open_alert` and committing (required so `lab_tag.py`'s own, separate connection can see the
  fixture rows) reproduced this exactly: `test_schema_v3_017.py`'s append-only row-count assertions
  on `audit_events` went from green to red (`assert 14 == 1`) the first time this file ran inside a
  full `make test-db`. Switched to a direct `INSERT` (no `audit_events` write) and added an autouse
  cleanup fixture that deletes every `lt-`-prefixed `alerts` row after each database test (a second,
  unrelated pollution the direct `INSERT` did not fix by itself: `test_schema_v3_016.py`'s
  unfiltered `SELECT source FROM alerts` also assumes it owns the whole table). Both are reproduced
  and re-verified fixed above (§2, acceptance 8's `make test-db`); `alerts` is not in the append-only
  set (context pack §6.1), so the cleanup is architecturally sound, not a workaround around a
  guard.
- **The three "#### Benign twin" / "#### Negative check" local-rule sections were restructured
  once, in-session**, after acceptance-3's own grep count first came back `5` instead of `8` for
  `Benign twin`: the first draft folded a category's benign command directly under
  `#### Negative check`, so `ransomware`/`data_exfiltration`/`c2_beacon` had no separate
  `#### Benign twin` heading. Split into both headings (twin command + expected label under
  `Benign twin`; the before/after rule-count assertion under `Negative check`) so every one of the
  eight categories has exactly one `#### Benign twin`, and the three local-rule ones additionally
  have `#### Negative check` — matching acceptance 3 exactly.
- **No separate `#### Window` subsection** (design note 2 mentions one). The Owner's explicit
  instruction for this run ("every scenario block must carry … a blank start/end HH:MM:SS line")
  is met by putting `Start:`/`End:` directly inside each `#### Attack`/`#### Benign twin` block,
  next to the command and its rule-scoped indexer check, rather than in a separate subsection the
  reader would have to cross-reference. Acceptance 3's actual grep commands do not check for a
  `#### Window` heading.
- **`ssh_brute_force`'s and `privilege_escalation`'s benign twins are not spelled out verbatim in
  design note 3** (only `suspicious_login`, `recon`, `malware`, and the three local-rule categories
  are). Designed and documented with rationale in the runbook itself: `ssh_brute_force`'s twin is a
  single mistyped-then-corrected login (below the ≥8-in-2-minutes frequency threshold);
  `privilege_escalation`'s attack flavour is the *failed* `sudo`/`su` (the card's own "attack
  flavour" language), its twin the successful `sudo -k && sudo true` DEC-055 already names as the
  ambiguous, labeller-judged case.
- **No rule id is named for a failed `su`.** The archive has no `pam_unix(su` failure line in 30
  days (only two successful-session lines, `5501`/`5502`) — the command is kept in the runbook (it
  is the manual attack flavour the card names) but its rule id is explicitly left unverified rather
  than guessed, per rule 10 ("never invent a rule id").
- **`recon`'s `40601`** is flagged in the runbook as possibly not firing from a single-port loop (it
  is typically a multi-port/multi-host correlation) — stated as a thin premise, the same shape
  `conf/local_rules.xml`'s own comments use for the three local rules, not asserted as a guaranteed
  hit.
- Every other design note in the card (the pre-flight items, the window protocol, the CLI contract,
  the validation order, the exit codes) was followed as written; none required a deviation.
