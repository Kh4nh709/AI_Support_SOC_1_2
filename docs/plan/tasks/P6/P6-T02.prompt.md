  **1 · Data sources and paths (planning decision 1).** `backend/app/tier1/labels.py` resolves `REPO_ROOT = Path(__file__).resolve().parents[3]` (the same construction `kb/lookup.py` uses for `kb/`), `CANDIDATES_PATH = REPO_ROOT / "eval" / "gold_candidates.csv"`, `G1_CLUSTERS_PATH = REPO_ROOT / "eval" / "g1_clusters.csv"`, `FREEZE_MARKER = REPO_ROOT / "eval" / "gold_v1.sha256"`.   **2 · Order and "next" (planning decision 8).** `labeler_order(candidates, labeler_id: str, *, seed=LABEL_ORDER_SEED) -> list[str]`: `ids = sorted(c.cluster_id for c in candidates)`; `rng = random.Random(int(hashlib.sha256(f"{seed}:{labeler_id}".encode()).hexdigest()[:16], 16))`; `rng.shuffle(ids)`; return. `next_unlabelled(conn, order, labeler_id) -> NextResult(cluster_id: str | None, done: int, total: int)`: `done` = `SELECT count(*) FROM triage_labels WHERE labeler_id = %s AND source = 'gold_offline' AND alert_id = ANY(%s)` over the candidate ids; the next id is the first in `order` not in `SELECT alert_id FROM triage_labels WHERE labeler_id = %s AND source = 'gold_offline'`; `None` when every id is labelled. Two labellers get **different permutations of the same set** (a test), and a restart changes nothing (the order is a pure function).

  **3 · The view is an allowlist (planning decision 9).** `cluster_view(conn, candidate, *, g1_clusters) -> dict` returns **only** these keys: `alert_id, rule_id, rule_level, severity, description, agent_name, alert_time, alert_user, srcip, dstip, category, raw_log, raw_log_truncated_for_display, occurrence_count, first_seen, last_seen, playbook, correlation, gold_cluster_id`. The alert columns come from one query with an **explicit column list** — `SELECT alert_id, rule_id, rule_level, severity, description, agent_name, alert_time, alert_user, srcip, dstip, category, raw_log FROM alerts WHERE alert_id = %s` — nothing else is selected, so `source`, `status`, `triage_status`, `suggestion_visible`, `risk_score`, the four `*_context` columns, `lookup_status`, `case_id`, `autoclose_rule_id`, `acknowledged_*`, `closed_*`, `close_reason`, `duplicate_of`, `occurrence_count`, `first_seen_at`, `last_seen_at` never enter the process. **`occurrence_count`, `first_seen`, `last_seen` are the candidate's (the file's)** — for G1 the DB's values are the replay afternoon's clock (index §5) and for G2 T01 already recomputed them clock-free. `raw_log` is shown whole up to 32,768 bytes; beyond that the display is cut there and `raw_log_truncated_for_display = true` renders a visible *"[cut for display at 32 KB]"* line — the labeller is told, never silently shown less. `playbook` = `kb.lookup.get_playbook(category)` or, for `unknown` (and any category without a file), the fixed sentence *"No playbook covers this category."* **Correlation:** for `gold_set == "G1"`, `g1_correlation(g1_clusters, head, window_hours=2) -> list[CorrelationView]` computed in Python over the file — the same three-way OR as phase-4 P4-2 (`agent_name == head.agent_name or (head.alert_user and alert_user == head.alert_user) or (head.srcip and srcip == head.srcip)`), a cluster counts when its `[first_seen, last_seen]` intersects `[head.first_seen − 2 h, head.first_seen + 2 h]`, excluding the head itself, grouped by `(rule_id, category)` into `CorrelationView(rule_id, category, cluster_count, alert_count, first_seen, last_seen)` (`alert_count` = sum of `occurrence_count`), ordered by `alert_count` desc, at most 20 rows, plus up to 5 sample heads (their `description` and `raw_log` from `alerts` by the same explicit-column query) — this function is public and documented because P7 will import it (`P6-tasks.md` §12 item 1). Both branches produce the same `CorrelationView` shape, so the template has one loop. Finally the whole dict passes through P4's visibility filter in `labeling` mode before it is returned or rendered (belt and braces: the allowlist is the mechanism, the filter is P4's guarantee).
