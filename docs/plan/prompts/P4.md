## Phase spec
**Objective.** Two analysts can work Tier-1 in a browser; the blind branch is enforced at the API; the pilot starts today.
**Deliverables.**
- `infra/auth.py`: argon2id password hashing, JWT HS256 with 8 h TTL, per-request DB read of `is_active`, `role`, `sessions_invalid_before`; lockout after `LOGIN_MAX_FAILS` for `LOCKOUT_MINUTES`; `POST /api/auth/login`, `POST /api/auth/logout` (sets `sessions_invalid_before = now()`); CLI `seed_users` creating two users (tier1+tier2 combined role is not allowed — create one `tier1`, one `tier2`, one `admin`; the Owner may hold two accounts).
- `tier1/queue.py` (`list_queue` with `LEFT JOIN llm_runs`, ordering `needs_retriage DESC, risk_score DESC NULLS LAST, first_seen_at ASC`, OFFSET pagination, risk shown as the phase-4 display band — `docs/phase-4-enrichment.md:198`–`:207`, a band of `risk_score`, unrelated to the severity band, which is `rule.level` per `docs/phase-1-tiep-nhan-chuan-hoa.md:148`), `tier1/decide.py` (`acknowledge` idempotent, `decide` with optimistic lock returning N and M on 409 and fan-out, `escalate` creating the case, `reopen` from `auto_closed` only) + REST routes.
- Suggestion stripping: a single response filter that removes the ① suggestion (and `llm_runs`-derived fields) from **every** response while `suggestion_visible = false` and status ∉ closed/escalated, for every role including admin; the labeling page in P6 will reuse it. **The same filter has a `labeling` mode (DEC-019) that strips `alerts.source` on top of everything LLM-derived, regardless of `suggestion_visible`: a labeller who can see `replay` against `wazuh` can infer the storm day, and blind labelling is never relaxed. Build and test that mode here so P6 reuses the filter instead of forking it.**
- `web/`: login, queue, alert detail (raw_log, correlation ±2 h, targeted accounts, playbook, ① verdict + reasons with quotes + `gate_result` summary when visible, decision form with reason and `seen_occurrence_count`), HTMX partials for decide/escalate/reopen, flash messages for 409 with N and M.
- **`infra/intake.py` + `POST /webhook/alerts` — task P2-T12, moved into this phase (DEC-040; DEC-041 lever (a)).** Its card is complete at `docs/plan/tasks/P2/P2-T12.prompt.md` except two `⟨KEY⟩` placeholders: fill them from DEC-040 — `WEBHOOK_API_KEY` (empty → the route answers `503 webhook disabled`) and `WEBHOOK_IP_ALLOWLIST` (a JSON list of CIDRs, empty → deny all), both in §6.3 since 06/09 — and re-home the card under `tasks/P4/` with a P4 task id, renaming its STATE row, so `tasks/P2/` stops misrepresenting P2 (inventory C4). `should`, off this phase's exit gate; depends on P2-T02 and P2-T08 merged and on this phase's `infra/auth.py`.

## Design notes for the coder prompts
- JWT payload: `sub`, `role`, `iat`, `exp`; the DB check on every request is mandatory (one SELECT on `users` by PK).
- Templates: Jinja2 with autoescape on; HTMX from cdnjs pinned; no build step; one base layout; Vietnamese labels are fine in templates (the analysts are Vietnamese) — code stays English.
- The suggestion filter lives in one place (`tier1/visibility.py`) and is unit-tested with role × status × visibility matrix; its `labeling` mode adds `alerts.source` to the stripped set (DEC-019) and the matrix gains that mode.
- `tier1.decided` audit payload must include `llm_suggestion`, `llm_confidence`, `gate_result.forced`, `suggestion_visible` — this is the evaluation join.
- Pilot start = Owner logs in as tier1 and decides real alerts; nothing else.
