## DEC-020 · 2026-09-05 · DEC-016 was wrong: migration 017 goes back to the Owner
Scope: contract
Decided by: Director (withdrawal) · **Owner (both questions below — escalated)**
Context: An adversarial verification run I commissioned before ruling on route D returned after DEC-016 was already committed, and rejected it. I re-tested every claim myself rather than take it on trust. Four hold, and together they mean DEC-016 accepted route D on a verification that was too narrow — I tested `audit_events` and never `intake`, and I tested this host and called the result portable.
Decision: **Withdraw DEC-016's acceptance.** Migration 017 is blocked again, on two Owner questions, not one.
Consequences:
  - **1. Fatal, and route-independent — §6.1 contradicts G12.** §6.1 specifies `REVOKE UPDATE, DELETE ON audit_events, llm_runs, intake FROM app_rw` plus a BEFORE UPDATE/DELETE trigger. But G12 requires "every `intake` row gets `processed_at` or `error` within 60 s", and `intake.outcome` is only knowable once the pipeline job has run — the row is INSERTed on arrival and UPDATEd on completion. As written, the contract makes its own pipeline's commit step impossible **under every route**, D included. This has nothing to do with roles and would have failed P1-T05 on the first integration test. I missed it because I verified `audit_events` and stopped.
    **Verified fix, measured on a stand-in table with `intake`'s shape:** `REVOKE UPDATE, DELETE, TRUNCATE ON intake FROM app_rw, PUBLIC` then `GRANT UPDATE (processed_at, outcome, error) ON intake TO app_rw`, plus a trigger pinning the receipt columns. Result as `app_rw`: `INSERT` → 1 row; `UPDATE … processed_at, outcome` → 1 row (**G12 satisfied**); `UPDATE … raw_payload` → `permission denied` (**G9 protected at the privilege layer, before the trigger**); `DELETE` → `permission denied`. This is a §6.1 wording change and therefore the Owner's.
  - **2. §6.1 says, verbatim, "The application connects as `app_rw`".** Route D has it connect as the owner and `SET ROLE`. That is a change to frozen text — the same standard under which I said route C needed sign-off. I applied it to C and not to D, which was inconsistent, and the verification was right to call it. Escalated.
  - **3. The escape surface is wider than I disclosed.** I recorded "a session can `RESET ROLE`". Measured, all four return the pooled connection to the owner: `RESET ROLE`, `SET ROLE NONE`, `SET ROLE user1`, `SET SESSION AUTHORIZATION user1` — and `DISCARD ALL`, which is pgbouncer's default reset query, does the same outside a transaction block. The limitations line must say "the application's own connection can return to the owner by several ordinary means", not name one.
  - **4. P1's gate wording was false off this host.** DEC-016 said "013–017 apply on a clean `soc_dev`, nothing carved out". Roles are **cluster-global**, and `user1` cannot `CREATE ROLE` at all — measured, the conditional `DO` block fails with `permission denied to create role` when the role is genuinely absent. It passes here only because a superuser created `app_rw` before any of this. That is route B with its manual pre-step hidden inside an `IF NOT EXISTS`, and presenting it as self-contained would have been the exact "never report a gate as met on a path you did not run" failure `director.md` warns about. The gate must read "013–017 apply on a clean `soc_dev` **on a cluster where `app_rw` already exists**", or the Owner grants `CREATEROLE` and it needs no qualifier.
